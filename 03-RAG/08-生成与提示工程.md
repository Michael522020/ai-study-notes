# 生成与提示工程

> **核心问题**：怎么把检索到的证据变成一个「可信、有引用、知道何时闭嘴」的答案？

---

## 1. 提示模板的结构

一个 RAG 的提示模板通常包含四部分：

```markdown
# 角色
你是一个严谨的企业知识库问答助手。

# 指令
1. 仅根据下面的「参考资料」回答问题
2. 每个结论后面必须用 [编号] 标注依据
3. 如果参考资料不足以回答，明确说"根据现有资料无法回答"
4. 不要使用参考资料之外的知识

# 参考资料
[1] 来源：《员工手册》2024版 · 第3.2节 · 考勤制度
{chunk_1}

[2] 来源：《财务报销制度》 · 第5条 · 付款周期
{chunk_2}

# 问题
{query}

# 答案
```

**四个要点**：
1. **角色** 设定「只依据资料」的倾向
2. **明确的引用格式** → 让引用可校验
3. **明确的拒答条件** → 抑制幻觉
4. **问题放最后** → 符合「Lost in the Middle」的结论，也符合 LLM 对末尾指令更敏感的特点

## 2. 上下文组装（Context Assembly）

### 2.1 组装的四个动作

```
检索结果 → ① 去重 → ② 压缩 → ③ 排序 → ④ 截断
```

| 动作 | 做什么 | 为什么 |
|---|---|---|
| **去重** | 同一文档的相邻 chunk 合并；重复内容去掉 | 避免冗余占位置 |
| **压缩** | 删掉无关句子；保留句子级结构 | 少占 token，减少噪音 |
| **排序** | 按相关性 / 按「重要的放两头」 | 利用位置效应 |
| **截断** | 按 token 预算裁剪 | 控制成本和延迟 |

### 2.2 去重

```python
def dedupe_chunks(chunks, similarity_threshold=0.95):
    """
    1. 精确去重（相同 doc_id + 相同内容）
    2. 近似去重（相邻位置的重叠 chunk）
    """
    seen_content = set()
    result = []
    for c in chunks:
        content_hash = hash(c.text)
        if content_hash in seen_content:
            continue
        seen_content.add(content_hash)

        # 相邻 chunk 合并（同一文档且位置连续）
        if result:
            last = result[-1]
            if (last.metadata.get("doc_id") == c.metadata.get("doc_id")
                and last.metadata.get("end", 0) >= c.metadata.get("start", 0)):
                # 合并
                last.text = last.text + "\n" + c.text
                last.metadata["end"] = c.metadata.get("end", 0)
                continue

        result.append(c)
    return result
```

### 2.3 句子级压缩（Sentence-Level Reranking）

**思想**：chunk 里可能只有 2~3 句真正相关，把其余去掉。

```python
def compress_chunk(query, chunk_text, embedder, keep_ratio=0.3):
    """把 chunk 拆成句子，用 reranker 打分，只保留最相关的部分"""
    sentences = split_sentences(chunk_text)
    if len(sentences) <= 2:
        return chunk_text

    scores = reranker.predict([(query, s) for s in sentences])
    k = max(1, int(len(sentences) * keep_ratio))
    keep_idx = sorted(np.argsort(-scores)[:k])

    # 保持原文顺序
    return " ".join(sentences[i] for i in keep_idx)
```

**收益**：
- token 消耗减少 50~70%
- 上下文噪音降低 → 生成质量提升

**注意**：句子级压缩会**破坏上下文连贯性**。要小心处理指代（「它」「该政策」）。

### 2.4 排序策略

**基于「Lost in the Middle」的排序**：

```python
def order_context(chunks, strategy="relevance"):
    if strategy == "relevance":
        # 降序：最相关的在前面
        return sorted(chunks, key=lambda c: -c.score)

    elif strategy == "sandwich":
        # 最重要的放两头
        sorted_chunks = sorted(chunks, key=lambda c: -c.score)
        head = sorted_chunks[:len(sorted_chunks)//2]
        tail = sorted_chunks[len(sorted_chunks)//2:]
        return head[::-1] + tail[::-1]   # 具体顺序可实验调

    elif strategy == "question_last":
        # 资料在前，问题在后（问题单独放，不算进 chunk 列表）
        return sorted(chunks, key=lambda c: -c.score)
```

**实测建议**：
- **默认用「相关性降序」**，最简单且通常有效
- 如果发现模型总是忽略中间的片段，试试 **sandwich**（最重要的放最前和最后）
- 一定要**做 A/B 测试**，不同模型对位置的敏感度不同

### 2.5 Token 预算控制

```python
def build_context(chunks, tokenizer, max_tokens=4000, reserve_for_output=1000):
    """
    动态分配预算：
    - 保留 max_tokens 给 prompt 模板和输出
    - 逐条加入 chunk，超预算就停（或截断该 chunk）
    """
    used = 0
    selected = []
    for i, c in enumerate(chunks):
        n = len(tokenizer.encode(c.text))
        if used + n > max_tokens:
            # 尝试截断这一条
            remaining = max_tokens - used
            if remaining > 100:
                truncated = tokenizer.decode(
                    tokenizer.encode(c.text)[:remaining])
                selected.append({**c, "text": truncated, "truncated": True})
            break
        selected.append(c)
        used += n
    return selected, used
```

**实践建议**：
- 给输出预留足够的 token（否则答案会被截断）
- **宁可少放几条，也不要放不完整的**（截断的 chunk 语义不完整，反而是噪音）

## 3. 引用（Citations）

### 3.1 为什么要引用

| 价值 | 说明 |
|---|---|
| **可信度** | 用户能验证 |
| **可调试** | 出错时能定位是检索问题还是生成问题 |
| **合规** | 企业场景常需要溯源 |
| **降低幻觉** | 强制引用会抑制编造 |

### 3.2 两种引用风格

**风格 A：句内标注（推荐）**

```
员工入职后需在 30 天内完成入职手续 [1]，否则系统账号将被冻结 [2]。
年假申请需要提前 3 个工作日提交 [1]。
```

**风格 B：答案后附来源列表**

```
员工入职后需在 30 天内完成入职手续，否则系统账号将被冻结。
年假申请需要提前 3 个工作日提交。

参考来源：
[1] 《员工手册》2024版 · 第2.1节
[2] 《IT系统使用规范》 · 第4条
```

**推荐 A**，因为它把证据和结论绑定得更紧，也更容易校验。

### 3.3 引用校验

**关键**：模型会**编造引用编号**（引用了不存在的 [5]）。必须校验。

```python
import re

def validate_citations(answer, num_sources):
    """检查答案中的引用编号是否都有效"""
    refs = re.findall(r'\[(\d+)\]', answer)
    invalid = [r for r in refs if int(r) < 1 or int(r) > num_sources]
    used = sorted(set(int(r) for r in refs))

    # 检查是否有来源完全没被引用（可能是浪费的上下文）
    unused = set(range(1, num_sources + 1)) - set(used)

    return {
        "valid": len(invalid) == 0,
        "invalid_refs": invalid,
        "used_refs": used,
        "unused_refs": sorted(unused),
        "citation_coverage": len(used) / max(1, num_sources),
    }
```

**「引用覆盖率」是一个很好的质量指标**：
- 覆盖率太低 → 检索到的很多内容没用上（可能检索不准，或上下文太多）
- 覆盖率 100% → 每条都用上了（理想）

### 3.4 引用的一致性校验

**更强的校验**：验证引用编号对应的内容**确实支持**该处的陈述。

```python
def verify_claim_entailment(reranker_or_llm, claim, source_text):
    """检查 source_text 是否真的支持 claim"""
    prompt = f"""判断「资料」是否支持「陈述」。只回答"支持"或"不支持"。

陈述：{claim}
资料：{source_text}

判断："""
    return llm.invoke(prompt).content.strip()
```

## 4. 抑制幻觉

### 4.1 四层防御

```
第 1 层：提示约束    —— "仅根据资料回答"
第 2 层：引用强制    —— "每个结论必须标注 [n]"
第 3 层：拒答机制    —— "资料不足请说无法回答"
第 4 层：输出校验    —— 程序检查引用有效性 + 蕴含校验
```

**关键认知**：**单靠提示词挡不住幻觉**。必须配合程序化校验。

### 4.2 拒答的触发

**不要让模型自己判断「资料够不够」**（它倾向于自信地编造）。用规则：

```python
def should_refuse(query, retrieved_chunks, min_relevance=0.5):
    """基于检索质量决定是否允许生成"""
    if not retrieved_chunks:
        return True
    top_score = retrieved_chunks[0].score
    if top_score < min_relevance:
        return True
    # 检查是否有足够的内容
    total_len = sum(len(c.text) for c in retrieved_chunks)
    if total_len < 50:
        return True
    return False
```

**三种拒答策略**：

| 策略 | 说明 | 适用 |
|---|---|---|
| **硬拒答** | 不检索到就不回答 | 高风险场景（医疗、法律） |
| **软拒答** | 检索不到时用 LLM 的通用知识回答，但**明确标注**「以下内容不来自知识库」 | 低风险场景 |
| **转人工** | 拒答并转给客服 | 客服场景 |

### 4.3 「引用无效」时的降级

```python
def post_process(answer, sources):
    result = validate_citations(answer, len(sources))
    if not result["valid"]:
        # 策略 1：把无效编号替换为最相关的来源
        # 策略 2：重新生成
        # 策略 3：标记为低置信度
        answer = re.sub(r'\[(\d+)\]',
                        lambda m: f"[{sources[0].idx}]"
                        if not (1 <= int(m.group(1)) <= len(sources)) else m.group(0),
                        answer)
    return answer
```

## 5. 提示模板精选

### 5.1 基础问答（通用）

```markdown
你是一个知识库问答助手。请严格遵守以下规则：

1. **只依据**「参考资料」回答，不要使用你自己的知识
2. 每个事实性陈述后面用 `[编号]` 标注依据
3. 参考资料不足以回答时，回复："根据现有资料无法回答该问题"
4. 保持客观，不要添加资料中没有的推断

## 参考资料
{context}

## 问题
{query}

## 答案
```

### 5.2 多跳问答（带推理）

```markdown
你是一个严谨的知识库问答助手。请按以下步骤工作：

1. 先列出「回答这个问题需要哪些信息」
2. 对每一项，说明它来自哪条参考资料
3. 如果某项信息在参考资料中找不到，明确说明「缺少：xxx」
4. 基于找到的信息给出答案，并标注引用

## 参考资料
{context}

## 问题
{query}

## 回答步骤
```

### 5.3 对比类问题

```markdown
请对比以下内容，输出表格形式。

对比维度：{dimensions}

## 参考资料
{context}

## 问题
{query}

## 表格
| 维度 | A | B |
|---|---|---|
```

### 5.4 结构化输出（JSON）

```markdown
你是一个知识库问答助手。请以 JSON 格式输出，不要有任何其他文字。

输出格式：
{{
  "answer": "答案文本",
  "citations": [{{"index": 1, "quote": "支撑该结论的原文片段"}}],
  "confidence": "high|medium|low",
  "not_found": ["资料中缺失的信息点"]
}}

## 参考资料
{context}

## 问题
{query}
```

**结构化输出的价值**：可以直接被下游系统消费（UI 渲染、写入工单、触发流程）。

### 5.5 带元数据的引用

```markdown
## 参考资料
[1] 《{title}》（{source}，{date}）
{chunk_1}

[2] 《{title}》（{source}，{date}）
{chunk_2}
```

**元数据要出现在 prompt 里**，这样模型才能在答案里引用具体来源。

## 6. 生成参数

| 参数 | 推荐 | 说明 |
|---|---|---|
| **temperature** | 0~0.3 | RAG 场景要**确定性**，幻觉和随机性直接相关 |
| **top_p** | 0.9 | |
| **max_tokens** | 预留充分 | 截断是最差的失败模式 |
| **stop** | — | 如果格式严格，用结构化输出而不是 stop |

**temperature = 0 不是万能**：
- 有时模型在 temperature=0 下会陷入重复循环
- 实践中用 0.1~0.3，并在极端情况下检测重复

### 6.1 流式输出

```python
for chunk in llm.stream(prompt):
    print(chunk, end="", flush=True)
```

**流式的价值**：用户感知的延迟（TTFT）大幅改善，即使总延迟不变。

## 7. 处理「模型忽略上下文」

**症状**：检索到了正确的 chunk，但答案里没有用到。

**排查与对策**：

| 原因 | 对策 |
|---|---|
| **上下文太长** | 减少 chunk 数量（3~5 条） |
| **指令不明确** | 把「仅根据资料回答」放在开头和结尾 |
| **模型能力弱** | 换更强的模型 |
| **资料本身不够** | 改进检索 |
| **位置问题** | 试试 sandwich 排序 |
| **chunk 之间矛盾** | 合并或重新切分 |

**验证方法**：把正确答案手动写进 prompt，看模型能不能答对。
- 能答对 → 生成阶段没问题，是检索问题
- 不能答对 → prompt 或模型问题

## 8. 后处理

```python
def post_process(answer, sources, metadata=None):
    # 1. 去除重复内容
    answer = dedupe_sentences(answer)

    # 2. 去除「作为一个AI」之类的开场白
    answer = re.sub(r'^(作为[一个a-zA-Z]+AI[，,]?|好的[，,]?|当然[，,]?)\s*', '', answer)

    # 3. 校验引用
    citation_result = validate_citations(answer, len(sources))

    # 4. 补全来源列表（如果有未引用的，提示用户）
    if citation_result["unused_refs"]:
        metadata = metadata or {}
        metadata["unused_sources"] = citation_result["unused_refs"]

    return answer, metadata
```

**流式场景的特殊处理**：引用校验在流式下做不了完整校验，只能在生成后做，或用「先输出引用列表，再输出答案」的两段式。

## 9. 上下文顺序的实验设计

**要验证「位置效应」，做一个简单的对照实验**：

```
组 A（降序）：  [最相关] [次相关] [第三] [第四] [最不相关]
组 B（升序）：  [最不相关] [第四] [第三] [次相关] [最相关]
组 C（三明治）：[最相关] [第三] [第四] [次相关] [次相关]
```

**记录指标**：
- 答案正确率（人工或 LLM 评判）
- 忠实度（faithfulness）
- **各位置的引用率**（看模型实际引用了哪几条）

**引用率分析**能告诉你模型实际在用哪部分上下文 —— 这比猜「哪个位置更好」直接得多。

---

## 10. 工程结论

1. **提示模板要包含四要素**：角色、仅依据资料、强制引用、拒答条件。缺一个效果都会掉。
2. **引用必须程序化校验**。模型会编造编号，这是必须防的。
3. **上下文宁少勿多**。3~8 条，每条 300~800 token。
4. **拒答要在检索层做判定**，不要指望模型自己判断。
5. **temperature ≤ 0.3**，RAG 不需要创造性。
6. **验证生成问题还是检索问题的方法**：手动把正确答案塞进 prompt。
7. **用引用率分析定位问题**，比盲猜位置效应高效。
