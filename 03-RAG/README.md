# 03 · RAG 研究笔记

> **从朴素实现到 GraphRAG / Agentic RAG 的完整架构地图。**

RAG（Retrieval-Augmented Generation，检索增强生成）要解决的是一个具体问题：

> **LLM 的参数里没有你的企业知识，而且你无法（也不应该）为了更新知识去重新训练它。**

RAG 的本质是一个**信息检索系统 + 生成系统**的组合工程。但真正难的从来不是「把向量塞进 prompt」，而是：

1. **切分** —— 切得不好，后面全崩
2. **检索** —— 检不准，模型只能靠参数里的模糊记忆瞎编
3. **评测** —— 怎么知道系统好不好，而不是靠「感觉还行」

## ⚡ 一张表看懂 RAG 的演进

| 阶段 | 特征 | 代表工作 | 典型问题 |
|---|---|---|---|
| **Naive RAG** (2020) | 固定切分 + 向量检索 + 塞进 prompt | Lewis et al. | 切分碎、检索不准、无法溯源 |
| **Advanced RAG** (2023) | 加了切分优化、混合检索、重排、引用 | 各种工程实践 | 仍是「一次性」流程，无法自我纠错 |
| **Modular RAG** (2024) | 每个模块可插拔、可独立优化 | LangChain / LlamaIndex 架构 | 需要理解大量概念 |
| **Agentic RAG** (2025) | 模型自己决定「要不要检索、检索几次、怎么组合」 | Self-RAG, CRAG, FLARE, ReAct | 成本高、延迟不可控、调试难 |

## 🧭 三个贯穿全篇的核心矛盾

### 矛盾 1：召回 vs 精度
- 检索召回多了 → 上下文噪声大 → 模型被干扰（「Lost in the Middle」）
- 检索少了 → 关键信息缺失 → 幻觉

**解法**：混合检索 + 重排 + 上下文压缩（见 §06、§08）

### 矛盾 2：结构化 vs 语义化
- 向量检索懂语义，但不懂「第三章在讲什么」
- BM25 / 全文索引懂结构和关键词，但不懂同义表达

**解法**：混合检索 + RRF 融合（见 §06）

### 矛盾 3：成本 vs 质量
- 多轮检索、rerank、GraphRAG 都能提质
- 但每一步都加延迟、加成本

**解法**：分层缓存、查询路由、按需检索（见 §11、§09）

## 📌 一句话决策指南

| 你的情况 | 起点 |
|---|---|
| **刚开始做** | Naive RAG + 混合检索（BM25 + 向量）+ 交叉编码器重排 |
| **文档格式复杂（PDF/表格）** | 先解决解析（§02），否则切分再好也没用 |
| **知识有明确的层级/关系** | GraphRAG 或 LightRAG（§09） |
| **文档很长、需要全局理解** | RAPTOR（层次摘要树） |
| **答案需要严格溯源** | 引用落地 + 章节级 chunk + 拒答机制（§08） |
| **延迟敏感（<1s）** | 语义缓存 + 轻量 rerank + 限制 top-k（§11） |
| **多跳问题（需要关联多个文档）** | 查询分解 + 多轮检索（§07） |
| **企业内网、有权限体系** | **必须先解决权限过滤**（§12），否则会泄露 |
