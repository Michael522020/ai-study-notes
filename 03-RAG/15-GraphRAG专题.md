# GraphRAG 专题：从社区摘要到低成本图检索

> **核心问题**：图检索到底什么时候值得付这个钱？微软自己 2024 年 11 月就推出了一款索引成本只有原版 0.1% 的 LazyGraphRAG，2026 年学术界又测出「朴素 RAG 平均分最高」——那么「图 RAG 更强」这个说法，还剩多少是真的？

本篇是 [`03-RAG/09-高级RAG架构.md`](./09-高级RAG架构.md) §3.1 的展开。09 给出的是 GraphRAG 的骨架；这篇往下钻三层：**索引流水线每个环节到底在做什么**、**成本怎么算**、**以及它到底什么时候是负收益**。

## 1. 先把问题问对：GraphRAG 到底解决什么

### 1.1 官方叙事

原始论文的题目就是答案：*From Local to Global: A Graph RAG Approach to Query-Focused Summarization*（Edge et al., 2024-04，[arXiv:2404.16130](https://arxiv.org/abs/2404.16130)，2024 年 7 月开源）。

它区分两类查询：

| 查询类型 | 例子 | 朴素 RAG 的表现 |
|---|---|---|
| **Local（局部）** | 「报销流程需要哪些材料？」 | ✅ 正常。找到含答案的 chunk 塞进 prompt 即可 |
| **Global（全局）** | 「这份报告的主要结论有哪些？」「文档里提到的所有风险因素是什么？」 | ❌ 失效。这类问题需要**综合整份语料**，不存在某个「正确的 chunk」 |

朴素 RAG 在全局查询上失效的机制很具体：

1. 全局问题的答案**分散在成千上万个 chunk 里**，top-k 检索必然漏
2. 把整份语料塞进 context 会超 token limit
3. 退而求其次拼接检索片段 → 丢失「整体结构」，得到的是**碎片罗列而非综合判断**

GraphRAG 的解法：**在检索之前，先把语料压缩成层次化的摘要结构。**

### 1.2 但先问一句：你的查询里有多少是全局问题？

这是整个专题里最该先问的问题，也是微软自己后来用 LazyGraphRAG 承认的问题。

> **全局查询在真实企业问答里通常是个位数百分比。** 大部分问题是「这个产品怎么退款」「这个字段什么意思」「这份合同的违约条款」——全是局部查询。

而原版 GraphRAG 的成本是**按语料规模一次性付出**的（不管你之后问不问全局问题）。也就是说：

> **你为 5% 的查询，付了 100% 的索引成本。**

这个不匹配，正是 LazyGraphRAG 的全部出发点。

## 2. 标准 GraphRAG 的索引流水线，逐环节拆解

```
        原始语料（文本单元 TextUnit）
                   ↓
    ┌──────────────────────────────────────┐
    │ ① 实体与关系抽取（LLM，逐块调用）      │  ← 最贵的一步
    │   · 实体白名单（entity_types）        │
    │   · 关系 + 关键点（claims）           │
    │   · Gleaning：增量补抽（见 §2.2）     │
    └──────────────────┬───────────────────┘
                       ↓
    ┌──────────────────────────────────────┐
    │ ② 图构建                             │
    │   节点 = 实体 / 文本单元               │
    │   边 = 关系（带权重、描述）             │
    │   · 实体描述合并（同一实体的多次抽取）  │
    └──────────────────┬───────────────────┘
                       ↓
    ┌──────────────────────────────────────┐
    │ ③ 层次化 Leiden 社区检测              │
    │   · resolution 参数控制粒度           │
    │   · 每一层社区 = 一个「更全局」的单位   │
    └──────────────────┬───────────────────┘
                       ↓
    ┌──────────────────────────────────────┐
    │ ④ 社区报告（Community Report）        │  ← 第二贵的一步
    │   每个社区一份 LLM 摘要 + 要点 + 评分   │
    │   层级越高 = 越全局的摘要              │
    └──────────────────┬───────────────────┘
                       ↓
    ┌──────────────────────────────────────┐
    │ ⑤ 向量化                             │
    │   · 社区报告 → 向量（全局检索入口）     │
    │   · 实体 / 关系 / 文本单元 → 向量       │
    └──────────────────────────────────────┘
```

### 2.1 实体抽取：白名单 + 关系

实体抽取不是「让 LLM 自由发挥」，而是给一份**实体类型白名单**（`entity_types`）让它填。典型配置：

```yaml
entities:
  - organization
  - person
  - geo
  - event
```

**这个白名单是整条链路的「先验」来源**——它决定了什么样的关系会被建出来，也间接决定了图能回答什么问题。这一点在 §7 的批判部分会再回来算账。

### 2.2 Gleaning：迭代补抽

第一轮抽取后，系统会检查「还剩多少 token 预算」，然后**让 LLM 继续找漏掉的实体和关系**，直到：

- 达到 token 上限，或
- LLM 回答「没有更多了」

这个机制叫 **gleaning**，是原论文用来对抗「一次抽取必然漏」的工程手段。代价是每轮都是一次完整的 LLM 调用。

### 2.3 层次化 Leiden：分辨率参数是「全局性的旋钮」

社区检测用 **Leiden 算法**（不是 Louvain——Leiden 保证社区内部连通）。关键是它能**一次跑出多层层次**：

- `resolution` 参数控制社区划分的粒度
- 每一层社区包含下一层的社区 → 形成**树状层次**
- 层号越大，社区越大、摘要越全局

原论文里社区层级与查询类型的对应关系：

| 社区层级 | 典型用途 |
|---|---|
| Level 0 / 1 | 局部搜索的事实来源 |
| Level 2（**C2**） | **微软推荐给多数应用的全局查询档位** |
| Level 3+ | 更全局、但边际收益递减且成本陡增 |

> **这是个必须理解的机制细节**：所谓「全局性」在 GraphRAG 里**不是模型自己涌现的洞察，而是算法按 `resolution` 参数切出来的层级**。切多细、切多粗，是你在建索引时就定死的。

### 2.4 社区报告：层级的第二份索引

每个社区（每个层级）生成一份 LLM 摘要，含：

- 摘要正文
- 关键要点（key points）
- 评分（rating，如「洞察深度 1–5」）

这些社区报告**全部向量化**，构成 Global Search 的检索空间。

## 3. 三种查询模式，机制与代价

### 3.1 Local Search（局部）

```
用户问题
   ↓
① 向量检索 → 命中的实体（不只是文本 chunk）
   ↓
② 取每个命中实体的：
   · 邻居实体 + 关系
   · 相关文本单元
   · 所属社区报告
   ↓
③ 拼成上下文 → LLM 生成
```

比朴素 RAG 多的东西：**结构化的邻域上下文**。你问「张伟和李娜是什么关系」，图能直接给出边，而不是指望向量检索碰巧同时召回两个 chunk。

**代价**：比纯向量检索慢（多一跳图查询），收益在**关系密集型**语料上最明显。

### 3.2 Global Search（全局）：Map-Reduce

这是原版 GraphRAG 的招牌，机制上就是一次**并行 map + 归并 reduce**：

```
用户问题
   ↓
① MAP（并行，对每个社区报告各问一次）
   「根据这份社区摘要，针对 <原问题>，提取相关要点；
    记录能支撑答案的要点编号；若无相关信息则输出 NONE」
   ↓
   每个社区 → 一组带编号的要点 + 覆盖率评分
   ↓
② 归并：按「相关度评分」排序，**丢掉低分的**
   ↓
③ REDUCE（一次 LLM 调用）
   「根据下列要点清单，回答原问题」
```

**两个关键设计**：

1. **每个社区独立回答，LLM 不知道别的社区说了什么**——这是它能扩展到大规模语料的原因，但也意味着**跨社区的推理必须在 reduce 阶段完成**，而 reduce 阶段只有一个 LLM 调用，没有中间迭代。
2. **中间要点带编号 + 覆盖率评分**——这让最终答案可以标注「这个结论来自哪些社区」，可溯源性比朴素 RAG 更好。

**代价**：社区报告越多，map 阶段并行度越高，总 LLM 调用次数线性增长。

### 3.3 DRIFT Search（2024 年末）：混合

DRIFT = 动态推理与灵活遍历。三个阶段：

| 阶段 | 做什么 |
|---|---|
| **A. Primer** | HyDE 扩展查询 → 与所有社区报告匹配选 Top-K → 生成初步答案 + **后续追问**（轻量版 Global Search） |
| **B. Follow-Up** | 用初步答案里的**种子实体**做局部搜索 → 迭代精炼（默认 2 轮） |
| **C. Output Hierarchy** | 按相关性排布的问答层次输出 |

定位是**跨领域推理 / 跨社区证据追踪**的「黄金标准」，但迭代检索带来明显的效率下降——每个追问都是一轮完整的检索 + 生成。

## 4. 成本：把「很贵」换成具体数字

### 4.1 索引期的钱花在哪

原版 GraphRAG 的索引成本 = **两次全量 LLM 批处理**：

| 阶段 | 调用形态 | 成本占比 |
|---|---|---|
| 实体/关系抽取 | 每个文本块 1+N 次（N = gleaning 轮数） | **主要成本** |
| 社区报告 | 每个社区 × 每个层级 1 次 | 次要但随层级数增长 |

公开可查的量级：**100 万 token 的播客转录语料，用 GPT-4-turbo 索引耗时约 281 分钟**（16 GB 内存机器）。

### 4.2 查询期的钱

| 模式 | 调用次数 | 说明 |
|---|---|---|
| Local | 1 次生成 + 图查询 | 与朴素 RAG 同量级 |
| **Global** | **N 个社区 × 1 次 map + 1 次 reduce** | 社区报告数以百计时，是几十到上百次 LLM 调用 |
| DRIFT | Primer(N) + Follow-Up(2 轮局部) | 最贵 |

### 4.3 微软自己的账：LazyGraphRAG

2024-11-25，微软发布 **LazyGraphRAG**（[arXiv:2411.04952](https://arxiv.org/abs/2411.04952)，Darren Edge、Ha Trinh 等）。它做的事只有一句话：

> **把索引期的 LLM 计算全部推迟到查询期。**

具体做法：

| 环节 | 原版 GraphRAG | LazyGraphRAG |
|---|---|---|
| 实体抽取 | LLM | **NLP 名词短语抽取**（无 LLM） |
| 图结构 | 有向实体关系图 | **无向概念共现图** |
| 社区检测 | 层次化 Leiden | **保留**（仍要社区结构） |
| 社区报告 | 每社区 LLM 摘要 | **丢弃**（不预生成） |
| LLM 调用时机 | 全在索引期 | **全在查询期** |
| 检索方式 | 社区报告向量检索 | **查询拆分为子问题 → 图遍历 + 按文本块相关性排序筛选社区 → map-reduce** |

微软自测结果（**微软自己的 benchmark，第三方未独立复现**）：

| 指标 | 数值 |
|---|---|
| 索引成本 | **= 向量 RAG**，即完整 GraphRAG 的 **0.1%** |
| 全局查询质量 | 与 GraphRAG Global Search（C2）**相当** |
| 全局查询成本 | 比 C2 **低 700 倍以上** |
| 局部查询 | 在与向量 RAG 同成本下**超过所有对手**（含长上下文向量 RAG、DRIFT、Local Search） |
| 成本旋钮 | **relevance test budget**：100 / 500 / 1500 三档，质量随预算平滑上升 |

**这条新闻的意义不在于「GraphRAG 更便宜了」，而在于微软自己承认了原版架构过度设计。** 中文社区当时把它概括为「成本降低到原版的 0.1%」，其实是批评。

### 4.4 别只算 LLM 账：存储也是成本

图检索方案普遍需要图数据库，而图数据库的常驻成本在生产环境不是小数目：

| 方案 | 存储 | 成本量级 |
|---|---|---|
| Graphiti | AWS Neptune Analytics 等 | **约 $0.48/小时 ≈ $350+/月**（常驻即产生） |
| Fast GraphRAG | FalkorDB / Neo4j / LadybugDB | 视部署形态 |
| 原版 GraphRAG | **不需要图数据库**（Parquet + 向量库，社区结构靠层次索引表达） | 最低 |
| nano-graphrag | 默认文件存储 + NetworkX | 最低 |

> **微软原版不用图数据库**，这一点反直觉但很关键：它把图当成**一次性的中间产物**（社区层级索引），而不是**需要在线查询的持久图**。想清楚这一点，你就知道原版和 Graphiti 其实是**两种不同的问题**（见 §6.1）。

## 5. 2026 的图 RAG 家族版图

2024 年只有「GraphRAG」这一个名字，2026 年已经分化成几个定位完全不同的东西。

### 5.1 四个家族的区分框架

一个有用的切分方式（来自 [Fast GraphRAG Tools Compared](https://shirokoff.ca/blog/fast-graphrag-tools-compared)）：

> **「语料库 GraphRAG」和「Agent 记忆图谱」是两个不同的问题，不该横向比较。存储层选型更不该拿来比。**

| 家族 | 代表 | 要解决的问题 | 典型存储 |
|---|---|---|---|
| **A. 语料库图 RAG** | 原版 GraphRAG、LazyGraphRAG、Youtu-GraphRAG | 「这份语料整体在讲什么」 | 向量库 + Parquet（**不需要图数据库**） |
| **B. 轻量实现 / 学习用** | nano-graphrag（~1100 行） | 同上，但代码量小到能读完 | 文件 + nano-vectordb + NetworkX |
| **C. 快速图探索** | Fast GraphRAG（Circlemind，~3.7k stars） | 图上 PageRank 探索 + **可视化调试图结构** | FalkorDB / Neo4j / LadybugDB |
| **D. Agent 记忆图谱** | Graphiti（Zep，~20k stars） | **会随时间变化的事实**、增量摄入 | Neptune / Neo4j / FalkorDB |

### 5.2 各家的关键差异

| 项目 | 核心机制 | 增量更新 | 定位 |
|---|---|---|---|
| **原版 GraphRAG**（微软，~35.6k stars） | 社区摘要 | ⚠️ 需重跑索引 | 2026 年**已转维护模式**（只修 bug 与安全更新） |
| **LazyGraphRAG** | 延迟计算 + 混合检索 | ✅ | 微软自己推荐的**新起点**（0.1% 索引成本） |
| **LightRAG**（HKUDS，~29.3k stars，EMNLP 2025） | 双层检索（实体级 + 关系级） | ✅ 增量友好 | 微软原版 token 成本已降约 **77%** |
| **nano-graphrag**（~1100 行代码） | **保留完整核心链路**（分块→抽取→社区→摘要），只是实现极简 | ✅ | **学原理 / 快速原型首选** |
| **Fast GraphRAG** | PageRank 图探索 + 可视化 | 部分 | 需要**看清图长什么样**时 |
| **Graphiti**（Zep） | **双时序（bi-temporal）事实** + 语义/BM25/图混合检索 | ✅ **免全量重建** | **Agent 长期记忆**（事实会随时间变化） |
| **Youtu-GraphRAG**（腾讯优图，ICLR 2026） | — | — | 工业界方案 |

> **nano-graphrag 的定位值得单独强调**：它不是「阉割版」，而是**完整保留**了文本分块 → 实体关系抽取 → 社区检测 → 摘要生成这条链路，只是把实现压到一千多行、去掉协变量生成等非核心抽象。想读懂 GraphRAG 到底怎么跑的，读它比读微软那二十万行快得多。

### 5.3 Graphiti 的双时序：Agent 记忆的真正难题

Agent 记忆场景和知识库问答有一个本质区别：**事实会变**。

「张三在 A 公司」这条边，今天成立、三个月后不成立。普通知识图谱只有一条边，改了就是覆盖，历史丢失。Graphiti 的 **bi-temporal** 设计给每条事实打两个时间戳：

- **有效时间（valid time）**：这个事实在**现实世界**中何时成立
- **事务时间（transaction time）**：系统**何时知道**它

于是「张三 2024 年在 A 公司」和「系统在 2025 年 3 月才记录到这条」可以同时保留。**这是做「AI 员工的记忆」时绕不开的**，静态知识库方案在这里是残缺的。

## 6. 批判性审视：哪些说法需要打折

这一节是本篇最有价值的部分。上面全是「它怎么工作」，这里说**「它凭什么被相信」**。

### 6.1 原论文的基准本身有争议

原论文的评测方法是 **LLM-as-judge**，在三个维度上让 LLM 给 GraphRAG 打分：

| 维度 | 含义 |
|---|---|
| **Comprehensiveness** | 答案覆盖了问题的多少方面 |
| **Diversity** | 答案视角是否多样 |
| **Empowerment** | 答案是否让读者有能力做后续判断 |

问题在于：**打分者和被评者都是 LLM**。原论文用的语料是播客转录和新闻这类**叙事性文本**——而 GraphRAG 恰恰是为「叙事性私有数据」设计的（论文在 Nature 版标题里就是这么写的：*Unlocking LLM Discovery on Narrative Private Data*）。

> **在一个为叙事文本优化的方法上，用叙事文本证明「对叙事问题的理解更好」，这是一个很难证伪的循环论证。**

后续还有工作指出，这些「comprehensiveness / diversity」类指标与人工判断的相关性本身很弱——**LLM 倾向于给更长、更全面的答案打高分，而 GraphRAG 的答案天然更长**。

### 6.2 ACL 2026 的反证：朴素 RAG 平均分最高

2026 年一项大规模 QA 研究（[ACL 2026 智能体证据合成](https://graphastra.com/zh/summaries/acl-20261027-13d_%E5%A4%A7%E8%A7%84%E6%A8%A1%E6%99%BA%E8%83%BD%E4%BD%93%E8%AF%81%E6%8D%AE%E5%90%88%E6%88%90QA)）给出的结果值得每个想上图 RAG 的人先看一眼：

| 方法 | 平均分 | 多跳召回 | 建图耗时 | 建图 token |
|---|---|---|---|---|
| **NaiveRAG** | **62.38（最高）** | — | **43 秒** | — |
| Fast-GraphRAG | 整体平均**垫底** | **100%** | **2.3 小时** | **17.6M** |
| Fast-GraphRAG 的图规模 | — | — | — | 14.6K 节点 / 35.4K 边 |

读法：

1. **图方法的多跳召回确实接近满分**（100%），这一点是真的
2. **但整体平均分垫底**——多跳能力换来的收益，被其他维度的损失抵消了
3. **成本差了三个数量级**：43 秒 vs 2.3 小时

> **这张表的工程含义**：图 RAG 不是「全面更强」，而是「在多跳这一维上显著更强，代价是其余维度全面变弱 + 成本飙升」。如果你的评测集里多跳问题只占 20%，这个交换大概率是亏的。

### 6.3 「全局洞察」是被制造出来的

回到 §2.3。GraphRAG 声称能提供「全局洞察」，但这套洞察的产生路径是：

```
LLM 按白名单抽取实体关系  →  Leiden 按 resolution 参数切社区  →  LLM 为每个社区写摘要
       ↑                        ↑                                    ↑
   抽取偏好决定              参数决定                          摘要措辞决定
   「什么算实体」          「多粗算全局」                    「什么算洞察」
```

三个环节**全部是人设定的先验 + LLM 的偏好**，不是从语料里「涌现」的结构。换句话说：

> **你得到的全局，是「LLM 觉得重要的东西」的全局。** 它的价值取决于抽取质量，而抽取质量取决于模型能力、提示词、白名单——也就是你能不能把这几件事调好。

**这也解释了为什么 GraphRAG 对「关系密集」的语料（人物、组织、事件）收益大，而对「扁平的文档集合」收益小**：前者天然有实体和关系可抽，后者的「全局」本来就该靠 RAPTOR 那种层次摘要树来做。

### 6.4 图的误差会被固化并放大

这是图 RAG 最少被讨论、但工程上最要命的一点：

| 阶段 | 图 RAG | 向量 RAG |
|---|---|---|
| 抽取阶段 | LLM 抽错一个关系 → **写进图** | 抽错只影响这个 chunk |
| 索引阶段 | 错误的关系参与社区划分 → **影响整个社区摘要** | 无此传导 |
| 查询阶段 | 错误关系被检索命中 → **当证据用** | chunk 错了只是一段文本错 |

**向量 RAG 的错误是局部的，图 RAG 的错误会沿着社区层级向下传导。** 图规模越大、社区越高，这个放大效应越强。

缓解手段：社区报告保留**原始文本单元的引用**，让最终答案能回溯到原文核对——但前提是你在生成阶段真的做了溯源（见 [`08-生成与提示工程.md`](./08-生成与提示工程.md)）。

### 6.5 二手信息失真的活教材

写这篇时检索到的一条中文资讯很有代表性：

> 某中文博客称「2026 年 6 月，GraphRAG 论文登 Nature 子刊，标志技术规模化」。

**核实结果**：Nature 系期刊确实在 2026 年发表了一篇 GraphRAG 相关论文（[*A unified multimodal GenAI platform integrating GraphRAG multi-agent systems...*](https://www.nature.com/articles/s41598-026-47145-x)，Scientific Reports），但那是**一篇使用 GraphRAG 的多模态应用论文**，不是 GraphRAG 方法论论文本身。方法论文仍是 2024 年的 arXiv 版本。

**「用了 GraphRAG 的论文发在 Nature」被说成「GraphRAG 论文发在 Nature」**——这是二手信息在传播链上最常见的失真形态。

> **教训**：RAG 方向的中文二手解读密度极高、生命周期极短。**引用前必须回原始出处**（arXiv / ACL Anthology / 官方仓库），这跟你仓库顶层免责声明是同一条原则。

### 6.6 还有一条要打折：微软的 700 倍

§4.3 的 0.1% / 700 倍全部来自**微软自己的 benchmark**，没有第三方独立复现。而且这个对比的基准是**原版 GraphRAG 的最贵配置**。

公允的读法是：

> **「LazyGraphRAG ≈ 原版 GraphRAG 的质量，0.1% 的索引成本」是微软的官方说法；「原版 GraphRAG 值得花那个钱」已经被微软自己用新产品否定了。**

## 7. 工程落地：四个必须做的决策

### 7.1 决策一：存储层

| 你的情况 | 选择 |
|---|---|
| 只是要回答「这份语料整体讲什么」，查询量不大 | **原版架构**：向量库 + Parquet，**不要引入图数据库** |
| 知识会持续变化，要增量更新 | **Graphiti**（双时序）或 **LightRAG**（增量友好） |
| 要在线图查询、需要看图结构 | Neo4j / FalkorDB / Memgraph |
| 预算和人力都紧，先学原理 | **nano-graphrag**（~1100 行，文件存储即可） |

### 7.2 决策二：增量更新

这是 2026 年的**必答题**，原版 GraphRAG 在这里是明显短板（无原生增量摄入）：

```
新文档 → 抽取实体关系（GLiNER / LLM）
       → 向量相似度做实体匹配（与已有实体对齐）
       → 局部子图插入
       → 只对 2-hop 邻域重跑 Leiden
       → 只为受影响社区重生成报告
```

关键是**只重算受影响的局部**，而不是全量重建。

### 7.3 决策三：混合检索 + 查询路由

2026 年最主流的架构已经不是「二选一」，而是：

```
                 ┌──────────────────┐
用户问题 ──────→ │  查询路由器       │  ← 自动分类器
                 └────────┬─────────┘
          ┌───────────────┴───────────────┐
          ↓                               ↓
   简单/局部问题                      多跳/全局问题
          ↓                               ↓
   向量 RAG                          图 RAG
          └───────────────┬───────────────┘
                          ↓
                    混合检索 + 重排
```

再往上一层是 **Agentic 编排**：顶层 agent 决定检索策略，中间向量广播 + 图遍历，底层图数据库 + 向量库。

### 7.4 决策四：知识时效性

一个具体的坑：

> **时效性查询的准确率在图 RAG 上会下降约 16.6%**（重索引成本太高，新事实进不来）。

实践建议：

| 知识类型 | 方案 |
|---|---|
| 稳定知识（制度、架构、历史文档） | 图 RAG 收益大 |
| 快变数据（实时工单、监控指标、库存） | **向量 RAG + 定期重建** |
| 混合 | 冷数据上图、热数据走向量 |

## 8. 什么时候该上图：一张决策表

| 你的情况 | 建议 | 理由 |
|---|---|---|
| 查询**大部分是局部**（<10% 全局） | ❌ **不上**。用混合检索 + 重排 | 成本不匹配（§1.2） |
| 查询**确实是全局总结型** | ⚠️ **先试 LazyGraphRAG**，不要一上来就原版 | 原版已被微软自己降级为「过度设计」 |
| 知识库**关系密集**（人物/组织/事件/供应链） | ✅ 值得试 | 图有东西可抽（§6.3） |
| 知识库是**扁平文档集合** | ❌ 不划算 | 用 RAPTOR 层次摘要树更直接 |
| 需要**多跳事实追踪**（「A 和 B 之间经过了什么中介」） | ✅ 值得试 | 这是图方法的真实强项（ACL 2026 实测召回 100%） |
| 文档**少于 100 篇** | ❌ 全量塞 context | 长上下文成本低于建图 |
| 需要**知识随时间变化** | ✅ Graphiti（双时序） | 其他方案没有时间维度 |
| 需要**解释「为什么这两条相关」** | ✅ 图可解释性有价值 | 但要配合溯源到原文 |
| 预算紧、要先**学原理** | ✅ nano-graphrag | 一千多行，读得完 |

**一条反向判断**（同样重要）：

> **如果你在纠结「要不要上图」，多半说明答案是不要。** 上图是**在标准 RAG 优化到瓶颈之后**才考虑的选项，不是起点。

## 9. 复现路径：从零到跑通

### 9.1 最小可跑（理解原理，半天）

```bash
# nano-graphrag：保留完整链路，实现压到一千多行
git clone git@github.com:<owner>/nano-graphrag.git
cd nano-graphrag
pip install -e .

# 准备：环境变量 + 一批纯文本语料
export OPENAI_API_KEY=...
export EMBEDDING_MODEL=text-embedding-3-small
export LLM_MODEL=gpt-4o-mini
python nano_graphrag.py --input ./example/data --output ./example/output
```

**为什么要从它开始**：微软那套的 prompt 模板、配置项、缓存机制加起来的代码量是它的几十倍，你分不清哪些是核心机制、哪些是工程包装。nano-graphrag 把前者剥出来给你看。

### 9.2 生产形态（按 §7 选型）

| 目标 | 起点 |
|---|---|
| 全局查询质量优先，预算充足 | `microsoft/graphrag`（注意已是维护模式） |
| 全局查询 + 成本敏感 | **LazyGraphRAG**（微软官方博客有实现指引） |
| 增量更新 + 关系推理 | `HKUDS/LightRAG` |
| Agent 记忆 / 事实随时间变 | `getzep/graphiti` |
| 需要可视化调试图 | `circlemind-ai/fast-graphrag` |

### 9.3 评测：别只信 LLM-as-judge

如果要做自己的选型对比，**至少混合三种评测**：

| 方法 | 优点 | 局限 |
|---|---|---|
| **LLM-as-judge**（comprehensiveness / diversity / empowerment） | 快、便宜、贴近原论文 | 打分者偏差、长度偏好（§6.1） |
| **人工评测**（小样本、盲评） | 唯一可信的裁判 | 贵、慢、难复现 |
| **可验证指标**（多跳召回率、答案-证据一致性、覆盖率） | 客观、可自动化 | 只能覆盖能自动验证的维度 |

ACL 2026 那项研究用**多跳召回率**这类可验证指标，恰恰因为它绕开了 LLM 打分的循环论证——**这也是它能给出反直觉结论的原因**。

## 10. 工程结论

1. **先量一下你的全局问题占比，再决定要不要上图。** 这是唯一一个成本为零、收益极高的问题。占比低于 10%，标准 RAG 优化到瓶颈后大概率还是不上图。

2. **要上就从 LazyGraphRAG 起步，不要从原版起步。** 微软自己 2024 年 11 月就给出了「索引成本 0.1%、全局质量相当」的替代方案。**从原版起步等于从已经被官方否定的架构起步。**

3. **图 RAG 的真实强项是「多跳」和「关系追踪」，不是「全面更好」。** ACL 2026 的公开数据：多跳召回接近满分，但整体平均分垫底、建图成本高三个数量级。**把图的价值定位在它真正强的那一维上。**

4. **「全局洞察」是被制造出来的，不是涌现的。** 实体白名单、Leiden 的 `resolution` 参数、社区报告的提示词——三个先验共同决定了你能得到什么样的全局。**调图就是调这三个旋钮。**

5. **图的误差会沿社区层级向下传导，比向量 RAG 更容易固化。** 社区报告必须保留对原始文本单元的引用，否则你无法发现并纠正一个被写进摘要的错误关系。

6. **别信二手解读，回原始出处。** 本篇 §6.5 就是一个现成的例子：中文博客把「一篇用了 GraphRAG 的 Scientific Reports 论文」说成了「GraphRAG 论文登 Nature 子刊」。RAG 方向的中文二手内容生命周期极短、转述失真率高。

7. **微软的成本数字是自测值。** 0.1% / 700 倍 / 4% 预算全面超越，都是微软自己 benchmark 的结论（对比基准还是原版的最贵配置）。方向可信，倍数打折看。
