# 切分策略

> **核心问题**：chunk 切多大？怎么切？为什么固定长度切分会失败？

---

## 1. 切分的目标与矛盾

**目标**：让每个 chunk **语义完整**（能独立表达一个意思），同时**足够小**（能塞进有限的上下文且检索精确）。

**矛盾**：

| 切太大 | 切太小 |
|---|---|
| 嵌入向量语义模糊（包含多个主题） | 上下文不足（缺主语、缺前提） |
| 检索不准（召回的片段什么都有） | 检索到的内容看不懂 |
| token 成本高 | 需要更多 chunk 才能覆盖 |
| 「Lost in the Middle」加剧 | 关系断裂（表格被切坏） |

**没有万能解**。切分策略必须**针对你的文档类型和问题类型**调。

---

## 2. 六种切分策略

### 2.1 固定长度切分（Fixed-size）

```python
def fixed_split(text, chunk_size=500, overlap=50):
    """最简单，也最常用（LangChain 的 RecursiveCharacterTextSplitter 的基础）"""
    chunks = []
    step = chunk_size - overlap
    for i in range(0, len(text), step):
        chunk = text[i:i + chunk_size]
        if chunk.strip():
            chunks.append(chunk)
    return chunks
```

**优点**：实现简单，token 可控
**缺点**：
- 可能在句子中间切断
- 忽略语义边界
- **表格、代码会被切坏**

**改进：按分隔符递归切（Recursive Splitting）**

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=50,
    separators=["\n\n", "\n", "。", "！", "？", "；", " ", ""],  # 优先级从高到低
)
chunks = splitter.split_text(text)
```

**原理**：先按最高优先级的分隔符切；如果块还太大，就用下一个分隔符继续切；如果都切不动（超长单词），按字符硬切。

**这是目前的默认选择**，因为它兼顾了语义边界和可控性。

### 2.2 按结构切分（Markdown / 标题层级）

**推荐做法**（如果你的文档是 Markdown 或能转成 Markdown）：

```python
def markdown_split(text, chunk_size=800, overlap=100):
    """按标题层级切分，保留完整的标题路径"""
    lines = text.split("\n")
    sections = []      # (heading_path, content)
    path = []
    buf = []

    for line in lines:
        if line.startswith("#"):
            # 遇到新标题，先结算上一节
            if buf:
                sections.append((" > ".join(path), "\n".join(buf)))
                buf = []
            level = len(line) - len(line.lstrip('#'))
            path = path[:level - 1]
            path.append(line.lstrip('#').strip())
        else:
            buf.append(line)

    if buf:
        sections.append((" > ".join(path), "\n".join(buf)))

    # 过长的小节再递归切分，并继承标题路径
    final = []
    for heading, content in sections:
        if len(content) <= chunk_size:
            final.append({"text": content, "metadata": {"heading": heading}})
        else:
            sub = RecursiveCharacterTextSplitter(
                chunk_size=chunk_size, chunk_overlap=overlap,
                separators=["\n\n", "\n", "。", " ", ""]).split_text(content)
            for s in sub:
                final.append({"text": s, "metadata": {"heading": heading}})
    return final
```

**关键优势**：
- **标题路径作为元数据**（"第3章 > 3.2 > 3.2.1"）→ 检索时可以精确限定范围
- 语义边界自然
- 引用时可以给出「在《技术报告》第 3.2.1 节」这样的定位

**这是生产环境最推荐的切分方式**。

### 2.3 语义切分（Semantic Splitting）

**论文**：*GPT-4 Advanced数据分析...*，LangChain 的 `SemanticChunkSplitter`

**原理**：用嵌入模型计算相邻句子的余弦相似度，在相似度**骤降**的地方切分。

```python
import numpy as np

def semantic_split(text, embedder, buffer_size=1, threshold_percentile=95):
    sentences = split_sentences(text)
    # 组合成窗口
    windows = []
    for i in range(len(sentences)):
        window = " ".join(sentences[max(0, i - buffer_size): i + buffer_size + 1])
        windows.append(window)

    embeddings = embedder.encode(windows, normalize_embeddings=True)
    distances = 1 - np.dot(embeddings, embeddings.T)   # 距离矩阵

    # 取每个句子的前邻距离
    distances = [distances[i, i+1] if i < len(sentences)-1 else 0 for i in range(len(sentences))]

    # 阈值 = 距离的分位数
    threshold = np.percentile(distances, threshold_percentile)

    # 超过阈值处切分
    chunks, start = [], 0
    for i, d in enumerate(distances):
        if d > threshold:
            chunks.append(" ".join(sentences[start:i+1]))
            start = i + 1
    chunks.append(" ".join(sentences[start:]))
    return chunks
```

**优点**：切点一定在语义转折处
**缺点**：
- **慢**（要为每个句子算嵌入）
- **成本高**
- 阈值不好调
- 对结构化文档（技术手册）效果反而不如按标题切

**适用**：文学/叙事性文本、对话记录。**不适合**结构化文档。

### 2.4 父子分块（Small-to-Big / Parent-Child）

**这是目前最推荐的「进阶」方案。**

**思想**：
- **子块（child）**：小（200~300 token），用于**嵌入和检索** → 检索精确
- **父块（parent）**：大（1000~2000 token），用于**送入 LLM** → 上下文完整

```
文档
 ↓
切成父块（按结构，大）
 ↓
每个父块切成子块（小）
 ↓
只对子块做嵌入 → 向量库
 ↓
检索命中子块 → 返回其父块给 LLM
```

**解决的问题**：
- 小块检索精确，但喂给 LLM 上下文不足
- 大块上下文完整，但检索不精确
- **父子方案两者兼得**

```python
class ParentChildRetriever:
    def __init__(self, embedder, vector_db, parent_store):
        ...

    def retrieve(self, query, top_k=5):
        # 1. 用子块检索
        child_hits = self.vector_db.search(
            self.embedder.encode(query), top_k=top_k * 2)

        # 2. 映射回父块，去重
        parent_ids = [h.metadata['parent_id'] for h in child_hits]
        # 按子块得分排序父块
        parents = []
        for pid in parent_ids:
            if pid not in [p.id for p in parents]:
                parents.append(self.parent_store.get(pid))

        # 3. 取 top_k 个父块
        return parents[:top_k]
```

**变体**：
- **Sentence Window Retrieval**：检索到句子，向外扩展到前后几句
- **Auto-merging**（LangChain）：把相邻的高分 chunk 合并

### 2.5 命题切分（Proposition Chunking）

**论文**：*Dense Xyr: Automatic Dense Retriever Augmentation...*，更准确的是 *Propositions as Context*（Chen et al., 2023）

**思想**：用 LLM 把一段文本拆成**独立的、自包含的命题（propositions）**。

```
原文："2024 年我们推出了产品 X，它采用了自研的 Y 算法，性能提升了 30%。"

命题 1："2024 年我们推出了产品 X。"
命题 2："产品 X 采用了自研的 Y 算法。"
命题 3："产品 X 的性能提升了 30%。"
```

**优势**：
- **每个命题独立完整**，嵌入质量极高 → **检索精确度大幅提升**
- 不会出现「命题 2 缺主语」的问题

**劣势**：
- **成本高**（每篇文档都要调 LLM）
- 命题可能丢失上下文（谁是「我们」？）
- 需要在检索到命题后**回溯原文**（否则 LLM 看到的上下文是割裂的）

**实测经验**：在长文档 + 精确问答场景下，命题切分能带来 **+10~20% 的召回率提升**，但成本增加 10~50 倍。**只在高价值场景用。**

### 2.6 延迟切分（Late Chunking）

**论文**：*Late Chunking: Contextual Chunk Embeddings Using Long-Context Embedding Models*, arXiv:2407.05704
**作者**：Jina AI

**思想**：**先让长文本通过 embedding 模型，再对 token 级别的向量做池化得到 chunk 向量**。

```
传统：
  文本 → 切块 → 每块独立过 embedding 模型 → 向量

Late Chunking：
  全文（长上下文）→ 过 embedding 模型 → 得到每个 token 的向量
                                              ↓
                            按 chunk 边界对 token 向量池化 → chunk 向量
```

**优势**：
- **chunk 向量包含了全文上下文** → 语义更丰富
- 解决了「chunk 缺少前文导致指代不明」的问题

**劣势**：
- 需要**长上下文 embedding 模型**（如 Jina Embeddings v3，8192 token）
- 全文都要过模型（比传统慢，但不需要多次调用）
- 需要模型支持长上下文

**这是目前最有前景的切分方案之一**，值得在效果瓶颈时尝试。

## 3. chunk size 怎么定

### 3.1 经验值

| 文档类型 | 推荐 chunk_size | overlap | 理由 |
|---|---|---|---|
| **FAQ / 短问答** | 200~300 | 30~50 | 一个问答本身完整 |
| **技术文档 / 手册** | 500~800 | 80~120 | 一节的内容 |
| **论文** | 800~1200 | 100~150 | 一段论证 |
| **合同 / 法务** | 400~600 | 100 | 条款 |
| **代码文档** | 600~1000 | 100 | 一个函数/类 |
| **新闻** | 500~800 | 100 | |
| **聊天记录** | 1000~2000 | 200 | 保持对话上下文 |

### 3.2 通用公式

$$
\text{chunk\_size} \approx \frac{\text{平均 token 消耗}}{1 - \text{噪声率}}
$$

**更实用的经验**：
- **英文**：1 token ≈ 4 字符；中文：1 token ≈ 1.5 字符
- **chunk_size = 300 tokens** 是一个安全的起点（≈ 450 英文字符 / 450 中文字）

### 3.3 调参方法（不要瞎猜）

```
1. 固定嵌入模型和检索策略
2. 准备 30~50 个真实查询 + 标注好的相关 chunk（评测集）
3. 遍历 chunk_size ∈ {128, 256, 512, 1024, 2048}
4. 每个 size 重建索引，跑评测集
5. 选 Recall@k 最高的
```

**注意**：chunk_size 和 top_k 是**耦合**的。
- chunk 变小 → 需要更大的 top_k 才能覆盖同样的内容
- chunk 变大 → top_k 可以小，但每个 chunk 占更多 token

**经验关系**：总 token 预算固定时，**小块 + 多条**通常优于**大块 + 少条**（除非内容本身高度关联）。

## 4. overlap 的作用与代价

```
chunk 1: [AAAA][BBBB]
chunk 2:       [BBBB][CCCC]     ← BBBB 重叠
```

**作用**：
- 防止关键句子正好被切断
- 保留上下文连续性

**代价**：
- **存储浪费**（overlap 比例高的索引大）
- **检索时重复**（同一内容被多个 chunk 召回）→ 需要去重
- **可能引入噪声**（重叠部分可能不相关）

**建议**：
- overlap = chunk_size 的 **10~20%**
- **代码和表格用 0 overlap**（重叠无意义，只会重复）
- 检索后**按内容去重**（用 doc_id + 位置范围判断重叠）

## 5. 切分的常见错误

| 错误 | 后果 | 修正 |
|---|---|---|
| **固定长度硬切** | 语义破碎 | 用 Recursive Splitting |
| **忽略文档结构** | 标题和内容分离 | 按 Markdown 标题切 |
| **表格被切坏** | 检索到半张表 | 表格作为原子单元 |
| **代码被切坏** | 代码不可用 | 代码块作为原子单元 |
| **chunk 太大** | 嵌入语义模糊 | 减小 |
| **chunk 太小** | 上下文不足 | 增大或用父子分块 |
| **丢掉元数据** | 无法引用、无法过滤 | 每个 chunk 带 metadata |
| **不处理重复内容** | 检索结果冗余 | 去重 |
| **忽略语言差异** | 中文按字符数算会偏小 | 中文按 token 数设置 |

## 6. 表格与代码的特殊处理

### 6.1 表格作为原子单元

```python
def split_document(text):
    """表格和代码块作为原子单元，其余按结构切"""
    import re
    # 1. 找出所有表格和代码块
    pattern = r'(```.*?```)|(\|.*?\|\n(?:\|.*\|\n)*)'
    parts = re.split(pattern, text, flags=re.S)

    chunks = []
    buffer = ""
    for part in parts:
        if not part:
            continue
        if part.startswith("```") or part.startswith("|"):
            # 原子单元：先 flush buffer
            if buffer.strip():
                chunks.extend(split_by_structure(buffer))
                buffer = ""
            # 表格/代码单独成块，加上下文前缀
            chunks.append({
                "text": part,
                "metadata": {"type": "table" if part.startswith("|") else "code"}
            })
        else:
            buffer += part

    if buffer.strip():
        chunks.extend(split_by_structure(buffer))
    return chunks
```

**给表格加上下文前缀**很重要：

```
表格说明：以下是 2024 年各产品的销售数据（单位：万台）
| 产品 | Q1 | Q2 |
|---|-----|-----|
| A | 10 | 12 |

（仅表格内容，检索时能匹配到"销售数据"）
```

### 6.2 代码块的上下文

```
文件：src/cache.py
函数：semantic_cache_lookup
代码：
```python
def semantic_cache_lookup(query): ...
```

**加上文件名和函数名**，检索质量会好很多。

## 7. 实战对比

同一份技术文档（100 页），同一批 30 个查询：

| 策略 | Recall@5 | 构建耗时 | 索引大小 | 备注 |
|---|---|---|---|---|
| **固定长度 500** | 0.62 | 30s | 1.0× | 基线 |
| **Recursive 500** | 0.68 | 30s | 1.0× | 略好 |
| **Markdown 结构切** | 0.75 | 35s | 1.1× | 结构保留 |
| **父子（子 256 / 父 1000）** | 0.79 | 60s | 1.4× | 需两套存储 |
| **命题切分** | 0.85 | 45 min | 2.5× | LLM 成本高 |
| **Late Chunking** | 0.81 | 120s | 1.0× | 需长上下文模型 |

> **注意**：这些数字是示意性的量级关系，不是实测。**具体效果必须在自己的数据上测。**

**性价比观察**：
- **Markdown 结构切 + 父子块** 是最划算的组合
- 命题切分效果最好但成本高，适合高价值场景

## 8. 工程结论

1. **优先按文档结构切**（Markdown 标题 / 章节），而不是固定长度。
2. **父子分块是最推荐的进阶方案**：小块检索 + 大块生成。
3. **表格和代码是原子单元**，切坏它们是常见错误。
4. **chunk_size 必须用评测集调**，不能拍脑袋。300~500 token 是安全起点。
5. **overlap 用 10~20%**，代码和表格用 0。
6. **每个 chunk 必须带元数据**（标题路径、页码、来源），这是引用和过滤的基础。
7. **切分和检索要一起调**。chunk_size 变了，top_k 也要跟着变。
