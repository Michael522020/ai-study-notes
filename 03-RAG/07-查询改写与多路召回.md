# 查询改写与多路召回

> **核心问题**：用户的问法和他想找的内容往往不一样。怎么把「问法」翻译成「检索式」？

---

## 1. 为什么需要查询处理

**用户会怎么问**：

| 用户输入 | 用户真正想要的 |
|---|---|
| 「报销的钱多久到账？」 | 「财务报销付款周期」 |
| 「怎么请假」 | 「年假申请流程」 |
| 「A4 纸的尺寸」 | 「A4 尺寸 210×297mm」 |
| 「它坏了」 | （依赖上下文指代） |
| 「上个月那个订单」 | （依赖上下文的时间/实体） |

**直接嵌入用户原问题，效果往往不好**：
- 口语 vs 书面术语的分布差异
- 省略、隐含前提
- 拼写错误、缩写

**查询处理**是提升召回率最有效的手段之一。

---

## 2. 查询改写（Query Rewriting）

### 2.1 论文

**论文**：*Rewrite-Retrieve-Read: A Query-Generation Approach to Overcoming Passage Retrieval Deficiencies in Retrieval-Augmented Generation*, Shi et al., 2023

### 2.2 做法

```
原查询: "报销的钱多久到账"
     ↓ LLM 改写
改写后: "财务报销审批通过后的付款周期是多久个工作日"
     ↓ 用改写后的查询做检索
```

**关键**：
- 改写要**补充隐含信息**（口语 → 术语）
- 改写后可能**检索不到原词**（问题：「报销」变成了「财务报销审批」，但文档写的是「报销流程」）
- **解法：同时用原查询和改写查询检索，然后融合**（这正是 RAG-Fusion 的思路）

### 2.3 改写的实现

```python
REWRITE_PROMPT = """你是一个检索查询优化助手。用户会用口语提问，你需要把问题改写成更适合在企业知识库中检索的形式。

要求：
1. 补充隐含的术语和正式表达（口语 → 书面）
2. 保持原意，不要回答问题
3. 如果问题有歧义，输出 2-3 个可能的查询
4. 只输出查询，用换行分隔

原始问题：{query}

改写后的查询："""

def rewrite_query(llm, query):
    resp = llm.invoke(REWRITE_PROMPT.format(query=query))
    return [q.strip() for q in resp.content.strip().split("\n") if q.strip()]
```

### 2.4 注意事项

| 问题 | 对策 |
|---|---|
| **改写引入了错误** | 保留原查询，两路都检索 |
| **改写成本** | 一次 LLM 调用（可缓存） |
| **改写过度** | Prompt 里强调「不要回答问题，只输出查询」 |
| **简单查询不需要改写** | 用规则/分类器跳过（比如「什么是 X」这种定义型查询） |

## 3. HyDE（假设性文档嵌入）

**论文**：*Precise Zero-Shot Dense Retrieval without Relevance Labels*, Gao et al., ACL 2023

### 3.1 思想

**问题**：稀疏查询（如「报销周期」）和文档的表述不同，向量匹配不上。

**HyDE 的解法**：
```
查询: "报销的钱多久到账"
     ↓ LLM 生成一个「假设的答案」（可能不准确，但语义方向对）
假设文档: "财务报销通常在审批通过后的 5 个工作日内完成打款..."
     ↓ 用「假设文档」而不是原查询去做嵌入检索
```

**为什么有效**：
- 查询和文档**在同一个「答案空间」里**，语义更接近
- LLM 生成的假设文档包含**领域术语**，弥补了用户表述的模糊

**关键洞察**：**假设文档的准确性不重要，方向性才重要。** 即使答案是错的，只要它「指向」了正确的文档类型，检索就能命中。

### 3.2 实现

```python
HYDE_PROMPT = """请写一段简短的 hypothetical answer（假设性回答）来回答下面的问题。
要求：
1. 用 2-3 句话
2. 包含该领域的专业术语
3. 即使你不确定答案，也要给出最可能的回答
4. 不要说"我不知道"

问题：{query}

假设性回答："""

def hyde_retrieve(llm, embedder, vector_db, query, top_k=5):
    hyde_doc = llm.invoke(HYDE_PROMPT.format(query=query)).content
    # 用假设文档做检索
    emb = embedder.encode([hyde_doc], normalize_embeddings=True)
    return vector_db.search(emb[0], top_k=top_k)
```

### 3.3 HyDE 的适用与局限

| 适用 | 不适用 |
|---|---|
| **零样本**场景（没有训练数据） | 有大量同域训练数据时收益小 |
| 口语化 / 模糊查询 | 精确的关键词查询（编号、型号） |
| 知识库表述规范、用户表述随意 | 需要精确匹配的场合 |

**HyDE 的变体**：
- **HyDE + 原查询混合检索**（更稳）
- **Promptagator**（用 Few-shot 示例生成更好的假设文档）

## 4. 多查询（Multi-Query / Query Fan-out）

**论文**：*RAG-Fusion: A Simple and Effective Approach to Enhance Retrieval-Augmented Generation*, Zhao et al., 2023
**也见**：*Generating Multiple Search Queries for Retrieval-Augmented Generation*, Han et al., 2023

### 4.1 做法

```
原查询: "报销的钱多久到账"
     ↓ LLM 生成 N 个不同角度的查询
  1. "报销周期是多久"
  2. "财务付款流程和时间"
  3. "报销审批通过后几天到账"
  4. "费用报销时效规定"
     ↓
每一路独立检索 → 合并去重 → 重排
```

### 4.2 关键：**必须用 RRF 融合**

**论文的核心结论**：
> **多查询的效果不佳，不是因为多查询本身没用，而是因为用「拼接结果」或「简单相加」的方式合并损害了排名。**
> **用 RRF 融合后，多查询能稳定提升 Recall。**

**对比**：

| 合并方式 | 问题 |
|---|---|
| **拼接所有结果** | 第一个查询的结果全部占前排，其他查询的贡献被淹没 |
| **分数相加** | 各查询分数尺度不一致 |
| **RRF** | ✅ 只看排名，天然稳健 |

### 4.3 实现

```python
MULTI_QUERY_PROMPT = """你是一个 AI 助手，需要生成多个不同的搜索查询来检索相关信息。
生成 3-5 个不同角度的查询，涵盖不同的措辞和术语。

原始查询：{query}

生成的查询（每行一个）："""

def multi_query_retrieve(llm, embedder, vector_db, reranker, query, top_k=5):
    # 1. 生成多查询
    resp = llm.invoke(MULTI_QUERY_PROMPT.format(query=query))
    queries = [query] + [q.strip() for q in resp.content.strip().split("\n") if q.strip()]

    # 2. 每一路检索
    all_hits = []
    for q in queries:
        emb = embedder.encode([q], normalize_embeddings=True)
        hits = vector_db.search(emb[0], top_k=50)
        all_hits.append(hits)

    # 3. RRF 融合
    fused = rrf_fusion(all_hits, k=60)

    # 4. 重排
    scores = reranker.predict([(query, h["text"]) for h in fused[:30]])
    return [h for h, _ in sorted(zip(fused[:30], scores),
                                  key=lambda x: x[1], reverse=True)[:top_k]]
```

### 4.4 成本

```
多查询：N+1 次检索 + 1 次 LLM 生成 + 1 次重排
```
- **延迟**：检索并行的话增加不多；LLM 生成是主要开销
- **成本**：N 倍的检索 + 1 次 LLM

**优化**：
- 用小模型做查询生成
- 缓存常见的查询模式
- 只在「简单查询判定失败」时启用

## 5. 查询分解（Query Decomposition）

### 5.1 Least-to-Most

**论文**：*Least-to-Most Prompting Enables Complex Reasoning in Large Language Models*, Zhou et al., ICLR 2023

**思想**：把复杂问题拆成子问题，**先解子问题，再用子问题的答案构造更简单的子问题**。

```
原始: "对比 A 方案和 B 方案在成本和交付周期上的差异"

分解:
  子问题 1: "A 方案的成本是多少？"    → 答案 1
  子问题 2: "B 方案的成本是多少？"    → 答案 2
  子问题 3: "A 方案的交付周期是多少？" → 答案 3
  子问题 4: "B 方案的交付周期是多少？" → 答案 4

最终: 基于 1-4 的答案综合对比
```

### 5.2 Self-Ask

**论文**：*Measuring and Narrowing the Compositionality Gap in Language Models*, Press et al., NeurIPS 2023

**让模型自己决定「我需要先知道什么」**：

```
Q: 文档 A 中提到的 X 公司在 2023 年的营收是多少？
A: 我需要先知道文档 A 中提到的 X 公司是谁。
   → 检索 → "X 公司是..."
   我需要知道该公司的 2023 年营收。
   → 检索 → "..."
   最终答案：...
```

### 5.3 实现

```python
DECOMPOSE_PROMPT = """把下面的问题分解成 2-4 个可以独立检索的子问题。
每个子问题应该能通过知识库中的单一文档或段落回答。

原问题：{query}

子问题（每行一个）："""

def decompose_and_retrieve(llm, embedder, vector_db, query, top_k=5):
    resp = llm.invoke(DECOMPOSE_PROMPT.format(query=query))
    subqs = [q.strip() for q in resp.content.strip().split("\n") if q.strip()]

    contexts = []
    for sq in subqs:
        emb = embedder.encode([sq], normalize_embeddings=True)
        contexts.extend(vector_db.search(emb[0], top_k=top_k))

    # 去重后交给生成
    return dedupe(contexts)
```

### 5.4 何时用分解

| 场景 | 是否需要 |
|---|---|
| **单跳问题**（一个文档能回答） | ❌ 分解是浪费 |
| **多跳问题**（需要关联多个文档） | ✅ 必须 |
| **比较类问题**（A vs B） | ✅ 有帮助 |
| **需要时间推理**（「去年」要跨文档） | ✅ |
| **简单 FAQ** | ❌ 明显浪费延迟 |

**优化**：先用**分类器/LLM 判定复杂度**，只在需要时分解。

## 6. 查询路由与意图分类

### 6.1 意图分类

```
用户查询 → 意图分类器 → 不同的检索策略
```

| 意图 | 例子 | 策略 |
|---|---|---|
| **定义型** | 「什么是 RAG」 | 直接检索 + 简洁回答 |
| **事实型** | 「年假天数是多少」 | 精确检索（BM25 权重高） |
| **比较型** | 「A 和 B 哪个好」 | 分解 + 多路 |
| **多跳型** | 「X 公司的 CEO 设计的产品的价格」 | 迭代检索 |
| **时效型** | 「最新的政策」 | 时间过滤 |
| **闲聊型** | 「你好」 | 直接回复，不检索 |

### 6.2 实现

```python
def classify_intent(llm, query):
    prompt = f"""判断用户查询的类型，只输出一个词：
定义型 / 事实型 / 比较型 / 多跳型 / 时效型 / 闲聊型

查询：{query}
类型："""
    return llm.invoke(prompt).content.strip()
```

**更轻量的做法**：用规则 + 小模型分类，或者用嵌入相似度匹配到「查询模板」。

### 6.3 路由到不同的 RAG 策略

```python
def route(llm, query, ...):
    intent = classify_intent(llm, query)

    if intent == "闲聊型":
        return direct_response(query)
    elif intent == "多跳型":
        return agentic_rag(query)          # 迭代检索
    elif intent == "比较型":
        return decompose_and_retrieve(query)
    elif intent == "时效型":
        return retrieve_with_time_filter(query)
    else:
        return standard_hybrid_retrieve(query)
```

## 7. 上下文感知查询（会话式 RAG）

**问题**：多轮对话中，「它」「那个」指代不清。

**方案**：
1. **查询改写**：把当前 query 改写成**包含对话历史的完整问题**
2. **历史摘要 + 当前查询**拼接后检索
3. **会话摘要**：维护一个滚动摘要

```python
def contextualize_query(llm, history, query):
    if not history:
        return query
    hist_text = "\n".join(f"{m.role}: {m.content}" for m in history[-4:])
    prompt = f"""根据对话历史，把用户的最后一个问题改写成独立的、完整的查询。

对话历史：
{hist_text}

最后一个问题：{query}

改写后的完整查询："""
    return llm.invoke(prompt).content.strip()
```

**这是 Conversational RAG 的标准做法**，也是「多轮对话 RAG」效果好坏的关键。

## 8. 特殊技巧

### 8.1 查询扩展（Query Expansion）—— 纯规则版

```
同义词词典扩展：
  "报销" → ["费用", "开销", "票据", "发票"]
  "请假" → ["休假", "年假", "事假", "病假"]
```

**优点**：零 LLM 成本、延迟低
**缺点**：覆盖不全

**可用于**：作为 BM25 的一路补充检索（和查询改写互补）。

### 8.2 查询拆解（拆成关键词）

```
"Python 和 PyTorch 的区别"
→ ["Python", "PyTorch", "Python PyTorch 区别"]
```
用关键词做 BM25，用完整句做稠密检索。

### 8.3 拼写纠错 / 同义词归一

- **中文**：错别字、繁简、英文大小写
- **英文**：拼写纠错（编辑距离）
- **专有名词**：建立术语映射表

### 8.4 元数据过滤（结构化约束）

不是改写查询，而是**加过滤条件**：

```
"2023 年的销售数据"  → filter = {"year": 2023}
"华东区的政策"        → filter = {"region": "华东"}
```

**这比改写更精确**。可以用 LLM 把查询转成「过滤条件 + 检索词」：

```python
FILTER_PROMPT = """从查询中提取结构化过滤条件（JSON）和检索关键词。
可用字段：year, department, product_line, doc_type, region

查询：{query}
JSON（filter 和 keywords）："""
```

## 9. 各方法对比

| 方法 | 额外 LLM 调用 | 额外检索次数 | 延迟增量 | 召回提升 | 适用 |
|---|---|---|---|---|---|
| **原始查询** | 0 | 1 | 0 | 基线 | 精确查询 |
| **查询改写** | 1 | 1 | +200~500ms | 中 | 口语化查询 |
| **HyDE** | 1 | 1 | +200~500ms | 中 | 零样本 |
| **多查询** | 1 | N+1 | +300~800ms | **高** | 通用兜底 |
| **查询分解** | 1 | N | +500~1500ms | 高（多跳） | 多跳问题 |
| **意图路由** | 1（可小模型） | 视情况 | +50~200ms | 避免浪费 | 生产系统 |
| **上下文改写** | 1 | 1 | +200~500ms | 高（多轮） | 对话式 |

## 10. 工程结论

1. **先做最简单的：意图路由 + 必要时改写**。不要一上来就全套。
2. **多查询 + RRF 是召回提升最明显的组合**，成本可控。
3. **HyDE 适合零样本和口语化查询**，精确查询上反而可能变差。
4. **多跳问题必须分解**，否则再好的检索也拼不出答案。
5. **对话式 RAG 必须做上下文改写**，否则第二轮之后的检索基本是乱的。
6. **元数据过滤比查询改写更精确**，能用过滤就别用改写。
7. **所有查询处理都是「延迟换召回」**。用意图路由做分流，只在需要时启用昂贵路径。
