# 检索与重排

> **核心问题**：怎么把「相关的内容」找出来并排到前面？这是 RAG 质量的第一道关。

---

## 1. 检索的三个阶段

```
用户查询
   ↓
┌──────────────┐
│ ① 召回       │  追求「不漏」(Recall)  →  粗筛 50~200 条
│  (Retrieval) │  稠密 + 稀疏 + 混合
└──────────────┘
   ↓
┌──────────────┐
│ ② 重排       │  追求「准」(Precision)  →  精排 3~10 条
│  (Reranking) │  Cross-Encoder / LLM
└──────────────┘
   ↓
┌──────────────┐
│ ③ 上下文组装 │  压缩、去重、排序、预算控制
└──────────────┘
   ↓
   LLM 生成
```

**关键认知**：
> **召回阶段宁多勿缺，重排阶段宁缺勿滥。**
> 召回漏了的东西，重排救不回来；重排放进去的垃圾，重排会帮你删掉。

## 2. 稀疏检索：BM25

### 2.1 BM25 公式

$$
\text{BM25}(q, d) = \sum_{t \in q} \text{IDF}(t) \cdot \frac{f(t,d)(k_1+1)}{f(t,d) + k_1(1-b + b\frac{|d|}{\text{avgdl})}
$$

| 参数 | 含义 | 默认 |
|---|---|---|
| $k_1$ | 词频饱和速度 | 1.2~2.0 |
| $b$ | 长度归一化强度 | 0.75 |
| IDF | 词的稀有度权重 | $\log\frac{N - n(t) + 0.5}{n(t) + 0.5} + 1$ |

**直觉**：
- **IDF**：罕见词权重高（「张伟」比「的」重要）
- **词频饱和**：同一个词出现 10 次和 100 次，区别不大（$k_1$ 控制饱和速度）
- **长度归一化**：长文档不天然占优（$b$ 控制）

### 2.2 BM25 的强项与弱项

**强项**：
- 专有名词、产品型号、编号、错误码（**RAG 场景里极其常见**）
- 精确短语匹配
- 可解释（能看哪个词命中）
- 零训练成本

**弱项**：
- 同义词（「报销」vs「费用报销」）
- 语义漂移
- 中文需要分词（分词质量影响很大）

### 2.3 中文分词

| 方案 | 说明 |
|---|---|
| **jieba** | 经典开源，词典 + HMM |
| **jieba-fast** | 更快 |
| **HanLP** | 学术级，多种任务 |
| **pkuseg** | 腾讯，领域模型 |
| **Jieba + 自定义词典** | **生产环境必做**：加入产品名、术语、缩写 |
| **字符 n-gram** | 避免分词问题，但索引膨胀 |

**实践建议**：
```python
import jieba
# 加载领域词典
jieba.load_userdict("domain_terms.txt")   # 每行一个词 + 词频 + 词性
# 停用词
STOPWORDS = set(open("stopwords.txt").read().split())
```

### 2.4 学习式稀疏检索

| 方法 | 思路 |
|---|---|
| **SPLADE** | 用 MLM 的 MLM 头学习高维稀疏表示（学「词权重」） |
| **SPLADE v2** | 改进的表达 + 蒸馏 |
| **BGE-M3 稀疏** | 模型直接输出稀疏向量 |
| **uniCOIL** | 把词权重和上下文表示结合 |

**优势**：比 BM25 更懂语义，稀疏（存储友好），且可以直接与稠密向量融合。

## 3. 稠密检索

见 [`04-嵌入模型选型.md`](./04-嵌入模型选型.md)。

**度量方式**：

| 度量 | 公式 | 适用 |
|---|---|---|
| **余弦相似度** | $\frac{a \cdot b}{\|a\|\|b\|}$ | **最常用**，需归一化 |
| **点积** | $a \cdot b$ | 不归一化时用（模型训练目标决定） |
| **欧氏距离** | $\|a-b\|$ | L2 归一化后等价于余弦 |
| **BM25 分数** | 见上 | 稀疏 |

> **注意**：嵌入模型的训练目标决定了该用什么度量。用 cosine 训练的模型用点积，排序会变。**Qdrant/Milvus 里要配对**。

## 4. 混合检索

### 4.1 为什么混合一定更好

```
查询："ERR-1024 怎么处理"
  → BM25 命中（含精确错误码）    ✅
  → 稠密可能命中"常见错误处理流程"  ⚠️

查询："怎么申请年假"
  → BM25 弱（"申请"和"休假"不同词）  ⚠️
  → 稠密命中（语义相近）            ✅
```

**两者的失败模式互补**，这就是混合检索的收益来源。

### 4.2 融合方法

#### 方法 A：加权分数相加

$$
\text{score} = w_d \cdot \text{score}_{\text{dense}} + w_s \cdot \text{score}_{\text{sparse}}
$$

**问题**：**两种分数的尺度不同**（余弦是 [-1,1]，BM25 是 [0, 20+]），直接加权不合理。

**解法**：先归一化
- **Min-Max 归一化**：(x - min) / (max - min)
- **Z-score 归一化**
- **Sigmoid 映射**

#### 方法 B：RRF（Reciprocal Rank Fusion）—— **推荐**

**论文**：*Reciprocal Rank Fusion outperforms Condorcet and individual Rank Learning Methods*, Cormack et al., SIGIR 2009

**公式**：
$$
\text{RRF}(d) = \sum_{r \in \mathcal{R}} \frac{1}{k + \text{rank}_r(d)}
$$

其中 $k$ 通常取 **60**。

**RRF 的优势**：
- **只用排名，不用分数** → 天然解决尺度问题
- **无需调参**（k=60 在各场景都稳健）
- **实现极简**

```python
def rrf_fusion(rank_lists, k=60, top_k=10):
    """
    rank_lists: list of lists，每项是 doc_id 的排名顺序
    """
    scores = {}
    for ranks in rank_lists:
        for rank, doc_id in enumerate(ranks, start=1):
            scores[doc_id] = scores.get(doc_id, 0) + 1.0 / (k + rank)

    sorted_docs = sorted(scores.items(), key=lambda x: x[1], reverse=True)
    return [doc_id for doc_id, _ in sorted_docs[:top_k]]
```

**RRF 的局限**：
- 忽略了分数的**差距**（排第 1 和排第 2 在 RRF 里几乎一样）
- 对**头部结果的置信度**不敏感

#### 方法 C：加权 RRF

$$
\text{score}(d) = \sum_r w_r \cdot \frac{1}{k + \text{rank}_r(d)}
$$

**推荐**：给稠密和稀疏不同的权重（如 dense 1.0, sparse 0.5），比纯 RRF 稍好。

#### 方法 D：D学习型融合（Learning to Rank）

用一个小模型（LambdaMART / Cross-Encoder）学习「什么样的检索组合更好」。

**代表**：
- **RankFusion**（Elastic, 2023）
- **BLADE**（2024）

**代价**：需要训练数据。

#### 方法 E：分数级融合（Score-level）

用 **CombSUM / CombMNZ / CombMRA** 等经典融合方法。

## 5. 重排（Reranking）

### 5.1 为什么需要重排

```
召回阶段：Bi-Encoder（独立编码）
  → 快，但每个 chunk 独立打分，对 chunk 内部的具体内容判断粗糙

重排阶段：Cross-Encoder（拼接后一起编码）
  → 慢（要跑 N 次前向），但能精细判断 query 和 chunk 的交互
```

**经验值**：
```
召回 top-100 → 重排 → 取 top-5~10 → 送 LLM
重排把 NDCG@10 提升 10~25%
```

### 5.2 Cross-Encoder 重排模型

| 模型 | 语言 | 特点 |
|---|---|---|
| **BAAI/bge-reranker-base/large** | 中英 | **中文首选**，v2-m3 支持多语言 |
| **BAAI/bge-reranker-v2-m3** | 多语言 | 通用 |
| **jinaai/jina-reranker-v2-base/multilingual** | 多语言 | 强 |
| **mixedbread-ai/mxbai-rerank-base/large** | 英 | 英文强 |
| **Alibaba-NLP/gte-reranker-modernbert-base** | 多语言 | 新架构 |
| **Alibaba-NLP/Qwen3-Reranker-0.6B/4B/8B** | 多语言 | **指令式**，最强 |
| **Cohere Rerank 3.5** | 多语言 | 商业 API |
| **Voyage rerank-2** | 多语言 | 商业 API |
| **Jina AI reranker API** | 多语言 | 商业 API |

**Cross-Encoder 的工作方式**：

```python
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("BAAI/bge-reranker-large", max_length=512)

query = "如何申请年假"
docs = [
    "年假申请流程：1. 在OA系统提交申请 2. 主管审批...",
    "报销流程说明：提交发票...",
    "员工手册第三章 考勤制度：年假天数根据司龄...",
]
scores = reranker.predict([(query, d) for d in docs])
# → [8.9, 1.2, 7.4]   重排后顺序：年假申请 > 考勤制度 > 报销流程
```

### 5.3 指令式重排（Qwen3-Reranker）

新一代重排模型用**自然语言指令**描述评分标准：

```python
from transformers import AutoModelForCausalLM, AutoTokenizer

model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen3-Reranker-0.6B", trust_remote_code=True)
tok = AutoTokenizer.from_pretrained("Qwen/Qwen3-Reranker-0.6B", trust_remote_code=True)

def get_inputs(pairs, prompt=None):
    if prompt is None:
        prompt = "Given a web search query, retrieve relevant passages that answer the query"
    prefix = "<Query>: " + pairs[0][0] + "\n<Document>: " + pairs[0][1]
    return tok(prefix, return_tensors="pt", padding=True, truncation=True, max_length=8192)

# 打分：yes/no 的 logits
```

**优势**：可以针对不同场景定制指令（「找出能直接回答问题的段落」vs「找出主题相关的段落」）。

### 5.4 LLM 重排（Listwise）

**论文**：*Is ChatGPT Good at Search? Investigating Large Language Models as Re-ranking Agents*, Sun et al., 2023（RankGPT）

**思想**：把候选文档列表给 LLM，让它输出**排序后的列表**。

```
Prompt:
  I will provide you with 10 passages, each indicated by a numerical identifier []. Rank the passages
  based on their relevance to the search query: {query}.
  Search Query: {query}
  Passages: [1] {passage1} [2] {passage2} ...

Output:
  [4] > [7] > [1] > [9] > ...
```

**做法**：**滑动窗口（Sliding Window）** —— 每次给 LLM 20 个候选，输出排序，取 top-10 进入下一轮，重复直到排完。

**优点**：效果最好，能理解复杂的排序意图
**缺点**：
- **慢且贵**（多轮 LLM 调用）
- **有 position bias**（LLM 偏爱靠前的文档）
- **不保证稳定性**（同样的输入可能给不同排序）

### 5.5 ColBERT / 晚交互

**论文**：*ColBERT: Efficient and Effective Passage Search via Contextualized Late Interaction over BERT*, SIGIR 2020

**核心：编码阶段早交互，检索阶段晚交互**

```
Bi-Encoder：
  doc → 一个向量
  query → 一个向量
  相似度 = 一个点积

ColBERT：
  doc → N 个 token 向量（每个 token 一个）
  query → M 个 token 向量
  相似度 = MaxSim（每个 query token 找最匹配的 doc token，再求和）

  Score(q, d) = Σ_{i∈q} max_{j∈d} (q_i · d_j)
```

**优势**：精度接近 Cross-Encoder，速度接近 Bi-Encoder（用 PLAID 索引）
**劣势**：
- **存储大**：每个 chunk 存 N 个 token 向量（1024 维 × 20 token = 80KB/条）
- 索引复杂

**工程折中**：**ColBERT 只在 top-20 上做精算**（比 Cross-Encoder 快，且存储可控）。

### 5.6 重排方案对比

| 方案 | 速度 | 质量 | 成本 | 部署复杂度 |
|---|---|---|---|---|
| **无重排** | 最快 | 低 | 无 | 无 |
| **Cross-Encoder** | 中 | **高** | 低 | 低 |
| **ColBERT (top-20)** | 中 | **高** | 中 | 中 |
| **LLM Listwise** | **慢** | 最高 | **高** | 低 |

**推荐**：**Cross-Encoder 重排**是默认选择。只有在「重排后质量仍不够」且「延迟预算宽松」时才上 LLM 重排。

## 6. 检索的完整实现

```python
from typing import List, Dict
import numpy as np

class HybridRetriever:
    """混合检索 + RRF 融合 + Cross-Encoder 重排"""

    def __init__(self, vector_db, bm25_index, embedder, reranker,
                 dense_weight=1.0, sparse_weight=0.5):
        self.vdb = vector_db
        self.bm25 = bm25_index
        self.embedder = embedder
        self.reranker = reranker
        self.dense_weight = dense_weight
        self.sparse_weight = sparse_weight

    def retrieve(self, query: str, top_k=10, recall_k=100,
                 filters: Dict = None) -> List[Dict]:
        # 1. 稠密召回
        q_emb = self.embedder.encode(query, normalize_embeddings=True)
        dense_hits = self.vdb.search(q_emb, top_k=recall_k, filter=filters)

        # 2. 稀疏召回
        sparse_hits = self.bm25.search(query, top_k=recall_k, filter=filters)

        # 3. 加权 RRF 融合
        fused = self._weighted_rrf([dense_hits, sparse_hits],
                                   [self.dense_weight, self.sparse_weight])

        # 4. 交叉编码器重排
        pairs = [(query, h["text"]) for h in fused]
        scores = self.reranker.predict(pairs)

        # 5. 排序取 top_k
        reranked = sorted(zip(fused, scores), key=lambda x: x[1], reverse=True)
        return [h for h, _ in reranked[:top_k]]

    def _weighted_rrf(self, hit_lists, weights, k=60):
        scores = {}
        for hits, w in zip(hit_lists, weights):
            for rank, hit in enumerate(hits, start=1):
                doc_id = hit["id"]
                scores[doc_id] = scores.get(doc_id, 0) + w / (k + rank)
        # 汇总同一 doc 的信息
        doc_map = {}
        for hits in hit_lists:
            for hit in hits:
                doc_map.setdefault(hit["id"], hit)
        return sorted(doc_map.values(),
                      key=lambda h: scores[h["id"]], reverse=True)
```

## 7. 参数配置经验

| 参数 | 推荐值 | 说明 |
|---|---|---|
| **召回 top_k（每路）** | 50~100 | 太低会漏，太慢 |
| **融合后重排数** | 20~50 | |
| **最终进上下文** | **3~8 条** | 多了是噪音 |
| **每条 chunk 长度** | 300~800 token | |
| **总上下文预算** | 2K~8K token | 视模型和延迟要求 |
| **RRF k** | 60 | 通用 |
| **混合权重** | dense 1.0 / sparse 0.5~1.0 | 关键词型查询可提高 sparse |
| **efSearch (HNSW)** | 100~200 | 召回率优先可更高 |

## 8. 常见错误

| # | 错误 | 后果 | 修正 |
|---|---|---|---|
| 1 | **只做稠密检索** | 专有名词/编号检索不到 | 加 BM25 |
| 2 | **不做重排** | 上下文全是噪音 | 加 Cross-Encoder |
| 3 | **重排后取太多** | 「Lost in the Middle」 | 取 3~8 条 |
| 4 | **BM25 没加领域词典** | 中文分词错 | 加自定义词典 |
| 5 | **两路分数直接相加** | 尺度混乱 | 用 RRF |
| 6 | **过滤后没验证召回** | 权限过滤导致召回为空 | 用支持联合过滤的库 |
| 7 | **重排模型不支持中文** | 中文效果差 | 用 bge-reranker-v2-m3 |
| 8 | **查询和文档编码方式不一致** | 排序异常 | 检查前缀/归一化 |
| 9 | **召回多但不去重** | 上下文重复 | 按 doc_id + 位置去重 |
| 10 | **没做 Recall 评测** | 全靠感觉调参 | 建评测集 |

## 9. 工程结论

1. **混合检索（BM25 + 稠密）是基线**，不是可选项。纯稠密在有专有名词、编号、型号的场景会明显失效。
2. **用加权 RRF 融合**，k=60 起步。这是最省心且鲁棒的方案。
3. **Cross-Encoder 重排是标准配置**。召回 100 条 → 重排 → 取 5 条，是最常见的流程。
4. **最终上下文只放 3~8 条**。这是「Lost in the Middle」给出的直接指导。
5. **中文场景用 bge-reranker-v2-m3 或 Qwen3-Reranker**。
6. **先建 Recall 评测集再调参**。没有评测，参数调整全是盲猜。
7. **LLM 重排留给高价值场景**。延迟和成本是硬约束。
