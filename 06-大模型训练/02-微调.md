# 微调：SFT、偏好对齐与全参 vs 高效微调

> **核心问题**：微调到底解决什么问题？全参微调要花多少显存？SFT 数据怎么造？DPO 到底省了什么？

---

## 1. 微调在整个体系里的位置

### 1.1 先把「训练」拆成五件不同的事

很多人说「微调」时其实在说五件不同的事。它们的**成本、风险、收益完全不同**：

| 手段 | 解决什么 | 知识更新 | 成本 | 可溯源 | 典型数据量 |
|---|---|---|---|---|---|
| **继续预训练**（中期训练） | 领域语言风格、术语、分布对齐 | ✅ 改变模型参数 | 高（10¹⁰+ token） | ❌ | 10¹⁰ ~ 10¹¹ tokens |
| **SFT**（监督微调） | 任务格式、指令跟随、输出风格 | ⚠️ 有限 | 中 | ❌ | 10³ ~ 10⁵ 条 |
| **偏好对齐**（RLHF / DPO） | 「哪种答案更好」、价值观、安全边界 | ⚠️ 有限 | 中高 | ❌ | 10⁴ ~ 10⁶ 对 |
| **RAG** | 动态事实知识 | ✅ 只改索引 | 低 | ✅ | 任意规模文档 |
| **ICL / Prompt** | 少样本格式、临时任务 | ✅ 只改 prompt | 极低 | ✅ | 几条示例 |

### 1.2 决策树：什么时候该微调

```
你的问题是什么？
  │
  ├─ 模型不知道「最新事实 / 私有文档」
  │     → 用 RAG，不要微调
  │     （见 ../03-RAG/）
  │
  ├─ 模型知道，但「不会按你要的格式/风格/步骤输出」
  │     → 先试 Prompt + few-shot
  │     → 不够再 SFT
  │
  ├─ 模型「领域感」不够——术语、行话、领域文体
  │     → 继续预训练（中期训练）
  │     → 或 SFT + 大量领域样本
  │
  ├─ 模型输出「能跑但不是我要的那种好」
  │     → 偏好对齐（DPO / RLHF）
  │
  └─ 要做「没有先例的新任务能力」
        → SFT（数据是唯一杠杆）
```

### 1.3 一个必须纠正的误解：「微调能注入知识吗」

**流行说法**：「微调不能注入知识，知识要用 RAG。」

**这句话对了一半**。更准确的表述：

| 知识类型 | 微调能学到吗 | 说明 |
|---|---|---|
| **广为流传的事实** | ✅ 能 | GPT-4 这类强模型上，1,000~10,000 条 SFT 就能让模型稳定复述新事实 |
| **长尾 / 罕见事实** | ⚠️ 不稳定 | 模型倾向于「知道大概」然后编出细节 |
| **需精确取值的知识**（数字、ID、参数） | ❌ 不能 | 这类必须走检索或工具调用 |

**Gekhman et al.（2024/2025）**系统研究了这个问题，结论是：

> 模型微调后**倾向于使用新知识**，但**当某个事实在预训练中本就「不太常见」时，微调后的模型更容易产生幻觉**——它会硬答而不是说不知道。而且模型越强（GPT-4 级），越倾向于「自信地使用新知识」。

**工程结论**：

- **知识型需求 → RAG**（可溯源、可更新、可删除）。
- **行为型需求 → SFT**（格式、风格、流程、判断规则）。
- **两者不互斥**：**生产系统的最优解通常是 RAG（管知识） + SFT（管行为）**。SFT 让模型学会「怎么用检索到的证据」，RAG 提供证据本身。

## 2. 全参微调（Full Fine-tuning）

### 2.1 显存账单

以 **AdamW + bf16 混合精度**为例（详见 [`01-预训练.md`](./01-预训练.md) §5.1）：

| 项 | 每参数字节 | 7B | 13B | 70B |
|---|---|---|---|---|
| 参数（bf16） | 2 | 14 GB | 26 GB | 140 GB |
| 梯度（bf16） | 2 | 14 GB | 26 GB | 140 GB |
| AdamW $m$（fp32） | 4 | 28 GB | 52 GB | 280 GB |
| AdamW $v$（fp32） | 4 | 28 GB | 52 GB | 280 GB |
| fp32 master weights | 4 | 28 GB | 52 GB | 280 GB |
| **优化器+参数+梯度合计** | **16** | **112 GB** | **208 GB** | **1.12 TB** |
| 激活（batch×seq 变化） | — | 10~40 GB | 20~80 GB | 100+ GB |

**结论**：7B 全参 SFT **单卡放不下**（80GB 卡也因为激活而不够），实务上：

- 2~4 × A100/H100 80GB + ZeRO-2/3，或
- 8 卡 × 48GB（4090 / L40S）+ ZeRO-3 + 梯度检查点，或
- 换 8-bit Adam / Adafactor 省 4~6 bytes/param。

### 2.2 全参 vs LoRA 的能力对比

| 维度 | 全参微调 | LoRA |
|---|---|---|
| 可训练参数 | 100% | 0.01% ~ 5% |
| 显存 | 16 bytes/param + 激活 | 近似只存 adapter + 激活 |
| 单卡可训 7B？ | ❌（需多卡） | ✅（量化后可到 24GB 以内） |
| 存储 | 每个任务一份完整权重 | 每任务几十 MB |
| 多任务切换 | 要存 N 份权重 | 挂 N 个 adapter |
| 推理开销 | 零 | 合并后零（不合并则多 10~30%） |
| 表达能力 | 上限最高 | 受低秩限制，某些任务接近全参 |
| 灾难性遗忘 | 风险高 | **风险低**（低秩本身是一种正则） |
| 合并进基座 | 不适用 | 可以，且是标准做法 |

### 2.3 灾难性遗忘（Catastrophic Forgetting）

**现象**：在窄领域数据上微调后，模型在通用能力上明显退化——通用问答变笨、长文本总结变差、代码能力掉点。

**常见原因**：

1. 数据分布过窄（全是同一领域的窄格式样本）
2. 学习率过大（相对全参微调）——把基座的通用能力冲掉了
3. epoch 过多（同一个分布反复强化）
4. 缺少 KL 约束（RLHF 阶段）或正则项

**缓解手段**：

| 手段 | 做法 |
|---|---|
| 混数据 | 训练集里混入 5~20% 通用指令数据（保持分布） |
| 低学习率 + 少 epoch | 全参 SFT 常用 1e-5 ~ 2e-5，2~3 epoch |
| 参数高效微调 | LoRA 的低秩约束天然减小了改动幅度 |
| KL 正则 | 对齐阶段对参考模型的 KL 惩罚 |
| EWC / L2-SP | 惩罚相对基座权重的偏移量 |
| 早停 | 用通用能力保持指标做 early stopping 判据 |

> **避坑**：**灾难性遗忘是「静默失败」**——你的业务指标涨了，但你不知道通用能力掉了，直到某天用户来投诉。

## 3. SFT 数据工程

### 3.1 数据的三个维度

| 维度 | 问题 | 常见做法 |
|---|---|---|
| **覆盖** | 任务类型够不够全？ | 按「意图 × 输入形态 × 输出格式」建矩阵，逐格填 |
| **格式** | 输入输出结构统一吗？ | 固定模板（Alpaca / ChatML / Llama 3 chat template） |
| **质量** | 答案本身对不对？ | 校验、过滤、去重、人工抽检 |

**最容易被忽略的是「覆盖」的完整性。** 用一张矩阵自查：

```
              输入是纯文本   输入含代码   输入含图片/表格   输入超长
问答                ✓              ✓             ✓              ✓
摘要                ✓              ✓             ✓              ✓
改写                ✓              ✓             ✓              ✓
分类/抽取           ✓              ✓             ✓              -
拒答/边界           ✓              -             -              -
```

> **每多一格新场景，都可能需要新样本。** 训练集里没出现过的输入形态，模型在推理时会「退化到训练分布里最近的那个」。

### 3.2 数据来源与构造

| 方法 | 代表 | 优点 | 缺点 |
|---|---|---|---|
| **人工标注** | Dolly（15k）、OpenAssistant | 质量最高，分布真实 | 贵、慢、覆盖有限 |
| **强模型蒸馏** | Alpaca（52k）、Magicoder | 便宜、量大、覆盖面广 | 会继承教师模型的偏见与幻觉 |
| **Self-Instruct**（Wang et al. 2022） | 自举生成指令 | 无需人工，可无限扩展 | 容易自我重复、坍塌 |
| **Evol-Instruct**（Xu et al. 2023） | 指令复杂度进化 | 提升难题上的表现 | 过程复杂，可能偏离 |
| **真实业务日志** | 线上 trace | 分布最真实 | 需要脱敏、需清洗、量少 |
| **人工精修蒸馏数据** | LIMA（1k） | 质量极高 | 量太小，覆盖有限 |

**规模经验（论文报告值）**：

| 数据集 | 规模 |
|---|---|
| LIMA | **1,000** 条 |
| InstructGPT SFT | 13,000 条 |
| Dolly | 15,000 条 |
| Alpaca | 52,000 条 |
| ShareGPT / UltraChat | 100k ~ 1.5M |

### 3.3 LIMA 的核心结论（必读）

**《LIMA: Less Is More for Alignment》（Zhou et al., 2023）**：用 **1,000 条**精心构造的高质量样本，对 LLaMA-65B 做 SFT，就达到了接近 GPT-4 的对话质量（MT-Bench 43 分量表）。

**结论不是「数据越少越好」**，而是：

> **对齐阶段的关键是「风格对齐」而非「知识灌输」，所以高质量少量数据 > 低质量海量数据。**

**LIMA 论文自己给出的三个前提**（引用时不要省略）：

1. base model 已经足够强（**它学的是风格，不是知识**）
2. 样本数量足够多样（1,000 条覆盖 1,000 个不同主题）
3. 样本质量足够高（人工精修，拒绝低质样本）

> **工程结论**：**先做数据质量，再做数据数量。** 用 5,000 条精心构造的数据，通常打得过 50,000 条粗制滥造的数据。

### 3.4 模板与 loss mask

**通用模板（Alpaca style）**：

```
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
{instruction}

### Input:
{input}

### Response:
{response}
```

**多轮模板（ShareGPT style）**：

```
<|system|>
{system}
<|user|>
{first input}
<|assistant|>
{first response}
<|user|>
{second input}
<|assistant|>
{second response}
```

**关键：loss mask（只对 assistant 部分算 loss）**

$$
\mathcal{L} = -\frac{1}{\sum_{t \in \text{assistant}} \sum_{i=1}^{T} m_t} \sum_{t=1}^{T} m_t \sum_{i} \log p_\theta(x_{t,i} \mid x_{<t,i}), \quad m_t = \mathbb{1}[\text{position } t \text{ 属于 assistant 段}]
$$

如果不 mask，模型会**花容量去学「怎么提问」**——而推理时没有提问方，这是纯粹的资源浪费，且会削弱指令跟随。

**用 `apply_chat_template` 而不是手拼字符串**：

```python
messages = [
    {"role": "system", "content": "你是专业的机械工程师。"},
    {"role": "user",   "content": "解释一下轴承的失效模式。"},
    {"role": "assistant", "content": "常见的失效模式有……"},
]
text = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_mask=True)
```

> **避坑（新手第一大坑）**：**模板必须和 base model 训练时用的完全一致。** 用 chat 模型时套 base 模板、或把自己的 `<user>` 标签写错，模型表现会断崖式下降，而 loss 曲线看起来还挺正常。

### 3.5 数据清洗

| 动作 | 说明 |
|---|---|
| **去重** | 精确 + 近似（MinHash）+ 语义去重；重复样本会让模型过拟合到那一条 |
| **去污染** | 检查与评测集（MMLU / HumanEval / 业务测试集）的 n-gram 重叠 |
| **长度过滤** | 剔除超长 / 超短样本，或单独分桶 |
| **质量过滤** | 剔除：答案截断、答非所问、包含「作为一个 AI 语言模型」类模板、重复行 |
| **人工抽检** | **至少人工看 50~100 条**。这是唯一能发现「模板错位」这类系统性 bug 的手段 |

## 4. 参数高效微调（PEFT）全景

### 4.1 手法谱系

| 方法 | 年份 | 注入位置 | 可训练参数占比（7B 量级） | 推理开销 | 合并 |
|---|---|---|---|---|---|
| **Adapter** | 2019 | 层内并行分支 | 0.1% ~ 1% | +5~10% | 难 |
| **Prefix-Tuning** | 2021 | 每层前缀 KV | 0.01% ~ 1% | 变长前缀 | 难 |
| **Prompt-Tuning** | 2021 | 输入层 | < 0.1% | 略增 | 难 |
| **P-Tuning v2** | 2022 | 各层深层 prompt | 0.01% ~ 1% | 变长前缀 | 难 |
| **LoRA** | 2021 | 任意线性层 | 0.01% ~ 5% | 合并后 0 | ✅ 易 |
| **QLoRA** | 2023 | 同 LoRA（4bit 基座） | 同上 | 合并后 0 | ✅ 易 |
| **DoRA** | 2024 | 分解权重模长+方向 | 同上 | 合并后 0 | ✅ 易 |
| **PiSSA** | 2024 | 主奇异值初始化 | 同上 | 合并后 0 | ✅ 易 |
| **VeRA** | 2023 | 共享随机矩阵 | < 0.01% | 合并后 0 | ✅ 易 |
| **AdaLoRA** | 2023 | 秩预算自适应分配 | 0.01% ~ 5% | 合并后 0 | ✅ 易 |
| **OFT / BOFT / LoHa** | 2023~2024 | 正交 / Hadamard 参数化 | 极低 | 合并后 0 | ✅ 易 |

### 4.2 怎么选

| 你的约束 | 选择 |
|---|---|
| 单卡、显存紧张、任务多 | **LoRA / QLoRA**（默认选择） |
| 要极致省显存、任务极多 | VeRA / AdaLoRA |
| LoRA 训完了还想再涨一点 | DoRA / PiSSA |
| 需要在训练中动态增删秩 | AdaLoRA |
| 想保留基座完全不动、只加条件 | Prefix / Prompt / P-Tuning（但推理开销难消） |
| 有充足多卡、要榨干任务上限 | 全参微调 |

> **工程结论**：**LoRA 是当前默认答案。** 其余方法是在 LoRA 基础上的边际改进，除非你明确遇到了 LoRA 的某个具体瓶颈（比如秩不够），否则换方法带来的收益小于「把数据和超参调好」的收益。

## 5. 偏好对齐

### 5.1 RLHF 三步法

```
① SFT
   用 (prompt, chosen_response) 对做监督微调
        ↓
② 训练奖励模型 (RM)
   用 (prompt, chosen, rejected) 三元组训练一个标量打分模型
        ↓
③ PPO 强化学习
   用 RM 的分数作为奖励，优化策略模型，同时用 KL 惩罚约束它别跑偏
```

**论文**：InstructGPT（Ouyang et al., 2022）

**RLHF 的三个真实成本**：

| 成本 | 说明 |
|---|---|
| **RL 训练不稳定** | PPO 超参敏感，容易 reward collapse、长度爆炸、KL 惩罚失效 |
| **需要额外 2~3 个模型同时在显存里** | policy + ref + reward + critic，显存翻 3~4 倍 |
| **调参黑洞** | 同一套数据换个 PPO 超参结果差很多，且不直观 |

### 5.2 DPO：把 RL 变成一个分类问题

**论文**：*Direct Preference Optimization*（Rafailov et al., NeurIPS 2023）

**核心洞察**：既然最终目标是「让策略模型更偏好 chosen 而不是 rejected」，那么可以在**参考模型**的约束下，直接用偏好数据做监督式优化——**完全跳过显式的奖励模型和 PPO 采样**。

**DPO 损失**：

$$
\mathcal{L}_{\text{DPO}}(\theta) = -\mathbb{E}_{(x, y_w, y_l)\sim\mathcal{D}}
\left[
\log \sigma\left(
\beta \log\frac{\pi_\theta(y_w \mid x)}{\pi_{\text{ref}}(y_w \mid x)}
-
\beta \log\frac{\pi_\theta(y_l \mid x)}{\pi_{\text{ref}}(y_l \mid x)}
\right)
\right]
$$

**逐项拆解**：

| 项 | 含义 |
|---|---|
| $\pi_\theta$ | 待训练的策略模型（初始化自 SFT 模型） |
| $\pi_{\text{ref}}$ | 冻结的参考模型（通常就是 SFT 模型） |
| $\sigma$ | 把「两个 log-ratio 之差」映射成偏好概率 |
| $\beta$ | KL 强度的隐式控制：$\beta$ 越大越保守（越贴参考模型），越小越激进 |
| $\log\frac{\pi_\theta(y)}{\pi_{\text{ref}}(y)}$ | 隐式的 KL 约束——**参考模型出现在分母里，这就是「跳过显式 KL 项」的关键** |

**DPO 相对 RLHF 的优势**：

| 维度 | RLHF | DPO |
|---|---|---|
| 需要奖励模型 | ✅ 需要 | ❌ 不需要 |
| 需要在线采样 | ✅ 需要（PPO rollout） | ❌ 不需要（离线偏好对） |
| 显存占用 | policy + ref + RM + critic | policy + ref |
| 训练稳定性 | 敏感 | **稳**（本质是二分类） |
| 调参难度 | 高 | 低（主要调 $\beta$ 和 lr） |
| 表达能力 | 上限更高（可迭代） | 略低（离线数据分布固定） |

**DPO 的代价**：没有探索机制，只能优化偏好数据覆盖到的方向；且对**参考模型与初始策略差异过大**的情况（$\pi_\theta$ 离 $\pi_{\text{ref}}$ 太远）会退化。

### 5.3 DPO 的变体与 RLVR

| 方法 | 年份 | 改动 |
|---|---|---|
| **IPO** | 2023 | 用平方损失替代 sigmoid，缓解 DPO 的「过拟合偏好数据」问题 |
| **KTO** | 2024 | 不用成对偏好，只用「好/坏」的单条标注，数据获取成本大降 |
| **ORPO** | 2024 | 单阶段：SFT + odds-ratio 偏好损失一起做，不需要参考模型 |
| **SimPO** | 2024 | 去掉参考模型（无需 ref），用长度归一化的奖励 margin |
| **RRHF** | 2023 | 多条回复 + 排序信息（比纯二元偏好信息更多） |
| **CDPO** | 2024 | 引入「偏好 + 对比」双损失，缓解过度偏好导致的输出退化 |
| **GRPO** | 2024 | 群组相对策略优化：同一个 prompt 采样一组回答，用组内相对排名做优势估计（DeepSeekMath） |
| **RLVR** | 2025 | 用**可验证奖励**（数学答案对错、代码是否通过测试）替代人类偏好（DeepSeek-R1） |

**RLVR / GRPO 的意义**：当任务**有客观正误**时，偏好信号不需要人标——数学题能验、代码能跑、SQL 能查。这把 RL 的数据瓶颈从「人标偏好」转成「构造可验证任务」，是 2025 年推理模型能力的核心推动力。

### 5.4 工具链

| 工具 | 定位 |
|---|---|
| **TRL**（HuggingFace） | 事实标准，SFTTrainer / DPOTrainer / GRPOTrainer / PPOTrainer 一体化 |
| **OpenRLHF** | 更贴近生产的大规模 RLHF |
| **veRL** | 高性能、面向 RL 的分布式训练框架 |
| **axolotl / LLaMA-Factory** | 开箱即用的微调脚本（配置驱动） |
| **Unsloth** | 加速 + 显存优化（把全参微调压到单卡可行） |

## 6. 超参实操表

### 6.1 全参 SFT

| 超参 | 推荐起点 | 说明 |
|---|---|---|
| **learning rate** | **1e-5 ~ 2e-5** | 最大的坑。太大直接毁掉基座能力 |
| **epochs** | **2 ~ 3** | 数据多时 1~2；数据少时 3~5 但要防遗忘 |
| **batch size（单卡）** | 8 ~ 64 | 配合梯度累积 |
| **effective batch size** | 64 ~ 256 | 总数（单卡 bs × 累积步数 × 卡数） |
| **warmup ratio** | 0.03 ~ 0.1 | 小数据集要拉长 |
| **lr scheduler** | cosine | 配 min_lr_ratio = 0.1 |
| **max seq length** | 按数据 P95 分位定 | 别拍脑袋定 4096，绝大多数样本用不到 |
| **weight decay** | 0.0 ~ 0.1 | AdamW 的 decoupled 版本 |
| **max_grad_norm** | 1.0 | |
| **optimizer** | AdamW (fp32 master) | 显存紧张换 8-bit Adam |
| **precision** | bf16 | fp16 需要 loss scaling |
| **gradient checkpointing** | 显存紧张时开 | 慢 20~40% |

### 6.2 LoRA / QLoRA（详见 [`03-LoRA.md`](./03-LoRA.md)）

| 超参 | 推荐起点 | 说明 |
|---|---|---|
| **learning rate** | **1e-4 ~ 3e-4** | 比全参高 1~2 个数量级 |
| **epochs** | 1 ~ 3 | 同上 |
| **rank `r`** | 8 ~ 32 | 论文实测 r=8 已接近饱和 |
| **alpha** | 2r（常见 16 / 32） | 缩放系数 |
| **dropout** | 0.05 ~ 0.1 | 数据少时调高 |
| **target_modules** | `q_proj,k_proj,v_proj,o_proj` | 加上 FFN 通常更好 |
| **warmup ratio** | 0.03 ~ 0.1 | |
| **effective batch size** | 16 ~ 64 | |

> **这些不是「最佳值」，是「不会出事的起点」。** 任何超参在换模型 / 换数据后都要重新验证。仓库里放一张自己的实验记录表，比抄别人的超参重要得多。

## 7. 评测：怎么判断微调是「成功」还是「只是看起来更好」

### 7.1 三个必须同时看的轴

| 轴 | 测什么 | 常用指标 |
|---|---|---|
| **能力不退化** | 通用能力有没有掉 | MMLU, GSM8K, HumanEval, IFEval（对比 base model） |
| **任务达成** | 目标任务做对了没 | 业务自己的测试集 / 自动指标 |
| **对齐与安全** | 格式、拒答、越狱 | IFEval, 自建红队集, 长度分布 |

**只看第一个轴（业务任务）会漏掉灾难性遗忘；只看第二个轴会漏掉「模型学会了新任务但变笨了」。**

### 7.2 评测集建设的要点

| 要点 | 说明 |
|---|---|
| **和训练集严格隔离** | 同源划分的测试集不算测试集 |
| **足够大** | 50 条能看出明显差异，200 条以上才能做显著性判断 |
| **覆盖边界** | 必须包含「模型应该拒答/走 fallback」的样本 |
| **人工与自动双轨** | 自动指标（格式匹配、精确率）用于回归，人工/LLM-as-judge 用于主观质量 |
| **固定随机种子** | 采样评测必须固定 seed，否则分数抖动无法比较 |

### 7.3 LLM-as-a-Judge 的注意事项

| 问题 | 对策 |
|---|---|
| 位置偏见（偏好靠前的回答） | 交换顺序各判一次，取一致的结果 |
| 长度偏见（偏好长的回答） | 控制长度或在 prompt 里显式要求 |
| 自我偏好（同族模型更偏爱同族输出） | 用不同家族的 judge 模型 |
| 分数虚高 | judge 模型的分数只做相对比较，不当绝对指标 |

> **避坑**：**不要用被测模型自己当 judge 评估自己的输出。** 这是自证清白，不是评测。

## 8. 常见坑清单

| # | 坑 | 症状 | 解法 |
|---|---|---|---|
| 1 | **聊天模板不匹配** | 输出格式乱、不听指令 | 用 `apply_chat_template`，确认 base/chat 模型选对模板 |
| 2 | **loss 没做 mask** | 能力提升有限 | 只对 assistant 段算 loss |
| 3 | **lr 过大** | 输出退化、复读、通用能力崩 | 降一个数量级；对比 base 的通用基准 |
| 4 | **数据泄漏到评测集** | 离线分数虚高、上线翻车 | n-gram 检查 + 按来源/时间分组切分 |
| 5 | **数据分布过窄** | 只会一种格式，换个问法就不行 | 建覆盖矩阵，逐格补样本 |
| 6 | **epoch 过多 / 样本重复** | 过拟合，输出开始复述训练样本 | 降 epoch、去重 |
| 7 | **max_len 拍脑袋设太大** | OOM + 大量 padding 浪费 | 用数据长度的 P95 |
| 8 | **padding side 错** | 批量推理时输出异常 | decoder-only 模型左 padding；training 保持一致 |
| 9 | **seed 不固定** | 分数抖动，无法判断改动效果 | 全链路固定 seed 并记录 |
| 10 | **忽略 base 的对照** | 不知道是模型好还是数据好 | 永远保留 base model 作为对照组 |
| 11 | **EOS / 终止符没训对** | 模型不停地说、停不下来 | 检查模板里的 EOS 处理与生成参数 |
| 12 | **用采样评测对比 greedy** | 分数不可比 | 明确固定 decoding 参数 |

## 9. 工程结论

1. **先分清你要解决的是「知识」还是「行为」。** 知识走 RAG，行为走 SFT——这是本笔记最重要的一条分流。
2. **数据质量 > 数量。** LIMA 用 1,000 条打赢了很多 50,000 条的方案（前提是 base 够强、覆盖够广、质够高）。
3. **默认选 LoRA**，除非你有明确理由要全参。全参的成本主要在显存和遗忘风险，不在效果上限。
4. **对齐先用 DPO**，它比 RLHF 稳、便宜、好调；等 DPO 到顶了再考虑 RL。
5. **灾难性遗忘是静默失败。** 必须同时监控业务指标和通用能力保持指标。
6. **模板和 loss mask 是两个最常见也最容易修的 bug。** 遇到「怎么都不对」，先查这两个。
7. **永远保留 base model 作为对照组。** 没有对照的实验结论不可信。
