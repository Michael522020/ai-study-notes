# 03 · Super Agent：长任务自治

> **一句话：Super Agent 不是「跑得更久的 Agent」，而是「把一件事做成一个可中断、可恢复、可验收的作业」。**
> 它的结束条件不由模型自称，而由**机器可判的验收标准**决定。

---

## 0. 定义与分界

### 0.1 三个特征同时成立，才是 Super Agent

| 特征 | 含义 | 反例 |
|---|---|---|
| **目标模糊** | 交付物清楚，但路径要自己找 | 「把这段话翻译成英文」 |
| **过程跨阶段** | 有依赖关系，中间会失败、会中断 | 「查一下这个订单」 |
| **结果要验收** | 有客观标准可判通过与否 | 「聊聊天」 |

第三条是**分水岭**。只有前两条，那是「跑得久的工作流」；加上第三条，才产生自治。

### 0.2 一句话判据

> **这件事怎么算做完？**
> - 「用户觉得可以」→ Bot
> - 「产出了一份文档」→ Agent
> - 「文档通过了 5 条验收标准中的 4 条，且第 5 条被标记为待人工确认」→ **Super Agent**

### 0.3 典型场景

| 场景 | 目标 | 验收标准举例 |
|---|---|---|
| 供应商尽职调查 | 给一家供应商出风险评估报告 | 工商信息已核对 / 3 年财报已分析 / 风险点已列全 |
| 批量数据迁移 | 把 N 个系统的主数据统一 | 字段映射已确认 / 抽样 100 条一致 / 回滚脚本已生成 |
| 合规文档准备 | 出一份完整的投标材料 | 资质齐全 / 参数逐条对齐 / 格式符合招标方要求 |
| 代码库迁移 | 把旧框架迁到新框架 | 测试全绿 / 行为快照一致 / 文档已更新 |
| 竞品分析 | 输出带数据来源的竞品报告 | 覆盖 5 家 / 每条结论有出处 / 数据带时间戳 |

> **工程结论**：如果你的任务没有第 3 列那种**能被机器逐条判定**的标准，
> 那你做出来的不是 Super Agent，是一个**没有验收的长循环** —— 后者比前者更危险。

---

## 1. 五个必备机制

```
        ┌──────────────┐
目标 ──▶│  ① 分解       │ 目标 → 可独立验证的子任务
        └──────┬───────┘
               ▼
        ┌──────────────┐
        │  ② 并行       │ 互不依赖的子任务同轮发起
        └──────┬───────┘
               ▼
        ┌──────────────┐
        │  ③ 检查点     │ 每步落盘，可断点续跑
        └──────┬───────┘
               ▼
        ┌──────────────┐
        │  ④ 上下文治理 │ 压缩/编辑/摘要，防撑爆窗口
        └──────┬───────┘
               ▼
        ┌──────────────┐
        │  ⑤ 验收       │ 逐条判定，全过才算完成
        └──────────────┘
```

少任何一个，长任务都会以某种方式崩掉：

- 少 ① → 做着做着跑偏，且无法回溯；
- 少 ② → 串行导致耗时与成本线性膨胀；
- 少 ③ → 进程一挂全白跑；
- 少 ④ → 撑爆上下文后半程质量断崖；
- 少 ⑤ → 模型说「完成了」就算完成。

## 2. 架构：阶段状态机

本仓库的实现（`code/agent-lab/agentlab/profiles/superagent.py`）是三段式状态机：

```python
# 阶段一：分解
plan_runtime = self._runtime(["plan_tasks", "search_knowledge", ...])
plan_result = self._run_phase(plan_runtime, plan_prompt, history)
for call in plan_result.tool_calls:
    if call.name == "plan_tasks" and call.status == "ok":
        plan = list(call.input.get("steps") or [])

# 阶段二：逐条执行（每步一个独立 runtime，共享预算）
for step in plan:
    if step in completed:      # ← 断点续跑靠这行
        continue
    step_result = self._run_phase(exec_runtime, step_prompt, history)
    completed.append(step)

# 阶段三：验收
verify_result = self._run_phase(verify_runtime, verify_prompt, history)
for call in verify_result.tool_calls:
    if call.name == "check_acceptance" and call.status == "ok":
        verification = {"criteria": ..., "results": ...}
passed = all(verification["results"])
status = STATUS_COMPLETED if passed else "verification_failed"
```

### 2.1 验收必须机器可判

`check_acceptance` 工具的入参是 `criteria[]` 与 `results[]` 一一对应：

```python
ToolSpec(
    name="check_acceptance",
    description=(
        "对验收标准逐条判定。criteria 与 results 一一对应，全部为 true 才算通过。"
        "这是长任务收尾的自检环节，不要跳过。"
    ),
    input_schema={
        "type": "object",
        "properties": {
            "criteria": {"type": "array", "items": {"type": "string"}},
            "results":  {"type": "array", "items": {"type": "boolean"}},
        },
        "required": ["criteria", "results"],
    },
)
```

**注意 `results` 是布尔数组，不是自然语言。** 这是刻意的：
自然语言判断会让「通过」变成模型的自由发挥。

> **工程结论**：验收标准要写成**模型能逐条判定真假**的形式。
> 「报告质量良好」不可判定；「每个数据结论都带来源链接」可判定。

### 2.2 验收不通过不是失败，是「返工」

```python
status = STATUS_COMPLETED if passed else "verification_failed"
```

`verification_failed` 与 `completed` 是两个不同的终态。
这个区分让上层能做不同的事：前者触发返工队列，后者才交付。

## 3. 检查点与断点续跑

### 3.1 检查点存什么

```json
{"goal": "...", "plan": ["..."], "completed_steps": ["..."],
 "verification": {"criteria": [...], "results": [...]}, "cost_usd": 1.23}
```

**只存可序列化的状态**，不存消息历史 —— 历史靠模型重新读文件恢复，
这样检查点才能跨进程、跨机器。

### 3.2 原子写

```python
tmp = path.with_suffix(path.suffix + ".tmp")
tmp.write_text(json.dumps(state, ensure_ascii=False, indent=2), encoding="utf-8")
tmp.replace(path)   # 原子替换，避免半截文件
```

**不原子写就会出现「进程被杀 → 检查点损坏 → 续跑时 JSON 解析失败 → 任务永久卡死」。**
这类事故排查起来极其耗时，写法只要一行。

### 3.3 续跑的判定

```python
state = self._load_checkpoint(goal) if resume else {}
...
for step in plan:
    if step in completed:
        continue
```

注意：**只有 `goal` 完全一致才复用检查点。** 目标变了还续跑，等于在错误的基线上继续。

## 4. 长时可靠性

### 4.1 失败要分类，不要一律重试

| 失败类型 | 例子 | 处置 |
|---|---|---|
| **可重试的瞬时错误** | 网络超时、429 限流 | 指数退避重试，最多 N 次 |
| **不可重试的输入错误** | 参数非法、文件不存在 | 不重试，回到规划阶段 |
| **需要人工的** | 权限不足、数据缺失、口径不明 | 停下，`needs_human` |
| **资源类** | 预算耗尽、步数上限 | 停下，保留检查点 |

**最常见的错误是「一律重试」**：同一个错误重试 5 次，浪费 5 份成本，
而且掩盖了真正的设计问题。本仓库的做法是：同一（工具名 + 入参）连续失败 2 次即转人工。

### 4.2 幂等

子任务必须**可重复执行**。典型反例：

- 建单：重试会建两单 → 用业务幂等键（订单号 + 问题类型）；
- 发信：重试会发两封 → 记录已发标记；
- 写文件：重试会覆盖 → 检查点里记已写路径。

> **工程结论**：**先想清楚「这一步重跑会怎样」，再写这一步。**
> 长任务必然会有重试，幂等不是加分项。

### 4.3 并行的正确姿势

模型在**一个回合里发起多个工具调用**即并行（API 侧会并发执行）。
本仓库的运行时把同一回合的多个 `tool_use` 收集起来，一次性回结果：

```python
# 一次 assistant 回合里的多个 tool_use，必须在同一条 user 消息里回结果
messages.append({"role": "user", "content": tool_result_blocks})
```

**并行只对无依赖的子任务用。** 有依赖就必须串行，否则拿到的是半成品状态。

## 5. 上下文治理：长任务必然撑爆上下文

三种做法，本仓库用了最朴素的第 3 种作为保底：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **本地裁剪** | 保留首条目标 + 最近 N 条消息 | 零成本、绝不炸 | 会丢细节，质量随裁剪下降 |
| **模型摘要** | 让模型写摘要替换历史 | 语义保真 | 多一次调用，摘要本身可能丢东西 |
| **服务端压缩** | `compact-2026-01-12` beta，API 侧自动摘要 | 省心 | 需回传 compaction 块，有 beta 限制 |

本地裁剪的实现（`SuperAgent.compact_history`）：

```python
head = messages[:1]        # 首条用户目标永远保留
tail = messages[-keep_last:]
dropped = len(messages) - len(head) - len(tail)
marker = {"role": "user", "content": [{"type": "text",
          "text": f"[上下文压缩] 已裁剪 {dropped} 条历史消息，关键结论请写在 output 字段里。"}]}
```

**关键设计**：裁剪时在提示里明确要求「关键结论请写在 output 字段里」。
子任务的产出落在结构化字段里，而不是留在对话历史里 —— 这样裁剪不会伤到关键信息。

> **工程结论**：长任务里，**结构化产出（output 字段、产物文件）才是真正的记忆**，
> 对话历史只是施工过程，丢了可以重来。

服务端压缩的正确用法有个硬细节：**回传时必须拼回整个 `response.content`**（含 compaction 块），
只拼文本会静默丢失压缩状态。

## 6. 成本：长任务是账单事故的高发区

### 6.1 单任务成本模型

假设一个长任务：30 步，每步输入 30K token、输出 800 token。

| 模型 | 单步成本 | 30 步总计 |
|---|---|---|
| Opus 5.5 | 30,000×4/1e6 + 800×20/1e6 ≈ $0.136 | **≈ $4.08** |
| Sonnet 5.5 | ≈ $0.068 | **≈ $2.04** |
| Haiku 5.5 | ≈ $0.0034 | **≈ $0.10** |

**一个长任务的成本可以轻松超过一次人工工时。** 所以：

### 6.2 预算要分阶段分配

不要给整个任务一个总预算然后任其花。分阶段：

| 阶段 | 预算占比 | 理由 |
|---|---|---|
| 规划 | 10% | 规划错了后面全白花，宁可少花 |
| 执行 | 60% | 主战场 |
| 验收 | 15% | 验收要真的逐条判，不能草率 |
| 缓冲 | 15% | 返工与重试 |

### 6.3 降本手段按优先级

1. **削减每步的输入上下文**（长任务的上下文是复利的：第 30 步带着 30 步历史）；
2. **把独立子任务并行**（并行不省钱，但省时间，而时间就是超时重试的成本）；
3. **模型分档**：格式化、抽取类子任务用 Haiku，判断类用 Sonnet；
4. **缓存**：固定的系统提示与工具描述务必放前面并打缓存断点；
5. **任务预算**（`task-budgets-2026-03-13` beta）：给 agentic loop 一个 token 上限，
   模型能看到倒计时并自觉收尾 —— 比事后截断优雅。注意最小值是 20,000 token。

## 7. 指标体系

### 7.1 核心指标

| 指标 | 定义 | 意义 |
|---|---|---|
| **验收通过率** | 通过全部验收标准的任务占比 | **唯一的北极星** |
| 一次通过率 | 首次就通过验收（无需返工） | 反映规划质量 |
| 平均轮次 | 完成一个任务的模型回合数 | 效率 |
| 每任务成本 | 美元/任务 | 商业可行性 |
| 人工介入率 | 需要人接手的任务占比 | 自治程度 |
| 断点续跑成功率 | 中断后续跑能完成的比例 | 可靠性 |

### 7.2 过程指标

| 指标 | 作用 |
|---|---|
| 规划质量 | 计划与目标的偏差（人工抽检） |
| 单步失败率 | 定位到具体子任务 |
| 重规划次数 | 计划失败率 |
| 验收条目数 | 验收标准是否被稀释 |

### 7.3 一个容易忽略的指标：**验收条目数**

如果任务越做越复杂，验收标准可能被悄悄放宽（从 8 条降到 5 条）。
**记录每次任务的验收条目数**，能发现这种「通过率上升但质量下降」的假象。

## 8. 风险清单

| 风险 | 表现 | 防线 |
|---|---|---|
| **半成品交付** | 看起来完成了，其实有缺口 | 验收标准逐条判；验收不过不标完成 |
| **成本失控** | 无限循环、反复重试 | 分阶段预算 + 步数上限 + 重试上限 |
| **越权操作** | 中途执行了不该执行的动作 | 副作用工具干跑 + 人工闸门 |
| **上下文丢失** | 后半程忘了前面的约束 | 结构化产出 + 关键约束进系统提示 |
| **目标漂移** | 执行到一半改了目标 | 目标与验收标准固定在提示里，不随历史滚动 |
| **自欺验收** | 模型给自己打高分 | 验收用机器可判的布尔项；必要时用独立 Judge |
| **不可复现** | 同样输入结果差异大 | 固定模型版本、记录完整轨迹、种子与温度策略明确 |

> **关于自欺验收**：让模型自己判自己的产出，天然有偏。
> 至少要做「**产出方与验收方分离**」：如果产出报告的是 A 角色，验收就要用另一套提示与标准。

## 9. 落地路线

| 阶段 | 周期 | 做什么 | 退出条件 |
|---|---|---|---|
| **P0 人做 Agent 辅** | 2 周 | 人做全部决策，Agent 只做单步执行 | 单步执行成功率 ≥ 95% |
| **P1 阶段化** | 3 周 | 引入规划阶段与验收阶段 | 一次通过率 ≥ 40% |
| **P2 长程可靠性** | 3 周 | 检查点、断点续跑、幂等、失败分类 | 续跑成功率 ≥ 90% |
| **P3 规模化** | 持续 | 多任务并发、成本优化、分档 | 验收通过率达标且成本在预算内 |

**P0 这一步是 Super Agent 独有的。**
前面 01 篇说过「没有评测集的 Agent 不许上线」，Super Agent 还要再加一条：
**没有「人做 Agent 辅」的阶段，就直接上自治，成功率会低得让人失去信心。**

## 10. 工程结论

1. Super Agent 的定义性特征是**结果要验收**，不是任务长。
2. 五个机制缺一不可：分解、并行、检查点、上下文治理、验收。
3. 验收标准必须**机器可判**（布尔项，不是自然语言）。
4. `verification_failed` 与 `completed` 是两个终态，返工要能被调度。
5. 检查点只存可序列化状态，写入必须原子。
6. 长任务的重试前提是幂等 —— 先想清楚重跑会怎样。
7. 上下文里的**结构化产出才是记忆**，对话历史丢了可以重来。
8. 成本按阶段分配预算，不要给一个总预算任其花。
9. 验收方与产出方要分离，否则是自欺验收。
10. 记录验收条目数，防「通过率上升但标准被稀释」。
11. 先做「人做 Agent 辅」，再谈自治。
