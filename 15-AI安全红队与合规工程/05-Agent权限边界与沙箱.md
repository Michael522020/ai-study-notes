# Agent 权限边界与沙箱

> **核心问题**：Agent 该有多大的权限？怎么在「模型已被完全控制」的前提下仍然安全？

---

## 0. Agent 的信任模型

**传统系统里，模型（如果存在）只是计算的一环；Agent 里，模型是「决策 + 执行」的一体。**

```
传统：  用户 → [校验] → [业务逻辑] → [执行]
                     ↑ 逻辑是确定的，权限是固定的

Agent：用户 → [模型决定调什么、带什么参数] → [执行]
                     ↑ 决定是概率性的，权限是模型说了算
```

**推论**：**Agent 的权限不能由模型「自觉」约束。**
权限必须在**模型之外**强制。

> **一句话**：**把模型当成一个「不完全可靠的、权限很大的实习生」**——
> 你给他一把钥匙（工具权限），但所有危险操作都要有人签字，且他看不到保险柜密码。

---

## 1. 三条权限轴（必须独立校验）

```
┌─────────────────────────────────────────────────────────────┐
│ ① 身份轴  你是谁？                                          │
│    · 认证 / 会话 / 租户隔离                                 │
│    · 模型调用必须携带「代表谁」的凭证，不能是服务账号          │
├─────────────────────────────────────────────────────────────┤
│ ② 能力轴  你能做什么？                                       │
│    · 工具白名单 + 动作分级                                   │
│    · **模型的权限 ≤ 用户的权限**                             │
├─────────────────────────────────────────────────────────────┤
│ ③ 数据轴  你能看什么？                                       │
│    · 行级 / 列级 / 文档级权限                                 │
│    · **在检索层强制**，不是应用层过滤                          │
└─────────────────────────────────────────────────────────────┘
```

### 1.1 为什么必须独立

**最常见的错误：把三条轴混成一条。**

| 错误做法 | 为什么错 |
|---|---|
| 「用户是管理员 → 模型能看全库 → 让模型生成全库报表」 | 一次报表 = 一次批量数据外泄 |
| 「服务账号有权限 → 模型用服务账号调工具」 | **越权提权**：模型的行为被放大到服务账号的权限 |
| 「应用层过滤过了 → 可以把全量检索结果送给模型」 | 无权数据已经进了上下文，模型可能复述 |

### 1.2 权限继承的正确规则

```
模型的有效权限 = 用户权限 ∩ 模型可用工具的权限 ∩ 工具自身的资源权限
```

**三者的交集，不是并集。** 任何一个为 0，整体就是 0。

**实现要点**：
- 工具调用时**用用户的凭证**（透传），**不要用服务账号**
- 工具内部**再校验一次**（防御纵深，防模型绕过编排层直接调）
- 权限判定在**服务端**，不在 prompt 里

---

## 2. 最小权限的具体落地

| 资源类型 | 最小权限做法 |
|---|---|
| **文件系统** | 只读挂载需要读的目录；写只允许指定的临时目录；**绝不挂载密钥目录** |
| **数据库** | 只读账号 + 限定表/列；写用另一个账号且需额外审批 |
| **出网** | **白名单**（只允许业务必需域名），其余默认拒绝 |
| **凭据** | 按需临时签发（STS 风格），用完即销；**不长期持有** |
| **工具集合** | **按场景分组加载**，不要全量挂载 |
| **执行环境** | 沙箱隔离，见 §4 |
| **时间与费用** | 硬上限（见 §5） |

> **出网白名单是投入产出比最高的一条**：
> 它一次性阻断「读→外发」整类链，且**不依赖任何检测**。

## 3. 工具分级与闸门

### 3.1 三级分类

| 级别 | 例子 | 授权方式 |
|---|---|---|
| **L1 只读** | 搜索、查库、读文件、列目录 | **自动执行**（但返回值不可信） |
| **L2 可写** | 建草稿、存笔记、建工单（不通知外部） | **一次确认**（展示将写入的内容） |
| **L3 不可逆 / 对外** | 发邮件/消息、支付、删除、发布、提交审批 | **人工闸**（见 §4），且**不可批量** |

### 3.2 分级之外的三个限制

| 限制 | 说明 |
|---|---|
| **不可批量** | L3 工具必须有「单次上限」，防止模型一次性做 1000 次 |
| **不可并发** | 同一 L3 工具的并发调用要串行化或加锁 |
| **必须有幂等键** | 重试不能产生重复的不可逆动作 |

### 3.3 参数也要收紧

**工具权限不只是「能不能调」，还有「能调成什么样」。**

```python
# ❌ 宽松：模型可以传任意 url
def http_post(url: str, body: str): ...

# ✅ 收紧：白名单 + schema 严格化
def http_post(
    body: str,
    # 不给 url 参数，或用 Literal 限定
) -> str:
    """向已配置的业务端点发送数据（端点不可由模型指定）。"""
```

**要点**：
- **不给模型「任意 URL」这种参数**——出网由服务端配置决定
- **schema 用 `additionalProperties: false`**，多传字段直接拒绝
- **枚举值用 `Literal`**，不让模型自由发挥

> **`additionalProperties: false` 是本库里反复出现的一个手段**——
> 它把「模型多输出一个字段」从「静默通过」变成「明确失败」。
> 在合规场景里，**「明确失败」比「静默通过」安全一个数量级**。

## 4. 人工闸的设计

### 4.1 触发条件（哪些动作必须过闸）

| 类别 | 触发 |
|---|---|
| **不可逆** | 发送 / 发布 / 删除 / 支付 / 提交 / 变更生产配置 |
| **对外** | 任何离开系统的动作 |
| **敏感数据** | 输出包含个人信息、密钥、跨租户数据 |
| **超预算** | 费用、步数、影响行数超阈值 |
| **权限提升** | 请求了超出当前用户权限的资源 |
| **低置信** | 模型自评置信度低于阈值 |

### 4.2 闸门界面必须展示什么

**只显示「确认/取消」是不够的**——人没有信息就无法判断。

| 必须展示 | 为什么 |
|---|---|
| **AI 想做什么**（自然语言 + 具体参数） | 不能让人猜 |
| **将影响的对象与范围**（哪些文件、哪些记录、发给谁） | 判断影响面 |
| **依据来源**（引用了哪些文档/数据） | 判断可信度 |
| **可编辑的最终内容** | **人可以直接改，而不是只能同意或拒绝** |
| **不可逆提示**（明确标注「此操作不可撤销」） | 让人知道自己点的不是「取消」 |

> **「审核即编辑」是最优形态**：
> 它把人工从「审核者」变成「编辑者」，既保证质量，又**把人审的时间转化为产出价值**。
> 详见 [`../12-AI落地方法论与FDE实战/02-ROI与成本测算.md`](../12-AI落地方法论与FDE实战/02-ROI与成本测算.md) §4.2。

### 4.3 闸门的三个反模式

| 反模式 | 表现 | 为什么危险 |
|---|---|---|
| **橡皮图章** | 人只看到「AI 建议：批准」，点一下过 | 人根本没看内容，闸门形同虚设 |
| **默认通过** | 超时/无人处理自动放行 | **不可逆动作绝不能默认通过** |
| **一次授权长期有效** | 「以后都允许这个 Agent 操作」 | 权限漂移，范围失控 |

> **规则**：**不可逆动作的闸门必须「每次问、逐次答、默认拒绝」。**

## 5. 沙箱

### 5.1 四级隔离（按强度递增）

| 级别 | 手段 | 适用 | 成本 |
|---|---|---|---|
| **L1 进程级** | 子进程 + 环境变量隔离 + 无网络 | 生成代码执行 | 低 |
| **L2 容器级** | 独立 namespace + 只读根 + 网络策略 + cgroup 限额 | 代码执行、第三方工具 | 中 |
| **L3 VM 级** | 微型虚拟机 + 快照 + 无外设 | 不可信代码、强合规 | 高 |
| **L4 物理隔离** | 独立设备/网络域 | 最高安全等级场景 | 最高 |

### 5.2 沙箱必配项

| 项 | 要求 |
|---|---|
| **文件系统** | 只读 + 临时可写目录；**挂载为空或最小** |
| **网络** | **默认拒绝**；按需出网且走白名单 |
| **资源** | CPU / 内存 / 磁盘 / 时间 / 进程数 全部限额 |
| **凭据** | **不继承**宿主凭据；需要时临时注入且用完即销 |
| **输出** | 单独收集，**不直接进入主流程**，先经过滤 |
| **审计** | 沙箱内的所有动作都记录 |

> **「不继承宿主凭据」是最容易被忽略的一条**：
> 沙箱里跑着的是**模型的输出**，而模型的输出是被攻击者影响的。

### 5.3 沙箱不等于安全

**沙箱解决的是「爆炸半径」，不是「正确性」。**

| 问题 | 沙箱能解决吗 |
|---|---|
| 代码执行逃逸 | ✅ 隔离 |
| 恶意文件写满磁盘 | ✅ 限额 |
| 通过 HTTP 外发数据 | ✅ 网络策略 |
| **读到了不该读的数据**（在沙箱外） | ❌ **不能** |
| **触发了不可逆的业务动作** | ❌ **不能**（要靠闸门） |

## 6. 凭据管理

**凭据一旦进入上下文，就等于交给模型了。** 而模型的所有输出都要经过攻击者的手。

| 禁止 | 原因 |
|---|---|
| ❌ 凭据放进 prompt / system prompt | 模型会复述、会出现在日志里 |
| ❌ 凭据放进工具描述 | 同上，且描述常被第三方提供 |
| ❌ 凭据出现在工具返回值里 | 模型会把它当数据再输出 |
| ❌ 凭据写进日志 | 日志的访问范围远大于 prompt |
| ❌ 错误信息里回显凭据 | 超常见的泄露路径 |

**正确做法**：

| 做法 | 说明 |
|---|---|
| **服务端注入** | 凭据在服务端拼接，模型只见到结果 |
| **临时凭据 + 最小作用域** | STS 风格，签发范围刚好够这次调用 |
| **按需签发 + 用完即销** | 不长期持有 |
| **结果脱敏** | 返回给模型前把凭据字段替换成 `<REDACTED>` |
| **日志脱敏** | 统一的日志过滤器，含异常堆栈与请求体 |
| **密钥管理服务** | 集中托管、定期轮换、全链路审计 |

> **一条经验规则**：
> **模型能看到的任何东西，都当作公开信息处理。**

## 7. 审计：不可改的记录

### 7.1 三层递进（一个真实工程形态）

| 层 | 手段 | 防住什么 |
|---|---|---|
| **1 权限层** | `REVOKE` 一切写/删权限 | 应用账号直接改 |
| **2 触发器层** | 触发器拦截 `UPDATE`/`DELETE`，**含 `TRUNCATE` 语句级** | 绕过权限的直连写、整表清空 |
| **3 hash chain** | 每行存前一行内容的哈希，形成链 | **整表重建**（删了重插一遍） |

```
行 N:  [内容 | 前一行 hash | 本行 hash]
行 N+1: [内容 | 行 N 的 hash    | 本行 hash]
```

> **前两层不够**：如果攻击者有数据库直连权限，可以「删掉所有行，
> 再按原样插回去」——内容完全一致，但**中间发生了什么，没有任何记录**。
> **hash chain 让这种重建可检出**（链上的哈希对不上）。

### 7.2 审计要记录什么

| 字段 | 说明 |
|---|---|
| **谁**（主体） | 用户 / 服务 / 账号 |
| **何时** | 时间戳（可信时源） |
| **什么**（动作） | 读/写/调用了哪个工具、访问了哪个资源 |
| **依据** | 这次操作的输入摘要、引用来源、模型版本与提示词版本 |
| **结果** | 成功/失败/被拦截 |

> **「依据」字段最常被漏**，但它是**事后复盘和合规取证的关键**：
> 没有依据，就无法证明「这次访问是合法的」。

### 7.3 审计的三个工程细节

| 细节 | 做法 |
|---|---|
| **时间可信** | 用受控时源，不要用业务服务器本地时间 |
| **日志本身不泄露** | 审计日志里的输入摘要要脱敏 |
| **审计与业务分离** | 审计写到独立的存储，业务账号写不进去 |

## 8. 越权响应不可区分

**这是本章最容易被忽略、但合规价值极高的一条。**

### 8.1 问题

```
接口：「查患者 12345 的记录」
  用户不存在 → 404「患者不存在」   (响应快、响应体短)
  密码错误   → 401「密码错误」     (响应慢、响应体长)
```

**后果**：**这个接口成了「存在性预言机」**——
攻击者可以用它枚举「院内/库里有某个患者/某个人」。**这本身就是合规问题**
（个人信息泄露的辅助手段）。

### 8.2 解法：三者对齐

| 维度 | 对齐方式 |
|---|---|
| **响应时间** | 两者走**相同的计算路径**（都去查一次库，都失败），并加**固定时长**的兜底 |
| **状态码** | 用**同一个**状态码，或用同一段文案 |
| **响应体大小** | 响应体长度一致（填充到相同长度） |

```
成功 → 返回数据
不存在 → [走完整查询路径] → 返回"凭据无效或对象不存在"（统一文案）
密码错 → [走完整查询路径] → 返回"凭据无效或对象不存在"（统一文案）
```

> **关键不是「隐藏」，而是「两者走同一条路径」**——
> 这样即使攻击者做精细的时序分析，也拿不到区分信号。

### 8.3 更上一步

- **账号枚举**：注册/登录接口同理
- **资源存在性**：查询不存在的订单、文件、工单，同理
- **错误信息**：异常堆栈**不返回给用户**，只记日志

## 9. Agent 特有的失控

**这些不是攻击，是模型的行为特性导致的意外。** 防御靠**上限**。

| 失控 | 表现 | 上限 |
|---|---|---|
| **循环** | 反复调同一个工具 | 重复调用检测 + 熔断 + 步数上限 |
| **费用** | 单任务烧掉大量 token | 费用硬上限 |
| **范围蔓延** | 做了用户没要求的事 | 任务边界 + 工具集合限定 + 确认点 |
| **递归** | 工具 A → B → A | 深度上限 |
| **批量** | 一次性做 1000 次 | 单次上限 + 速率限制 |
| **顺序错乱** | 先执行了本该先确认的动作 | **闸门前置**（确认必须在执行前，不是后补） |

> **「闸门前置」特别重要**：
> 如果确认发生在动作之后，那就不是闸门，只是通知。

## 10. 自查表

**逐条过一遍。**

### 权限
- [ ] 模型调工具用的是**用户凭证**，不是服务账号
- [ ] 权限在**服务端**判定，不在 prompt 里
- [ ] 数据权限在**检索层**过滤
- [ ] 模型权限 ≤ 用户权限（交集）
- [ ] 工具参数已收紧（无任意 URL、schema 严格化）

### 动作
- [ ] 工具已分级（L1/L2/L3）
- [ ] L3 不可逆动作**逐次人工确认**，默认拒绝
- [ ] L3 有**单次上限**、不可并发、有幂等键
- [ ] 闸门界面展示「做什么/影响谁/依据/可编辑的最终内容」
- [ ] 确认发生在**执行之前**

### 环境
- [ ] 出网白名单已配置
- [ ] 沙箱隔离（文件系统/网络/资源/凭据/输出/审计）
- [ ] 沙箱内**不继承宿主凭据**

### 凭据
- [ ] 凭据不在 prompt / 工具描述 / 工具返回值 / 日志里
- [ ] 临时凭据 + 最小作用域 + 用完即销
- [ ] 返回给模型前已脱敏

### 审计
- [ ] 审计日志 append-only（权限 + 触发器 + hash chain）
- [ ] 记录了「谁/何时/什么/依据/结果」
- [ ] 越权响应的**时间、状态码、体大小**三者对齐
- [ ] 异常堆栈不返回给用户

### 上限
- [ ] 步数 / 费用 / 深度 / 调用次数 / 输出长度 都有硬上限
- [ ] 超限行为是「强制收尾」而不是崩溃

## 11. 工程结论

1. **权限必须在模型之外强制。** 模型是被当作「不完全可靠的、权限很大的实习生」来设计的。
2. **三条权限轴（身份/能力/数据）独立校验**，有效权限取**交集**不是并集。
3. **工具用用户凭证调用，不用服务账号**——否则模型的行为被放大到服务账号的权限。
4. **工具按 L1/L2/L3 分级**，L3 不可逆动作逐次人工确认、默认拒绝、不可批量。
5. **闸门界面必须展示「做什么/影响谁/依据/可编辑的最终内容」**——
   只有确认/取消两个按钮的闸门是橡皮图章。
6. **「审核即编辑」比「只审不改」更优**：既保质量，又把人工时间变成产出价值。
7. **出网白名单是性价比最高的一条**，一次性阻断「读→外发」整类链。
8. **沙箱解决爆炸半径，不解决正确性**——它挡不住「读到不该读的数据」。
9. **模型能看到的任何东西都当公开信息处理**；凭据不进 prompt、不进日志。
10. **审计要三层递进**（权限 + 触发器 + hash chain），且必须记「依据」字段。
11. **越权响应的三种信号对齐**（时间/状态码/体大小），核心是「两者走同一条路径」。
12. **失控靠上限防，不靠识别**；且**闸门必须前置**（确认在执行之前）。
