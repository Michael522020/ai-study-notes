# 合规工程落地

> **核心问题**：一纸合规要求，怎么变成一行代码、一个 CI 断言、一份能交给测评机构的证据？

---

## 0. 前提：合规是工程约束，不是审批流程

**在 AI 应用里，合规要求会直接倒推架构**：

```
「数据不得出院」
   → 部署形态：私有化（不是云 API）
   → 依赖清单：不能引入需要外网的组件
   → 模型选型：只能用可私有化部署的权重
   → 日志策略：不能有外部遥测
   → 密钥管理：不能用托管密钥服务
```

**所以「先做完再合规」在 AI 项目里行不通**——
合规不是最后一道检查，它是一组**在设计阶段就要满足的约束**。

> **工程结论**：把合规条款当作**架构约束条件**输入，而不是**验收清单**输出。

---

## 1. 法规地图

> **⚠️ 免责声明**：以下是**工程视角的地图**，用于判断「哪些方向需要工程动作」。
> **具体条文、适用范围、生效状态与处罚口径一律以官方最新发布为准**，
> 真实上线前必须由法务逐条确认。

### 1.1 国内

| 方向 | 代表性规范 | 对工程的含义 |
|---|---|---|
| **网络安全基线** | 《网络安全法》、等保 2.0（GB/T 22239-2019） | 安全物理/通信/区域/计算环境 + 管理要求，**逐条要落到技术措施** |
| **数据安全** | 《数据法》 | 数据分类分级、重要数据保护、风险评估 |
| **个人信息** | 《个人信息保护法》 | 告知同意、最小必要、单独同意（敏感个人信息）、影响评估 |
| **生成式 AI 服务** | 《生成式人工智能服务管理暂行办法》及配套 | 面向公众提供服务时的内容安全、标识、备案等要求 |
| **内容标识** | AI 生成合成内容标识相关办法与强制性国家标准 | 对生成内容做**显式/隐式标识** |
| **行业专用** | 卫健委电子病历应用管理规范、医疗器械指导原则、网安/数安行业要求 | 场景内的额外硬约束 |

### 1.2 国际（做出海或涉外数据处理时）

| 方向 | 代表性规范 | 工程的含义 |
|---|---|---|
| **通用数据保护** | GDPR | 合法性基础、数据主体权利、DPIA、境外传输 |
| **AI 风险分级** | EU AI Act | 按风险等级施加透明度、记录、人工监督等义务 |
| **跨境贸易** | 出口管制与制裁名单 | 业务规则层的筛查（不是 AI 系统问题） |

> **关键判断**：**大部分 AI 项目真正的合规压力来自三处**——
> 数据边界（能不能出院/出境）、个人信息处理、AI 的决策责任。
> 其余是通用要求。

## 2. 条款 → 工程动作的翻译方法

**这是本章的核心方法论。** 每一条合规要求都走一遍这张表：

| # | 列 | 说明 |
|---|---|---|
| 1 | **条款原文** | 引用（写明出处与版本） |
| 2 | **工程含义** | 用一句工程语言复述（不看原文也能懂） |
| 3 | **工程动作** | 具体做什么（代码/配置/流程） |
| 4 | **验证方式** | 怎么证明做到了（**最好是自动化断言**） |
| 5 | **证据** | 测评时拿什么出来（脚本、日志、报告） |

### 2.1 一张示例表

| 条款方向 | 工程含义 | 工程动作 | 验证方式 | 证据 |
|---|---|---|---|---|
| **访问控制** | 用户只能访问授权范围内的数据 | **权限过滤在检索层**，不依赖应用层过滤 | 越权测试用例全通过 | 测试报告 + 检索层代码 |
| **审计** | 关键操作可追溯且不可篡改 | 审计表 append-only（权限 + 触发器 + hash chain） | 尝试改/删/整表重建，**全部可检出** | SQL 脚本 + 执行输出 |
| **个人信息最小必要** | 不把无关的个人信息送进模型 | **敏感字段在入模前屏蔽** | 屏蔽前后各打一次分，**差值为 0** | 偏差审计报告 |
| **数据本地化** | 数据不得离开指定环境 | 私有化部署 + 无外网依赖 + 无外部遥测 | 部署清单 + 网络策略 | 架构图 + 配置导出 |
| **AI 决策边界** | AI 不得独立作出受监管的结论 | 边界写进产品；**用 schema 严格化在编译期强制** | 编译期负向断言（`@ts-expect-error`） | CI 日志 + 断言数统计 |
| **可解释与追溯** | 每条结论可回指依据 | 证据回指机制（引用必须能定位到原文） | 回指率 100% 断言 | 评测报告 |
| **责任归属** | 最终结论由有资质的人确认 | 电子签名 + 服务端权威锁定 | 篡改正文后签名失效 | 签名校验脚本 |

### 2.2 三条经验

| # | 经验 | 说明 |
|---|---|---|
| 1 | **验证方式优先选自动化断言** | 人工检查会退化成「上一版检查过了」 |
| 2 | **证据要能重跑** | 测评机构可能要求现场复现 |
| 3 | **「不符合」也要写进表** | 明确豁免项与理由，避免被当成漏做 |

## 3. 等保 2.0 三级：技术要求的工程映射

> **说明**：等保是**管理体系 + 技术措施**的组合。
> 这里只列**技术措施**这一侧，并映射到工程动作；
> **管理制度部分由甲方/乙方的管理体系文件承担**，不属本库范围。

| 技术要求 | 工程含义 | 工程动作 | 验证 |
|---|---|---|---|
| **身份鉴别** | 谁能进来 | 强认证 + 失败锁定 + 会话管理 | 认证测试用例 |
| **访问控制** | 进来的人能干什么 | 最小权限 + **检索层权限过滤** | 越权测试全通过 |
| **安全审计** | 做过什么、能不能改 | 审计全覆盖 + **append-only** + 记录依据 | 篡改检测测试 |
| **入侵防范** | 边界怎么守 | 网络隔离 + 出网白名单 + 入侵检测 | 配置导出 + 演练 |
| **恶意代码防范** | 进来的东西会不会带毒 | 依赖扫描 + 模型来源校验 + 沙箱 | 扫描报告 + 哈希清单 |
| **数据完整性与保密性** | 数据会不会被改/被偷 | 传输与存储加密 + 完整性校验 | 加密配置 + 校验脚本 |
| **数据备份恢复** | 坏了能不能恢复 | 备份策略 + **恢复演练** | **恢复演练记录** |
| **剩余信息保护** | 删了会不会残留 | 存储擦除 + 密钥销毁 + 缓存清理 | 擦除验证脚本 |
| **个人信息保护** | 个人信息的处理 | 最小必要 + 去标识 + 访问控制 | 字段清单 + 屏蔽测试 |

### 3.1 最容易被漏的两项

| 项 | 为什么容易漏 |
|---|---|
| **剩余信息保护** | 「删了」不等于「没了」——日志、缓存、备份、临时文件、显存里都还有 |
| **数据备份恢复** | **恢复演练**才算数，只有备份策略不算 |

> **备份恢复演练是合规测评的高频问点，也是最常答不上来的。**

## 4. 六个「用机制代替规范」的模式

**这六个模式可以直接复用到你自己的项目里。**

### 模式 1 · 编译期强制

```typescript
// AI 输出边界：schema 严格化 + 编译期负向断言
const DiagnosisSchema = {
  type: "object",
  additionalProperties: false,     // 多一个字段就失败
  properties: { segmentation: { type: "array" }, measurement: { type: "object" } },
  required: ["segmentation"],
} as const;

// 负向断言：试图越界时**编译不过**
// @ts-expect-error AI 不得输出诊断结论字段
const bad: typeof DiagnosisSchema = { ..., diagnosis: "..." };
```

> **为什么有效**：运行时校验是「人记得加的」，编译期是「加不了就编译不过」。
> **合规边界一旦用语言约束，就一定会被绕过；用类型约束，绕不过去。**

### 模式 2 · 单一数据源 + CI 门禁

```
设计 Token / 权限配置 / 第三方许可清单 / 字段白名单
   → JSON 是唯一权威
   → 其他副本由脚本生成
   → CI 断言「没有手写副本」且「生成物与源一致」
```

> **980 条静态断言**这个数量本身不重要，**重要的是它可以自动跑、每次提交都跑**。

### 模式 3 · 审计三层递进

见 [`05`](./05-Agent权限边界与沙箱.md) §7.1。

### 模式 4 · 越权响应不可区分

见 [`05`](./05-Agent权限边界与沙箱.md) §8。

### 模式 5 · 边界同时是产品文案和验收标准

```
产品界面：     「AI 只做辅助标记，不出具诊断结论」
用户文档：     同一句话
验收标准：     「系统输出中不含诊断结论字段」→ 变成一条 CI 断言
```

### 模式 6 · 自动生成的清单

| 清单 | 生成方式 |
|---|---|
| 第三方依赖许可 | 从 `requirements.txt` / `package-lock.json` 自动扫描 + 人工确认新增项 |
| 模型权重清单 | 从部署配置导出 + 哈希 + 许可证 |
| 数据集清单 | 从训练配置导出 + 哈希 + 许可快照 |
| 个人信息字段清单 | 从 schema 自动导出 |

> **人工维护的清单一定会漂移。** 自动生成 + 门禁校验是唯一可靠的做法。

## 5. 合规测试套件

**把每条合规要求变成一个自动化断言，进 CI。**

```python
# compliance_suite.py —— 伪代码
COMPLIANCE_CHECKS = [
    check_no_extra_fields_in_ai_output(),      # 模式 1
    check_permission_filtered_at_retrieval(),   # 检索层过滤
    check_audit_rows_immutable(),               # 审计不可改
    check_audit_detects_rebuild(),              # 整表重建可检出
    check_no_pii_in_model_input(),              # 入模前屏蔽
    check_bias_audit_delta_zero(),              # 屏蔽前后一致
    check_unauthorized_response_indistinguishable(),  # 越权不可区分
    check_third_party_license_manifest_current(),      # 许可清单最新
    check_backup_restore_drill_recorded(),      # 恢复演练有记录
]
```

### 5.1 组织方式

| 层面 | 内容 | 失败后果 |
|---|---|---|
| **静态断言** | 编译期/类型级（模式 1） | **构建失败** |
| **单元断言** | 纯逻辑（脱敏、字段白名单） | **测试失败** |
| **集成断言** | 需要真实数据库/服务（审计不可改、越权不可区分） | **流水线失败** |
| **演练记录** | 无法自动化的（恢复演练、攻防演练） | **人工核对 + 归档** |
| **外部测评** | 等保测评、密评、备案 | **外部流程** |

> **前三层必须每次提交都跑**；后两层按周期跑。
> **合规不是一次性的验收动作，是持续的 CI 门禁。**

### 5.2 一个容易忽略的点：断言要断言「行为」不是「代码形状」

```python
# ❌ 断言代码里出现了某个关键字 —— 改个写法就失效
assert "REVOKE" in source_code

# ✅ 断言行为 —— 怎么写都有效
assert cannot_modify_audit_table(conn)
assert rebuild_detected(conn)
```

> **合规断言的价值在于「无论怎么重构都仍然成立」。**
> 断言代码形状的检查会在第一次重构时就变成噪音，然后被删掉。

## 6. 证据包

**测评时拿什么出来。** 提前整理，不要等通知。

| 类别 | 材料 |
|---|---|
| **架构与部署** | 架构图、部署清单、网络策略、依赖清单 |
| **配置导出** | 权限配置、加密配置、密钥策略、备份策略 |
| **测试记录** | 合规断言的 CI 报告、越权测试报告、恢复演练记录 |
| **评估报告** | 风险评估、个人信息影响评估、安全测试报告 |
| **清单** | 第三方许可清单、模型权重清单、数据集清单、PI 字段清单 |
| **流程文件** | 变更管理、事件响应、供应商管理、培训记录 |
| **证据固化** | 关键脚本与输出的哈希、生成时间、执行环境说明 |

> **证据要能复现**。测评机构常要求现场跑一遍——
> **「能重跑」比「有文档」重要得多**。

## 7. 合规与速度的关系

**常见的误解：合规会拖慢项目。** 实际上：

| 做法 | 短期 | 长期 |
|---|---|---|
| **合规作为审批环节**（上线前走一遍） | 慢一次 | **反复返工**——审计不可改、权限位置、边界文案都要改代码 |
| **合规作为设计约束**（进架构） | 设计时多花一点 | **一次做对**，且**变成可复用资产** |

> **结论：合规的返工成本远高于设计成本。**
> 这和「安全」是同一个道理——**安全不是加在最后的一层，是设计时的一个维度**。

### 7.1 三个提速的做法

| 做法 | 说明 |
|---|---|
| **合规要求进需求模板** | 每个需求带一行「本条涉及哪些合规约束」 |
| **把条款翻译表做成共享文档** | 全团队复用，避免每人理解一遍 |
| **合规断言进 CI 而不是进检查表** | 自动化跑，不占用人力审查时间 |

## 9. 工程结论

1. **合规是架构约束，不是验收清单。** 「数据不出院」会直接倒推部署形态、依赖清单与模型选型。
2. **条款翻译成五行**：条款 / 工程含义 / 工程动作 / 验证方式 / 证据。
   **验证方式优先选自动化断言。**
3. **合规断言要断言「行为」不要断言「代码形状」**——断言代码形状的检查活不过第一次重构。
4. **机制优于规范**：编译期强制、单一数据源 + 门禁、审计三层、越权不可区分、
   边界同时是文案和验收标准、自动生成的清单——这六个模式可直接复用。
5. **等保三级的技术措施里，「剩余信息保护」和「备份恢复演练」最常被漏**，
   而且恢复**演练**才算数。
6. **合规的返工成本远高于设计成本。** 放进 CI 的断言是资产，进检查表的是负担。
7. **证据要能重跑**——「能重跑」比「有文档」重要得多。
8. **具体条文与适用范围以官方最新文本为准，法务逐条确认**；本库只给工程视角。
