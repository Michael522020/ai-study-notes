# 导出部署与推理加速

> **核心问题**：从 PyTorch 权重到板子上跑起来，中间有哪些坑？哪些坑是「必踩」的？

本章混合了**通用知识**与**本机 RK3588S（LubanCat-4）实测经验**。实测部分标注了「实测」，其余为方法论说明。

---

## 1. 导出格式选型

| 格式 | 适用场景 | 优点 | 缺点 |
|---|---|---|---|
| **PyTorch (.pt)** | 继续训练 / PyTorch 生态 | 无损 | 需要 PyTorch 运行时，慢 |
| **ONNX (.onnx)** | **通用中间格式** | 生态最广，TensorRT / OpenVINO / RKNN / TVM 都吃 | 算子不完整时导出失败 |
| **TensorRT (.engine / plan)** | NVIDIA GPU 极致性能 | 最快 | **与 GPU 架构/驱动版本强绑定**，不可移植 |
| **RKNN (.rknn)** | Rockchip NPU | 板端直跑 | 只能跑在 Rockchip 上，工具链版本严格 |
| **OpenVINO IR** | Intel 硬件 | Intel CPU/VPU 优化 | 非 Intel 硬件无用 |
| **TFLite / CoreML** | 移动端 | 系统原生支持 | 转换链路长，动态算子易失败 |
| **NCNN** | 移动端 | 国产手机芯片友好 | 需要切分模型 |

**决策树**：
```
目标是 Rockchip NPU？  → ONNX → RKNN
目标是 NVIDIA GPU？    → ONNX → TensorRT（或直接 torch.compile）
目标是 Intel CPU？     → ONNX → OpenVINO
目标是手机 App？       → ONNX → TFLite / CoreML / NCNN
只想快速验证？         → ONNX Runtime
```

## 2. ONNX 导出

### 2.1 Ultralytics 导出

```bash
# 导出 ONNX（opset 12 兼容性最好）
yolo export model=yolo11s.pt format=onnx opset=12 simplify=True dynamic=False

# 导出 INT8 ONNX（内置校准）
yolo export model=yolo11s.pt format=onnx opset=12 int8=True data=coco.yaml fraction=0.1

# 批量导出全部格式
yolo export model=yolo11s.pt format=onnx,tensorrt,engine,openvino,tflite,edgetpu,tfjs,paddle
```

### 2.2 导出时的关键参数

| 参数 | 作用 | 注意事项 |
|---|---|---|
| `opset` | ONNX 算子集版本 | **RKNN 建议 12~13**；新算子（如 opset 18+ 的部分）RKNN 不支持 |
| `imgsz` | 导出时的输入尺寸 | **必须与实际推理时一致**，否则 shape 不匹配 |
| `dynamic` | 动态尺寸 | RKNN **不支持**；TensorRT 可开但需 profile |
| `simplify` | onnx-simplifier | 会消除冗余节点，**可能改变数值精度**，量化前建议开 |
| `half` | FP16 | TensorRT 用；RKNN 用 `quantized_dtype` 控制 |
| `batch` | 批大小 | RKNN 通常固定 1 |

### 2.3 常见导出错误

| 报错 | 原因 | 解法 |
|---|---|---|
| `Unsupported opset` | RKNN 不支持该 opset | 降到 12/13 |
| `Non-maximal suppression` 报错 | NMS 算子不被支持 | `model.end2end=True`（v10+）或导出时分离 NMS |
| `Tensor with dynamic dimension` | 开了 `dynamic=True` | 关掉 |
| `Concat out of bounds` | simplify 改变了图结构 | 试 `simplify=False` |

## 3. TensorRT 优化（NVIDIA）

### 3.1 基础导出

```bash
yolo export model=yolo11s.pt format=engine half=True device=0 workspace=4 simplify=True
```

### 3.2 性能优化清单

| 手段 | 收益 | 代价 |
|---|---|---|
| **FP16** | 1.5~2× | 精度略降 |
| **INT8 校准** | 2~3× | 需要代表性数据；精度损失需验证 |
| **Sparse Tensor Core** | 1.2~1.5× | 需要 2:4 结构化稀疏权重 |
| **Layer Fusion** | 自动 | 默认开 |
| **Multi-Plan Optimization** | 多输入尺寸 | 编译时间变长 |
| **CUDA Graph** | 减少 launch 开销 | 需要固定 shape |
| **去除 NMS** | 端到端模型省 10~30% 延迟 | 需换端到端模型 |

### 3.3 NMS 延迟的真实占比

**实测经验**：在 YOLOv8n 这类小模型上，**NMS 的 CPU 耗时常常超过 GPU 前向**。

```
YOLOv8n 640×640, RTX 3060:
  GPU 前向:  ~2.1 ms
  NMS (CPU): ~1.8 ms   ← 接近一半！
  后处理(解码+画框): ~1.2 ms
```

**优化路径**：
1. 用端到端模型（v10 / v26）→ 直接消除 NMS
2. 用 TensorRT 插件实现 GPU NMS
3. 用 `nms` 的 `agnostic=False` 且提前按阈值过滤（`max_det=300, conf_thres=0.25`）

## 4. Rockchip RKNN 部署（RK3588S 实测）

### 4.1 环境与版本纪律（实测）

> **本机实测结论（2026-10）**

| 项目 | 版本/路径 | 说明 |
|---|---|---|
| 转换端 | `rknn-toolkit2` | **必须锁 2.3.2**，与板端 `rknn-toolkit-lite2` 2.3.2 对齐 |
| 板端运行时 | `rknn-toolkit-lite2` 2.3.2 | `~/.local/lib/python3.12/` |
| NPU 驱动 | rknpu 0.9.7 | **走 DRM 路径**，节点 `/dev/dri/renderD129` |
| 硬件加速 | `librga2` 2.2.0 | 做 resize 等预处理加速 |
| 板端 Python | 3.12 | pip 受 PEP 668 保护，装包需 `--user --break-system-packages` |

> **⚠️ 常见误判（实测）**
> - 板上**没有** `/dev/rknpu`（旧驱动路径）。脚本里检查 `/dev/rknpu` 会报 `[FAIL]`，**这是误报**，NPU 完全可用。
> - 正确的判断方式是查 **`/dev/dri/renderD129`**（对应 `platform/fdab0000.npu`），librknnrt 2.3.2 写死了这个路径。
> - `/proc/stat` 的 CPU 记账很粗（实测约每秒只前进 800 jiffies）。两次读数落在同一记账周期内会算出 0% 或 100% 的假值。做 CPU 占用测量**必须强制最小窗口 ≥0.5s 并丢弃 `d_total` 过小的样本**，否则闭环控制器会被假值带偏。交叉验证用 `top -bn3 -d 2` 或 `mpstat 1 3`。

### 4.2 转换流程

```bash
# Step 1: PyTorch → ONNX
yolo export model=yolov8n.pt format=onnx opset=12 simplify=True imgsz=640

# Step 2: ONNX → RKNN (INT8)
python convert_rknn.py \
    --onnx yolov8n.onnx \
    --output yolov8n_int8.rknn \
    --dataset calib/images \
    --input-size 640 \
    --mean '0,0,0' --std '255,255,255' \
    --quant-dtype asymmetric \
    --toolkit-version 2.3.2
```

**转换脚本核心**（rknn-toolkit2 API）：

```python
from rknn.config import RKNNConfig
from rknn.api import RKNN

# 必须显式指定 target_platform，否则会选错 NPU 版本
TARGET = 'rk3588s'   # 注意：RK3588 和 RK3588S 是不同的 target

rknn = RKNN(verbose=True)
rknn.config(target_platform=TARGET,
             quant_algorithm='normal',
             quantization_type='asymmetric',   # 或 'symmetric'
             target_version='2.3.2',           # 与板端 lite2 对齐
             # 单输入模型可省，多输入模型建议显式声明
             )
rknn.load_onnx(onnx_model='yolov8n.onnx')
rknn.build(do_quantization=True, dataset='calib.txt')
rknn.export_rknn(out_file='yolov8n_int8.rknn')
```

> **⚠️ `target_platform` 必须与实际 SoC 匹配**：`rk3588` / `rk3588s` / `rv1126` 等是不同 target，混淆会导致运行时错误或性能骤降。

**校准数据集的写法**：

```
# calib.txt：每行一个图片路径
/workspace/calib/0001.jpg
/workspace/calib/0002.jpg
...
```
建议 100~500 张，覆盖**光照、尺度、类别**的多样性。**校准集必须来自实际部署场景**，否则量化误差大。

### 4.3 板端推理

```python
from rknnlite.api import RKNNLite

rknn = RKNNLite()
rknn.load_rknn('yolov8n.rknn')
# rknn.set_core_mask(RKNNLite.NPU_CORE_0_1_2)   # 三核都开
rknn.init_runtime()

# 预处理必须与训练一致（见 §4.4）
img = Image.open('bus.jpg').convert('RGB')
img = img.resize((640, 640))                     # 关键
img = np.array(img, dtype=np.float32)            # 关键
img = np.expand_dims(img, 0)

outputs = rknn.inference(inputs=[img])
```

### 4.4 预处理必须与训练一致（实测踩坑点）

> **本机实测结论**：板端图像预处理**必须用 PIL**，不能用 OpenCV。

**原因**：
- **OpenCV 的 `cv2.resize` 用的是 INTER_LINEAR（双线性）**，而 **PIL 的 `Image.resize` 默认是 BICUBIC**
- 双线性 vs 双三次插值出来的像素值有可见差异
- 对于 YOLO 这种对像素值敏感的模型，差异会被 INT8 量化进一步放大
- 更隐蔽的问题：**RGBA → RGB 的转换方式不同**。OpenCV 的 `cv2.imread` 默认按 BGR 读，`cv2.cvtColor` 转换；PIL 的 `convert('RGB')` 直接丢弃 alpha 通道。如果通道顺序搞反，模型输出会严重退化。

**推荐的预处理契约**（写进 `preprocess.json`，板端和训练端共用）：

```json
{
  "resize_method": "bilinear",
  "target_size": [640, 640],
  "color_order": "RGB",
  "scale": 0.00392156862745098,
  "mean": [0.0, 0.0, 0.0],
  "std": [1.0, 1.0, 1.0],
  "pad_value": 114,
  "input_dtype": "float32",
  "layout": "NCHW"
}
```

**板端读取这个契约**：

```python
import json
from PIL import Image
import numpy as np

cfg = json.load(open('preprocess.json'))

def preprocess(path):
    img = Image.open(path).convert('RGB')        # 必须 PIL
    img = img.resize(tuple(cfg['target_size']), Image.BILINEAR)
    arr = np.asarray(img, dtype=np.float32) * cfg['scale']
    arr = (arr - np.array(cfg['mean'], np.float32)) / np.array(cfg['std'], np.float32)
    arr = np.transpose(arr, (2, 0, 1))[None]     # HWC → NCHW
    return arr.astype(np.float32)
```

> **校验方法**：在转换机上用 ONNX Runtime 跑一遍同样的预处理函数，把输出和板端的中间张量对比（max abs diff 应 < 1e-3）。这一步能省掉后面几天的排查。

### 4.5 INT8 量化的实测坑（本机 YOLOv8n）

> **本机实测结论**：YOLOv8n 转 INT8 RKNN 后**输出异常（框位置错乱 / 置信度虚高）**，FP16 版本正常。

**根因分析**：

YOLOv8/v11 的检测头包含 **DFL（Distribution Focal Loss）** 结构：

```
回归分支 → 64 通道（4 边 × 16 bins）→ softmax → 加权求和 → 4 个边距
```

**两个量化敏感点**：
1. **softmax 在 INT8 下精度塌陷**：输入动态范围大（logits 可达 ±10），INT8 的 8 位精度在 exp 之后完全不够
2. **加权求和累积误差**：16 个 bin 的概率值累加，误差累积

**解决方案（按优先级）**：

| 方案 | 说明 |
|---|---|
| **换 YOLO26（无 DFL）** | **首选**。回归头直接输出 4 通道，量化友好 |
| **DFL 部分用 FP16** | RKNN 支持混合精度，但配置复杂 |
| **提高量化位宽** | 部分量化算子可指定 16bit |
| **换更好的校准集** | 校准集覆盖充分时误差减小 |
| **PTQ/QAT** | QAT 效果最好但工作量大 |
| **用 FP16 RKNN** | 兜底方案，内存占用翻倍但仍比 CPU 快很多 |

**其他 INT8 敏感点**：

```
敏感度排序：
1. DFL 的 softmax + 加权求和     ← 极高
2. 检测头的 sigmoid（分类/置信度）  ← 高（输出范围小，相对安全）
3. SiLU/Mish 激活                  ← 中
4. Backbone 卷积                   ← 低
```

### 4.6 板端性能实测要点

**RK3588S NPU 资源分配**：

```python
# 三核全开（三个 NPU core）
rknn.set_core_mask(RKNNLite.NPU_CORE_0_1_2)
# 双核
rknn.set_core_mask(RKNNLite.NPU_CORE_0_1)
```

**实测经验**：
- 单核 → 三核的加速**不是线性的**（约 2~2.5×，因为有同步开销）
- **RGA 做预处理**（resize）比 CPU 的 PIL 快，但要注意 RGA 的插值方式也要和训练对齐
- 推理耗时测量要**预热 10~20 次**再计时（首次包含模型加载和内存分配）

**一个可靠的板端基准脚本骨架**：

```python
import time, numpy as np

# 预热
for _ in range(20):
    rknn.inference(inputs=[dummy])
rknn.inference(inputs=[dummy])   # 再同步一次

# 计时
N = 100
t0 = time.perf_counter()
for _ in range(N):
    out = rknn.inference(inputs=[dummy])
t1 = time.perf_counter()
print(f"NPU 推理: {(t1-t0)/N*1000:.2f} ms/帧  → {(t1-t0)/N:.4f} FPS")
```

## 6. 部署前后的精度验证

### 6.1 必做的三步验证

```
Step 1: PyTorch 原始权重 → 跑一遍验证集，存 mAP（基准）
Step 2: ONNX (FP32) → 跑同一验证集
        期望：与 Step 1 差异 < 0.3 mAP
        若差异大 → 是导出问题（opset / simplify / 动态轴）
Step 3: 量化模型 (INT8/FP16) → 跑同一验证集
        期望：FP16 差异 < 1 mAP；INT8 差异 < 2 mAP
        若差异大 → 是量化问题（校准集 / DFL / 预处理）
```

### 6.2 逐层输出对齐（排查利器）

```python
# 把 ONNX 的中间层也导出，逐层对比
import onnxruntime as ort, numpy as np, torch

sess = ort.InferenceSession('model.onnx', providers=['CPUExecutionProvider'])
pt_out = model(img_tensor).detach().numpy()
ort_out = sess.run(None, {'images': img_tensor.numpy()})[0]

print("max abs diff:", np.abs(pt_out - ort_out).max())
print("relative:", np.abs(pt_out - ort_out).max() / (np.abs(pt_out).max() + 1e-9))
```

**判定标准**：
| max abs diff | 判断 |
|---|---|
| < 1e-4 | 正常 |
| 1e-4 ~ 1e-2 | 可能是 FP16 或 simplify 引起，可接受 |
| > 1e-2 | 导出有问题 |

### 6.3 板端与转换机的输入一致性

```python
# 在转换机保存一份参考输入
np.save('ref_input.npy', preprocessed_tensor)   # shape (1,3,640,640)

# 板端读取后对比
ref = np.load('ref_input.npy')
diff = np.abs(ref - board_input).max()
print(f"输入差异: {diff}")   # 期望 < 1e-6
```

**这一步是排查板端输出异常的第一道关口**，比什么都快。

## 8. 工程结论

1. **「预处理不一致」是边缘部署排第一的问题源**。在动手转换模型之前，先把训练端和板端的预处理写成同一个函数/同一份 JSON 契约。
2. **DFL 是 INT8 的头号敌人**。做边缘部署，优先选**无 DFL 的模型（YOLO26）**，或者接受 FP16。
3. **端到端模型（无 NMS）在部署链路上优势巨大**：图简单、NPU 友好、延迟稳定、不会有 CPU 后处理瓶颈。
4. **量化精度必须实测**，不能假设。校准集质量比量化算法选择更重要。
5. **版本纪律**：转换端 toolkit 版本必须与板端 runtime 版本严格一致。跨版本转换的模型在板端可能直接跑不起来或结果异常。
6. **测量先于优化**：板端计时要预热、要固定窗口、要用 `/proc/stat` 之外的方法交叉验证。
