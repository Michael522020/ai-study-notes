# YOLO11–26：新周期

> **核心问题**：从「加模块」到「改范式」，YOLO 的新周期有哪些结构性变化？

---

## 1. YOLO11（2024-09）

**仓库**：`ultralytics/ultralytics`（与 YOLOv8 同一仓库）
**论文**：无

### 1.1 两个新模块

#### C3k2

YOLOv8 的 C2f 里，每个 bottleneck 是单个 Bottleneck（两个 3×3 Conv）。YOLO11 的 C3k2 把每个 bottleneck 换成 **C3k**（两个小核并行分支）：

```
C2f (v8) 的 bottleneck:        C3k2 (v11) 的 bottleneck:
  [3×3 Conv]                      ┌─→ [3×3 Conv, c=3]  ─┐
  [3×3 Conv]                      └─→ [3×3 Conv, c=3]  ─┴→ concat
```

- 每个分支的通道数只有 1/3，总通道数不变
- 作用：增加分支多样性，提升特征表达

#### C2PSA（Position Sensitive Attention）

在 C2 块后接一个 **PSA 块**：

```
x ─→ C2 block ─→ PSA block ─→ out
```

**PSA 的结构**：
1. 把特征 reshape 成 `(H, W, B, N, C)`
2. 在 **B（batch）和 N（空间邻域）** 维度上做 attention（多头）
3. 保留位置信息（Position Sensitive）

**与 SE / CBAM 的区别**：SE 只做通道注意力（全局池化），CBAM 是通道 + 空间，PSA 显式建模**空间位置邻域**。

**代价**：PSA 增加了显存和计算，v11 官方在 `yolo11.yaml` 里**默认只在最后一层（index 23）使用**：

```yaml
# ultralytics/ultralytics/cfg/models/11/yolo11.yaml
# C2PSA 模块只在最后一层使用
- [-1, 1, C2PSA, [1024]]  #  C2PSA
```

### 1.2 YOLO11 相对 v8 的改动清单

| 改动 | 说明 |
|---|---|
| C3k2 替代 C2f | 更丰富的分支 |
| C2PSA 注意力 | 最后一层引入位置敏感注意力 |
| Anchor-free 回归 | 沿用 v8 |
| DFL | 沿用 v8 |
| TAL TopK 标签分配 | 沿用 v8 |
| 解耦头 | 沿用 v8 |
| mosaic 收尾 | 沿用 v8 |

### 1.3 性能（COCO val, 640）

| 模型 | mAP@0.5:0.95 | 参数量 | GFLOPs |
|---|---|---|---|
| YOLO11n | 39.5 | 2.6M | 6.5 |
| YOLO11s | 47.0 | 9.4M | 21.5 |
| YOLO11m | 51.5 | 20.1M | 68.0 |
| YOLO11l | 53.4 | 25.3M | 86.5 |
| YOLO11x | 54.7 | 56.9M | 194.9 |

**对比 YOLOv8**：

| 模型 | v8 mAP | v11 mAP | 提升 |
|---|---|---|---|
| n | 37.3 | 39.5 | +2.2 |
| s | 44.9 | 47.0 | +2.1 |
| m | 50.2 | 51.5 | +1.3 |

> **口径**：Ultralytics 官方 README，COCO val，640 输入。

### 1.4 实际增益的来源

值得注意：**v11 的提升主要来自训练配方，而非模块**。Ultralytics 在 v11 发布时同时更新了训练超参。所以：

> **工程结论**：如果你从 v8 升级到 v11，务必同时用 v11 的 `hyp.yaml`，否则模块改了但超参还是 v8 的，收益会打折。

## 2. YOLO12（2025-02）

**仓库**：`ultralytics/ultralytics` ｜ **论文**：无

### 2.1 核心主张：Attention-Centric Architecture

v12 的观点：**卷积是"局部静态"的，注意力是"全局动态"的**。既然两者各有优势，就该在合适的地方各用各的，而不是全卷积或全注意力。

### 2.2 A2C（Attention-to-Convolution）

用 **FlashAttention** 实现的高效注意力块，替代部分 3×3 卷积：

```
普通卷积块：      x ─→ [3×3 Conv] ─→ [Channel Attn] ─→ [SPPF] ─→ out
                            ↓
v12 注意力块：    x ─→ [FlashAttention] ─→ [Channel Attn] ─→ [SPPF] ─→ out
```

**为什么 FlashAttention 能在检测里用？**
- 传统注意力：$O(N^2)$ 显存，特征图大时爆炸
- FlashAttention：通过分块计算 + 重计算，把显存降到 $O(N)$，速度提升 2~4×
- v12 在高分辨率特征层（P3, 步长 8）上使用注意力，那里 $N$ 相对小

### 2.3 v12 的改动清单

| 改动 | 说明 |
|---|---|
| **A2C 模块** | 引入 FlashAttention 替代部分卷积 |
| **注意力中心架构** | 主干 + 颈部统一改造 |
| **保留 DFL** | ⚠️ 移除 DFL 是 YOLO26 的事，不是 v12 |
| 简化的检测头 | 更少的头分支 |

### 2.4 性能

| 模型 | mAP@0.5:0.95 | 参数量 | GFLOPs |
|---|---|---|---|
| YOLO12n | 40.1 | 2.5M | 6.7 |
| YOLO12s | 48.0 | 9.3M | 21.2 |
| YOLO12m | 52.5 | 20.1M | 59.8 |
| YOLO12l | 53.7 | 25.4M | 90.0 |
| YOLO12x | 55.2 | 56.7M | 200.9 |

### 2.5 评价

**优点**：结构设计有明确原则，不是模块堆砌。
**局限**：
- **FlashAttention 对目标硬件要求高**。很多 NPU 不支持 FlashAttention 的算子模式，导出可能失败或需要 fallback
- 在 CPU / MCU 上 FlashAttention 的优势不明显甚至更慢

> **工程结论**：v12 在 NVIDIA GPU 上表现好，但**在边缘 NPU 上要谨慎**。先确认你的 NPU 算子库支持对应的注意力实现，否则会掉到慢路径。

## 3. YOLO26（2025-09）

**仓库**：`ultralytics/ultralytics` ｜ **论文**：无（Ultralytics 以工程论文形式发布技术报告）

### 3.1 三大变化

#### 变化 1：移除 DFL（Distribution Focal Loss）

**v8/v11 的头**：
```
回归分支 → 输出 4 × 16 = 64 个通道 → DFL 期望 → 4 个边距
```
- `reg_max=16`：每个边距用 16 个离散 bin 表示
- DFL 对 16 个 bin 做 softmax 后取期望

**v26 的头**：
```
回归分支 → 直接输出 4 个边距（不需要 64 个通道，不需要 softmax + 期望）
```

**移除 DFL 的三个好处**：

| 好处 | 说明 |
|---|---|
| **量化友好** | DFL 的 softmax + 加权求和在 INT8 量化下误差大，是量化精度的主要杀手之一。移除后回归头就是 4 个数的线性输出，量化友好度大幅提升 |
| **延迟降低** | 回归头通道数 64 → 4，减少大量卷积计算 |
| **导出简单** | 少一层 softmax + 求和，ONNX 图更简单，NPU 更容易支持 |

**代价**：
- DFL 的作用是「把连续回归变成离散分布学习」，提供更强的定位监督信号。移除后需要靠 ProgLoss 等新损失补回来。
- 极端小目标 / 高精度场景可能掉点。

> **工程结论**：**如果你在 RK3588S / 其他 INT8 NPU 上部署，v26 的「去 DFL」是重大利好**。这是 v26 最值得关注的点。

#### 变化 2：ProgLoss + STAL

**ProgLoss（Progressive Loss）**：渐进式标签分配 —— 从易到难地分配正样本，早期训练用更宽松的分配，后期收紧。

**STAL（Stable Loss Assignment）**：v10「一致双分支」的稳定化版本。v10 的一对多分支出问题：
- 一对多分支和一对一分支的训练样本分布不一致，导致模型在两个任务上的表现冲突
- v10 用两个对齐损失（cls-align / box-align）强行拉近，训练不稳定

STAL 的思路：**用一对多分支的输出指导一对一分支的分配**，而不是简单地对齐输出。

#### 变化 3：MuSGD 优化器

「MuSGD」= Momentum SGD，带：
- Nesterov 动量
- 自适应学习率缩放
- 更好的权重衰减解耦

**收益**：收敛更快，训练时间相比 AdamW 系列显著降低。

### 3.2 端到端默认开启

v26 **默认端到端（无 NMS）**，类似 v10。这带来：
- 导出图更简单
- 延迟更稳定
- NPU 友好

### 3.3 性能

> 具体数值以 Ultralytics 官方仓库当前 README 为准（v26 迭代较快，数字会更新）。总体趋势：**同等算力下比 YOLO11/v12 略高，且小目标与密集场景提升明显**。

### 3.4 YOLO11/12/26 对比

| 维度 | YOLO11 | YOLO12 | YOLO26 |
|---|---|---|---|
| 时间 | 2024-09 | 2025-02 | 2025-09 |
| 核心改动 | C3k2 + C2PSA | 注意力中心 + FlashAttention | 端到端 + 去 DFL + MuSGD |
| DFL | ✅ 有 | ✅ 有 | ❌ **移除** |
| NMS | 需要（默认） | 需要（默认） | **默认不需要** |
| 优化器 | AdamW / SGD | AdamW / SGD | **MuSGD** |
| GPU 友好度 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| NPU / INT8 友好度 | ⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐⭐⭐ |

## 4. YOLOE（2025）：开放词汇 YOLO

**论文**：*YOLOE: Real-Time Seeing Any Open-Vocabulary Object in the Wild*, arXiv:2503.18865
**仓库**：`Alibaba-NLP/YOLOE`

### 4.1 问题

闭集 YOLO 只能识别训练时给定的类别。开放词汇检测（Open-Vocabulary Detection）要解决：文本描述任意类别 → 检测出图中的实例。

已有的开放词汇方法（GLIP、Grounding DINO、YOLO-World）的问题是：
1. **文本编码要在推理时在线做**（CLIP 文本编码器）
2. **速度慢**（双流架构，文本分支不能预计算）
3. **精度低于闭集**（大量伪标签训练导致的知识冲突）

### 4.2 YOLOE 的三个设计

#### 设计 1：分离视觉与文本编码

- **文本侧**：训练时用 LLM/CLIP 生成类别的文本嵌入，**离线预计算并缓存**
- **视觉侧**：视觉编码器 + 检测头，**推理时只需视觉分支**
- **结果**：推理速度接近闭集 YOLO

#### 设计 2：提示切换（Prompt Switching）

不同任务需要不同形式的文本提示：
- 类别名：`person`
- 描述：`a person wearing a red hat`
- 短语：`a person`

**挑战**：这些提示的嵌入空间不一致，直接换会掉点。

**YOLOE 的解法**：用 **LSE（Latent Space Alignment）** 把不同提示的文本嵌入对齐到同一潜在空间，从而**无需重新训练**即可切换提示模式。

#### 设计 3：区域-文本对齐的预训练

在大规模图文数据上预训练视觉编码器，用 region-text 对比损失对齐。

### 4.3 YOLOE 的意义

YOLOE 把「开放词汇」的可用性从「离线批处理」推进到「**实时**」。对于需要「识别训练集外的新类别」的场景（比如业务新增一个 SKU 品类），YOLOE 提供了不重训的路径。

> **工程结论**：YOLOE 的定位是**闭集 YOLO 的补充**，不是替代。如果你的类别固定，闭集模型精度仍高得多。

## 5. YOLO-World（2024）：开放词汇的另一条路

**论文**：*YOLO-World: Real-Time Open-Vocabulary Object Detection*, arXiv:2405.17210
**仓库**：`AILab-CVC/YOLO-World`
**后续**：YOLO-World v2 (2025)

### 5.1 做法

- 用 **CLIP 文本编码器**产生文本嵌入，通过轻量映射投影到检测头的嵌入空间
- **预训练检测头**（text-to-box head），使其能处理任意文本嵌入
- v2 增加大规模预训练（MAE + 弱监督图文对 + Region-Text 对比损失）

### 5.2 与 YOLOE 的区别

| | YOLO-World | YOLOE |
|---|---|---|
| 文本编码器 | CLIP（推理时可预计算文本嵌入） | LLM/CLIP + 潜在空间对齐 |
| 提示切换 | 需重新编码文本（可离线） | **零重训**，运行时切换 |
| 开源程度 | 完整 | 完整 |
| 定位 | 通用开放词汇检测 | 实时开放词汇 + 灵活提示 |

> 详见 [`../02-视觉检测模型/10-开放词汇与基础模型.md`](../02-视觉检测模型/10-开放词汇与基础模型.md)

## 6. 新周期的横向总结

| 版本 | 一句话 | 最适合的场景 |
|---|---|---|
| **YOLO11** | v8 的全面加强，工程最稳 | **通用生产首选** |
| **YOLO12** | 引入注意力，GPU 上更强 | NVIDIA GPU 部署，追求精度 |
| **YOLO26** | 端到端 + 去 DFL，量化友好 | **边缘 NPU / INT8 部署** |
| **YOLOE** | 实时开放词汇 | 需要识别训练集外类别 |

---

## 7. 工程结论

1. **选型建议**：
   - 普通 GPU 部署 + 追求稳妥 → **YOLO11**
   - NVIDIA GPU + 追求精度 → **YOLO12**
   - 边缘 NPU / 需要 INT8 → **YOLO26**（去 DFL 是决定性优势）
   - 需要开放词汇 → **YOLOE** 或 YOLO-World

2. **升级 YOLO 时的检查清单**：
   - [ ] 训练超参是否同步更新（`hyp.yaml`）
   - [ ] 标签分配算法是否变化（TAL TopK）
   - [ ] 回归表示是否变化（DFL / 直接边距）
   - [ ] 后处理是否变化（NMS / 端到端）
   - [ ] 导出脚本是否需要重新适配（算子支持）
   - [ ] 量化校准数据是否需要重新采集

3. **别指望 YOLO 解决所有问题**：密集小目标（航拍）、开放词汇、长尾类别、精确分割 —— 这些是 YOLO 的能力边界，跨过去需要换模型族。
