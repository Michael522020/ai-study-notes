# ESP32-P4 视频推流方案：把板子的画面送出去

> **核心问题**：板子上的摄像头画面，怎么送到电脑或便携屏上？为什么「插根 HDMI 线」这条路从硬件上就堵死了？推流到底该走 MJPEG 还是 H.264？

本章记录 2026-11-12 的一次完整方案设计与**离线预编译验证**。

**数据口径**：本章分两类数据，请严格区分——

- **「本机实测」**：板级配置核对、依赖版本解析、编译产物大小、分区占用、编译期报错与修法。**这些都是作者本机跑出来的。**
- **「估算 / 待实测」**：带宽、端到端延迟、帧率、实际吞吐。**这些是按规格推算的，板端尚未烧录实测。**

> ⚠️ **本章没有一条板端运行时数据**——写这份笔记时板子不在手边，只做到了「编译通过」。所有 Phase 1 的实测项都还空着，**表里都标了「待实测」**。这是本章最重要的边界，请不要把它当成一份已验证的部署报告。

## 1. 先认清一件事：显示输出这条路是堵死的

起因是想把板子画面接到一台便携显示器上。核对下来，**这不是软件能解决的问题，是硬件没有这个接口**。

### 1.1 堵死的三道门

| 检查项 | 结论 | 依据 |
|---|---|---|
| 板子上有 HDMI 口吗？ | **没有** | 板卡实物接口：RJ45 / 4×USB-A / 2×Type-C（USB OTG + 串口）/ SD 卡槽 / MIPI-CSI / MIPI-DSI FFC / 3.5mm / MIC / 喇叭座 / 40 针排针 / PoE 座 —— **无 HDMI** |
| 官方 BSP 认哪种显示输出？ | **只有 MIPI-DSI 触摸屏** | 厂商 BSP 2.0.1 的 Kconfig：LCD 类型为 3.4 / 4 / 4.3 / 5 / 7 / 8 / 8.8 / 9 / 10.1 寸 DSI 屏，**没有 HDMI，也没有 RGB 并行 LCD 选项** |
| ESP32-P4 芯片有 HDMI / DP 发射 PHY 吗？ | **没有** | 芯片的显示外设只有 MIPI-DSI + RGB LCD + ISP + H.264 编码器；HDMI 需要外挂桥接芯片 |
| Type-C → HDMI 适配器能用吗？ | **不能** | 适配器要求源端具备 DP Alt Mode 发射；P4 的 USB 2.0 HS 无 DP PHY |

> 💡 **前两门是「产品没做」，第三门是「芯片就没有」。**
> 这两层要分开看：厂商完全可以再出一块带 HDMI 的板子（芯片层面也不是不行，可以外挂桥接），但**P4 这颗芯片本身没有 HDMI 发射能力**，所以「插个转接头就完事」这条路在原理上就不成立。

### 1.2 如果将来非要用 HDMI：官方路线长什么样（存档）

乐鑫官方的做法是 **LT8912B**（MIPI-DSI → HDMI 桥接芯片），见 `ESP32-P4-Function-EV-Board` 与 `ESP-HDMI-Bridge` 项目。

| 项 | 值 |
|---|---|
| 驱动组件 | Espressif 官方 `esp_lcd_lt8912b`（本地已有副本） |
| BSP 配置 | `CONFIG_BSP_LCD_TYPE_HDMI` + 分辨率枚举 |
| 支持分辨率 | 800×600@60 / 1024×768@60 / 1280×720@60 / 1280×800@60 / **1920×1080@30** |
| 本板 DSI 条件 | **2-lane**，lane bitrate 500~1500 Mbps 可配 |

**障碍**：需要额外购买 LT8912B 桥接小板、核对 Waveshare 的 DSI FFC 针脚是否与官方适配板一致、确认桥接片供电。

> **本章不推荐走这条路。** 理由在 §2 末尾。

## 2. 三条实现路线

### 2.1 A. MJPEG over HTTP —— 官方例程，几乎零改造 ★推荐先做

**代码**：官方 `17_simple_video_server` 例程。

| 端点 | 内容 |
|---|---|
| 端口 80 | Vue 前端（已 gzipped 嵌进固件），浏览器直接看实时画面 |
| 端口 81+ | 每路摄像头一个 `/stream`（multipart MJPEG） |
| REST | `/api/capture_image`、`/api/capture_binary`、`/api/get_camera_info`、`/api/set_camera_config` |
| mDNS | `esp-web.local` |

**客户端**：浏览器直接开 `http://<ip>/stream`；VLC 也能吃。

| | |
|---|---|
| ✅ **优点** | 改动最小（只改 sdkconfig 与板级 profile）；浏览器就能看；调试直观；A 的成果（采集 + ISP + 网络）可以**直接复用给 B** |
| ❌ **缺点** | 带宽高（见 §4）；延迟随帧率线性涨 |

### 2.2 B. H.264 over RTSP —— 低延迟低带宽

| | |
|---|---|
| **组件** | `espp/rtsp`（Espressif 官方 registry 组件，1.4.x 起支持多编解码器灵活框架；1.0.x 只支持 MJPEG） |
| **编码** | `esp_h264`（P4 硬件编码器）产出 H.264 码流 → RTSP 封包 |
| **客户端** | VLC / ffplay / PotPlayer，`rtsp://<ip>:8554/xxx` |
| ✅ **优点** | 同画质带宽只有 MJPEG 的 1/5 ~ 1/10；延迟低；抗弱网 |
| ❌ **缺点** | 要自己写「采集 → ISP → YUV420 → 硬件编码 → RTSP 封包」整条链，比 A 难一档 |

> ⚠️ **未核实项**：`espp/rtsp` 的 C API 具体形态（registry 页面当时网络访问受限）。**动手前先确认这一项**，它决定 B 的实际工作量。

### 2.3 C. WebRTC —— 先不做

`esp-webrtc-solution` 存在，但依赖重（体积、CPU、TURN 服务器），对「能看见画面」这个目标过重。

### 2.4 路线对比

| | **A. MJPEG / HTTP** | **B. H.264 / RTSP** |
|---|---|---|
| 改造量 | 改 sdkconfig + 板级 profile | 需新写编码 + RTSP 链路 |
| 800×640@15fps 带宽 | ≈ 4 ~ 8 Mbps（估算） | ≈ 0.5 ~ 1 Mbps（估算） |
| 端到端延迟 | 200 ~ 500 ms（估算） | 100 ~ 250 ms（估算） |
| 客户端 | 浏览器 / VLC | VLC / ffplay |
| 适合 | **先跑通**，验证摄像头与网络 | 正式演示、弱网环境 |

**建议路径**：先 A 跑通（验证 OV5647 → ISP → JPEG → Wi-Fi → HTTP 全链路），再按需要上 B。

### 2.5 但要认清链路的终点

> **推流只能送到 PC / 手机。**

要在便携屏上看，链路只能是：

```
板子 ──WiFi──▶ 笔记本（VLC / 浏览器）──HDMI──▶ 便携显示器
```

**便携屏最后一段由笔记本的 HDMI 输出来扛，便携屏本身不需要任何改动。**

如果你的目标是「一块板子 + 一块屏，摆在野外」，那 A/B 两条推流路线**都不满足**——那种需求只能走 §1.2 的 LT8912B 桥接，或者换一颗有显示输出的芯片。

## 3. 硬件能力坐标：推流需要的东西，板子上有没有

| 能力 | 结论 | 依据 |
|---|---|---|
| 摄像头 | **有** —— OV5647，MIPI-CSI 2-lane | `esp_cam_sensor` 的 OV5647 驱动；官方例程 `16_video_lcd_display` 就是这块板 + OV5647 |
| 摄像头可选格式 | 800×640@50 RAW8 / 800×800@50 RAW8 / 800×1280@50 RAW8 / 1920×1080@30 RAW10 / 1280×960@45 RAW10 | `esp_cam_sensor/sensors/ov5647/Kconfig.ov5647` |
| ISP | **有** —— RAW → YUV420 / RGB565 | `esp_video` 的 ISP pipeline |
| JPEG 硬件编码 | **有** —— `/dev/video10`（M2M） | `esp_video` 硬件表 |
| **H.264 硬件编码** | **有** —— `/dev/video11`（M2M，输入 YUV420 → 输出 H.264） | 同上 |
| H.264 编码器规格 | P4 专用硬件编码器：**1080p > 30fps**；baseline；宽 80~1088 / 高 80~2048；支持 RC 码率控制、ROI、GOP 1~255 | `esp_h264` 组件 README |
| Wi-Fi | **有** —— 板载 C6 走 SDIO（ESP-Hosted），Wi-Fi 6 | `esp_wifi_remote` + `esp_hosted`，这块板**已实测跑通** |
| 有线网口 | 有 RJ45，但**官方例程未覆盖这块板的 PHY 路径** | 官方兼容性矩阵把 `11_ethernetbasic` / `15_eth2ap` 标 ❌ |

### 3.1 OV5647 该选哪个格式

| 格式 | 像素量 | 建议 |
|---|---|---|
| **800×640@50 RAW8** | 51.2 万 | ✅ **最适合推流**——像素量只有 800×1280 的一半，且 RAW8 带宽最省 |
| 800×1280@50 RAW8 | 102.4 万 | 官方 `16_video_lcd_display` 例程用的就是这个 |
| 1920×1080@30 RAW10 | 207.4 万 | 带宽吃紧，**推流场景不推荐**（见 §4） |

**本板 MIPI-CSI 是 2-lane**，这个约束直接决定了可用格式的上限。

## 4. 带宽与算力账

> 本节全部是**估算**。板端实测待做（Phase 1）。

### 4.1 码流估算

| 格式 | 单帧 / 码率 | 10 fps | 15 fps |
|---|---|---|---|
| JPEG q80 @ 800×640 | 40 ~ 70 KB/帧 | 3.2 ~ 5.6 Mbps | 4.8 ~ 8.4 Mbps |
| H.264 @ 800×640，RC 512k~1M | 固定码率 | 0.5 ~ 1 Mbps | 同左 |

### 4.2 链路上限

- **ESP-Hosted**：SDIO 4-bit @40 MHz（引脚 CMD=19 / CLK=18 / D0~D3=14~17 / Reset=54），裸带宽上限远远够用。
- **真正的瓶颈是 C6 的 Wi-Fi 6 实际吞吐**：2.4GHz 802.11ax，近距离干净信道下通常在十几到几十 Mbps 量级，**校园网环境还要再打折**。

> **结论：800×640 的 MJPEG 可行；上 720p MJPEG 会顶到墙。**
> 这也是「先 A 后 B」的另一个理由——A 在低分辨率下就够用，B 是留给「分辨率上去了或者信道变差」的。

### 4.3 P4 侧算力

- H.264 走**硬件编码器**，CPU 只剩拷贝与封包，400 MHz 双核完全够。
- JPEG 也有硬件编码器（`/dev/video10`）。
- **但不要指望推流和 YOLO 实时检测同时跑**——见 §8。

## 5. 网络拓扑：最容易翻车的地方

已知条件：**校园网开启了客户端隔离**——电脑 ping 不通板子（板子自己上网没问题，但「电脑访问板子」是两件事）。

| 拓扑 | 做法 | 评价 |
|---|---|---|
| **① 板子开 SoftAP** ⭐ | P4 用 `esp_netif` + `esp_wifi` 起 AP（`WIFI_MODE_AP`），电脑 / 手机连板子的 SSID | **不依赖任何外部网络，隔离问题彻底消失，演示最稳。** 代价：`protocol_examples_common` 的 `example_connect()` 只做 STA，AP 模式要自己写几十行 |
| **② 笔记本开热点** | Windows 移动热点，板子以 STA 连热点（`192.168.137.x/24`），电脑就是网关 | 零额外代码，改 sdkconfig 里的 SSID / 密码即可。**注意热点默认也对客户端开隔离**，必要时把板子设成「允许本地连接」，或改用 ① |
| **③ 有线** | 板子 RJ45 + 电脑网口直连，静态 IP | 带宽最稳、不受无线干扰，但**官方例程没覆盖这块板的 PHY 路径**，要自己配 PHY（型号 / 地址 / 时钟） |
| ④ 校园网直连 | 板子连校园网，电脑也连校园网 | ❌ **客户端隔离，通不了** |

> ⚠️ **这两件事必须分开看**：
> 板端连校园网 captive portal 的登录流程本身已经跑通（Dr.COM 认证），但**那解决的是「板子能上网」，不解决「电脑能连到板子」**。
> 很多人在这里卡住，就是因为以为「板子能上网 ⇒ 电脑能访问板子」——**在开了客户端隔离的网络里，这个推论是错的。**

## 7. 三个编译期踩到的坑

这三个坑**在预编译阶段全部暴露了**，也正是不烧板子也能发现的那类问题。

### 7.1 `esp_hosted` 必须钉死版本

**现象**：`esp_wifi_remote` 0.14.x 的清单里只写了 `espressif/esp_hosted: '>=0.0.6'`（**没有上限**），依赖解析器会拉到**最新的 3.1.0**。而 3.x 是配 `esp_wifi_remote >= 1.6` 编译的，拿 0.14.x 注入的 `esp_wifi.h` 编不过：

```
error: 'CONFIG_WIFI_RMT_DYNAMIC_RX_MGMT_BUF' undeclared
error: 'CONFIG_WIFI_RMT_ESPNOW_MAX_ENCRYPT_NUM' undeclared
```

**修法**：在 `main/idf_component.yml` 里显式钉版本——

| IDF 版本 | 钉的 esp_hosted |
|---|---|
| IDF < 6.0 | `1.4.*` |
| IDF ≥ 6.0 | `>=2.12,<3.0` |

**`1.4.7` + `esp_wifi_remote 0.14.5` 就是这块板已验证跑通的组合。**

> 💡 **这条的普适价值**：`>=0.0.6` 这种**没有上限的版本约束**，在任何依赖解析器里都是隐患——它意味着「下次构建可能拉到一个不兼容的版本」。**在 IoT 项目里这条尤其致命，因为构建常常隔几个月才做一次。**

### 7.2 `ESP_IDF_VERSION` 必须自己设

**现象**：绕过 `export.ps1` 直接调工具链时，`ESP_IDF_VERSION` 环境变量就没了。Kconfig 把它当环境符号用，而 `esp_wifi_remote` 的 Kconfig 里有这么一行：

```
orsource "./idf_v$ESP_IDF_VERSION/Kconfig.slave_select.in"
```

**`orsource` 找不到文件时是静默跳过的。** 于是 `SLAVE_IDF_TARGET_*` 这组 choice 根本没定义，编译时报：

```
esp_hosted_config.h:59: error: #error "Unknown Slave Target"
```

**修法**：手动设 `ESP_IDF_VERSION=5.5`（**major.minor**，对应组件里的 `idf_v5.5/` 目录名）。

> ⚠️ **「静默跳过 → 后面报一个语义完全不相关的错」**，是 Kconfig 体系里最难查的一类问题。排查这类问题的通用手法：**从报错信息往回找它依赖的那个符号是怎么来的**，一路追到 Kconfig 源头。

### 7.3 旧 sdkconfig 会盖掉 defaults 里的板型选择

**现象**：先前用 EV-Board 板型生成过一次 `sdkconfig` 之后，再在 `sdkconfig.defaults` 里写

```
CONFIG_EXAMPLE_SELECT_CUSTOMIZED_DEV_BOARD=y
```

**不生效**。Kconfig 会报：

```
warning: unknown kconfig symbol ...
CONFIG_EXAMPLE_MIPI_CSI_SCCB_I2C_SCL_PIN was replaced with CONFIG_EXAMPLE_MIPI_CSI_SCCB_SCL_PIN
```

最终 SCCB 引脚和板型**都还是旧的**。

**修法**：换板型 / 换依赖后**必须让 sdkconfig 重新生成**。不想删文件的话：

```bash
idf.py -DSDKCONFIG=sdkconfig_wifi build      # 换一个 sdkconfig 文件名
idf.py -B <新构建目录> build                  # 或者换一个构建目录
```

> **这条和 04 主线第 01 章的「换后端必须做跨后端结果对齐」是同一类教训**：**配置改了但没重新生成，工具链不会报错，只会拿旧配置继续跑。**

### 7.4 还有一条与编译环境有关的坑

**本机 bash 里跑不了 `idf.py`**：Claude Code 的 Bash 工具会给每个子进程注入 `MSYSTEM=MINGW64`，而 `unset` / `env -u` 都不管用，而 `idf.py` 内部有一行 `if 'MSYSTEM' in os.environ:` 会直接退出。

**修法**：用一个自写的启动器脚本绕开（它负责清掉 `MSYSTEM` 再调 `idf.py`）。

## 8. 架构结论：别指望推流和 YOLO 同时跑

本机已测数据：**YOLO26n INT8 512×512 ≈ 980 ms/帧（≈ 1 FPS）**。

推流本身不吃多少算力（H.264 走硬件编码，CPU 只剩拷贝封包），但 YOLO 在 P4 上是实打实的 1 FPS。**两个加起来不会变成 2 FPS，只会变成一个更卡的 1 FPS。**

**合理的架构是「抽样检测」，不是「逐帧检测」**：

```
摄像头 ─┬─▶ ISP ─▶ JPEG 编码 ─▶ MJPEG 流 ──▶ 客户端（连续画面）
        │
        └─▶ 每 N 秒抽 1 帧 ─▶ YOLO 推理（980ms）
                                 │
                                 └─▶ 框与标签 ─▶ 叠加到推流帧 / 推给云端
```

| 设计要点 | 说明 |
|---|---|
| **检测走旁路** | 检测不在视频帧的实时路径上，只抽样 |
| **检测与推流解耦** | 推流帧率由网络与编码器决定，检测频率由算力决定 |
| **结果叠加有两条路** | 前端画（零板端开销）或 PPA 画（板端画，代价小） |

## 9. 本章结论

1. **「插 HDMI」这条路在硬件层面堵死**，不是软件问题。Type-C 转接器也不行——P4 没有 DP 发射 PHY。
2. **推流只能送到 PC / 手机。** 要在便携屏上看，中间必须过一台有 HDMI 输出的机器；或者改走 LT8912B 桥接（需要额外采购）。
3. **先 A 后 B**：MJPEG over HTTP 改造量最小、浏览器直接能看；H.264 over RTSP 带宽只有 1/5~1/10，适合正式演示。
4. **网络拓扑先于一切**。客户端隔离会让「板子在线但电脑打不开」。**优先让板子开 SoftAP**。
5. **「不烧板子也能发现问题」**——离线预编译抓到了分区表不够、依赖版本漂移、Kconfig 静默跳过、旧 sdkconfig 覆盖这四类问题，**其中三个只会在烧板子后以更难懂的形式爆出来**。
6. **抽样检测，不要逐帧检测**。1 FPS 的检测能力必须按「每 N 秒一次」来设计。
