# WiFi CSI 感知与 RuView 核心闭环重写

> **核心问题**：能不能不用摄像头、不用穿戴设备，光靠 WiFi 信号就把「房间里有没有人」「他在呼吸」测出来？如果能，一整套传感器要多少钱、要多少代码？

本章记录一次**从零重写**的实践：把 [ruvnet/RuView](https://github.com/ruvnet/RuView)（无摄像头 WiFi 感知平台）拆开看，判断哪些值得重写，然后在手边一块 ESP32-P4 开发板上把**核心感知闭环**真正跑通。

**数据口径**：
- **本机实测**：作者的 ESP32-P4-WIFI6-DEV-KIT 开发板 + x86 主机，2026-11-22。
- **转述公开值**：RuView 仓库 README / ADR / model zoo 中的数字，标注出处。
- **合成源实测**：用程序生成的 CSI 序列验证信号处理链路，**不是真机**。
- 凡属"计划中 / 未验证"的，一律显式标注，不充作结论。

## 2. WiFi CSI 是什么，为什么能测呼吸

**CSI（Channel State Information，信道状态信息）** 是 WiFi 接收端在解调时顺手算出来的一个量：每个子载波上的**幅度**和**相位**，反映的是"信号从发射端到接收端这一路上经历了什么"。

人站在链路中间，会遮挡、反射、衍射电磁波 → 多径结构改变 → **相位出现微小起伏**。起伏的频率就是呼吸的频率。

```
人体呼吸（≈0.25 Hz）
        ↓ 胸腔起伏 ±1~2 cm
多径结构改变 → CSI 相位扰动
        ↓
解缠 → 去趋势 → 带通 0.1–0.5 Hz
        ↓
频域谱峰 / 时域过零  →  呼吸率（BPM）
```

工程上有三个必须知道的现实：

1. **相位是缠绕的**。ESP-IDF 给的 CSI 相位在 ±π 之间循环，直接算频谱全是毛刺，必须先 `unwrap`。
2. **幅度可以做基线**。很多"存在检测"方案用 CSI 幅度变化而不是相位，幅度对 AGC 抖动更敏感但更稳。
3. **呼吸（0.1–0.5 Hz）可测，心跳（0.8–2.0 Hz）勉强**。心跳引起的胸腔位移是毫米级，远小于 2.4 GHz 波长（≈12 cm），多径变化基本淹没在噪声里。RuView 自己的 README 也把心率标为 "Experimental 40–120 BPM output; **not a medical measurement**"。

## 3. RuView 是什么，有多大

| 项 | 值 |
|---|---|
| 仓库 | `ruvnet/RuView`，MIT |
| 规模 | **4023 个文件**（Rust 1080 / Markdown 1054 / Python 338 / JS 203 / TS 179） |
| 星标 | 10 万量级（2026-11-22 实测 104,759） |
| 硬件 | ESP32-S3（$9）/ ESP32-C6（$6–10）/ 研究级 NIC（Intel 5300 等） |
| 能力 | 存在检测、呼吸率、心率、跌倒、17 关键点姿态、房间指纹、睡眠分期、105 个 "cog" 边缘模块、MQP/Matter/Apple Home 集成 |

**为什么只重写核心闭环**：整体重写既不现实也没价值。那 105 个 cog、MCP harness、Matter 桥接、HuggingFace 预训练权重（17 关键点姿态）、OccWorld 世界模型——这些是**生态**，不是感知闭环，而且大多依赖 GPU / 云 / 预训练数据。

> 顺带一个诚实的观察：RuView README 自己承认，17 关键点姿态模型是 "first-cut"，**PCK@20 = 3.0%**，远低于 ADR-079 里 ≥35% 的目标；README 里那个 **82.69%** 是另一个独立基准（MM-Fi）上的公开结果，不是这个在-device 模型的成绩。读这类项目的数据时，**先分清"本仓模型实测"和"外部基准引用"**。

**值得重写的是这条**：

```
WiFi 射频 → CSI 采集 → 二进制帧 → UDP 推流 → 解缠/去趋势
        → 选子载波 → 带通 → 谱峰/过零 → 呼吸率
        → 相位活动度 vs 自适应门限 → 存在检测
```

本项目把这条链路的**两半**都实现了：节点侧固件（ESP32-C6）+ 主机侧管线（Python）。

**独立性声明**：本次全部代码从零重写，**没有导入、复制或执行该仓库的任何代码**。唯一的关联是 **ADR-018 二进制帧格式**——一份公开的帧格式规范，按规范独立实现了序列化与解析，好处是两边产生的 CSI 帧可以互相读取。属于格式兼容，不属于代码复用。

## 4. 第一道门槛：你手上那颗芯片到底有没有射频

这是整件事最容易翻车的地方，也是本次最花时间的一步。

作者手边的板子是 **Waveshare ESP32-P4-WIFI6-DEV-KIT**，上面有**两颗**芯片：

| 芯片 | 角色 | 有 WiFi 射频吗 |
|---|---|---|
| **ESP32-P4** | 主控（双核 RISC-V 400 MHz，32 MB PSRAM，ISP/PPA/硬件编码） | **没有**。芯片里就没集成射频 |
| **ESP32-C6** | 协处理器（Wi-Fi 6 + BLE 5，走 SDIO 当 P4 的射频） | **有**，整块板唯一的射频 |

**CSI 必须在有射频的那颗芯片上采。** P4 自己没有射频，所以：

> 把 RuView 的 ESP32 节点固件编译给 P4 是**没有意义的**——它连 WiFi 都开不起来。

而且 P4 通过 SDIO 用 C6 的射频时，C6 跑的是乐鑫的 **esp-hosted 从机镜像**，那套镜像**不做 CSI 透传**。于是问题变成：**怎么把 C6 换成跑我们自己的固件？**

### 4.1 死路：esp_hosted 自带的 CSI 透传

直觉上最省事的做法是"保留出厂 esp-hosted 固件，让 P4 转发 C6 的 CSI"。**这条路是死的**，源码核实：

| 检查项 | 结果 |
|---|---|
| 协议定义里有 `Req_WifiSetCsiConfig` / `Req_WifiSetCsi` / `WifiCsiInfo` | ✅ 有 |
| 从机侧会接收 `csi_enable` 并传给 WiFi 驱动 | ✅ 有（`slave/main/slave_control.c`） |
| **host 侧 `esp_hosted_api.c` 里那组 CSI 函数** | ❌ **整段被注释掉** |
| `esp_wifi_remote_set_csi_rx_cb()` | ❌ 只剩 WEAK stub，返回 `ESP_ERR_NOT_SUPPORTED` |
| esp_hosted 的 Kconfig 里有没有 CSI 开关 | ❌ **没有** |
| 从机侧有没有把 CSI 数据回传 host 的代码路径 | ❌ **没有** |

**结论**：协议层预留了口子，但 host 侧没接。**必须把 C6 换成自己的固件。**

### 4.2 通路：SDIO OTA 把固件推进 C6

esp_hosted 组件自带**从机 OTA** 能力：主机调 `rpc_ota_begin/write/end`，从机把固件写进 C6 的另一个 OTA 槽位并设置启动分区，然后自己重启。

| 要点 | 值 |
|---|---|
| 入口函数 | `rpc_ota_begin/write/end`（在 `host/drivers/rpc/wrap/rpc_wrap.c`，**非公共头文件，要自己声明 extern**） |
| 单次写入上限 | **1400 字节**（组件里的 `CHUNK_SIZE`） |
| C6 分区表 | nvs 0x9000 / otadata 0xd000 / phy_init 0xf000 / **ota_0 0x10000 (1536K)** / ota_1 0x190000 (1536K)，4 MB flash |
| app 链接偏移 | 必须是 **0x10000** |
| 镜像校验 | 从机侧 `esp_ota_end()` 会验 magic + 校验和，**镜像坏了会干净地失败，不会写坏 flash** |

**板上实测（2026-11-22）**：

```
rpc_ota_begin ok
  ... 856,432 bytes ...
PUSH-DONE C6 will reboot into the new firmware
```

推送成功，从机自己重启进新固件。**这条路是通的。**

### 4.3 但随即撞上一个"先有鸡先有蛋"

C6 换成我们的固件之后，它**不再是 esp-hosted 从机**了 → P4 再也没法通过 SDIO 推它 → **修好的固件推不上去**。

这形成一个死结：**C6 的 flash 只能从它自己的 UART 写进去。**

## 5. 不用 USB-TTL：让 P4 当串口桥

板子上有一组 **"ESP32-C6 UART 焊盘"**（C6_U0TXD / C6_U0RXD / GND / C6_IO9），官方文档里明确它是给 C6 单独刷固件用的。常规做法是接一个 USB-TTL 适配器。

**但 USB-TTL 本身是可以省掉的**：让 **P4 变成 C6 的串口桥 + 编程器前端**。

```
PC 的串口 (CH343 → P4 UART0)  ═══ 字节透明转发 ═══►  P4 UART1 → C6 的 UART
```

P4 顺带负责把 C6 弄进 ROM 下载模式：

| C6 的什么 | P4 怎么控制 |
|---|---|
| 复位线（EN） | **P4 GPIO22**（板上实际连线，见下） |
| IO9 | P4 的一个 GPIO：平时拉高（正常启动），复位瞬间拉低（= ROM 下载模式） |

### 5.1 ⚠️ 一个 Kconfig 默认值对这块板是错的

esp_hosted 的 `CONFIG_ESP_HOSTED_SDIO_GPIO_RESET_SLAVE` 在 ESP32-P4 上**默认 54**。而这块板的实际连线（从 Zephyr 板级定义 `reset-gpios = <&gpio1 22 GPIO_ACTIVE_HIGH>` 核实）是 **GPIO22**。

**GPIO54 在这块板上是空脚。** 后果：

- esp_hosted 打印 "Reset slave using GPIO[54]" → **它一直在复位一个无关的脚**，C6 从来没被复位过。
- 更危险的是：esp_hosted 的连接重试逻辑 `transport_drv_reconfigure()` 在连不上从机时**每 10 次重试就 `reset_slave()` 一次**（`host/drivers/transport/transport_drv.c`）。**如果复位脚配对了，C6 换成自己的固件之后，P4 会每 10 秒把 C6 复位一次**，我们的节点固件永远起不来。

> **这是换固件时最容易踩的坑**：换完之后 P4 还在按"我是它的射频"的方式工作。把复位脚改指到一个空脚，C6 才能自己跑起来。

### 5.2 接线（4 根，2.54mm 排针，位置从官方 40 针图核对）

| C6 焊盘 | 接 P4 排针 | 排针位置 |
|---|---|---|
| **C6_U0TXD**（C6 发） | **GPIO47** | 右列倒数第 3 |
| **C6_U0RXD**（C6 收） | **GPIO46** | 右列倒数第 4 |
| **C6_IO9** | **GPIO48** | 左列倒数第 4 |
| **GND** | 任意 GND | 如左列最下方 |

C6 的复位线已经焊在板上（P4 GPIO22），**不用接**。

### 5.3 串口桥固件的关键设计

| 设计点 | 为什么 |
|---|---|
| **串口控制台整个关掉**（`CONFIG_ESP_CONSOLE_NONE`） | 串口上多一个字节就会破坏 esptool 的同步握手。诊断信息改走原生 USB（USB Serial-JTAG），不影响桥接数据 |
| 刷 C6 时必须 `--before no_reset --after no_reset` | CH343 的 DTR/RTS 接的是 **P4** 的 EN/IO0。带 reset 去刷，复位的是 P4 不是 C6 |
| 开机自动做下载模式握手 | IO9 拉低 → 复位 C6 → C6 进 ROM 下载模式 → 开始转发 |
| 静默 15 秒后自动放 C6 出来 | 刷完后把 IO9 拉高并复位 C6，C6 于是正常启动进新固件 |

## 6. 节点侧固件（C6）：独立实现要点

### 6.1 CSI 采集：回调里不能分配内存

`esp_wifi_set_csi_rx_cb()` 的回调跑在 **WiFi 驱动上下文**里，不能阻塞、不能 malloc。做法是固定槽位池 + 两个 FreeRTOS 队列在回调和发送任务之间倒手：

```c
free_q  : 空闲槽位下标
ready_q : 已填好、待发送的槽位下标
```

**限速 50 Hz**（20 ms 门限）。CSI 回调在接收密集时可以到几百 Hz，不限速会把 WiFi ISR 压垮——C6 只有 320 KB SRAM，余量很小。

### 6.2 ADR-018 帧格式（与上游一致）

```
Offset  Size  Field
0       4     Magic: 0xC5110001 (LE)
4       1     Node ID
5       1     天线数
6       2     子载波数 (LE u16)
8       4     频率 MHz (LE u32)
12      4     序号 (LE u32)
16      1     RSSI (i8, dBm)          ← 有符号
17      1     噪声底 (i8, dBm)         ← 有符号
18      1     PPDU 类型（0=HT/legacy 1=HE-SU 2=HE-MU 3=HE-TB）
19      1     标志位（bit0=BW40 bit2=STBC bit4=sync bit5=首字已清洗）
20      N*2   I/Q 对（每子载波 2 字节：低字节=Imag，高字节=Real）
```

字节序 `[ant0_sc0_I, ant0_sc0_Q, ant0_sc1_I, ...]`（天线优先，再子载波）。

> ✅ **RSSI / 噪声底是 i8 有符号**。按无符号解析会得到 `205` 而不是 `-51`——这是本次单元测试抓出来的 bug（见 §7.3）。

### 6.3 两种模式，运行时可切

| 模式 | 谁是 AP | 用途 |
|---|---|---|
| `softap`（默认） | C6 自己开热点 | **自包含**，不依赖任何外部网络 |
| `sta` | 外部 AP（如 PC 开的移动热点） | 更接近"教科书"拓扑（node=STA 测下行 CSI） |

切换通过 UDP 控制通道（文本行命令）：`status / mode / ssid / pass / target / port / nodeid / save / restart`。节点每 2 秒向广播地址发一行状态，主机据此发现它。

### 6.4 三个 UDP 通道

| 端口 | 方向 | 用途 |
|---|---|---|
| 5005 | 节点 → 主机 | CSI 帧（ADR-018 二进制） |
| 5006 | 双向 | 控制命令 + 状态通告 |
| 5008 | 主机 → 节点 | **照明包**。内容毫无意义，唯一作用是在射频层产生可测 CSI |

> 照明包必须发**够大**（1400 字节）才能走 HT/HE 的长 PPDU，子载波才完整。主机以 25 Hz 持续打，节点就能拿到约 25 帧/秒的 CSI。

## 7. 主机侧管线（Python）：三个自己踩出来的坑

预处理链：**解缠 → 去趋势 → 选 top-4 子载波 → 合成标量 → 带通 → 谱峰 + 过零**。

### 7.1 ⚠️ 坑一：去趋势窗口会把呼吸信号整除掉

长度为 T 的滑动均值，其频率响应在 **f = k/T** 处是**零点**。呼吸频带是 0.1–0.5 Hz，如果去趋势窗口取 **T = 12 s**，那么 **0.25 Hz（= 15 BPM）正好落在 k/T 上，会被完全消掉**。

> 这个 bug 是在合成源上测出来的：15 BPM 的输入，读数直接没有输出。
>
> **规律**：去趋势窗口必须**远长于**最长的信号周期。取 **T = 30 s**，零点落在 0.033 Hz，远低于呼吸频带下限。

这类"参数刚好等于信号的某个倒数"的坑，靠读代码是看不出来的，只能靠**已知答案的合成源**去撞。

### 7.2 ⚠️ 坑二：存在检测的活跃度不能用归一化信号

"存在检测"的经典做法是相位方差。实现时很容易顺手把合成信号**归一化**（让频谱干净）——**那样活跃度恒等于 1.0，跟环境噪声比不了**。

正确做法：给存在检测用**未归一化**的原始相位方差（弧度量纲），归一化只给生理率提取用。

### 7.3 ⚠️ 坑三：单帧尖刺不该翻转判定

门限用"基线 + k×MAD"，在空房间这种基线极低的环境下，一个突发干扰就能冲过门限。

**加 3 帧迟滞**：连续 3 次超阈才判"有人"，连续 3 次不超才判"没人"。

### 7.4 合成源自检方法（没有硬件时怎么验证 DSP）

用程序生成一段"像真的"的 CSI：只有几个子载波是"活的"（被多径激发）、呼吸叠加在相位上、幅度远小于慢漂移、量化成 int8 的 I/Q（**这一步会造成 ±π 缠绕，正是要测的**）。

**结果（2026-11-22 本机实测）**：

| 场景 | 目标 | 测得 | 结论 |
|---|---|---|---|
| 呼吸率还原 | 15.0 BPM | **15.0 BPM，误差 0.01，置信度 0.97** | ✅ |
| 子载波选择 | 模拟器里"活"的 4 个 | **全选对** | ✅ |
| 存在检测翻转 | 无人 → 有人 | 正确从 no 翻到 YES | ✅ |
| 单元测试 | — | **25 个全过** | ✅ |

> ⚠️ **合成源证明的是"链路是通的"，不是"准"。** 合成源的呼吸是干净正弦；真实场景的 CSI 含 AGC 抖动、噪声底变化、多径闪烁，必须真机实测调参。**这一章所有"本机实测"里带"合成源"字样的数字，都不能当成真机精度。**

### 7.5 两种频率估计，各有各的精度天花板

| 方法 | 精度受限于 | 用途 |
|---|---|---|
| 频域谱峰 | FFT 分辨率 1/窗口时长（40 s 窗 → 0.025 Hz ≈ 1.5 BPM） | 主读数 |
| 时域过零 | 采样率（25 Hz → 0.05 BPM 量级） | 交叉验证 |

置信度 = 0.65 × 谱峰占比 + 0.35 × 两法一致性。**置信度低就不要当事实用**——这是 RuView README 里反复强调的纪律，这里把它做成了显式字段。

## 8. 诚实的边界

### 8.1 这不是医学设备

呼吸率是实验性的，置信度必须一起看。

### 8.2 存在检测的基线学习期

门限基线需要一段"环境学习期"（默认 60 s）来学空房间的水平。**如果学习期内房间里就有人，基线会把人吸进"环境"里**，之后一直判"无人"。判为"无人"时基线才缓慢跟随（α=0.02），有人时完全不更新。

### 8.3 ⚠️ 心率不做指标

频带选得好会出数，但那个数大概率是呼吸的谐波或基频泄漏，不是心率。2.4 GHz 的 CSI 对心跳不敏感——心跳引起的毫米级位移远小于波长。

### 8.4 RuView 自己的 17 关键点姿态

**未实现，也不打算实现。** 它需要摄像头配对的训练数据（ADR-079 的"摄像头 + ESP32 CSI 配对训练"），而且 RuView 公开的那个 in-device 模型 PCK@20 只有 3.0%。

### 8.5 没做的事

- 多人计数、跌倒检测、房间指纹、睡眠分期——RuView 有，本次没有。
- 多节点组网与跨节点时间同步。
- Rust v2 workspace（60+ crates）、MCP harness、HA/Matter 集成——生态，不是闭环。

## 10. 复现要点（速查）

```
① 构建 C6 节点固件（ESP-IDF 5.5.4，目标 esp32c6）
② 构建 P4 推送器，编译期内嵌 C6 镜像
③ 把 P4 推送器刷进 P4（CH343 串口）→ 它把 C6 固件经 SDIO 推过去
   —— 注意：这一版 C6 有 bug（见 §10.1），用它来验证"能不能推"即可
④ 修好 C6 固件后，改用 P4 串口桥直刷（不需要 USB-TTL）
⑤ 电脑连 C6 的 SoftAP，跑主机管线：
     python run.py --node-ip <节点 IP> --duration 120 --csv out.csv
⑥ 没有硬件时用合成源自检：
     python run.py --simulate --scenario breath   --duration 60 --fs 25 --breathing-bpm 15
     python run.py --simulate --scenario presence --duration 90 --fs 25 --baseline-s 30
     python -m pytest tests/ -q
```

### 10.1 ⚠️ 一个"配置读失败把默认值清空"的 bug

节点从 NVS 读配置时，如果**读失败就把目标缓冲区置空**，那么：

```
出厂 NVS 里没有我们的键 → 读失败 → SSID 变成空串
    → esp_wifi_start() 失败 → SoftAP 根本起不来
    → 扫描列表里什么都看不到（空 SSID 相当于隐藏 SSID）
```

症状极具迷惑性：**C6 在跑、网络在闪、但一个 SSID 都扫不到**——很容易误判成"固件没烧进去"。

**规律**：配置读取失败要**保留默认值**，而不是清空。读到了"空串"同样应当视为"没有这个配置"。

### 10.2 ⚠️ esp_hosted 在传输层没起来时会崩

`esp_wifi_init()` / `esp_wifi_start()` **不只是"开 WiFi"**——在 esp_hosted 架构里，**SDIO 从机连接是由它触发的**（日志里 "Attempt connection with slave" 出现在 `app_main` 里 `ESP_WIFI_MODE_STA` 之后）。

**先发 RPC 再初始化 WiFi 栈** → 传输层还没 ready → esp_hosted 走进错误分支**重复释放缓冲** → tlsf `block already marked as free` 断言 → 重启循环。

> 同一个坑还有第二层：esp_hosted 的**出厂从机镜像不支持较新的 `esp_hosted_get_coprocessor_fwversion()` RPC**，读不到版本号是正常的，不影响 OTA。

## 11. 一句话总结

> **WiFi 感知的门槛不在算法，在"你手上那颗芯片是不是真有射频"，以及"你能不能把固件塞进那颗芯片"。**
>
> 算法侧反而是最可控的部分——只要有一个已知答案的合成源，三个最阴险的 bug（去趋势窗口整除呼吸频率、归一化毁掉存在检测、单帧尖刺翻转判定）都会被当场撞出来。
>
> 硬件侧则有两个必须提前查证、查错了会浪费一整天的事实：**esp_hosted 的 host 侧 CSI 透传是注释掉的**（别指望它），**而它的复位脚 Kconfig 默认值对具体板卡可能是错的**（复位一个空脚 vs 每 10 秒真的把你的固件杀掉）。
