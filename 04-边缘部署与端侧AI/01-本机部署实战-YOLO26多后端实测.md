# 本机部署实战：YOLO26 多后端实测

> **核心问题**：没有独显的笔记本上，YOLO26 到底能跑多快？该选哪条后端？每条路上有什么必踩的坑？

本章记录 **2026-10-31** 在本机（华为 MateBook HKFG-XX，i5-13500H / 32GB / Intel Iris Xe 核显 / **无独显** / Windows 11 家庭版）部署 **YOLO26** 的完整过程与实测数据。

**数据口径（全章统一，引用时请照抄）**

| 项 | 取值 |
|---|---|
| 模型 | `yolo26n.pt`（Ultralytics 官方权重，COCO 80 类） |
| 输入 | 640×640 |
| 测试图 | `ultralytics/assets/bus.jpg` |
| 采样 | 每个后端 **11 次取中位数**（不是平均值） |
| 计时范围 | **Ultralytics 完整管线**：letterbox 预处理 → 前向 → NMS/解码 → Results 构造 |
| 性质 | **本机实测**，非转述第三方报告值 |

> ⚠️ 本章是全仓库少数**含作者本机复现数据**的章节，与其他章节「转述公开报告值」的性质不同，数字带本机特有限制（见 §4.2）。

## 1. 硬件前提：为什么没有 CUDA 这条路

选后端之前必须先认清硬件能给什么：

| 部件 | 本机实际 | 对推理路线的含义 |
|---|---|---|
| CPU | i5-13500H，12 核 16 线程，2.6 GHz | 无 AVX512-FP16、无 AMX → **FP16 反而更慢** |
| GPU | Intel Iris Xe 核显（共享内存），**无 CUDA** | `torch.cuda.is_available() == False`；TensorRT 完全不可用 |
| RAM | 31.7 GB | 足够跑任何 CPU 模型 |
| 磁盘 | C 盘仅剩 **17 GB**，D 盘 76 GB，E 盘 176 GB | 环境和权重必须放 E 盘 |

**结论先行**：本机的加速路线只剩两条——**Intel 核显**（OpenVINO / DirectML）和**纯 CPU**。任何教程里"先装 CUDA 版 torch"的步骤在这台机器上都是浪费 3GB 磁盘换来一个用不上的 runtime。

## 2. 环境搭建：为什么要 `--system-site-packages`

### 2.1 关键决策：复用系统已有的 CPU 版 torch

系统 Python 3.11 里已经装好 `torch 2.13.0+cpu` + `torchvision 0.28.0+cpu`（约 250MB）。如果新建普通 venv 让 pip 重新解析依赖，PyPI 的 Windows 默认 `torch` wheel 是 **CUDA 版**（约 3GB，且带一堆用不上的 cuDNN/cuBLAS），本机根本跑不了也用不上。

正确做法是让 venv 直接看见系统 site-packages：

```bash
python -m venv --system-site-packages E:/yolo-venv
```

此时 venv 内 `import torch` 命中的是系统的 `2.13.0+cpu`，pip 也认为 torch 需求已被满足，**不会重装**。

### 2.2 镜像：uv 走 pypi.org 会超时

本机 pip 全局已配清华源，但 `uv` 有独立配置，**默认走 pypi.org 会超时**（实测拉 matplotlib 时 3 次重试全失败）。结论：

```bash
# ✅ 用 pip + 清华源
E:/yolo-venv/Scripts/python.exe -m pip install -i https://pypi.tuna.tsinghua.edu.cn/simple/ ultralytics openvino

# ❌ uv 默认走 pypi.org，会卡在 88s 后报 "Failed to fetch"
uv pip install ultralytics
```

安装结果：

| 包 | 版本 | 来源 |
|---|---|---|
| ultralytics | 8.4.194 | PyPI（2026-10-30 发布，当时最新） |
| openvino | 2026.4.1 | PyPI |
| onnxruntime-directml | 1.24.4 | PyPI（装在 venv 内，遮蔽系统 onnxruntime 1.27.0） |
| torch / torchvision | 2.13.0+cpu / 0.28.0+cpu | 系统全局，未改动 |

## 3. 后端矩阵：七条路分别管什么

| 后端 | 执行设备 | 怎么用 | 适合场景 |
|---|---|---|---|
| `torch` | CPU | `YOLO("yolo26n.pt").predict(...)` | 基准线、最省事 |
| `openvino` | Intel CPU / **核显** | 先 `export(format="openvino")`，再 `YOLO("xxx_openvino_model")` | **本机最优** |
| `onnx`（ONNX Runtime） | CPU | `export(format="onnx")` | 与 ORT 生态对接 |
| `onnxruntime-directml` | **核显**（DirectX 12） | 需自己 patch `ort.InferenceSession` | 备选，见 §4.3 |
| TensorRT | NVIDIA | — | **本机不可用** |
| RKNN | Rockchip NPU | — | 见 `01-YOLO/08`，本机不适用 |

### 3.1 OpenVINO 的设备写法有个坑

`device="GPU"` 会被 Ultralytics 的设备选择器当成 CUDA，直接报错：

```
ValueError: Invalid CUDA 'device=gpu' requested. Use 'device=cpu' or pass valid CUDA device(s)
```

正确写法是 **Intel 专用前缀**：

```bash
yolo predict model=yolo26n_fp32_openvino_model source=bus.jpg device=intel:GPU
```

### 3.2 导出目录名必须以 `_openvino_model` 结尾

Ultralytics 靠**后缀匹配**识别格式（`AutoBackend._model_type`），目录名必须包含 `_openvino_model` 这个子串：

- ✅ `yolo26n_openvino_model`（官方导出默认名）
- ✅ `yolo26n_fp32_openvino_model`（自己加精度后缀也行）
- ❌ `yolo26n_openvino_fp32_model` —— **子串 `_openvino_model` 不存在**，报 `model='...' is not a supported model format`

## 4. 实测结果

### 4.1 主表：七个后端横向对比

| 后端 | 设备 | 精度 | 中位延迟 | 帧率 | 相对 PyTorch |
|---|---|---|---|---|---|
| **OpenVINO** | **核显** | FP32 | **32.1 ms** | **31.1 FPS** | **3.0×** |
| OpenVINO | 核显 | FP16 | 37.9 ms | 26.4 FPS | 2.5× |
| ORT DirectML | 核显 | FP32 | 45.1 ms | 22.2 FPS | 2.3× |
| PyTorch | CPU | FP32 | 95.9 ms | 10.4 FPS | 1.0× |
| OpenVINO | CPU | FP32 | 95.8 ms | 10.4 FPS | 1.0× |
| ONNX Runtime | CPU | FP32 | 100.2 ms | 10.0 FPS | 0.96× |
| OpenVINO | CPU | FP16 | 124.2 ms | 8.0 FPS | 0.77× |

> ORT DirectML 那一行的 **22.7 ms / 44.1 FPS** 是**纯前向**（不含 letterbox 与 NMS）的裸数据，
> 不可与主表直接比较；补上完整管线后是 45.1 ms，即表中数值。

**三个反直觉的结论：**

1. **核显比 CPU 快约 3 倍**。Intel Iris Xe 虽然没有 CUDA，但它的 OpenVINO GPU 插件在这类小模型上比 CPU 路径高效得多。
2. **FP16 在这台机器上是负优化**。i5-13500H 没有 AVX512-FP16 也没有 AMX，FP16 权重要靠软件转换；核显上 FP16 比 FP32 慢 18%（37.9 vs 32.1 ms），CPU 上慢 30%。
3. **OpenVINO CPU ≈ PyTorch CPU**（95.8 vs 95.9 ms）。如果只能跑 CPU，Ultralytics 原生的 `torch` 后端就够了，不必导出 OpenVINO。

### 4.2 数字波动比想象中大

同一份代码、同一个模型，20 次连续推理的延迟分布：

```
min = 75.6 ms   median = 90.0 ms   max = 174.7 ms
```

而在某一次独立的测试中，同一个 PyTorch CPU 后端测出了 **370.7 ms**（2.7 FPS）的离群值。

**结论：单次计时在笔记本上毫无意义。** 本章所有数字都取 11 次中位数。如果你在别的机器上看到"我的 YOLO 比官方快 3 倍"，大概率是它只测了一次、且恰好落在 boost 区间。

### 4.3 模型规模的影响（OpenVINO fp32 @ 核显）

| 模型 | 中位延迟 | 帧率 |
|---|---|---|
| `yolo26n` | 38.6 ms | 25.9 FPS |
| `yolo26s` | 45.7 ms | 21.9 FPS |
| `yolo26m` | 94.9 ms | 10.5 FPS |

> 延迟为**本机实测**（OpenVINO fp32 @ 核显）。官方文档只给出 YOLO26 五档整体区间
> **40.9–57.5 mAP（COCO）** 与 **1.7–11.8 ms T4 TensorRT 延迟**，未逐档列 mAP，
> 故此处不臆测各档精度——需要精确数值请查 arXiv:2606.03748 论文表。
>
> 注意 `yolo26n` 这次测到 38.6 ms，而 §4.1 主表里同配置是 32.1 ms——同属波动范围，再次说明为什么要取中位数。

### 4.4 正确性验证：加速不能改变结果

同一张图，四条后端的检测结果：

| 后端 | bus | person ×4 |
|---|---|---|
| PyTorch CPU | 0.88 | 0.87 / 0.86 / 0.85 / 0.66 |
| ONNX Runtime CPU | 0.90 | 0.85 / 0.85 / 0.84 / 0.56 |
| OpenVINO 核显 | 0.90 | 0.85 / 0.84 / 0.84 / 0.55 |
| ORT DirectML 核显 | 0.90 | 0.85 / 0.84 / 0.84 / 0.55 |

框坐标逐像素对齐（OpenVINO 核显 vs ORT DirectML 核显完全一致），置信度差异 ≤0.01 属于浮点误差范围。

> **这一步不能省。** 核显算出来的框和 CPU 不一样时，你无法判断是"硬件差异"还是"你把归一化搞错了"。先跑一次基线对齐，后面每次改后端都能快速判定。

### 4.5 完整管线的耗时拆解

`yolo predict ... device=intel:GPU` 的官方计时输出：

```
image 1/1 bus.jpg: 640x640 4 persons, 1 bus, 21.0ms
Speed: 10.2ms preprocess, 21.0ms inference, 3.4ms postprocess per image
```

**预处理（10.2 ms）占了总时延的 30%**，比推理（21.0 ms）的一半还多。letterbox 是纯 CPU 操作，在核显后端上成了新的瓶颈——如果要做高帧率视频流，**预处理搬到 GPU 或改用更轻的 resize 策略**比换模型收益更明显。

## 5. 踩坑清单（本机实际踩到的）

### 5.1 Ultralytics 8.4.x 的 API 变化

| 现象 | 原因 | 解法 |
|---|---|---|
| `TypeError: 'save=dml_result.jpg' is of invalid type str` | 8.4.x 里 `predict(save=...)` 只接受 bool，输出路径改由 `project`/`name` 控制 | 传 `save=True`，再用 `results[0].save("out.jpg")` 指定路径 |
| `AttributeError: 'Results' object has no attribute 'conf'` | 置信度不在 Results 上 | `results[0].boxes.conf` |
| `model='xxx' is not a supported model format` | 目录名不满足后缀匹配 | 见 §3.2 |

### 5.2 自己写后处理大概率是错的

手写 letterbox + NMS 时我踩了两个坑：

1. **`scale_boxes()` 不传 `ratio_pad` 时不会把 letterbox 坐标还原回原图**——它假设输入框已经在原图坐标系。不传这个参数，框会停在 640×640 空间里，位置全错。
2. **YOLO26 是 end-toend（One2One）头**，标准 NMS 的通道假设不一定成立。

**稳妥解法：让 Ultralytics 接管前后处理，只替换执行提供者。** `detect_dml.py` 的做法是 patch `ort.InferenceSession` 强制走 DirectML：

```python
_OrigSession = ort.InferenceSession

class _DmlSession(_OrigSession):
    def __init__(self, path_or_bytes, sess_options=None, providers=None,
                 provider_options=None, **kwargs):
        super().__init__(path_or_bytes, sess_options,
                         providers=["DmlExecutionProvider"],
                         provider_options=provider_options, **kwargs)

ort.InferenceSession = _DmlSession   # 之后 YOLO("yolo26n.onnx") 自动走核显
```

Ultralytics 的 ONNX 后端本身只认 CPU / CUDA / CoreML / MIGraphX，**没有 DirectML 分支**，所以必须自己打这个补丁。

### 5.3 Git Bash 的路径转换

`timeout` 包在中间时，Windows 路径不会被转换：

```bash
# ❌ 全部用例瞬间失败（timeout → exec Windows 路径失败）
timeout 180 E:/yolo-venv/Scripts/python.exe bench_one.py torch

# ✅ 用 POSIX 路径
timeout 180 /e/yolo-venv/Scripts/python.exe bench_one.py torch
```

**这个坑的隐蔽之处在于：它不报错，只是静默失败。** 批量跑 benchmark 时所有用例都返回空，我一度以为是模型问题。

### 5.4 跑分脚本要能隔离单个后端

一个后端挂死（核显插件初始化、DML 设备创建）会让整批测试卡住。正确做法是**每个后端一个子进程 + 超时**：

```bash
for c in torch ov-cpu-fp32 ov-gpu-fp32 ort-dml; do
  timeout 240 /e/yolo-venv/Scripts/python.exe -u bench_one.py "$c" > "log_$c.txt" 2>&1
  grep -a "^RESULT|" "log_$c.txt"
done
```

## 6. 工程结论

1. **先问硬件能做什么，再选后端。** 本机没有 CUDA，PyPI 的默认 torch 是 CUDA 版——`--system-site-packages` 复用系统的 `+cpu` 版本，既省 3GB 磁盘也避免版本漂移。
2. **有 Intel 核显时，OpenVINO + `device="intel:GPU"` 是默认首选**，比纯 CPU 快 3 倍，且精度与 CPU 基线逐像素对齐。
3. **FP16 不是免费午餐。** 没有 AVX512-FP16 / AMX 的 CPU 上，FP16 权重需要软件转换，反而更慢。本机核显上 FP32 快 18%。**上量化前先量一行基准，别信"FP16 一定更快"。**
4. **计时必须取中位数并跑多次。** 笔记本上单次计时波动可达 4.9 倍（75.6–370.7 ms），任何基于单次测量的结论都不可靠。
5. **后端切换后必须做一次跨后端结果对齐。** 框坐标和置信度都对比一遍，才能把"硬件差异"和"实现 bug"分开。
6. **预处理可能是真瓶颈。** 本机核显后端里 letterbox 占 30% 时延，高帧率场景应该先动预处理，而不是先换更大的模型。
7. **不碰本地后端时，`torch` CPU 就够了。** OpenVINO CPU 与 PyTorch CPU 差距在噪声内（95.8 vs 95.9 ms），多导一个格式并不划算。
