# ASR 语音识别

> **核心问题**：语音转文字有哪几种架构？流式识别怎么做到「边说边出字」？怎么衡量准确率？

---

## 0. 一张图看三种 ASR 架构

```
┌──────────── ① Encoder-Decoder（Whisper 系）────────────┐
│  音频 → Mel 频谱 → Encoder(Transformer) → Decoder → 文字 │
│  ✅ 鲁棒、精度高  ❌ 天然是「整段输入」→ 流式要改造        │
└────────────────────────────────────────────────────────┘

┌──────────── ② CTC（Conformer 系）─────────────────────┐
│  音频 → Encoder → CTC 头（逐帧字符 + 空白折叠）           │
│  ✅ 天然流式、快   ❌ 无语言建模能力 → 精度略低            │
└────────────────────────────────────────────────────────┘

┌──────────── ③ Audio-LLM（语音大模型）──────────────────┐
│  音频 → Neural Codec → 离散 token → LLM → 文字            │
│  ✅ 能理解「语气里的信息」、可做语音问答                   │
│  ❌ 慢、算力贵、仍在演进                                 │
└────────────────────────────────────────────────────────┘
```

> **实用判断**：
> **要准 → Whisper；要快和流式 → Conformer/CTC；
> 要「听懂语气」或直接语音问答 → 端到端语音模型。**

---

## 1. 特征：Mel 频谱

**几乎所有 ASR 都从 Mel 频谱开始**：

```
原始波形 (16kHz 单声道)
  ↓ 分帧（25ms）+ 窗函数
  ↓ FFT → 频谱
  ↓ Mel 滤波器组（人耳感知刻度）
Mel 频谱 (80~128 维) × T 帧
```

| 参数 | 常用值 | 说明 |
|---|---|---|
| 采样率 | **16 kHz** | 电话语音是 8k；**统一重采样到 16k** |
| 帧长 / 帧移 | 25 ms / 10 ms | 帧移决定时间分辨率 |
| Mel 通道数 | 80 / 128 | 128 略准，80 略快 |
| 归一化 | **按 utterance 归一化** | Whisper 的做法，对音量变化鲁棒 |

> **一个常见的坑**：不同系统的特征参数不一致，
> 导致「用 A 训练的模型跑 B 的特征」效果暴跌。
> **训练与推理的特征参数必须完全一致**（含 `hop_length`、`n_mels`、归一化方式）。

## 2. Whisper 家族

### 2.1 五个关键设计

| 设计 | 说明 |
|---|---|
| **大规模弱标注数据** | 68 万小时多语种数据 |
| **端到端 Transformer** | Encoder-Decoder，不是 CTC |
| **多任务训练** | 转写 + 翻译 + 语言识别**共用一个模型** |
| **鲁棒性技巧** | 用「噪声/口音/背景音」的数据增强，让模型见过各种恶劣条件 |

### 2.2 使用要点

```python
import whisper
model = whisper.load_model("medium")     # tiny/base/small/medium/large/large-v3
result = model.transcribe(
    audio,
    language="zh",           # ★ 显式指定语言，别让它自动检测
    task="transcribe",       # transcribe（转写原文）/ translate（译成英文）
    temperature=0.0,         # 0 = 确定性；用 0.0~0.2 更好
    initial_prompt="以下是普通话的句子。",  # ★ 提升中文与专有名词
)
```

| 参数 | 建议 |
|---|---|
| **`language`** | **显式指定**。自动检测在短音频上会错 |
| **`initial_prompt`** | 给出领域与语言风格，**显著改善专有名词** |
| **`temperature`** | 0.0（确定性）。需要时用 0.0→0.2 递增做「退化重试」 |
| **`condition_on_previous_text`** | 长音频时**建议关闭**——它会传播前文的错误 |
| **`word_timestamps`** | 需要逐字时间戳时开（会变慢） |

> **`initial_prompt` 是一个被严重低估的功能**：
> 写上「以下是中文客服对话」「以下是英文技术会议」，
> 专有名词与标点的准确率会有肉眼可见的提升。

### 2.3 Whisper 的两个已知局限

| 局限 | 表现 | 缓解 |
|---|---|---|
| **非流式** | 需要整段音频（30 秒 chunk） | 用 `chunk_length` 切分，但会有边界损耗；或用流式变体 |
| **幻觉** | 静音段被转写成「谢谢观看」「字幕由…」等 | **用 VAD 先切掉静音**；或检测低置信度段 |
| **长音频漂移** | 重复同一句话 | `condition_on_previous_text=False` |

> **幻觉是最需要防的一个**——在录音场景里，
> 静音段被转写成一整页无关文字，会严重污染下游处理。

## 3. 流式 ASR

### 3.1 流式的本质

**流式 = 音频边到边转，文本边出。** 核心矛盾：

| | 延迟 | 准确率 |
|---|---|---|
| **整段转写** | 高（要等说完） | **高** |
| **流式** | **低** | **低**（看不到未来） |

**关键设计问题：什么时候「切一刀」输出？**

### 3.2 两种切分策略

| 策略 | 做法 | 延迟 | 准确率 |
|---|---|---|---|
| **固定窗口** | 每 N 毫秒切一次，重跑整个窗口 | 低 | 中（重复计算） |
| **增量 + 局部一致（LocalAgreement）** | 新 chunk 到达时，只有**连续两帧一致的部分**才输出 | 中 | **较高** |

**LocalAgreement-2 的思路**：

```
chunk 1: 「今天天」      → 不输出（还没确认）
chunk 2: 「今天天气」    → 输出「今天」（与 chunk 1 的一致部分）
chunk 3: 「今天天气不」  → 输出「天气」（与 chunk 2 的一致部分）
...
```

> **代价**：会有一小段延迟（要等下一 chunk 确认）。
> **收益**：准确率显著高于固定窗口。

### 3.3 实用方案

| 方案 | 说明 |
|---|---|
| **现成流式模型** | 部分厂商提供（原生流式，端到端延迟 <300ms） |
| **Whisper 流式变体** | 社区实现（whisper_streaming 等），质量损失有限 |
| **级联方案** | 专用流式 ASR（Conformer-CTC）做实时转写 + 离线 Whisper 做最终校正 |
| **假流式** | 整段转写，但用时间戳切片模拟流式输出（**延迟不降，只降体验**） |

> **「级联方案」在工程上很实用**：
> 实时用快模型给用户即时反馈，最终用准模型校正后替换。
> **但要处理「已输出内容被修改」的问题**（见 §3.4）。

### 3.4 一个被忽略的工程问题：流式输出的「改口」

**流式转写天然会改口**——前面输出错了，后面要修正。

| 策略 | 做法 | 用户体验 |
|---|---|---|
| **静默修正** | 直接改前面的文本 | 用户已经读到了，改了会困惑 |
| **显式修正** | 输出「修正：……」 | 打断注意力，但诚实 |
| **延迟提交** | 攒够一段再输出 | 延迟变高，但稳定 |
| **双轨** | 实时版给用户看，最终版给系统用 | **最实用** |

> **「双轨」是本库推荐的默认做法**：
> **实时轨（低延迟，可错）给人看；最终轨（高质量）给业务系统用。**
> 这正好对应 08-AI招聘应用 里「影子运行」的思想。

## 4. 端点检测与 VAD

**VAD（Voice Activity Detection）是所有语音应用的入口。**

| 类型 | 做法 | 延迟 | 可靠性 |
|---|---|---|---|
| **能量阈值** | 音量超过阈值就算说话 | **最低** | 差（噪声误触发、呼吸误判） |
| **神经 VAD**（Silero 等） | 小模型判定语音概率 | 低 | **好** |
| **语义端点（SEM）** | 用语言模型判断「这句话说完了吗」 | **高** | **最好**（能识别犹豫、语气未完） |

**工程上常见的组合**：

```
神经 VAD（切出语音段） → ASR（转写） → 语义端点（判断说完没）
```

> **语义端点是「自然对话」与「「说完就提交」的关键区别**——
> 人说「我想要那个…（停顿）…红色的」时，能量 VAD 会以为说完了。

## 5. 评测：WER / CER

```
WER = (替换数 + 删除数 + 插入数) / 参考文本词数
CER = (替换数 + 删除数 + 插入数) / 参考文本字符数
```

| 指标 | 用于 | 注意 |
|---|---|---|
| **WER** | 英文等以词分隔的语言 | 中文不适用 |
| **CER** | 中文、日文等 | **中文的默认指标** |
| **时间戳误差** | 字幕、剪辑 | 需要 `word_timestamps` |

### 5.1 三个必须写进报告的口径

| 口径 | 为什么 |
|---|---|
| **文本归一化规则** | 是否去标点、去大小写、繁简转换、数字写法统一——**不统一就没法比** |
| **测试集构成** | 安静/噪声/口音/远场/电话/多人 |
| **音频预处理** | 重采样、降噪、VAD 是否启用 |

> **不写归一化规则的 WER 数字无法复现。**
> 这是评测报告里最常被省略、也最该补的一项。

### 5.2 一个实用的测试集构成

| 类别 | 占比建议 | 考察 |
|---|---|---|
| 安静近场 | 30% | 基线 |
| **噪声**（街道/餐厅/车内） | 20% | 鲁棒性 |
| **远场**（1~3 米） | 15% | 远场识别 |
| **电话**（8kHz） | 10% | 电话信道 |
| **口音/方言** | 15% | 语言鲁棒性 |
| **多人重叠** | 10% | 分离能力 |

> **安静场景的 WER 早就很低了**——
> **区分度在噪声、远场、口音这三类上。**
> 只在安静场景测的系统，上线必崩。

## 6. 工程结论

1. **三种 ASR 架构**：Encoder-Decoder（Whisper，准）、CTC（快、天然流式）、
   Audio-LLM（懂语气、贵）。
2. **Whisper 显式指定语言 + 给 `initial_prompt`** 是性价比最高的两个改动。
3. **长音频要关 `condition_on_previous_text`**——否则会重复传播错误。
4. **Whisper 会在静音段产生幻觉**——**用 VAD 先切静音**是必须的。
5. **流式的核心是「什么时候输出」**：LocalAgreement 比固定窗口准确。
6. **流式输出天然会改口** → 推荐**双轨**（实时轨给人看、最终轨给系统用）。
7. **语义端点（SEM）决定对话是否自然**——它能识别「还没说完」。
8. **WER/CER 必须写清文本归一化规则**，否则数字不可复现。
9. **区分度在噪声/远场/口音上**，不在安静场景。
10. **训练与推理的特征参数必须完全一致**（含 hop_length、n_mels、归一化）。
