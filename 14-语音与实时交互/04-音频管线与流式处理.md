# 音频管线与流式处理

> **核心问题**：从麦克风到模型，音频要经过哪些处理？每一段加了多少延迟？流式管线怎么搭？

---

## 0. 音频链路全景

```
麦克风 ──▶ ① 采集 ──▶ ② AEC ──▶ ③ 降噪 ──▶ ④ AGC ──▶ ⑤ VAD
                                                        │
                                                        ▼
                                    ⑥ 分块/缓冲 ──▶ ⑦ ASR（流式）
                                                        │
                                                        ▼
                                    ⑧ TTS（流式）──▶ ⑨ 播放 ──▶ ⑩ AEC 参考信号
```

**注意第 ⑩ 步**：播放的音频必须**回送**给 AEC，
否则系统听不清自己的声音，也就没法打断自己。

| 环节 | 增益延迟 | 说明 |
|---|---|---|
| ① 采集 | 10~30 ms | 帧大小决定 |
| ② AEC | **~10~40 ms** | 需要播放信号的延迟对齐 |
| ③ 降噪 | 5~20 ms | |
| ④ AGC | < 5 ms | |
| ⑤ VAD | 10~30 ms | 窗口 + 迟滞 |
| ⑥ 分块/缓冲 | **20~100 ms** | **可调，影响流式体验** |
| ⑦ ASR | 100~300 ms | 见 [`01`](./01-ASR语音识别.md) |
| ⑧ TTS 首包 | 50~200 ms | |

> **音频前处理总共加 50~130 ms**——
> **它不占大头，但它是「能不能用」的门槛**（AEC 没做好 → 自我打断）。

## 1. 采集参数

| 参数 | 建议 | 说明 |
|---|---|---|
| **采样率** | **16 kHz**（语音） | 与 ASR 训练一致；48 kHz 采集后**降采样** |
| **位深** | 16 bit | 足够；32 bit 无额外收益 |
| **声道** | **单声道** | 双声道无增益（除非做双麦阵列） |
| **帧大小** | 10~20 ms | 帧移；越小延迟低、计算更多 |
| **缓冲大小** | **20~60 ms** | 太小会频繁唤醒，太大增加延迟 |

**采样率不匹配是最常见的坑**：
模型按 16k 训练，你喂 48k → 效果显著下降（不是精度微降，是崩坏）。

```python
# 统一重采样
import numpy as np
import scipy.signal as sp

def resample_16k(audio: np.ndarray, sr_in: int) -> np.ndarray:
    if sr_in == 16000:
        return audio
    g = np.gcd(sr_in, 16000)
    return sp.resample_poly(audio, 16000 // g, sr_in // g)
```

> **统一在链路的**第一段**做重采样**，
> 并且**记录原始采样率**——后面所有环节都用统一的 16k。

## 2. AEC（回声消除）：全双工的地基

### 2.1 为什么必须有

```
系统正在播放："您的订单已于今日发货"
麦克风同时录到这句话 ──▶ VAD 判定「有人在说话」──▶ 系统以为用户插话 ──▶ 停止
```

**用户会看到系统突然卡住/中断。**

### 2.2 AEC 的原理

**AEC 用播放信号作为参考，估计扬声器→麦克风的声学路径，再从麦克风信号里减掉它。**

```
麦克风信号 = 用户语音 + 回声(扬声器输出经房间反射) + 噪声
                ↓
用播放信号 (reference) + 自适应滤波器 估计回声
                ↓
相减 → 干净的近端语音
```

### 2.3 工程要点

| 要点 | 说明 |
|---|---|
| **必须拿到播放参考信号** | 从音频输出的**最前端**取（不要经过任何处理后再取） |
| **延迟对齐** | 参考信号与麦克风信号之间有**几十毫秒**的延迟，必须对齐 |
| **自适应滤波器要收敛** | 需要几百毫秒的播放历史才能收敛 |
| **双讲检测** | 用户和系统同时说话时，AEC 会失效 → 这时靠「播放期间抑制上报」兜底 |

### 2.4 排查「自我打断」的顺序

```
① AEC 有没有生效？     → 播放参考信号接对了吗？延迟对齐了吗？
② VAD 阈值是不是太低？ → 安静时的误检率高吗？
③ 有没有「播放期间抑制」兜底？ → 这是最后一道保险
④ 打断判定是不是太激进？ → 是不是需要「持续 N 毫秒」才判定打断？
```

> **顺序很重要**：**先查 AEC，再查 VAD，最后才动模型。**
> 很多团队一上来就换 VAD 模型，其实问题在 AEC 的参考信号取错了点。

### 2.5 「播放期间抑制」兜底

**不管 AEC 做得多好，都要有一层保险**：

```python
if tts_is_playing and not strong_real_speech_detected:
    # 播放期间的输入只做记录，不触发打断
    log_only(input_chunk)
else:
    maybe_trigger_barge_in(input_chunk)
```

## 3. 降噪与 AGC

### 3.1 降噪

| 方法 | 做法 | 效果 |
|---|---|---|
| **传统降噪**（谱减、维纳滤波） | 频域抑制 | 对**稳态噪声**有效（风扇、空调） |
| **神经降噪** | 小模型（RNNoise 等） | 对**非稳态噪声**好（人声、键盘） |
| **多通道（双麦）** | 靠波束成形 | **效果最好**，但需要硬件支持 |

> **稳态噪声用传统方法就够**；
> **非稳态（背景人声、键盘声）必须用神经降噪**。

### 3.2 AGC（自动增益控制）

**把音量归一化**——否则：

- 用户声音太小 → ASR 识别率下降
- 用户声音太大 → 削波失真

**关键参数**：

| 参数 | 建议 |
|---|---|
| **目标电平** | 固定（如 -23 LUFS 或 RMS 某个值） |
| **最大增益上限** | **必须设上限**——否则安静时的环境噪声会被放大成嘶嘶声 |
| **限幅器** | 防止削波 |

> **AGC 的最大增益上限是常见坑**：
> 不设上限时，系统会在安静时把底噪拉到很大，反而干扰 VAD 与 ASR。

## 4. VAD 的工程实现

### 4.1 三种 VAD

| 类型 | 做法 | 延迟 | 可靠性 |
|---|---|---|---|
| **能量阈值** | RMS 超过阈值 | 最低 | **差** |
| **神经 VAD** | Silero 等小模型 | 低（~30 ms/帧） | **好** |
| **语义端点（SEM）** | 语言模型判断说完没 | **高**（~300~800 ms） | **最好** |

### 4.2 神经 VAD 的典型用法

```python
import torch

class StreamingVAD:
    def __init__(self, threshold=0.5, hangover_ms=300, min_speech_ms=200):
        self.sr = 16000
        self.frame = 512                    # 32 ms @16k
        self.thr = threshold
        self.hangover = int(hangover_ms / 32)
        self.min_speech = int(min_speech_ms / 32)
        self.speaking = False
        self.quiet_run = 0
        self.voice_run = 0

    def push(self, frame: np.ndarray) -> tuple[bool, float]:
        p = self.model_prob(frame)         # [0,1] 语音概率
        if p > self.thr:
            self.voice_run += 1
            self.quiet_run = 0
        else:
            self.quiet_run += 1
            self.voice_run = 0
        # 迟滞：连续 N 帧低概率才算结束（防抖）
        if self.voice_run >= 2:
            self.speaking = True
        if self.speaking and self.quiet_run >= self.hangover:
            if self.voice_run_total >= self.min_speech:
                self.speaking = False
                return True, p            # ← 检测到一段语音结束
        return False, p
```

**两个关键参数**：

| 参数 | 作用 | 调整后果 |
|---|---|---|
| **`hangover`（迟滞帧数）** | 说话中间的停顿**不算结束** | 太小 → 一停顿就切段；太大 → 响应慢 |
| **`min_speech`** | 太短的片段不当作语音 | 防止咳嗽、敲桌子触发 |

> **「停顿被误判为结束」是 VAD 最大的问题**——
> 中文句子里的逗号停顿常常 300~500 ms，
> hangover 设成 200 ms 就会把一句话切成两半。

### 4.3 「继续说」的合并机制

**用户停顿后继续说时，要合并上一段**：

```
段1: "帮我查一下订单"   ← 停顿 500ms
段2: "12345 的状态"
       ↓
合并 → "帮我查一下订单 12345 的状态"
```

**实现要点**：
- 段结束后**不立刻提交**，等一个「合并窗口」（如 800 ms）
- 窗口内有新语音 → 合并
- 窗口超时 → 才提交

> **这与语义端点是同一个问题的两种解法**：
> 合并窗口是「时间上的宽恕」，语义端点是「语义上的判断」。
> **两者可以叠加**。

## 5. 分块与缓冲

### 5.1 分块大小的影响

| 分块 | 延迟 | 计算量 | ASR 质量 |
|---|---|---|---|
| **10 ms** | 最低 | **高**（频繁调用） | 好 |
| **20~30 ms** | 低 | 中 | 好 |
| **100 ms+** | 高 | 低 | 好 |
| **整段（5~30 s）** | **很高** | 低 | 最好 |

> **流式 ASR 的分块通常 20~40 ms**（与音频帧对齐）。

### 5.2 缓冲策略

```
                    ┌──────────────┐
麦克风 ──▶ 采集缓冲 ──▶│ 处理缓冲池   │──▶ 分块器 ──▶ ASR
                    │（可回退 N 帧）│
                    └──────────────┘
```

**为什么要「可回退」**：

| 场景 | 需要回退 |
|---|---|
| **回声消除需要未来的播放参考** | 需要对齐，可能要调整几帧 |
| **降噪需要上下文** | 前后各几帧 |
| **VAD 判定「其实那是回声」** | 需要把那段从输入里剔除 |

> **「可回退 N 帧」是流式音频管线的必备能力**——
> 很多实现是「只进不出」，一旦 VAD 误判就回不去了。

## 6. 流式管线的并发模型

### 6.1 为什么要异步

**音频采集不能被任何慢操作阻塞**（模型推理、工具调用都可能耗时几百毫秒到几秒）。

```
❌ 同步阻塞：
   采集 → 等待 → ASR（阻塞 200ms）→ 采集（丢了一段音频！）

✅ 异步流水线：
   采集线程 ──▶ 环形缓冲（无锁）──▶ 处理线程 ──▶ 推理线程 ──▶ 播放线程
```

### 6.2 四个线程

| 线程 | 职责 | 不能被阻塞 |
|---|---|---|
| **采集** | 读麦克风、写环形缓冲 | **绝对不能**（丢音频 = 直接损坏） |
| **处理** | AEC/降噪/VAD/分块 | 基本不能（会积压） |
| **推理** | ASR / LLM / TTS | **可以**（积压由缓冲吸收） |
| **播放** | 读 TTS 音频、播放 | 不能阻塞在网络读上 |

### 6.3 环形缓冲

```python
class RingBuffer:
    def __init__(self, capacity_frames: int):
        self.cap = capacity_frames
        self.buf = np.zeros((capacity_frames, frame_len), dtype=np.float32)
        self.w = self.r = 0

    def write(self, chunk):
        # 覆盖最旧的（环形）；或阻塞（取决于策略）
        n = len(chunk)
        end = self.w + n
        if end <= self.cap:
            self.buf[self.w:end] = chunk
        else:
            first = self.cap - self.w
            self.buf[self.w:] = chunk[:first]
            self.buf[:end - self.cap] = chunk[first:]
        self.w = end % self.cap

    def read_available(self):
        if self.w >= self.r:
            return self.buf[self.r:self.w], self.w
        return np.concatenate([self.buf[self.r:], self.buf[:self.w]]), self.w
```

> **环形缓冲写满时怎么处理，是必须显式决策的**：
> **覆盖最旧的**（保新弃旧，适合实时对话）
> 还是**阻塞采集**（保全部但会丢实时性）。
> **实时对话应该选「覆盖最旧的」**——宁可丢一点历史，也不能让实时性崩掉。

## 7. 逐帧核算延迟

**做延迟优化前，先把每一帧的耗时列出来。**

| 帧 | 采集 | AEC | 降噪 | AGC | VAD | 合计 |
|---|---|---|---|---|---|---|
| 帧长 | 20 ms | +25 ms | +10 ms | +2 ms | +20 ms | **~77 ms** |

**再加：**

```
┌─────────────────────────────────────────────────────┐
│ 前端管线       77 ms                                  │
│ 缓冲/分块     +40 ms                                 │
│ ASR（流式）   +150 ms                                │
│ ─────────────────────────────────────────────        │
│ 用户说完 → 文本可用        ≈ 270 ms                   │
│ LLM 首 token              +400 ms                    │
│ TTS 首包                  +120 ms                    │
│ ─────────────────────────────────────────────        │
│ 用户说完 → 听到第一个字    ≈ 790 ms                   │
│ 尾点检测（等说完）        +400 ms                    │
│ ─────────────────────────────────────────────        │
│ 用户说完 → 听到回复        ≈ 1.2 s                   │
└─────────────────────────────────────────────────────┘
```

> **这张表是语音 Agent 延迟优化的工作底稿。**
> **每一项都要实测填数，不要用估算**——
> 不同库的 AEC/VAD 实现差异可以到 2~3 倍。

## 8. 工程结论

1. **音频前处理加 50~130 ms**，不占大头但**是「能不能用」的门槛**。
2. **播放参考信号必须从音频输出最前端取**并做延迟对齐——
   **AEC 没做好就是自我打断**。
3. **排查自我打断的顺序：AEC → VAD → 打断判定 → 模型**。
4. **要有一层「播放期间抑制上报」的兜底**，不指望 AEC 完美。
5. **AGC 必须设最大增益上限**，否则安静时底噪被放大，反而干扰 VAD 与 ASR。
6. **VAD 的 hangover 要大于中文的正常停顿**（300~500 ms），
   否则一句话被切成两半。
7. **「继续说」要用合并窗口处理**（与语义端点可叠加）。
8. **流式缓冲要「可回退 N 帧」**——只进不出的实现一旦误判就回不去。
9. **采集线程绝对不能被阻塞**；四线程分离；写满时**实时对话选「覆盖最旧的」**。
10. **延迟要逐帧实测列表**，不要估算——库的差异可达 2~3 倍。
