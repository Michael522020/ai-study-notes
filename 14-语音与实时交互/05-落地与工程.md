# 落地与工程

> **核心问题**：语音到底能用在哪些场景？每个场景的关键指标是什么？成本怎么算？录音合规吗？

---

## 0. 四个真实场景

| 场景 | 形态 | 核心指标 | 最容易翻车的地方 |
|---|---|---|---|
| **① 呼叫中心** | 电话 → ASR → 意图/机器人 → TTS | **人工接管率**、解决率 | IVR 集成与合规录音 |
| **② 语音助手**（音箱/车机/手机） | 唤醒词 → 端侧 ASR → 云端 LLM → TTS | **响应延迟**、唤醒准确率 | 端云分工与打断 |
| **③ 面试 / 培训评估** | 录音 → ASR → 评分 → 报告 | **评分一致性**、证据回指率 | **录音同意**与证据可回溯 |
| **④ 会议记录 / 转写** | 分段 → ASR → 说话人分离 → 摘要 | **说话人分离准确率**、摘要可用性 | 多人重叠、多语种 |

> **注意四个场景的技术栈几乎一样，但「关键指标」完全不同。**
> **混淆这一点是语音项目失败的主因**——
> 拿「ASR 准确率」去验收一个「面试评分」项目，必然对不齐。

---

## 1. 场景一 · 呼叫中心

### 1.1 链路

```
来电 ──▶ IVR ──▶ ASR（流式）──▶ 意图识别
                                   ├─ 机器人自助 → TTS → 结束
                                   ├─ 坐席辅助（实时给坐席建议）
                                   └─ 转人工 ──▶ 坐席（AI 持续听、给建议）
```

### 1.2 三种产品形态

| 形态 | AI 的角色 | 关键指标 |
|---|---|---|
| **语音机器人** | 直接对话 | **自助解决率**、转人工率 |
| **坐席辅助** | 实时转写 + 推荐话术 | **坐席处理时长**、**采纳率** |
| **质检** | 通话后分析 | 合规问题检出率、误报率 |

> **「坐席辅助」通常比「语音机器人」更容易落地、价值更确定**——
> 它不替代人，而是帮人，**风险与阻力都小得多**。

### 1.3 关键工程点

| 点 | 说明 |
|---|---|
| **IVR 对接** | SIP / 媒体流 / 云通信 SDK；**延迟链路长** |
| **坐席侧延迟** | AI 建议要在坐席说话前出现，**慢了就无用** |
| **双工** | 坐席说话时不能打断 |
| **录音与留存** | **合规重点**（见 §8） |
| **降级** | ASR/TTS/LLM 任一不可用 → 转人工或走 IVR 菜单 |

### 1.4 一个容易忽略的指标

**「AI 让坐席更忙了」= 失败的自动化。**
监控指标必须包含：

```
AI 辅助下的单通话处理时长  vs  无 AI 时的处理时长
```

> 这个指标比「AI 介入率」重要得多。参见
> [`../12-AI落地方法论与FDE实战/03-试点-影子-灰度-规模化.md`](../12-AI落地方法论与FDE实战/03-试点-影子-灰度-规模化.md) §3.5。

## 2. 场景二 · 语音助手

### 2.1 端云分工（这是本库 04 + 10 主线结论的应用）

```
┌──────────── 端侧 ────────────┐        ┌────────── 云端 ──────────┐
│ 唤醒词（离线、固定小模型）        │        │ 意图理解 / 复杂问答         │
│ 降噪 / AEC / VAD               │──音频──▶│ 工具调用 / 多轮上下文        │
│ 端侧 ASR（可选，简单指令）        │◀─文本─│ TTS（高质量音色）            │
│ 简单命令直接执行                │        │                            │
└────────────────────────────────┘        └────────────────────────┘
```

| 放端侧 | 放云端 |
|---|---|
| **唤醒词**（必须离线——不能每次都联网听） | 复杂问答 |
| **VAD / AEC / 降噪**（省带宽） | 工具调用与上下文 |
| **简单指令**（开灯、播放音乐） | 高质量 TTS |
| **隐私数据处理** | 需要知识库的问答 |

> **唤醒词必须离线**是硬约束——
> 如果唤醒需要联网，那设备在没网时就是砖头，而且**隐私上不可接受**（一直在录音上传）。

### 2.2 关键指标

| 指标 | 说明 |
|---|---|
| **唤醒准确率 / 误唤醒率** | **误唤醒是体验杀手**（电视声、聊天声） |
| **唤醒延迟** | 通常要求 < 500 ms |
| **端到端响应延迟** | < 1 s 为佳 |
| **打断体验** | 能否在播放时插话 |

## 3. 场景三 · 面试与培训评估

**这是最需要「证据回指」的场景**，也是本库 08 主线思想的延伸。

### 3.1 链路

```
录音（告知同意）──▶ VAD 分段 ──▶ ASR（含时间戳）
                                    ↓
                        按问题维度切片
                                    ↓
                     LLM 按维度评分（★ 证据必须可回指）
                                    ↓
                        结构化报告 + 原文引用
```

### 3.2 三个必做设计

| # | 设计 | 说明 |
|---|---|---|
| **1** | **评分必须逐条回指原文**（含时间戳） | 没有回指的评分不可信、不可复核、不可申诉 |
| **2** | **维度独立评分** | 每个能力维度单独评，不要混在一个大提示里 |
| **3** | **锚点题集校准** | 一组固定的锚点题，模型版本变更后重跑校准 |

### 3.3 与 08 主线的对照

```
08-AI招聘应用 的四段流水线：屏蔽 → 硬过滤 → 打分 → 结论
                              ↓
语音面试的对应：      同意核验 → 硬性条件 → 分维度打分 → 结构化结论
```

> **语音场景比文本场景多两个风险**：
> 1. **ASR 错误会污染评分**（「抗压能力」的答案被听错）→ **评分时用原文+时间戳，让复核者可听**
> 2. **语气与停顿可能带偏见** → **评分维度尽量用内容证据，不用语气特征**

> **第 2 点尤其重要**：
> 用「语速慢」「声音发抖」这类声学特征做评分，
> **既不可靠也容易构成歧视**。这与 08 主线里「敏感字段屏蔽 + 偏差审计」是同一条原则。

### 3.4 合规（重点）

| 要求 | 说明 |
|---|---|
| **事前告知同意** | 录音前明确告知用途、时长、存储、谁能看到 |
| **数据最小** | 只保留必要的录音与转写 |
| **留存期限** | 明确期限并自动删除 |
| **访问控制** | 录音与报告的访问权限 |
| **申诉机制** | 被评估者有权查看依据并申诉 |
| **不得用于声纹识别** | 除非单独授权 |

> **面试录音涉及个人信息与（可能）生物识别信息**，
> **具体要求以适用法规与合规意见为准**（见 §8 与
> [`../15-AI安全红队与合规工程/06-合规工程落地.md`](../15-AI安全红队与合规工程/06-合规工程落地.md)）。

## 4. 场景四 · 会议记录与转写

### 4.1 链路

```
音频 ──▶ VAD 分段 ──▶ ASR（流式）──▶ 说话人分离 ──▶ 说话人归属
                                                    ↓
                              摘要 / 待办 / 决策点抽取
```

### 4.2 说话人分离（Diarization）

**把「谁说了什么」对应起来**——这是会议场景的核心难点。

| 方法 | 说明 |
|---|---|
| **声纹聚类** | 提取说话人嵌入 → 聚类 → 给每段分配说话人 |
| **监督式分离** | pyannote 之类，直接输出说话人标签 |
| **重叠语音分离** | 多人同时说话时分离（**更难**） |

**难点**：

| 难点 | 表现 |
|---|---|
| **重叠语音** | 两个人同时说话 → 无法准确归属（**会议室最常见**） |
| **远场** | 会议桌远端的人声音小 |
| **声线相似** | 亲属、同性别同年龄 |
| **串音** | 手机放桌上，有人用它外放 → 混进来 |

### 4.3 关键指标

| 指标 | 说明 |
|---|---|
| **DER**（Diarization Error Rate） | 说话人分离错误率（越小越好） |
| **说话人归属准确率** | 业务视角：谁说的话对不对 |
| **摘要事实一致性** | 摘要里的结论**是否在原文里能找到依据**（同 08 主线的证据回指） |
| **待办项召回率** | 该记的有没有记下 |

> **摘要的「事实一致性」要用「回指」来测**——
> 让模型给每条结论标出原文出处，人工核对。
> **没有回指的会议纪要不可信**——这是 LLM 摘要最常见的失败。

## 5. 评测体系

### 5.1 分层指标

| 层 | 指标 | 工具 |
|---|---|---|
| **① 音频前端** | 唤醒误触发率、VAD 漏检/误检 | 自建 |
| **② ASR** | **CER / WER**（带归一化规则） | 评测集 |
| **③ 说话人分离** | **DER** | pyannote 等 |
| **④ TTS** | **MOS / UTMOS**、**SECS**、**ASR 回读 WER** | 主观 + 自动 |
| **⑤ 端到端任务** | **任务成功率**、**人工接管率**、**转人工率** | 业务评测集 |
| **⑥ 体验** | **首包延迟**、**端到端延迟**、打断成功率 | 压测 |
| **⑦ 成本** | **每分钟通话成本**、每百次会话成本 | 账单 |

### 5.2 端到端评测集怎么建

**用真实场景的录音 + 「这件事到底算不算成功」的判定**：

```
输入：录音 + 场景上下文
期望：任务是否完成 + 完成方式（自助/转人工）
      + 若失败，失败原因分类
```

**失败原因分类（这是最有用的一张表）**：

| 原因 | 归属环节 |
|---|---|
| 没唤醒 / 误唤醒 | 前端 |
| **ASR 听错** | ASR |
| **端点切错**（说一半被截断） | VAD |
| **意图理解错** | LLM / 意图模型 |
| **工具调用错**（参数/选错工具） | Agent 层 |
| **TTS 说得难懂/太长** | TTS / 提示词 |
| 用户主动放弃 | 体验 / 超时 |

> **这张表让「端到端成功率低」变成「具体哪个环节低」**——
> 否则只能笼统地调模型。

### 5.3 主观评测怎么做

| 项 | 做法 |
|---|---|
| **AB 盲测** | A/B 两个系统的输出随机顺序呈现，评测员不知道来源 |
| **评分维度** | 自然度 / 可懂度 / 语气匹配 / 任务完成度 |
| **样本量** | 每个条件 ≥ 30 条（**少于这个数的 MOS 差异不可信**） |
| **一致性** | 多人评测时算 **Krippendorff's alpha**，低于 0.6 说明评分标准不清晰 |

## 6. 成本模型

### 6.1 每分钟通话的成本拆解

```
每分钟成本 = ASR(按分钟) + LLM(按 token) + TTS(按字符) + 线路/平台费
```

| 项 | 计量 | 特点 |
|---|---|---|
| **ASR** | 音频分钟 | **便宜**，流式按实际时长 |
| **LLM** | 输入/输出 token | 语音对话的 token 比文本多（要复述上下文） |
| **TTS** | **字符数** | **通常最贵**；用户打断能直接省 |
| **线路/云通信** | 分钟 | 不可省 |

### 6.2 降本顺序

| 顺序 | 手段 | 效果 |
|---|---|---|
| 1 | **用户打断即停止 TTS 合成** | **大**（语音独有） |
| 2 | **短回复**（提示词约束 + 长度上限） | 大 |
| 3 | **简单意图用小模型** | 中 |
| 4 | **缓存固定语音**（转人工提示语等） | 中 |
| 5 | **TTS 用小模型**（简单场景） | 中 |

### 6.3 一个反直觉的账

**「语音机器人」不一定比「人工便宜」**：

```
语音机器人：每分钟 $X，但有 <100% 的自助解决率
人工坐席：每分钟 $Y（人力 + 线路），解决率 ~85%

如果 X 的 10 倍 > Y，机器人就不划算
```

> **自助解决率是分母**——
> **只讲「每分钟成本」而不讲「解决率」的对比是无意义的。**
> 这个账要跟 12 主线的成本测算模板一起用。

## 7. 部署形态

| 形态 | 适合 | 说明 |
|---|---|---|
| **全云** | 呼叫中心、需要强 TTS 音色 | 简单；延迟含网络 |
| **端云混合** | **助手类**（音箱/车机） | 唤醒与简单指令在端 |
| **全端** | 涉密、离线 | **质量受限**，但隐私最好 |
| **私有化** | 数据不能出院 | 与 04/12 主线一致 |

> **语音的隐私特殊性**：
> **麦克风一直开着** = 持续采集环境音。
> **这在办公场所是敏感的**（会录到同事的谈话）。
> **必须有明确的采集指示（灯光/提示音）**——这是产品设计的硬要求，不是可选项。

## 8. 合规

> **⚠️ 以下为工程视角的梳理，不构成法律意见。**
> 具体要求以适用法规与法务意见为准。

### 8.1 录音与采集

| 事项 | 工程要求 |
|---|---|
| **告知同意** | 录音/转写前的明确告知（语音播报 + 界面 + 书面） |
| **采集指示** | **麦克风开启必须有可见指示**（灯光/提示音/界面状态） |
| **数据最小** | 只采集必要的音频与转写 |
| **留存期限** | 明确期限 + 自动删除机制 |
| **访问控制** | 录音、转写、报告的分级权限 |
| **跨境** | 数据处理方在境内还是境外 |

### 8.2 声音克隆与合成

| 事项 | 要求 |
|---|---|
| **被克隆者的授权** | **必须有书面授权**——声音具有人格利益 |
| **用途限制** | 授权书里写明用途与期限 |
| **禁止冒用** | 不得用于冒充本人做未经授权的陈述 |
| **标识** | 合成语音应有可感知或可检测的标识（**具体要求以官方发布为准**） |
| **不得用于伪造** | 不得用于伪造他人陈述、绕过身份验证 |

> **「用 AI 复刻某个人的声音」在多数法域已被专门关注**——
> 即使技术可行，**没有书面授权的克隆在商业上是不可用的**。

### 8.3 语音作为生物识别信息的边界

| 用途 | 风险 |
|---|---|
| **用声纹做身份认证** | 声纹是**生物识别信息**，处理要求更高（单独同意等） |
| **用声学特征做情绪/性格判断** | **推断敏感属性**，风险高且易涉偏见 |
| **用语气特征做能力评分** | **同 08 主线的敏感特征问题**——不可靠且易歧视 |

> **工程结论**：**声纹只用于「本人认证」（有明确授权），
> 不要用于「评估人」（如面试评分、情绪识别）**。

## 9. 常见错误

| 错误 | 表现 | 纠正 |
|---|---|---|
| **用 ASR 准确率验收业务项目** | 指标与目标错位 | 按场景选**端到端任务成功率** |
| **忽略端点截断** | 用户说一半被切 | hangover + 合并窗口 + 语义端点 |
| **自我打断** | 系统说话时自己停 | **先查 AEC** |
| **TTS 数字读错** | 金额、日期读错 | **预处理规则表** |
| **不缓存固定语音** | 每句「转人工请按 1」都合成 | 预合成缓存 |
| **摘要无回指** | 纪要里的结论无法核实 | **强制证据回指** |
| **用语气特征评分** | 偏见与不可靠 | **只用内容证据** |
| **无采集指示** | 办公场景的隐私事故 | 灯光/提示音是硬要求 |
| **未取得声音克隆授权** | 法律风险 | **书面授权书** |
| **成本只算单分钟** | 忽略解决率 | 用**每分钟 × 解决率**对比 |

## 10. 工程结论

1. **四个场景技术栈相似但关键指标完全不同**——
   **拿 ASR 准确率验收面试评分项目，必然对不齐。**
2. **「坐席辅助」通常比「语音机器人」更容易落地、价值更确定**（不替代人，风险小）。
3. **端云分工**：**唤醒词必须离线**；VAD/AEC/降噪放端侧省带宽；复杂问答放云端。
4. **语音的隐私特殊性**：**麦克风常开 = 持续采集环境音**，
   **采集指示是硬要求**（会录到同事谈话）。
5. **面试/评估场景必须证据回指（含时间戳）**，且**只用内容证据、不用语气特征**。
6. **会议场景的说话人分离（DER）是核心指标**；重叠语音是主要难点。
7. **端到端失败要按环节归因**（唤醒/ASR/端点/意图/工具/TTS/放弃），
   否则只能笼统调模型。
8. **主观评测要用 AB 盲测 + ≥30 条 + 算评分者一致性**。
9. **成本要按「每分钟 × 解决率」对比**，只比单分钟成本没有意义。
10. **TTS 是最贵的一项**，**用户打断即停止合成**是语音独有的省钱手段。
11. **声音克隆必须有书面授权**；声纹只用于本人认证，不用于评估人。
