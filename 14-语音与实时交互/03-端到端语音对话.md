# 端到端语音对话

> **核心问题**：级联（ASR→LLM→TTS）还是端到端？语音对话的延迟预算是怎么分配的？用户打断时怎么办？

---

## 0. 两种架构

```
┌─────────── ① 级联（Cascade）────────────────────────────┐
│  音频 → ASR → 文本 → LLM → 文本 → TTS → 音频 → 输出        │
│  ✅ 每段可替换、可观测、可缓存；LLM 能力最强                 │
│  ❌ 延迟累加；**韵律与情绪信息在转文本时丢失**                │
└───────────────────────────────────────────────────────────┘

┌─────────── ② 端到端（End-to-End）───────────────────────┐
│  音频 → Audio Token → LLM/Transformer → Audio Token → 音频 │
│  ✅ 首包快；**保留韵律与语气**；能理解「话里的信息」          │
│  ❌ 难观测、难控制、成本高、评测难                            │
└───────────────────────────────────────────────────────────┘
```

### 0.1 怎么选

| 维度 | 级联 | 端到端 |
|---|---|---|
| **首包延迟** | 慢（要等 ASR + LLM + TTS） | **快** |
| **韵律/情绪传递** | **丢失**（转成文本了） | **保留** |
| **可观测性** | **好**（每段都能看） | 差（黑箱） |
| **可控性** | **好**（能约束 ASR 与 TTS） | 差 |
| **成本** | **可分项优化**（小模型做 ASR/TTS） | 整体成本高 |
| **能力上限** | **高**（用最强 LLM） | 取决于模型 |
| **工具调用** | **好**（文本工具调用成熟） | 需要额外设计 |

> **实用判断**：
> **需要工具调用、需要审计、需要控制合规 → 级联。**
> **追求极致自然、需要理解语气 → 端到端。**
> **当前生产环境里，级联仍是主流**——不是因为更好，而是因为**可控**。

## 1. 级联架构的延迟账

**这是本章最实用的部分。** 一次「用户说完 → 听到回复」的总延迟：

```
总延迟 = 尾点检测延迟 + ASR 延迟 + LLM 首 token + TTS 首包
```

| 环节 | 典型值 | 优化手段 |
|---|---|---|
| **尾点检测（等用户说完）** | 200~800 ms | 语义端点；**但这是「自然」与「快」的取舍** |
| **ASR** | 100~300 ms | 流式 ASR；小模型 |
| **LLM 首 token** | 200~800 ms | 短 prompt、prompt 缓存、小模型 |
| **TTS 首包** | 50~200 ms | 流式 TTS（**首包远小于全量**） |
| **合计** | **550 ms ~ 2.1 s** | |

> **对话延迟的经验阈值**：
> - **< 300 ms**：感觉像「本地对话」，很自然
> - **300~800 ms**：可接受
> - **800 ms ~ 1.5 s**：能忍，但会感觉慢
> - **> 2 s**：**用户会重复说话或以为系统没听见**
>
> **人类对话的自然 turn-taking 间隔约 200 ms**——
> 这是「像真人」的物理参照。

### 1.1 一个重要的事实：尾点检测占了大头

**很多人优化 ASR 和 TTS，却忽略了「等用户说完」这一段。**

| 端点策略 | 尾点延迟 | 风险 |
|---|---|---|
| **固定静音阈值**（如 500ms 静音） | 短 | **说慢的人被截断** |
| **静音 + 最长时长** | 中 | 仍可能截断 |
| **语义端点（SEM）** | **长**（要判断语义是否完整） | **不截断**，但慢 |
| **混合**（静音 300ms + 语义确认） | 中 | 推荐 |

> **「说慢的人被截断」是语音产品的第一大差评来源。**
> **必须支持「继续说」的机制**——检测到用户继续说话时，**丢弃上一轮的转写并合并**。

### 1.2 TTS 的首包 vs 全量

```
全量 TTS：一段 50 字的回复 → 整段合成 → 播放     总延迟 = 合成(2s) + 播放(5s)
流式 TTS：边合成边播放 → 首包 100ms 后就开始播
```

| 方式 | 用户感知延迟 | 适用 |
|---|---|---|
| **流式 TTS** | **首包延迟**（~200ms） | **实时对话必用** |
| 全量 TTS | 首包延迟 = 全量合成时间 | 播报、录音 |

## 2. 全双工与打断（Barge-in）

### 2.1 什么是全双工

**能同时听和说**——而不是「说的时候不听」。

### 2.2 全双工的三个硬问题

| 问题 | 现象 | 解法 |
|---|---|---|
| **自我打断** | **系统自己的 TTS 被麦克风听到**，VAD 判定「用户开始说话」→ 系统停 | **回声消除（AEC）** + **播放期间抑制上报** |
| **打断时机** | 用户在系统说话时插话，什么时候应该停？ | **检测到真实人声 + 持续 N 毫秒**才打断 |
| **上下文丢失** | 打断后，已说的半句话怎么办？ | **保留 TTS 已生成的文本**，作为对话历史的一部分 |

> **「自我打断」是全双工最常见的事故**——
> 系统说到一半突然停住，用户完全不知道为什么。
> **排查顺序**：先看 AEC 有没有生效 → 再看 VAD 阈值 → 最后才调模型。

### 2.3 打断的正确处理流程

```
用户开始说话
   ↓
① AEC 回声消除（去掉系统自己的声音）
   ↓
② VAD 检测真实人声
   ↓
③ 取消正在进行的 TTS 播放（保留已合成文本）
   ↓
④ 丢弃本轮不完整的 ASR 结果
   ↓
⑤ 合并为新的输入
   ↓
⑥ 正常响应
```

> **第 ③ 步的细节很重要**：
> **已合成但未播放的文本不能丢**——
> 它是系统已经「说过」的内容，必须进对话历史，
> 否则用户会听到系统说过的话，但系统自己不记得。

## 3. 语音 Agent 的特殊性

**把文本 Agent 搬到语音上，会遇到五个新问题。**

### 3.1 工具调用需要「说出来」

**文本 Agent 的工具调用是静默的；语音 Agent 必须告知用户。**

```
文本：用户："查一下订单 12345"
      → [工具调用: get_order(12345)]  ← 用户看不见
      → "您的订单已发货"

语音：用户："查一下订单 12345"
      → "好的，我帮您查一下"          ← ★ 必须说出来
      → [工具调用]
      → "您的订单已发货，预计明天到达"
```

**带来两个新问题**：

| 问题 | 处理 |
|---|---|
| **工具调用要花时间**（可能 1~3 秒） | **必须先说一句过渡语**（「稍等，我查一下」），否则用户以为卡死 |
| **确认动作要能被听见** | 「确认要取消订单吗？请说'确认'」 |

### 3.2 错误难以察觉与纠正

| 问题 | 说明 |
|---|---|
| **ASR 可能识别错** | 用户说「删除订单」，识别成「删除预订单」——**用户完全不知道** |
| **系统提示听不到** | 文本 Agent 可以塞一大段系统提示；语音里说一大段是灾难 |
| **长回复听不下去** | 用户会打断或走神 |

**对策**：

| 对策 | 说明 |
|---|---|
| **高风险操作复述确认** | 「我理解您要**删除**订单 12345，回复'确认'以继续」——**关键信息用不同节奏/重音** |
| **输出长度控制** | 单次回复 ≤ 2~3 句；复杂内容**分段输出**（每段间留停顿） |
| **提供文字通道** | 重要信息同时给文字（短信/界面/邮件） |
| **错误自我纠正** | 「抱歉，我刚才听成了…，您是说…吗？」 |

> **「复述确认」是语音场景的安全底线**——
> 文本界面里用户能看见，语音里**必须说出来让用户有机会纠正**。

### 3.3 成本是三份

```
一次语音对话 = ASR 成本 + LLM 成本 + TTS 成本
```

| 项 | 特点 |
|---|---|
| **ASR** | 按音频时长计（通常便宜） |
| **LLM** | 与文本 Agent 相同（但**多轮语音的 token 更多**，因为要复述上下文） |
| **TTS** | 按字符计（**通常是最贵的一项**） |

**成本优化的顺序**：

| 手段 | 说明 |
|---|---|
| **流式 TTS + 提前打断** | 用户打断后立刻停止合成 → **直接省掉未播放部分的成本** ⭐ |
| **短回复** | TTS 成本 ∝ 字符数 |
| **缓存固定语料** | 「转人工请说 1」这类固定语音可缓存 |
| **小模型做 TTS** | 简单场景 |

> **「用户打断后停止合成」是语音场景独有的省钱手段**——
> 文本 Agent 没有这个问题（因为没有流式输出）。

## 4. 语音提示词工程

**语音 prompt 和文本 prompt 是两套东西。**

| 规则 | 说明 |
|---|---|
| **输出是「说出来的」，不是「写出来的」** | 不要用 markdown 表格、代码块、列表符号 |
| **短句** | 一句话一个意思 |
| **数字要能被听懂** | 「共 3 项」而不是「共 3 项（详见附件）」 |
| **不要在语音里给长列表** | 「有 3 个问题：第一…第二…第三…」，每项之间停顿 |
| **明确标记动作** | 「（正在查询，请稍等）」这类旁白可以由系统自动插入 |
| **不要让模型输出结构** | 需要结构化信息时，**在 TTS 之前用另一个模型生成结构，再转成口语** |
| **给出否定/澄清的话术** | 「抱歉，我没听清，您能再说一遍吗？」 |

### 4.1 「结构化 → 口语」的两段式

```
用户问题
  ↓
LLM A（结构化输出，JSON）：{"summary": "...", "items": ["...", "..."]}
  ↓
LLM B 或模板（转口语）："好的，我查到三件事。第一，…；第二，…；第三，…"
  ↓
TTS
```

| 做法 | 优点 | 缺点 |
|---|---|---|
| **单次 LLM 直接出口语** | 简单、快 | **格式不稳定**，可能漏项、可能说错数字 |
| **两段式（结构 → 口语）** | **可靠、可校验** | 延迟 +200~400 ms |

> **对可靠性要求高的场景（客服、政务、医疗）用两段式**；
> 对延迟敏感的场景用单次，但**要加兜底**（检测到 JSON 异常就重试或降级）。

## 5. 语音 Agent 的架构建议

```
┌──────────────────────────────────────────────────────┐
│  ① 音频采集（回声消除 + 降噪 + AGC）                    │
│      ↓                                                │
│  ② VAD（切出语音段）                                    │
│      ↓                                                │
│  ③ 流式 ASR（实时轨）+ 离线 ASR（最终轨）                │
│      ↓                                                │
│  ④ 意图判断 + 上下文管理                                │
│      ├─ 简单问题 ──→ 直接回答                            │
│      └─ 需工具 ──→ 先说过渡语 → 工具调用 → 组织答案        │
│      ↓                                                │
│  ⑤ 流式 TTS（首包 < 200ms）                             │
│      ↓                                                │
│  ⑥ 播放 + 全双工打断处理                                │
└──────────────────────────────────────────────────────┘
```

**六条工程建议**：

| # | 建议 | 原因 |
|---|---|---|
| 1 | **实时轨 + 最终轨分离** | 兼顾体验与准确性 |
| 2 | **AEC 必须用对** | 自我打断是头号事故 |
| 3 | **工具调用前先说过渡语** | 避免用户以为卡死 |
| 4 | **高风险操作必须复述确认** | ASR 会错，用户看不见 |
| 5 | **打断后立刻停止 TTS 合成** | 直接省钱 + 体验正确 |
| 6 | **提供文字通道** | 重要信息双通道 |

---

## 6. 工程结论

1. **级联 vs 端到端**：**需要工具调用、审计与合规 → 级联**（当前生产主流）；
   追求极致自然与语气理解 → 端到端。
2. **延迟账要算全**：`尾点检测 + ASR + LLM 首 token + TTS 首包`。
   **尾点检测往往是大头**，而它最容易被忽略。
3. **「自然对话」的阈值约 800 ms**；**超过 2 秒用户会以为系统没听见**。
4. **流式 TTS 是实时对话必用**——它把感知延迟从「全量合成」降到「首包」。
5. **全双工的三个硬问题**：自我打断（先查 AEC）、打断时机、上下文丢失。
   **已合成但未播放的文本不能丢**，它是对话历史的一部分。
6. **语音 Agent 的工具调用必须「说出来」**，并先给一句过渡语。
7. **高风险操作必须复述确认**——语音里用户看不见，必须说出来给他纠正的机会。
8. **成本是三份**，而 **TTS 通常最贵**；
   **「用户打断后立刻停止合成」是语音独有的省钱手段**。
9. **语音 prompt 要短句、无结构**；可靠性要求高的场景用**「结构化 → 口语」两段式**。
10. **提供文字通道**——重要信息双通道，别让用户只能靠听。
