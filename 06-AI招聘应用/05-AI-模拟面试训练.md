# 05 · AI 模拟面试训练

> **一句话：模拟面试的产品价值不在「像真人」，在「可重复、可控、便宜」——
> 同一份简历、同一套模型，每位候选人被问到同样的题，评分口径完全一致。**

配套实现：[`code/hr-agent/`](../code/hr-agent/)　离线评测当前基线：
6 题覆盖 6 个能力维度、每题都有原话引用、0 个 issue。

---

## 0. 需求：两类用户，两套产品

| | **候选人自助练** | **招聘方用作筛选** |
|---|---|---|
| 用户 | 求职者 | HR / 用人经理 |
| 目标 | 补短板、练表达、测手感 | 补充简历筛查，给出可比的维度分 |
| 题量 | 不限，按岗位练 | 固定 5~8 题 |
| 反馈 | 详细（逐题建议 + 示范答法） | 简要（维度分 + 风险点） |
| 允许看答案 | 练完后可看 | 不可 |
| 公平性要求 | 低（是练习） | **高（结论进档案）** |
| 合规要求 | 低 | **高（等同 04 篇的自动化决策约束）** |

**这两类不要用同一套产品。** 面向候选人的版本可以给建议、可以鼓励；
面向招聘方的版本必须冷静、可追溯、结论必须人工复核。

## 1. 产品形态与流程

```
       JD / 能力模型
            │
            ▼
      ┌───────────┐
      │  出题计划  │  绑定维度、控制题量与难度分布
      └─────┬─────┘
            ▼
      ┌───────────┐      ┌──────────────┐
      │  逐题面试  │ ───▶ │  追问（可选）  │  答得浅 → 追问补充
      └─────┬─────┘      └──────┬───────┘
            ▼                     │
      ┌───────────┐                │
      │  逐维打分  │ ◀──────────────┘
      └─────┬─────┘
            ▼
      ┌───────────┐
      │  反馈报告  │  亮点 / 缺口 / 建议 / 下一轮练什么
      └───────────┘
```

代码在 `code/hr-agent/hragent/interview.py`，状态机是
`plan → answer → (follow_up) → evaluate`。

## 2. 出题引擎

### 2.1 每道题必须绑定一个能力维度

```python
@dataclass
class Question:
    dimension: str        # 能力 key
    level: int            # 考察水平 1~5
    question: str
    expected_points: list[str]   # 期望考察的要点
    follow_up: str
```

**「每题绑定维度」是硬约束**，代码里有对应断言：

```python
for q in session.plan:
    if model.competency(q.dimension) is None:
        result.all_questions_bound = False
        result.issues.append(f"题目维度 {q.dimension} 不在能力模型内")
```

没有维度的题 = 无法评分 = 一次无效提问。

### 2.2 题目顺序：先问高权重与必备维度

```python
ordered = sorted(model.competencies, key=lambda c: (not c.required, -c.weight, c.key))
```

先问最重要的，是真人面试的通行做法，也是**控制总时长**的关键 ——
时间不够时，砍掉的都是低权重维度，不是随机砍。

### 2.3 题库 vs 生成

| | 静态题库 | 模型生成 |
|---|---|---|
| 可比性 | 高（所有人问一样的） | 低（每次不一样） |
| 覆盖度 | 受限于题库编写 | 高 |
| 难度控制 | 精确 | 需要额外约束 |
| 成本 | 一次性编写 | 每次生成 |
| 抗刷题 | 低（题库会被传出去） | 高 |

**建议：题库为主、模型补充。** 核心维度用固定题（保证可比），
模型只负责生成「换个说法」和追问（保证新鲜感）。

本仓库的规则后端就是这么做的：`QUESTION_BANK` 是 17 个维度的固定题库，
模型后端 `LlmInterviewerBackend` 负责动态出题。

### 2.4 好问题的三个特征

1. **能引出具体经历**：「请描述一次你处理交期延误的完整过程，谁在什么节点给了你什么信息？」
2. **不能背**：问「你最大的优点是什么」毫无信息量；
3. **有明确的判分依据**：`expected_points` 写清楚要找什么。

## 3. 追问策略

### 3.1 追问是模拟面试的价值所在

第一轮回答几乎都是「准备过的版本」。**追问才是区分候选人的地方。**

三种追问时机：

| 情况 | 现象 | 追问方向 |
|---|---|---|
| **信息不足** | 回答太短、太泛 | 「能补充一个具体的事例或数字吗？」 |
| **有细节可挖** | 提到了具体的人/时间/数字 | 顺着细节追问（规则后端：`question.follow_up`） |
| **逻辑断层** | 结论与过程对不上 | 「这个结论是怎么得出来的？」 |

### 3.2 规则后端的追问启发式

```python
def follow_up(self, question, answer, model):
    stripped = answer.strip()
    if len(stripped) < 20:
        return "这个回答比较简短，能补充一个具体的事例或数字吗？"
    if len(stripped) < 60:
        return ""
    return question.follow_up or ""
```

三档：**过短 → 追问补充；中等 → 不追问；充分展开 → 顺着细节追问。**

> **工程结论**：追问要有上限。真人面试一轮 1~2 个追问是常态，
> 每题都追问会让人疲劳，也会把成本推到不可控。本仓库每个问题最多追问一次。

### 3.3 模型后端的追问要用「基于回答内容」而不是「基于简历」

追问要顺着**候选人刚说的话**，而不是回到简历里的信息 ——
否则就变成 AI 在替候选人复习自己的简历。

## 4. 评分模型

### 4.1 逐维度打分，不给总分

```python
@dataclass
class DimensionScore:
    dimension: str
    level: int      # 1~5
    score: float
    comment: str
    evidence: str   # 候选人原话
```

**「评分必须能引用原话」和 04 篇的「证据必须能回指原文」是同一条原则**：
能追溯到具体表述的评价才有意义。

### 4.2 规则后端的评分口径

```python
hit = [p for p in points if p.lower() in text.lower()]
coverage = len(hit) / len(points)
has_number = any(ch.isdigit() for ch in text)
level = 1 + int(round(coverage * 3.0)) + (1 if has_number and coverage >= 0.5 else 0)
```

三个信号：**要点覆盖度** + **是否有具体数字** + **是否达到要求水平**。

「回答里有数字」这个信号看起来粗糙，但区分度很高 ——
「我负责跟单」和「准时交付率 96%，我每周跟一次生产进度」是两种回答。

### 4.3 综合分与建议

```python
overall = Σ(score × weight) / Σweight × 100
recommendation = "推荐进入下一轮" if overall >= 75 else \
                 "有条件推荐（需补充薄弱维度证据）" if overall >= 55 else "不推荐"
```

**建议语要保守。** 「有条件推荐（需补充薄弱维度证据）」比「基本符合要求」有用得多 ——
它直接告诉复核者下一步该做什么。

### 4.4 报告必须有的四段

| 段 | 内容 |
|---|---|
| 逐维度评分 | 维度 / 水平 / 评价 / **候选人原话** |
| 问答记录 | 完整 Q&A，可回看 |
| 亮点 | 具体到维度（`客户开发（5/5）`） |
| 待补强 | 具体到维度（`供应链与物流（2/5）`） |

「待补强」必须具体到维度。写「经验不足」等于没写 ——
它不能指导候选人下一轮练什么。

## 5. 语音链路（要诚实面对的边界）

如果要做「像真人一样说话」，就要接 ASR + TTS。

### 5.1 链路与延迟预算

```
麦克风 → VAD 断句 → ASR → LLM（流式） → TTS → 扬声器
```

| 环节 | 典型延迟 | 优化 |
|---|---|---|
| 端点检测（VAD） | 200~500ms | 静音阈值自适应 |
| ASR | 300~800ms | 流式识别，边说边出 |
| LLM 首 token | 500~2000ms | 思考深度调档 + 提示缓存 |
| TTS 首包 | 100~300ms | 句子级流式合成 |
| **合计（可感知）** | **1.1~3.6s** | 目标：**< 1.5s 才有对话感** |

**超过 2 秒的延迟会让面试体验崩掉** —— 人会以为卡住了，然后重复说话。

### 5.2 语音带来的三个额外问题

| 问题 | 说明 | 处置 |
|---|---|---|
| **ASR 错字影响评分** | 关键词匹配建立在转写文本上 | 评分用转写，但**把 ASR 置信度低的片段标注出来** |
| **打断与重叠** | 真人会打断，ASR 难处理 | 用 VAD + 静音检测兜底，允许「打断即停」 |
| **非语言信息丢失** | 语速、停顿、紧张度 | 初期**不要**试图分析情绪 —— 容易变成伪科学且有合规风险 |

### 5.3 不要一开始就做语音

文本模拟面试已经能覆盖 80% 的价值（题目、追问、评分、报告）。
**先把评分质量做扎实，再上语音。** 顺序反了会得到一个「说话很流畅但评分很水」的产品。

## 6. 评测体系

### 6.1 三类指标

| 类 | 指标 | 口径 |
|---|---|---|
| **出题质量** | 维度覆盖率 | 出题覆盖的能力维度数 / 岗位模型维度数 |
| | 题目绑定正确率 | 题目维度 ∈ 岗位模型的比例（必须 100%） |
| | 难度分布合理性 | 题目水平与期望水平的匹配度（人工抽检） |
| **评分质量** | 评分一致性 | 同一份回答多次评分的一致率 |
| | 评分与人工的相关性 | 模型分 vs 人工分的相关系数/一致率 |
| | 证据引用率 | 维度评分里有原话的比例（必须 100%） |
| **体验** | 平均完成时长 | 出题到报告的总时长 |
| | 追问次数 | 每题平均追问数（上限 1） |
| | 重测稳定性 | 同一人两次模拟的分数波动（应 < 5 分） |

### 6.2 当前离线基线

| 指标 | 结果 |
|---|---|
| 题数 | 6（上限内） |
| 维度覆盖 | 6 / 13（岗位模型维度） |
| 题目绑定正确率 | 100% |
| 证据引用率 | 100% |
| 追问触发 | 6 次（每题 1 次） |
| issue 数 | 0 |

### 6.3 评分一致性怎么测

**这是模拟面试最容易被糊弄过去的指标。** 做法：

1. 准备 50~100 条真实（脱敏）回答；
2. 同一份回答用同一模型评 3 次 → 测**自身稳定性**；
3. 换个模型版本再评 → 测**跨版本稳定性**；
4. 人工标注一次 → 测**与人的一致性**。

**第 3 项最容易被忽略**：换模型版本后评分整体漂移，历史数据就不可比了。
做法是每次换版本时**用固定的锚点集重标定**。

## 7. 成本

### 7.1 一次 20 分钟模拟面试的模型成本

口径：12 轮对话，输入从 8K 增长到 30K（均值 18K），每轮输出 300 token。

| 模型 | 输入成本 | 输出成本 | 合计 |
|---|---|---|---|
| Opus 5.5 | $0.864 | $0.072 | **≈ $0.94** |
| Sonnet 5.5 | $0.432 | $0.036 | **≈ $0.47** |
| Haiku 5.5 | $0.0216 | $0.0018 | **≈ $0.023** |

### 7.2 语音才是成本大头

| 项 | 单价量级 | 20 分钟一次 |
|---|---|---|
| 模型（Sonnet 5.5） | — | ≈ $0.47 |
| 云 ASR | $0.006~$0.02 / 分钟 | $0.12~$0.40 |
| 云 TTS | $0.01~$0.03 / 分钟 | $0.20~$0.60 |
| **合计（语音版）** | | **≈ $0.8~$1.5** |

**语音成本是模型成本的 1~3 倍。** 所以：

1. 先做文本版（成本 1/2，延迟 1/5）；
2. 语音版只做「需要练表达」的岗位（销售、客户成功），不做全量；
3. 长回答可以少输出，但**不能靠少提问省成本** —— 那是牺牲产品价值。

### 7.3 缓存能省多少

系统提示（角色 + 评分标准 + 能力模型）约 2,000 token，每轮都要发。
打上缓存断点后，这部分按 **0.1× 输入价** 计：

| | 未缓存 | 缓存后 |
|---|---|---|
| Sonnet 5.5 单轮 | ≈ $0.046 | ≈ $0.046 − $0.0002 ≈ **−0.4%** |

**缓存对短对话几乎没用。** 因为对话的主要成本是**增长中的历史**，
而历史每轮都在变，缓存不了。

> **工程结论**：**长对话靠压缩，不靠缓存。**
> 缓存优化的是「不变的前缀」，而长对话的瓶颈是「不断增长的后缀」。
> 这是很多人在成本优化里走反了的地方。

## 8. 风险与伦理

| 风险 | 说明 | 处置 |
|---|---|---|
| **题目外泄** | 题库被分享 → 背题 | 题目参数化 + 追问随机化；接受一定外泄，靠追问区分 |
| **自欺评分** | 模型给自己打高分 | 评分与出题分离；用人工标注集校准 |
| **训练污染** | 候选人用 AI 优化答案 | 追问深挖细节；关注「是否本人做过」 |
| **口音/表达偏见** | 语音版可能对非母语者不友好 | 文本版为主；语音版避免评价表达流畅度之外的特质 |
| **结论进档案** | 分数变成对候选人的长期标签 | 明确保留期限；提供删除与申诉通道 |
| **心理压力** | 模拟面试也让人紧张 | 明确标注「这是练习不是正式评价」 |
| **合规** | 自动化决策 | 与 04 篇同一套约束：人工复核、可解释、留痕 |

### 8.1 一条产品伦理提醒

**不要把模拟面试分数直接写进候选人档案而不告知。**
必须明示：这是 AI 辅助评估、依据是什么、可以申诉、保留多久。
偷偷打分再影响录用，是最容易上劳动争议的用法。

## 9. 落地路线

| 阶段 | 周期 | 做什么 | 退出条件 |
|---|---|---|---|
| **P0 文本 MVP** | 3 周 | 题库 + 追问 + 规则评分 + 报告 | 评分与人工一致率 ≥ 60% |
| **P1 模型评分** | 2 周 | 换模型后端 + 证据回指校验 | 证据引用率 100%，一致性 ≥ 75% |
| **P2 规模化题库** | 4 周 | 扩到 20+ 岗位 | 每个岗位独立校准 |
| **P3 语音版** | 4 周 | ASR/TTS + 延迟优化 | 端到端首包 < 1.5s |

**P0 用规则评分起步是对的**：先把「题目—维度—证据—报告」这条链路打通，
再换更强的评分后端。反过来做（一上来就接语音 + 大模型）会同时调试三件东西，
很难定位问题。

## 10. 工程结论

1. 两类用户两套产品：候选人自助练 vs 招聘方筛选，结论强度与合规要求完全不同。
2. 每道题必须绑定能力维度，否则无法评分。
3. 题目顺序按权重与必备性排，时间不够时砍低权重维度。
4. 追问是模拟面试的核心价值，每题最多一次追问。
5. 评分必须逐维度、必须引用原话，不给黑箱总分。
6. 「待补强」要具体到维度，否则不可行动。
7. 先做文本版，语音后做；语音会让成本翻 2~3 倍。
8. **长对话靠压缩不靠缓存** —— 缓存优化前缀，长对话的瓶颈是后缀。
9. 评分一致性要测三次：自身、跨版本、与人工。
10. 不把 AI 分数偷偷写进候选人档案。
