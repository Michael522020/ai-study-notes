# 05 · 客服售后与工单自动化

> **这一章的任务：把「客服」拆成三类问题，指出哪一类可以全自动、哪一类必须留人，并给出退换货判责的可落地做法。**

---

## 1. 三类问题的分界线

「AI 客服」之所以落地难，多半是因为把三类问题混在一起做。

| 类 | 例子 | 特征 | 自动化上限 |
|---|---|---|---|
| **售前问** | 「这个能装 500ml 吗」「有没有黑色」「什么时候发货」 | **答案唯一**，来自商品页与库存 | **高（可全自动）** |
| **售中催** | 「我的货到哪了」「发票什么时候开」 | **答案唯一**，来自订单与物流 | **高（可全自动）** |
| **售后退** | 「收到破损」「发错型号」「七天无理由」 | **答案不唯一**，涉及判责与赔付 | **低（必须留人）** |

**分界线是「答案是否唯一」。**

> **售前售中问的是「事实」，售后问的是「责任」。**
> 让 AI 判断事实很安全；让 AI 判断责任，等于让它承担损失。

---

## 2. 售前：能自动化的部分与前提

### 2.1 三个前提

1. **知识库有结构化版本**——不是一堆 PDF，是**能按字段查的结构**。
2. **答案必须带来源**——买家问「多久发货」，回答里要有「这个 SKU 的备货期是 X 天」而不是模型自己说的。
3. **查不到就转人工**——**不允许猜**。

### 2.2 答案的三种来源与优先级

```
1. 结构化字段（库存、备货期、尺寸表、SKU 属性）→ 最准，程序查
2. 政策文档（退换货规则、发票说明、保养手册）→ RAG 检索 + 引用
3. 历史人工答案（FAQ 库）→ 检索 + 复用
```

**模型的职责是「判断该用哪一类 + 组织语言」，不是「知道答案」。**

### 2.3 必答与禁答

| 类别 | 例子 | 处理 |
|---|---|---|
| **必答（自动）** | 规格、库存、物流、发票政策、保养 | 模板 + 检索 |
| **必答（转人工）** | 「和竞品比怎么样」「能不能定制」「帮我选一个」 | 直接转，不尝试回答 |
| **禁答** | 承诺交期、承诺结果、法律与医疗建议、承诺退款 | 模板拒答 + 转人工 |

**「帮我选一个」是最容易被忽略的必转人工类。**
它看似简单，实则是**推荐决策**，涉及转化率与售后的因果关系——AI 一旦推荐了错的型号，退货与差评都由你承担。

> **客服自动化的一个反直觉结论：能自动回答的问题里，「参数类」比「推荐类」重要得多。**
> 参数问题占了售前咨询的大头且答案唯一；推荐类问题占比小但错误代价高。**先做参数类。**

---

## 3. 多语种客服：三个坑

### 3.1 术语必须和商品页一致

同一款产品在 Listing 叫 `Stainless Steel 304`，客服话术里叫 `304 Stainless Steel`，买家会以为这是两个规格。
**术语表要跨内容与客服共用一份**，见 16 主线。

### 3.2 时区与日期

「本周发货」在不同语言与时区下的含义不同。**所有涉及时间的回答必须带时区与具体日期**（「8 月 14 日前发出」优于「本周」）。

### 3.3 语气要匹配目标市场

- 德语市场：客气、精确、**更接受长回答**；过长或过度热情反而减分。
- 美语市场：直接、结论先行。
- 日语市场：敬语、**道歉与致歉的权重更高**。
- 中东 / 拉美部分市场：**宗教与节假日的表达要特别小心**。

**这不是「翻译」问题，是「本地化」问题。** AI 出草稿，人审或用市场级风格模板。

## 4. 售后判责：把「责任」变成「规则」

这是本章最实操的部分。**判责不能交给模型，但可以交给规则引擎。**

### 4.1 判责所需的最小数据结构

```
订单:
  order_id, sku, 数量, 下单时间, 成交价, 币种
  收货地址国家, 是否含税, 是否含运费
  是否使用过优惠券, 优惠券类型
交付:
  发货时间, 承运商, 运单号, 承诺时效, 实际签收时间, 签收照片
  出库时的商品状态照片, 打包照片, 称重
售后:
  诉求类型, 客户描述, 照片/视频, 客户提交时间, 距签收天数
  客户是否已使用, 使用时长, 是否影响二次销售
```

**没有这些数据，任何自动判责都只能靠模型「看图说话」，风险极高。**

### 4.2 规则引擎的形状

```python
def adjudicate(order, delivery, claim):
    # 第一层：硬性政策（时间窗、法定权利）
    if within_statutory_rights_window(order, claim):
        return "approve", "法定无理由退货期"

    # 第二层：商品责任（我方问题 → 全额退 + 承担运费 + 视情况补发）
    if evidence_shows_product_defect(claim, order):
        return "approve_full", "商品缺陷"

    # 第三层：物流责任（在途损坏 → 我方/承运商承担）
    if claim.type == "damaged_in_transit" and delivery.signed_without_exception:
        return "approve_full", "运输损坏"

    # 第四层：客户责任（使用痕迹 / 超期 / 尺寸选错）
    if evidence_shows_used(claim) or days_since_delivery(order, claim) > policy.window:
        return "deny_with_offer", policy.partial_refund_offer

    # 第五层：证据不足 → 人工
    return "escalate", "证据不足，需人工判定"
```

**关键设计：**
- **规则前置，模型只处理「证据判定」这一个子问题**（如「这张照片能否证明是运输损坏」）。
- **每一层都有明确的 escalation 出口**，不是「模型觉得不像就拒绝」。
- **「我方全责」和「拒赔」是两个不同结论**，拒赔前必须先给一个折中方案（部分退款/退货退款）。

### 4.3 为什么必须给折中方案

**纯拒赔的争议处理成本远高于部分退款。** 一个 50 美元的订单，如果客户差评 + 平台介入 + 品牌受损，实际损失可能超过订单金额本身。

```
拒赔路径的真实成本 = 退款金额差 + 差评成本 + 平台介入成本 + 客服时间 + 品牌稀释
部分退款路径的成本 = 退款金额差 + 客服时间

→ 只要 真实成本差 < 部分退款金额，就该给部分退款。
```

**这个不等式应该由人定阈值并写进政策**，模型只负责执行。

### 4.4 退款金额：必须程序算

```
应退金额 = 成交价
         - 已使用的部分抵扣（按政策折价表）
         - 不可退的运费（按政策）
         + 退回运费补偿（若我方责任）
         + 法定利息/赔偿（若超过法定天数）
```

**注意「法定利息/赔偿」这一项**：很多市场的法定无理由退货期比商家的政策长，超期未退可能要承担利息。**这一项由程序查当地法律后计算，不允许模型判断。**

## 5. 差评处理：唯一不能自动化的是「发声」

### 5.1 差评的分类（先分类，再处理）

| 类型 | 识别 | 处理方向 |
|---|---|---|
| **产品缺陷** | 有实拍、有开箱证据 | 换货/退款 + 产品端反馈 |
| **物流问题** | 包装破损、延迟 | 补发/退款 + 物流端反馈 |
| **预期不符** | 「图片和实物不一样」「比想象的小」 | **多半是 Listing 问题**，改内容而不是道歉 |
| **使用不当** | 明显违反说明 | 礼貌说明 + 指引 |
| **恶意/无关** | 无关内容、竞品引流 | 平台申诉，不公开回应 |

**最有价值的一类统计是「预期不符」的比例**——它直接指向 Listing 与实物不符，是内容问题，不是客服问题。
**「预期不符」占比升高时，要改的是详情页，不是话术。**

### 5.2 公开回复的三条规则

1. **不辩解，先确认事实**（「我们看到您反馈的 X，确实是我们没做好」）。
2. **公开回复里不涉及订单号、姓名、金额**——平台评论是公开的。
3. **公开回复不能承诺具体赔偿**，赔偿走私信。

> **公开评论区的回复会被买家互相看到，它的读者是「其他潜在买家」而不是投诉人。**
> 所以公开回复的真正目标是**让其他买家看到这家店的处理方式**，而不是安抚当事人。
> 这改变了写法：公开回复要**展示流程与态度**，私密沟通才处理具体条件。

**AI 可以起草公开回复，但必须人签字。** 对外发声的责任不能外包给模型。

## 6. 工单系统：AI 该接在哪

### 6.1 工单流程

```
买家消息 → 意图分类 → (售前/售中) → 知识检索 → 生成回复草稿 → 规则校验 → 自动发送
                    ↓ (售后)
                    → 抽取证据 → 规则引擎判责 → 低金额自动执行 / 高金额转人工
                    ↓ 全部
                    → 写工单记录（含模型版本、引用来源、决策依据）
```

### 6.2 每张工单都要留的记录

| 字段 | 为什么 |
|---|---|
| 模型与提示词版本 | 出了事要能复现 |
| 引用的知识片段 | 答案依据 |
| 决策规则 ID | 判责依据 |
| 是否人工介入、人工改了什么 | **评估模型真实价值的唯一依据** |
| 最终结果（退款金额 / 解决时长 / 客户评分） | 回归测试的数据源 |

**「人工改了什么」这一列是整个系统最有价值的训练数据**，也是最容易被省掉的。
没有它，你无法回答「模型到底省了多少」，也无法持续改进。

### 6.3 自动回复的比例怎么定

```
建议的推进顺序：
阶段 1: 只做「分类 + 知识检索」，回复全部由人写（先验证检索质量）
阶段 2: 高频问题（占 top 20 的那几类）自动回复，其余转人工
阶段 3: 人工改写比例连续两周 < 10% 的问题类型，升级为自动
```

> **永远不要一步跳到「全自动客服」。** 阶段 1 几乎不省人力，但它能**在几周内告诉你知识库到底够不够**——
> 而这恰恰是自动客服失败的第一原因。

## 7. 本章工程结论

1. **客服分三类（售前问 / 售中催 / 售后退），分界线是「答案是否唯一」。** 售前售中问事实，售后问责任。
2. **售前先做「参数类」不做「推荐类」**——参数问题量大且答案唯一，推荐类占比小但错误代价高。
3. **「帮我选一个」必须转人工**，它是推荐决策。
4. **查不到就转人工，不允许猜**；答案必须带来源。
5. **多语种客服的三个坑**：术语与 Listing 一致、时间带时区与日期、语气按市场匹配。
6. **判责用规则引擎，模型只判「证据」这一个子问题**，每层都有 escalation 出口。
7. **拒赔前必须先给折中方案**；阈值由人定并写进政策。
8. **退款金额全部程序计算**，含法定无理由期与超期利息。
9. **差评先分类**，「预期不符」是 Listing 问题不是客服问题；公开回复的读者是其他买家。
10. **公开发声必须人签字**；公开回复不能含订单信息与赔偿承诺。
11. **自动回复按「人工改写比例」逐类升级**，不要一步到全自动。
12. **每张工单都要记「人工改了什么」**——这是评估模型真实价值与持续改进的唯一数据源。
