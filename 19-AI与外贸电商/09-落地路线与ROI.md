# 09 · 落地路线与 ROI

> **这一章的任务：把前面八章变成一条可执行的路线——先做哪一步、账怎么算、团队怎么排、哪些死法可以提前避开。**

---

## 1. 落地顺序：按「错了的代价 × 出现的频率」排

**不要按「哪个最酷」排，按「哪个最容易先证明有用」排。**

### 1.1 推荐的四个阶段

```
阶段 0（1~2 周）：准备，不上模型
  ├── 补齐结构化数据（SKU 参数、库存、单证要素、价表、术语表）
  ├── 建立评测集与基线（人工现在要花多久、出错率多少）
  └── 列出六个环节的「答案唯一性」与「出错代价」
      ↓ 产出：一张「先做哪三个」的清单

阶段 1（2~4 周）：单人可控的辅助场景
  ├── 典型：询盘摘要与分类、开发信草稿、Listing 草稿、竞品差评聚类、客服回复草稿
  ├── 全部是「AI 出草稿 + 人改」
  └── 产出：人工改写率、节省时长、错误类型清单

阶段 2（4~8 周）：有结构化输入的半自动
  ├── 典型：单证生成与交叉核对、售后判责（低金额）、客服参数类问题、库存预测
  ├── 引入规则引擎与硬校验
  └── 产出：可审计的决策记录、自动通过率、抽检不合格率

阶段 3（持续）：受控自动化
  ├── 只对「自动通过率稳定 + 抽检不合格率低于阈值」的子类开自动
  ├── 其余保持人工
  └── 产出：可回归的评测集、版本化的规则集
```

### 1.2 四个阶段的判据

| 阶段进入下一阶段的条件 |
|---|
| 0 → 1 | **有基线数据**。没有基线，后面所有的「提效 XX%」都是自说自话 |
| 1 → 2 | **人工改写率稳定低于 30%**，且错误类型已经收敛（不是「改的地方越来越多」） |
| 2 → 3 | **自动通过率稳定 + 抽检不合格率低于你定的阈值**（如 1%）连续两周 |

> **人工改写率是这一整套流程里最重要的单一指标。**
> 它同时反映了「模型好不好」和「场景选得对不对」，而且它不需要等业务指标，几周就能看出来。
> **如果改写率一直下不去，不要急着换更强的模型——先怀疑场景选错了。**

## 2. ROI 怎么算（用外贸自己的账）

### 2.1 三段式

```
第一段：直接节省（最容易算，最容易被高估）
  Δ时间 = (人工单件耗时 - AI辅助后单件耗时) × 单量
  Δ人力成本 = Δ时间 × 小时成本

第二段：质量与转化（需要自己的历史数据）
  Δ毛利 = Δ单量 × 有效毛利率 + Δ退货率带来的毛利变化 + Δ差评率带来的流量变化
  —— 这一段要用你自己的对照数据，不能用行业系数

第三段：风险（最容易漏，往往最大）
  期望损失 = Σ(场景发生概率 × 单次损失金额)
  单次损失包括：错报价赔付、平台下架损失、账号封停的机会成本、
                合规违规的潜在责任、数据泄露的潜在责任
```

### 2.2 一个必须做的敏感性分析

**不要只算一个数，要算「在什么条件下这件事划算」。**

```
设：月度询盘量 Q，单条期望毛利 M，当前响应率 r0，AI 后 r1
AI 辅助的月度额外成本 C（订阅 + token + 维护工时 + 人工复核工时）

净收益 = Q × (r1 - r0) × M - C

求「盈亏平衡的最低询盘量」：
  Q* = C / ((r1 - r0) × M)

然后问：
  你的 Q 是 Q* 的几倍？
  如果 (r1 - r0) 只有你预期的一半，Q* 会变成几倍？
  如果 C 因为 token 涨价或用量超预期翻倍，Q* 会变成几倍？
```

> **这个不等式的价值不在于算出 Q*，而在于它会告诉你「如果量不够，这条路不划算」。**
> 这就是为什么第一阶段要先测「有没有量」。

### 2.3 维护成本必须算进去

很多 ROI 测算漏掉了这一项，导致上线半年后项目变成负收益。

```
维护成本包含:
  - 提示词与规则的持续更新（业务变了就要改）
  - 评测集维护（业务变了，评测集不更新就失去意义）
  - 人工复核工时（这是最大的常常被漏掉的一项）
  - 模型/API 变更带来的适配成本
  - 合规检查（名单、规则、认证的更新）
  - 出错后的复盘与赔付
```

> **规则与提示词的维护成本随业务复杂度增长，而收益通常随规模增长。**
> **业务越复杂、量越小的团队，AI 化的边际收益越差**——这是一个很反直觉但很实用的结论。

## 3. 团队与分工：三个角色，不要一个人干完

| 角色 | 职责 | 关键能力 | 谁来当 |
|---|---|---|---|
| **业务专家** | 定义「什么是对的」、审草稿、写评测集、做取舍 | **懂业务 + 愿意写规则** | 外贸主管 / 运营负责人 |
| **工程实现** | 数据管道、RAG、规则引擎、监控、集成 | 会写代码 | 开发者 / 技术同事 |
| **合规责任人** | 闸门规则、名单、认证、留证 | 懂规则 + 敢签字 | 老板 / 合规 / 外贸负责人 |

**三个角色缺一不可，且必须有人明确负责「验收标准」。**
最常见的失败模式是：**业务方不写标准，工程方自己猜标准，最后双方都觉得效果一般。**

### 3.1 业务专家的时间投入

**不要假设业务方能投入大量时间。** 一个 10 人外贸团队，能稳定投入的通常是每人每周 2~4 小时。

```
把这个数字当作硬约束来设计:
  - 评测集靠业务方逐条标注 → 不可行（太贵）
    → 改为：业务方提供 30~50 个典型样例 + 判定标准，
      其余由工程方按标准扩展，人工抽检
  - 审草稿 → 不可能每条都审
    → 只对「高价值 + 高风险」的子类逐条审，其余抽检
```

> **「业务方每周能给你几小时」决定了这个方案能不能成。**
> 设计时先按这个约束倒推，比做完再抱怨「业务方不配合」要划算得多。

## 4. 评测：没有评测集就没有迭代

### 4.1 最小可行评测集

```
每个场景一份，50~200 条，来源：
  - 40%：最近三个月的真实样本（按时间倒序取，不要只取好处理的）
  - 30%：边界与失败案例（历史上人工处理过、结果不好的）
  - 20%：新业务/新规则带来的变化点
  - 10%：对抗性输入（超长、含注入尝试、含其他语言）
```

**「按时间倒序取」这条很重要。** 只用你记忆里印象深刻的样例，评测集会偏向「容易的」。

### 4.2 分开评「五类错误」

沿用 16 主线的多语言评测方法：**不同类型的错误要分开评，不能混成一个准确率。**

| 错误类型 | 例子 | 能不能自动判 |
|---|---|---|
| **内容错误** | 说错了参数、编了认证 | **能**（事实回指） |
| **遗漏错误** | 该说的没说（漏了限制条件） | 部分能（关键项检查表） |
| **越界错误** | 说了不该说的（承诺交期、报价、法律建议） | **能**（禁用模式匹配） |
| **格式错误** | 长度超限、字段缺失、格式不合规 | **能**（规则校验） |
| **风格错误** | 不像人、不合本地文化 | **不能**，要人判 |

**前四类可以全自动评测，第五类必须人判。**
这也是为什么「准确率 92%」这种数字没有意义——**你要知道那 8% 是什么错误**。

### 4.3 回归：每次改提示词都跑一遍

**提示词改动 = 代码改动。** 改完不跑评测集，就等于改完不跑单元测试。

```
每次改动后:
  1. 跑全量评测集，对比基线
  2. 看「哪些原本对的变成了错的」（**回归**，比新错的更值得看）
  3. 人工抽检新增的「自动通过」样本
```

## 5. 八种死法与规避

| # | 死法 | 早期信号 | 处方 |
|---|---|---|---|
| 1 | **先买工具再找场景** | 用了两周说不清省了什么 | 先跑阶段 0，写出基线 |
| 2 | **自由文本、无结构** | 输出每次都不一样，没法审 | 上固定骨架 + 槽位 |
| 3 | **让模型算钱** | 报价偶发差一分钱 | 拆出确定性程序 |
| 4 | **合规做成提示词** | 有人问「这条名单会不会漏」时答不上来 | 改成 fail-closed 的硬闸 |
| 5 | **自动化没留痕** | 出问题查不到当时用了哪版规则 | 每步留证 |
| 6 | **评测集偏向易例** | 线上错误比评测集多得多 | 按时间倒序取真实样本 |
| 7 | **只追回复率** | 回复率涨了、成交率没动 | 同时看两个指标，做对照 |
| 8 | **维护成本没算进 ROI** | 上线半年后变成负收益 | ROI 三段式 + 敏感性分析 |

**第 2、3、4 条是技术死法，第 1、5、6、7、8 条是流程死法。**
**流程死法的比例更高，而且更隐蔽**——因为它们不会报错，只会让项目慢慢失去价值。

## 6. 一个 12 周的最小可行路线（示意）

```
第 1~2 周   选场景、补数据
            产出：场景清单 + 基线 + 评测集 v0
第 3~4 周   提示词与骨架
            产出：可人工复核的草稿流；改写率首次测量
第 5~6 周   接入真实流程（仍全人工确认）
            产出：端到端跑通；错误类型清单
第 7~8 周   加硬校验与规则
            产出：越界/格式/事实错误的自动拦截
第 9~10 周  影子运行（AI 出结论但不生效，人按 AI 的建议做）
            产出：四格表（AI 对人错 / 人对 AI 错 / 双方都对 / 双方都错）
第 11 周    灰度（按比例放量，每档有回滚开关）
            产出：分档指标 + 回滚演练记录
第 12 周    复盘与下一场景排序
            产出：ROI 实测 vs 预估；下一步做什么的决策依据
```

> **影子运行的那一周是整个路线里价值最高的一周。**
> 它让你在不产生真实业务影响的前提下，看到 AI 会错在哪。
> **大部分团队跳过这一步直接灰度，然后在小比例流量上发现了本该在影子期发现的问题。**

## 7. 判断「该不该继续」的三个问题

在第 6 周、12 周各问一次：

```
① 人工改写率是否稳定下降？
   若稳定下降 → 模型与场景匹配，继续
   若不降或上升 → 场景选错或模型不对，换场景而不是换模型

② 出错是否「可发现」？
   若错误都能被人或规则发现 → 系统可控，继续
   若出现静默错误（尤其是算错的、漏掉的）→ 立刻停止，先修机制

③ 维护成本是否在可承受范围？
   若每周维护工时 > 节省工时的一半 → 收益结构有问题，考虑降低自动化范围
```

## 8. 本章工程结论

1. **落地按「错了的代价 × 出现的频率」排序**，先做「有基线、单人可控、答案是唯一」的辅助场景。
2. **人工改写率是最重要的单一指标**——它同时反映模型好坏与场景对不对，几周就能看出来。改写率不降，先怀疑场景而不是模型。
3. **ROI 用三段式**：直接节省 + 质量转化 + 风险期望损失。第三段最常被漏，往往最大。
4. **必须做盈亏平衡点与敏感性分析**，并据此判断「量不够就别做」。
5. **维护成本必须进 ROI**——提示词、评测集、复核工时、合规更新、复盘赔付，一项都不能漏。
6. **三个角色**：业务专家（定标准）、工程实现（做管道）、合规责任人（签字）。缺一不可。
7. **按业务方每周能投入的 2~4 小时倒推设计**，别做需要业务方持续高投入的方案。
8. **评测集按 40/30/20/10 取样**（真实倒序 / 失败案例 / 变化点 / 对抗），并分五类错误分开评。
9. **提示词改动要跑回归**，重点看「原本对的变错了」的样本。
10. **八种死法里，流程死法比技术死法更多也更隐蔽**——它们不报错，只让项目慢慢失去价值。
11. **影子运行那一周价值最高**，别跳过直接灰度。
12. **第 6 周和第 12 周各问三个问题**：改写率是否下降、错误是否可发现、维护成本是否可承受。
