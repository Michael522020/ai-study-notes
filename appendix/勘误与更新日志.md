# 勘误与更新日志

> **核心问题**：这篇笔记里的哪句话可能已经过期了？我该什么时候重新核一遍？

---

## 0. 为什么必须有这份文档

AI 领域的笔记有一个**结构性问题**：**结论的半衰期比文档的寿命短**。

| 例子 | 写下时的正确 | 半年后 |
|---|---|---|
| 「YOLO 家族最新是 v11」 | ✅ 2025 年 | ❌ 2026-01 就有了 YOLO26 |
| 「Ultralytics 的 `Trainer` 接口如此」 | ✅ | ⚠️ 每个大版本都在动 |
| 「模型价格是 X / 百万 token」 | ✅ | ⚠️ 定价与缓存策略频繁调整 |
| 「RKNN 工具链只支持这几个算子」 | ✅ | ⚠️ 随版本增加 |

一个**不带日期、不带状态、不带自查方法**的笔记库，半年后就是** misinformation 制造机**——
它看起来很权威，但读者无从判断哪些还能信。

**本文件的三件事**：

1. **§1 更新日志** —— 这个仓库改过什么、为什么改
2. **§2 时效敏感项台账** —— 哪些结论会过期、怎么自查、多久查一次
3. **§4 过期反馈机制** —— 读者发现过期时怎么反馈

### 2.8 什么**不会**过期

写下来是为了**划定边界**，避免过度焦虑：

| 稳定项 | 为什么稳定 |
|---|---|
| **技术原理与演进脉络** | 「为什么 YOLOv3 用三个尺度」「为什么 DETR 收敛慢」——这些是历史事实 |
| **工程方法论** | 评测口径、bad case 分析流程、影子运行、数据泄漏检查——方法不变 |
| **失败模式清单** | 七类 RAG 失败点、敏感字段屏蔽、证据回指——这些是系统性的 |
| **选型判据与决策树** | 「什么时候用 RAG 而不是长上下文」——判据稳定，参数会变 |
| **术语与缩写** | 极稳定（除非有重大更名） |

> **一句话**：**方法论永不过期，参数与版本会过期。**
> 引用本仓库时，优先引用方法论；引用参数时必须带版本与日期。

## 4. 过期反馈机制

### 4.1 读者发现过期时

**开 Issue，标题格式**：

```
[勘误] <文件路径> §<章节> —— <一句话说清哪里错了>
```

**Body 必须包含**（缺一项就没法修）：

```markdown
### 错误原文
> <逐字复制笔记里的原句>

### 为什么错
<你的依据：官方文档链接 / 复现结果 / 版本差异>

### 建议的修正
<改写后的句子>

### 依据来源
<URL + 查询日期>
```

### 4.2 维护者处理流程

```
收到 Issue
  ↓
判断：是个案还是版本漂移？
  ├─ 个案 → 直接改正文 + 在 §1.1 记一行勘误
  └─ 版本漂移 → 更新正文 + 更新 §2 台账的「自查方式/复核频率」
  ↓
若涉及结论被推翻 → 同步改《论文总索引》§6 时效台账
  ↓
提交 PR（一条改动一个 PR）
```

### 4.3 季度复核清单

每季度做一次，只查 §2 里的项：

- [ ] V1/V4：Ultralytics 有没有发新版本？
- [ ] V5：DETR 系有没有新的收敛方案？
- [ ] T1/T2：RKNN / TensorRT 有没有大版本？
- [ ] T4/T5/T6：llama.cpp / Ollama / vLLM 有没有 breaking change？
- [ ] P1/P2：模型定价有没有调整？
- [ ] L1/L2/L3：法规有没有更新？
- [ ] D1/D2：常用数据集有没有换版本或改许可？
- [ ] R1：有没有新 SOTA 推翻了台账里的结论？
- [ ] §3.1：各主线的最后更新日期是否还准确？
- [ ] §1：更新日志是否补齐了本季度的变更？

> **不要因为「这个季度没什么变化」就跳过。**
> 台账的价值恰恰在于**它大部分时候不动**——一旦动了，说明你正好赶在过期之前。

## 5. 本文件的边界

| 本文件**不**负责 | 原因 |
|---|---|
| 记录具体的技术内容 | 那是各主线章的事 |
| 逐条记录 diff | Git 历史已经做了这件事 |
| 保证笔记永远正确 | **做不到**。它只能保证「你知道哪里可能不可信」 |

> **工程结论**：一份会过期的笔记不可怕，**一份不知道自己会过期的笔记才可怕**。
> 这份文件的价值不是让笔记不变旧，而是让读者**知道哪些地方需要自己复核**。
