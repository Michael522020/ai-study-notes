# 04 · AI 简历筛查：从需求到落地的完整方案

> **一句话：简历筛查的产品不是「打分器」，是「缩小人工筛选范围 + 给出可追溯依据」的流水线。**
> 它的第一性要求不是准确率，是**可解释、可复核、可审计、不歧视**。

配套实现：[`code/hr-agent/`](../code/hr-agent/)　离线评测当前基线：
硬门槛判对率、结论判对率、证据可回指率、偏差不变性**均为 100%**。

---

## 0. 需求与角色

### 0.1 三个角色，三种诉求

| 角色 | 现在的痛 | 期望 AI 提供什么 | 期望 AI **不要**做什么 |
|---|---|---|---|
| **HR / 招聘专员** | 一天筛 100~300 份，80% 是明显不匹配的 | 快速过掉明显不匹配的，把时间留给边界样本 | 自动淘汰（结论要人工下） |
| **用人经理** | 看不懂 HR 的筛选标准，收到的人质量不稳 | 附「为什么推荐」与能力维度雷达 | 只给一个总分 |
| **候选人** | 不知道为什么被拒 | 至少有一次人工复核与申诉通道 | 被静默拉黑 |

### 0.2 价值假设（可证伪）

> **假设**：HR 筛 200 份简历的时间从 4 小时降到 1.2 小时，
> 且漏掉的高质量候选人不增加。

**可证伪点**：如果 AI 过掉的人里，被复核推翻的比例超过 5%，说明阈值设错了，
收益是负的（多了一道工序，还错了）。

### 0.3 明确不做的事

- ❌ 不做自动淘汰（AI 只做**排序与证据整理**，最终结论由人下）
- ❌ 不做能力测评（那是 05 篇的事）
- ❌ 不做薪资谈判建议（合规风险高）
- ❌ 不使用与岗位无关的个人属性做判断（见 §8）

## 1. 业务流

```
        JD 原文
           │
           ▼
   ┌────────────────┐
   │ ① JD → 能力模型 │  硬门槛 + 能力维度 + 权重 + 期望水平
   └────────┬───────┘
            ▼
  ┌──────────────────┐
  │ ② 简历 → 结构化   │  抽取 + 敏感字段屏蔽
  └────────┬─────────┘
            ▼
  ┌──────────────────┐
  │ ③ 硬门槛过滤     │  学历 / 年限 / 城市 / 薪资  一票否决
  └────────┬─────────┘
            ▼
  ┌──────────────────┐
  │ ④ 能力匹配打分   │  逐维度评分 + 原文证据
  └────────┬─────────┘
            ▼
  ┌──────────────────┐
  │ ⑤ 结论 + 报告    │  pass / review / reject + 依据
  └──────────────────┘
```

**每一步都要能单独评测。** 本仓库把它们拆成 `jd.py` / `fields.py` / `bias.py` /
`screening.py` / `matching.py` 五个模块，各自有独立断言。

## 2. 第 ① 步：JD → 能力模型

### 2.1 能力模型的两层结构

```python
@dataclass
class CompetencyModel:
    role_title: str
    hard_requirements: list[HardRequirement]   # 一票否决，不参与加权
    competencies: list[Competency]              # 加权打分
    soft_skills: list[str]
```

**为什么硬门槛不能折成分数**：学历不达标的简历应该在第一屏就被排除，
而不是「排在最后」。把不达标的和达标的混在一个排序里，
HR 会误以为系统「认为它还行，只是分数低」。

### 2.2 能力维度的四个字段

| 字段 | 作用 | 举例 |
|---|---|---|
| `key` | 稳定标识，对应能力图谱词典 | `customer_dev` |
| `weight` | 加权权重，同一岗位内归一化 | 1.2 |
| `min_level` | 期望水平 1~5 | 4 |
| `keywords` | 证据检索用的关键词 | 客户开发 / 询盘 / 线索 |

`key` 必须是**受控词表**里的值。这条约束让「模型抽 JD」这件事可校验：
模型抽出的 key 对不上词表，直接丢弃并记账（`LlmJdBackend.dropped`），
而不是让一个幻觉出来的技能进入打分。

> **工程结论**：**模型抽、规则校**。模型负责理解 JD 的语义，
> 规则负责保证输出的 key 是合法且可比较的。

### 2.3 抽取规则要容忍中文的写法差异

```python
# 「3 年以上外贸或跨境电商相关经验」「5 年以上外贸从业经验者优先」
m = re.search(r"(\d+)\s*年[^，。；\n]{0,12}?经验", jd_text)
```

早期版本写成 `(\d+)\s*年(?:以上)?(?:相关|工作|从业|运营|开发|管理)?经验`，
结果「3 年以上外贸或跨境电商相关经验」匹配不上 —— 年限门槛**根本没被抽出来**，
所有候选人都直接过了学历关。**这是我在本项目里实际踩到的坑**：
规则抽取的失败是静默的，不报错，只是让一道门槛消失。

> **工程结论**：任何「没抽到就不判负」的门槛，都要有独立测试断言
> 「这份 JD 确实抽出了年限门槛」。本仓库的
> `test_jd_model_extracts_expected_dimensions` 就是干这个的。

## 3. 第 ② 步：简历 → 结构化 + 屏蔽

### 3.1 抽取

支持 txt / md / docx / pdf，自带实现（`extract.py`），零第三方依赖。

**边界要写死**：

| 格式 | 支持程度 | 说明 |
|---|---|---|
| txt / md | ✅ | 多编码自动尝试（utf-8 / gb18030 / utf-16） |
| docx | ✅ | 段落保行，表格被拉平 |
| pdf（有文本层） | ✅ | 自带 zlib 解压 + 文本算子提取 |
| pdf（扫描件） | ❌ | **返回 `needs_ocr`，不返回空字符串** |

```python
if not text:
    return Document(text="", source=str(p), ok=False, error="needs_ocr",
                    meta={"hint": "PDF 无文本层，需先做 OCR"})
```

**空字符串是最危险的返回值** —— 下游会认为「这人没有任何经历」，
而不是「抽取失败，需要 OCR」。失败必须显式失败。

### 3.2 敏感字段屏蔽（详见 §8）

```python
mask = mask_sensitive(resume_text)   # 年龄/性别/婚育/民族/籍贯/政治面貌/照片/身份证/健康
working_text = mask.text              # 评分链路只看这个
```

逐字段（而不是一个大正则一把梭）替换，好处是能精确记账「屏蔽了什么」，
写进报告供合规审计；新增敏感字段只改词典。

## 4. 第 ③ 步：硬门槛过滤

### 4.1 「没写」不等于「不满足」

```python
if fields.years == 0:
    return ("简历未注明", True, "未注明不判负")
```

简历没写工作年限 → **不判负，但要在报告里说明**。
判负会导致大量本来合适的候选人被误杀，而且这种误杀在指标上看不出来
（因为被拒的人不会被复核）。

**例外**：如果「简历未注明」在某个岗位上是硬要求（比如体制内岗位要求明确年限），
就应该改成 `required=True` 且不满足即拒。这条要按岗位逐个定，不能一刀切。

### 4.2 门槛判定明细要留痕

```python
@dataclass
class FilterOutcome:
    key: str; label: str; expected: str; actual: str; passed: bool; required: bool
```

报告里逐条展示「期望 / 实际 / 是否通过 / 是否必须」。
HR 复核时最常见的问题是「为什么这个人被刷了」，答案必须在这一张表里。

## 5. 第 ④ 步：能力匹配与证据

### 5.1 证据必须能回指原文

这是简历筛查里**最重要的一条工程约束**：

> 模型说「候选人有 RAG 经验」不算数，**能指出是哪一句话**才算数。

```python
grounded = bool(quote) and quote.strip() in resume_text
if not grounded:
    self.ungrounded.append({"reason": "evidence_not_found", "payload": raw})
    if self.require_grounding:
        result.scores[key] = 0.0      # 无依据 → 该维度按未命中处理
        result.missing.append(key)
        continue
```

评测指标 `evidence_grounding_rate` 必须为 **100%**。有一条幻觉证据，
这份报告就不能给人看。

### 5.2 规则后端的局限（要诚实说明）

规则后端用「命中关键词数 + 深度信号词」估算水平：

```python
level = min(5, len(hits) + 1)
if quote and any(marker in quote for marker in DEPTH_MARKERS):
    level = min(5, level + 1)
```

它的已知问题：

1. **证据可能张冠李戴**。同一个「负责」可能被算进多个维度；
2. **关键词命中 ≠ 能力强度**。「负责过报价」和「搭建过报价系统」在关键词层面一样；
3. **同义词覆盖不全**。

所以规则后端是**基线与校验器**，不是最终能力评估器。
真实场景用 `LlmMatchBackend` + 证据回指校验。

## 6. 第 ⑤ 步：评分与阈值

### 6.1 加权公式

```
总分 = Σ(维度权重 × 维度得分) / Σ权重 × 100
必备维度缺失 → 按权重比例扣分（最多扣到 0）
```

必备能力缺失的扣分是**显式的**，并写进理由：

```python
penalties.append(f"缺少必备能力「{c.name}」（扣 {penalty:.1f} 分）")
```

### 6.2 三档结论

| 结论 | 条件 | 含义 |
|---|---|---|
| `pass` | 总分 ≥ 70 且证据覆盖达标 | 建议进入人工面试 |
| `review` | 总分 ≥ 45，或证据覆盖不足 | **必须人工复核** |
| `reject` | 总分 < 45，或硬门槛未过 | 不建议进入下一轮 |

**「证据覆盖不足就降级为 review」是硬规则**：

```python
if self.config.require_evidence and ratio < self.config.min_evidence_ratio:
    if decision_name == "pass":
        decision_name = "review"
    reasons.append(f"证据覆盖不足（{ratio:.0%}），降级为人工复核")
```

模型说「都挺匹配」但给不出原文依据时，**不能判 pass**。

### 6.3 阈值必须用真实数据校准

本仓库用 5 份合成简历 + 人工标注做回归，当前结果：

| 候选人 | 人工标注 | 系统结论 | 分数 | 说明 |
|---|---|---|---|---|
| R001 | review | review | 55.57 | 外贸能力达标、AI 能力缺失 |
| R002 | reject | reject | 0 | 经验 2 年 < 要求 3 年 |
| R003 | reject | reject | 0 | 学历大专 < 本科 |
| R004 | pass | pass | 85.57 | 全维度匹配 |
| R005 | pass | pass | 85.57 | 与 R004 仅差敏感字段，得分**完全一致** |

**注意 R005**：它只比 R004 多了婚育与籍贯信息。屏蔽后得分必须**严格相等**，
差值 `bias_score_delta = 0.0`。这是偏差审计的核心断言（见 §8.3）。

> ⚠️ 5 个样本**不是**有效的阈值校准集，只够做回归测试。
> 真实校准需要 50~200 份人工标注的样本，按「人工结论」反推阈值。

## 7. 成本与规模

### 7.1 单份简历的成本

口径：JD 1,500 token + 简历 2,000 token 输入，输出 1,200 token（逐维度评分 + 证据）。

| 模型 | 输入成本 | 输出成本 | 单份合计 | 1,000 份 |
|---|---|---|---|---|
| Haiku 5.5 | $0.00035 | $0.0006 | **≈ $0.00095** | **≈ $0.95** |
| Sonnet 5.5 | $0.007 | $0.012 | **≈ $0.019** | **≈ $19** |
| Opus 5.5 | $0.014 | $0.024 | **≈ $0.038** | **≈ $38** |

**模型成本在招聘场景里根本不是瓶颈**：1,000 份简历用 Opus 5.5 也才 38 美元。
真正贵的是**OCR**（扫描件按次计费）和**人工复核**（按人天算）。

这带来一个反直觉的结论：

> **招聘场景不要为了省钱而降模型档位。** 一次误杀一个好候选人的代价，
> 远大于 100 万份简历的模型差价。把预算花在证据质量与人工复核上。

### 7.2 成本分布

| 环节 | 单份成本量级 | 备注 |
|---|---|---|
| 文本抽取 | $0（本地） | 扫描件需 OCR，云 OCR 按次 |
| JD 抽取 | 摊薄 ≈ $0 | 一份 JD 只抽一次 |
| 敏感字段屏蔽 | $0（正则） | |
| 能力匹配 | $0.001~$0.04 | 看模型档位 |
| 报告生成 | $0 | 本地模板 |
| **人工复核** | **$20~$80 / 人时** | **真正的成本中心** |

**这决定了产品的优化方向**：把人工复核的时间省下来，比把模型换成 Haiku 值一百倍。

## 8. 合规与伦理（最重要的一节）

### 8.1 法律框架

| 法域 | 依据 | 对本产品的约束 |
|---|---|---|
| 中国 | 《就业促进法》第三十条 | 招用人员应提供平等就业机会，不得实施就业歧视 |
| 中国 | 《个人信息保护法》第二十四条 | 自动化决策应保证**透明度与结果公平、公正**，不得不合理差别待遇 |
| 中国 | 《个人信息保护法》第二十八条 | 医疗健康、生物识别等属**敏感个人信息**，需单独同意 + 严格保护 |
| 中国 | 《个人信息保护法》第六条 | 处理个人信息应遵循**最小必要**原则 |
| 欧盟 | GDPR 第 22 条 | 自动化决策的权利；第 15 条解释权 |
| 欧盟 | EU AI Act 附件 III | 招聘与选人属**高风险**场景，需风险管理、日志、人工监督、准确性/稳健性 |

> ⚠️ 以上是工程侧的常识性梳理，**不构成法律意见**。
> 真实落地必须让法务过一遍，尤其是跨境企业（欧盟 AI Act 的时间表与高风险清单）。

### 8.2 必须屏蔽的个人属性

本项目的 `MUST_MASK_FIELDS`：

```python
MUST_MASK_FIELDS = (
    "age",         # 年龄
    "gender",      # 性别
    "marital",     # 婚育
    "ethnicity",   # 民族
    "native_place",# 籍贯 / 户口 / 出生地
    "political",   # 政治面貌
    "photo",       # 照片
    "id_card",     # 身份证号
    "health",      # 健康状况 / 既往病史
)
```

**这不只是合规姿态，而是效果考量**：这些字段进上下文，模型就会（有意或无意）
在评分里用上它们，而且**很难被发现** —— 因为分差通常只有几分，
混在正常的维度波动里。

### 8.3 偏差审计：屏蔽是否真的生效

光屏蔽不够，要**验证**。做法是拿屏蔽前后的文本各打一次分：

```python
def audit_masking(original_text, masked_text, scorer):
    before = scorer(original_text)
    after = scorer(masked_text)
    delta = abs(before - after)
    return {"delta": delta, "pass": delta <= tolerance}
```

**判定标准：差值必须严格为 0。**
只要有任何一条代码路径绕过了屏蔽（比如某个缓存里存的是原文），
审计立刻报警。这是**回归防线**，不是一次性检查。

配套的断言：

```python
def test_audit_detects_leak():
    """如果打分函数用到了敏感字段，审计必须报错。"""
    def leaky_scorer(text): return 1.0 if "男" in text else 0.0
    report = audit_masking(SAMPLE, masked.text, leaky_scorer)
    assert not report["pass"]
```

### 8.4 报告本身也要能过审

每份报告都带：

- 「本报告由 AI 辅助生成，仅用于初筛排序，最终录用判断由人工做出」；
- 「已屏蔽敏感字段：age、gender、marital…」（可审计）；
- 逐条门槛判定与原文证据。

### 8.5 给候选人的通道

- 结论由人工下，且人工能看到 AI 的依据（可能推翻）；
- 提供申诉入口，申诉后要能回溯当时的屏蔽与打分记录；
- 简历保留期限要有明确策略（招满或 X 个月后删除）。

## 9. 落地路线

| 阶段 | 周期 | 做什么 | 退出条件 |
|---|---|---|---|
| **P0 影子运行** | 3 周 | AI 跑但不决定，只出排序与依据，人工照旧筛 | 与人工排序的一致率 ≥ 60% |
| **P1 辅助模式** | 2 周 | AI 出排序，HR 复核并记录推翻原因 | 推翻率 < 15%，原因可归类 |
| **P2 闭环** | 4 周 | 阈值按推翻原因调；接入 ATS | 复核时间下降 ≥ 30% |
| **P3 扩展** | 持续 | 多岗位、多渠道 | 每个岗位独立校准阈值 |

**P0 的关键产出是「推翻原因表」**：HR 每推翻一次，就记一次原因。
这批数据是阈值校准的唯一可靠输入，也是发现能力模型缺维度的唯一途径。

---

## 10. 红线清单

1. ❌ 不做自动淘汰。
2. ❌ 不把敏感字段喂进评分链路。
3. ❌ 没有偏差审计就不上线。
4. ❌ 不用没有原文依据的结论。
5. ❌ 证据覆盖不足不判 pass。
6. ❌ 不在报告里省略屏蔽记录。
7. ❌ 不把简历用于本次招聘之外的用途。
8. ❌ 不做与岗位无关的能力测评（见 05 篇，那是另一件事）。
9. ❌ 不以「节省人力」为唯一目标指标。
10. ❌ 不在候选人不了解的情况下使用自动化决策。

---

## 11. 工程结论

1. 产品的核心输出是**依据**，不是分数。
2. 硬门槛与加权打分分离，不达标的直接排除而不是排后面。
3. 「简历没写」不等于「不满足」，但不写要在报告里说明。
4. 证据必须逐字回指原文，幻觉证据率必须为 0。
5. 证据覆盖不足强制降级为人工复核。
6. 敏感字段逐字段屏蔽，并**用审计验证屏蔽真的生效**。
7. 规则抽取的失败是静默的，每个门槛都要有独立断言。
8. 阈值必须用人工标注数据校准，合成样本只能做回归。
9. 模型成本不是瓶颈，人工复核时间才是 —— 优化要往后者使劲。
10. 先影子运行，推翻原因表是校准的唯一可靠输入。
