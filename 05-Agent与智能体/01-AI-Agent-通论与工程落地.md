# 01 · AI Agent 通论与工程落地

> **一句话：Agent = 会用工具的模型 + 能记账的状态机 + 一道明确的人工闸门。**
> 少一样就是玩具，多一样就成成本黑洞。

这篇是 05 章的总纲。后两篇（Agent Bot、Super Agent）是这篇的两种特化形态，
06 章的两个招聘应用则是这篇方法论的一次完整落地。

---

## 0. 先回答产品问题：什么时候需要 Agent

在动手写代码之前，先过这一关。绝大多数被标成「Agent 项目」的需求，其实不需要 Agent。

| 需求形态 | 判据 | 该用什么 |
|---|---|---|
| 一次性转换 | 输入输出格式固定，无分支 | **单次 API 调用**（甚至正则） |
| 固定流程编排 | 步骤和顺序都已知 | **工作流**（代码控制循环） |
| 步骤依赖外部事实 | 每步要查实时数据 | 工作流 + 工具调用 |
| 路径未知、需边走边决策 | 目标清楚但路径依赖中间结果 | **Agent** |
| 目标模糊、需跨阶段交付 | 需要人工定义验收 | **Super Agent**（见 03 篇） |

四个判据要同时成立才值得上 Agent：

1. **复杂度** —— 任务多步，且无法事先完全枚举；
2. **价值** —— 产出值得更高的成本与延迟；
3. **可行性** —— 模型确实能胜任这类任务；
4. **错误可承受** —— 出错能被发现、能回滚、能人工接管。

> **工程结论**：任一条不成立，就退回工作流。工作流的成本、延迟、可测性全面优于 Agent，
> 这是 2026 年最被低估的一条建议。**Agent 不是流程的替代品，是流程的补充。**

## 1. Agent 的四要素

```
┌──────────────┐   prompt   ┌─────────────┐
│  当前状态     │ ─────────▶ │    LLM      │
│ (state)      │           └──────┬──────┘
└──────▲───────┘                  │ tool_call / final
       │                          ▼
       │                 ┌────────────────┐
       │                 │   工具执行      │
       │                 └────────────────┘
       └─────── observation ──────────────┘
```

| 要素 | 是什么 | 缺了会怎样 |
|---|---|---|
| **工具** | 可调用、输出确定性的函数 | 模型只能瞎编（「幻觉工具」） |
| **状态** | 跨步持久化的上下文，可回放可审计 | 无法多步，无法排障，无法算账 |
| **决策循环** | 「继续调工具」还是「给答案」 | 变成一次性问答 |
| **停止条件 + 边界** | 最大步数、人工闸门、危险动作白名单 | 无限循环 / 越权操作 |

代码在 `code/agent-lab/agentlab/runtime.py`，四种状态语义是显式的：

| 状态 | 含义 | 典型场景 |
|---|---|---|
| `completed` | 模型给出最终回答 | 正常结束 |
| `needs_human` | 触发人工闸门，附待确认动作 | 金额承诺、建单、投诉 |
| `budget_exceeded` | 步数 / 工具数 / 成本越界 | 死循环、账单保护 |
| `failed` | provider 或未分类异常 | 网络故障、schema 非法 |

> **工程结论**：失败语义必须由**规则**决定，不能由正文文本决定。
> 「模型回答里出现了『转人工』三个字」不等于「已转人工」。
> 这条在 06 章的招聘应用里是硬约束 —— 结论必须能追溯到规则与原文证据。

## 2. 三种推理范式与选型

| 范式 | 结构 | 适用 | 代价 |
|---|---|---|---|
| **ReAct** | 思考 → 行动 → 观察，循环 | 步骤 ≤ 3、路径灵活、边走边修 | 容易绕路，步数不可预测 |
| **Plan & Execute** | 先出计划，再逐步执行 | 步骤 ≥ 5、依赖强、结构稳定 | 计划错则全盘错，需要重规划机制 |
| **反思 / Critic** | 生成 → 自我批评 → 修订 | 质量敏感、格式要求严 | 多 1~2 倍成本与延迟 |

生产上最常见的是**混合**：Planner 出计划，Executor 内部用小 ReAct 循环，
收尾用 Critic 校验。代码里 `profiles/agent.py` 是这个结构的简化版：

```
Plan (plan_tasks) → Execute (execute_task × N) → Verify (check_acceptance)
```

**重规划的触发条件**（写死，别指望模型自己判断）：

- 同一子任务连续失败 N 次；
- 后续步骤依赖的输入与计划不符；
- 外部事件改变了目标。

## 3. 工具层：定义即契约

模型能读到的接口文档**只有**工具描述。写工具描述就是写 API 文档。

### 3.1 描述写法

```python
ToolSpec(
    name="calculate",
    description=(
        "计算一个算术表达式（只支持 + - * / // % ** 和括号）。"
        "涉及金额、比例、补偿的计算必须用本工具，不要心算。"
    ),
    input_schema={
        "type": "object",
        "properties": {"expression": {"type": "string", "description": "算术表达式，如 18400 * 0.03"}},
        "required": ["expression"],
    },
    handler=_calculate,
)
```

四条规矩：

1. **字段名用业务词**，不要缩写。`expression` 好过 `expr`；
2. **写清楚什么时候该用**。上面那句「不要心算」比什么参数说明都管用 ——
   工具描述同时是**行为规约**；
3. **枚举要穷举**，模型才不会自造值；
4. **有副作用就标出来**：`side_effect=True` 的工具在未放行时只出草稿。

### 3.2 严格 schema 与强制工具选择

Anthropic 的 **strict 工具模式**要求：

```json
{"name": "...", "description": "...", "input_schema": {...}, "strict": true}
```

且 schema 必须满足 `additionalProperties: false` + 显式 `required`。
`agentkit/schema.py` 的 `strict_schema()` 会递归补全这两项。

> ⚠️ **2026 年的一个坑**：`tool_choice: {"type": "any"}` 与 `{"type": "tool", ...}`
> 在 Opus 5.5 / Sonnet 5.5 / Fable 5.2 等当前模型上会**直接 400**。
> 想要「必须调用工具」，正确做法是 `tool_choice: auto` + `strict: true` + 提示词里点名工具。
> 本仓库的 `AnthropicProvider` 就是这么写的。

### 3.3 入参校验失败要能自修

工具入参非法时，**不要抛异常终止 Agent**，把错误信息喂回模型让它改：

```python
errors = validate(call.input, spec.input_schema)
if errors:
    return ToolResult(status="error",
                      message="工具入参校验失败，请按 schema 修正后重试：" + "；".join(errors),
                      error_code="invalid_input")
```

同一个（工具名 + 入参）连续失败 2 次就转人工 —— 不设这个上限，
模型会在两个错误入参之间来回撞，把预算烧光。

### 3.4 工具不是越多越好

工具面是产品设计：

- 给多了 → 模型乱调、描述互相干扰、每次请求都带一堆 schema（token 成本）；
- 给少了 → 模型绕路、幻觉出不存在的工具。

本仓库三种形态的工具面分别是 7 / 10 / 12 个（见 `code/agent-lab/README.md`）。

## 4. 运行时：手写循环 vs SDK 托管

| | 手写循环（本仓库做法） | SDK `tool_runner` | Managed Agents |
|---|---|---|---|
| 代码量 | 多写 200 行 | 少写 150 行 | 少写 400 行 |
| 可观测性 | **完全透明** | 事件回调 | 服务端会话事件 |
| 状态自持 | 自己管 | 自己管 | 服务端托管 |
| 沙箱 | 自己搭 | 自己搭 | Anthropic 托管容器 |
| 成本控制 | 完全自控 | 可控 | 可控 |
| 适用 | 学习/研究、强定制 | 常规业务 | 长时会话、持久化配置 |

```python
# SDK 托管版（本仓库未采用，但值得知道它长什么样）
runner = client.beta.messages.tool_runner(
    model="claude-opus-5-5",
    max_tokens=8000,
    messages=messages,
    tools=[...],
    max_iterations=10,
)
final = runner.until_done()
```

> **工程结论**：如果你的目标是「把 Agent 跑起来」，用 SDK。
> 如果你的目标是「搞清楚 Agent 为什么跑成这样」，手写循环。
> 教学与研究场景手写；规模化业务场景在掌握手写版之后再换 SDK —— 否则你无法排障。

## 5. 上下文、记忆与思考链

### 5.1 上下文预算

```
请求上下文 = tools（工具描述）+ system（系统提示）+ messages（历史 + 工具结果）
```

- 工具描述**常驻**，是固定成本 —— 工具多一个，每一轮都多付一次；
- 系统提示适合放**不变的规则**，放**会变的东西**就等于每轮失效缓存；
- 工具结果是最容易失控的部分（一次 `list_orders` 返回 500 行就是灾难）。

### 5.2 提示缓存

缓存是**前缀匹配**：`tools → system → messages`，任何一字节变化都会让其后全部失效。

- 渲染顺序固定：**稳定内容在前，易变内容在后**；
- 最多 4 个 `cache_control` 断点；
- 最小可缓存前缀依模型而异（512~4096 token），太短会静默不命中；
- **验证方法**：看 `usage.cache_read_input_tokens`，重复请求下它一直是 0 就有静默失效源。

### 5.3 思考链（thinking）的三条硬规则

1. **自适应思考**：2026 年起固定预算 `budget_tokens` 已废弃，
   在 Opus 5.5 / Sonnet 5.5 / Fable 5.2 上会 **400**。用 `thinking: {"type": "adaptive"}`，
   深度靠 `output_config.effort`（`low`/`medium`/`high`/`xhigh`/`max`）控制。
2. **thinking 块必须原样回传**（含 `signature`）。这是 preserved thinking 的硬要求，
   丢掉它模型就读不到自己的推理链，工具调用场景下质量明显下降。
   本仓库 `LLMResponse.to_message()` 保留 `signature` 就是为此。
3. **不要为了省 token 关思考**。Opus 5 上关掉思考有两个典型故障：
   把工具调用写进**可见文本**（调用不执行、不报错），以及泄漏 `<thinking>` 标签。

> **工程结论**：思考深度用 `effort` 调，不用关掉思考来调。
> Opus 5.5 的 `effort` 默认是 `medium`（比 Opus 5 的 `high` 低一档），**要显式设置**。

### 5.4 上下文的四种治理手段

| 手段 | 做法 | 适用 | 代价 |
|---|---|---|---|
| **上下文编辑** | 清理旧工具结果 / 旧思考块（`context-management` beta） | 工具结果占满窗口 | 会丢信息 |
| **服务端压缩** | `compact-2026-01-12` beta，自动摘要历史 | 超长会话 | 必须原样回传 compaction 块 |
| **消息线程** | `message-threads-2026-08-12` beta，服务端存会话 | 多轮长会话 | 与压缩不兼容 |
| **自己写摘要** | 让模型总结后替换历史 | 需要语义保真 | 多一次调用，质量最好 |

服务端压缩的关键细节：**回传时必须把整个 `response.content` 拼回去**（含 compaction 块），
只拼文本会静默丢失压缩状态。

## 6. 成本：把账单当成一等公民

### 6.1 定价（Anthropic 官方模型表，2026-11 缓存；**价格会变，落地前请回官方页面核对**）

| 模型 | Model ID | 上下文 | 输入 $/MTok | 输出 $/MTok | 缓存读 |
|---|---|---|---|---|---|
| Claude Opus 5.5 | `claude-opus-5-5` | 1M | 4.00 | 20.00 | 0.20 |
| Claude Opus 5 | `claude-opus-5` | 1M | 5.00 | 25.00 | 0.25 |
| Claude Sonnet 5.5 | `claude-sonnet-5-5` | 1M | 2.00 | 10.00 | 0.10 |
| Claude Haiku 5.5 | `claude-haiku-5-5` | 200K | 0.10 | 0.50 | 0.01 |
| Claude Fable 5.2 | `claude-fable-5-2` | 1M | 8.00 | 40.00 | 0.20 |

缓存写入按输入价 1.25× 计。Haiku 5.5 的价格在 100K prompt 以内，上限之外跳到 $0.50/$2.50。

### 6.2 三档模型怎么分

| 档位 | 适合 | 例子 |
|---|---|---|
| **Haiku 5.5** | 分类、抽取、改写、路由 | 从简历里抽字段、意图分类 |
| **Sonnet 5.5** | 常规 Agent 循环、匹配打分、问答 | 06 章的两个应用 |
| **Opus 5.5 / Fable 5.2** | 复杂推理、难代码、长时高难任务 | 复杂纠纷判断、超长任务 |

**同一份 prompt，Opus 5.5 与 Sonnet 5.5 差 2×，与 Haiku 5.5 差 40×。**
分档不是抠门，是**把预算花在需要推理的地方**。

### 6.3 成本模型（口径必须写清楚）

假设一轮对话：系统提示 1,200 token（可缓存）+ 检索片段 2,000 + 历史 1,500 + 输出 200。

| 模型 | 未缓存输入 | 缓存读 | 输出 | 单轮成本 |
|---|---|---|---|---|
| Opus 5.5 | 3,500 | 1,200 | 200 | **≈ $0.0182** |
| Sonnet 5.5 | 3,500 | 1,200 | 200 | **≈ $0.0091** |
| Haiku 5.5 | 3,500 | 1,200 | 200 | **≈ $0.0005** |

单轮 $0.0091 意味着：**1 万次对话 ≈ $91**。这个数字要拿去做业务测算，别用「感觉不贵」。

### 6.4 压降成本的四个杠杆（按性价比排序）

1. **免费的那几个先做**：缓存命中率、上下文瘦身、循环卫生（不重复读同一份文档）、批处理（异步场景 50% 折扣）；
2. **effort 调档**：编码与多步工具用 `high`/`xhigh`，简单路由降到 `low`；
3. **模型分档**：按任务难度分流，别拿 Opus 干分类的活；
4. **先量再调**：拿评测集测出「同一任务的更便宜模型是否也过线」。

> ⚠️ **一个反直觉的点**：更便宜但多绕两步的模型，**总账更贵**。
> 成本要按「完成一个任务」算，不是按「一次请求」算。

## 7. 评测：没有评测集的 Agent 项目等于没上线

### 7.1 五层指标

| 层 | 指标 | 怎么测 |
|---|---|---|
| 任务层 | 任务完成率、验收通过率 | 断言式用例集 |
| 轨迹层 | 步数、工具调用数、工具错误率 | 轨迹埋点 |
| 质量层 | 答案正确性、有用性 | LLM-as-Judge + 人工校准 |
| 成本层 | 每任务美元、token 分布 | 成本核算 |
| 安全层 | 越权调用、注入成功、敏感信息外泄 | 对抗用例集 |

### 7.2 轨迹埋点是前提

没有轨迹，评测和排障都无从谈起。本仓库的 `agentkit/tracing.py` 记录的事件：

```
run_start → model_turn → tool_call → (human_gate | budget_exceeded | provider_error) → run_end
```

每条带 `run_id` / `seq` / `ts`，可按序回放。**敏感内容默认不落原文**，只记长度与哈希。

### 7.3 LLM-as-Judge 的正确用法

Judge 不是「让模型打个分」就完事：

- **要校准**：抽一批人工标注的样本，算 Judge 与人工的一致率（Cohen's κ 或简单一致率）；
- **要固定量表**：给明确的评分维度与锚点示例；
- **要分离维度**：不要输出一个「总分」，要输出逐维度分，否则没法定位问题；
- **要注意偏好漂移**：换模型版本后 Judge 的分数会变，趋势要重新对齐。

### 7.4 回放测试与回归门禁

把生产轨迹固化成回归用例：

```
生产 trace → 脱敏 → 变成评测用例 → 每次发布跑
```

这是唯一能挡住「改个 prompt 结果变差」的机制。

### 7.5 离线评测的能力边界（重要）

本仓库的 `ScriptedProvider` 用写死的脚本替代模型，**工具仍然真跑、账仍然真算**：

- ✅ 能证明：编排逻辑、闸门触发、账目正确、状态语义、结论一致性；
- ❌ 不能证明：模型答得好不好。

这两类指标在评测报告里必须**分开列**，混在一起会误导决策。

## 8. 人工审核闸门

不是所有动作都该由 Agent 自己拍板。

### 8.1 三类必须进人工的动作

| 类型 | 例子 | 闸门位置 |
|---|---|---|
| **不可逆的外部动作** | 发邮件、建工单、改数据、付款 | 工具返回 `needs_human`，附待确认动作 |
| **对外承诺** | 金额、折扣、赔偿、交期、法律口径 | 同上 |
| **合规判定** | 录用/淘汰结论、涉及敏感属性的判断 | 结论层强制降级为人工复核 |

### 8.2 闸门的实现方式

在代码里，副作用工具默认**干跑**：

```python
def _create_ticket(args, ctx):
    if not ctx.allow_side_effects:
        return ToolResult(status="needs_human",
                          data={"would_create": {...}},
                          message="建单属于写操作，已生成待人工确认的工单草稿，未落库")
    ...
```

运行时收到 `needs_human` 就**立即停止**，把待确认动作返回给上层：

```json
{"status": "needs_human",
 "pending_action": {"tool": "create_ticket", "input": {...}, "reason": "..."}}
```

> **工程结论**：闸门不是「失败」，是**一种正常的结果状态**。
> 如果你的系统只有「成功/异常」两种状态，人工闸门就一定会被当成异常吞掉。

## 9. 安全：三类真实攻击面

| 攻击 | 手法 | 防线 |
|---|---|---|
| **提示注入** | 简历/文档/网页里塞「忽略之前指令」 | 数据与指令分离；外部正文明确标注为数据；工具层收口 |
| **工具滥用** | 模型被诱导调危险工具 | 工具白名单 + 副作用闸门 + 参数校验 |
| **数据外泄** | 把 A 客户信息说给 B | 按用户/会话隔离状态；工具层做权限校验，不靠提示词 |

关键原则：**安全边界要落在代码层，不能只写在提示词里。**
提示词是建议，代码是强制。

## 10. 落地路线（四阶段）

| 阶段 | 目标 | 验收标准 |
|---|---|---|
| **P0 单工具** | 一次模型调用 + 一个工具 | 能稳定返回结构化结果，错误可控 |
| **P1 多步 Agent** | 循环 + 状态 + 预算 | 评测集通过率 ≥ 目标值，成本可预测 |
| **P2 生产化** | 观测、护栏、人工闸门、回归门禁 | 有 trace、有看板、有回滚 |
| **P3 自治化** | 长任务、检查点、验收 | 验收通过率达标，人工介入率下降 |

**每一阶段的退出条件都必须是可测量的。** 「感觉好用了」不是退出条件。

---

## 11. 工程结论清单

1. 先问「要不要 Agent」，多数答案是不。
2. 四要素缺一不可，缺状态最致命。
3. 工具描述即契约，写行为规约而不是参数说明。
4. strict schema + `tool_choice: auto`；强制工具选择在新模型上会 400。
5. 入参非法要能自修，同一错误最多重试 2 次。
6. 预算三条线（步数 / 工具数 / 美元）同时设，任一越界即停。
7. thinking 用 `adaptive` + `effort`，不要用 `budget_tokens`，别关思考。
8. thinking 块带 `signature` 原样回传。
9. 成本按「完成任务」算，不是按「请求」算。
10. 没有评测集和回归门禁的 Agent 项目不允许上线。
11. 人工闸门是正常状态，不是异常。
12. 安全边界写在代码里，不写在提示词里。
