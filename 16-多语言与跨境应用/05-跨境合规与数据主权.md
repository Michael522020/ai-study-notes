# 跨境合规与数据主权

> **核心问题**：数据能不能出国？客户名单要不要做制裁筛查？这两件事是一回事吗？

---

## 0. 两个正交的问题

**跨境业务有两套完全独立的合规体系，经常被混为一谈。**

| | **① 数据合规** | **② 贸易合规** |
|---|---|---|
| **管什么** | **数据**能不能跨境、怎么处理 | **人和物**能不能做交易 |
| **主管** | 数据保护/网安部门 | 商务/海关/出口管制部门 |
| **触发** | 传输个人信息、处理个人数据 | 交易对手、货物、技术、最终用途 |
| **典型问题** | 欧盟客户的数据能不能存到国内 | 这个客户是不是被制裁对象 |
| **失败后果** | 监管处罚、数据被要求删除 | 交易被冻结、账户被关闭、法律责任 |
| **工程动作** | 数据流梳理、传输机制、同意管理 | **名单筛查**、留痕、拒交易 |

> **关键区分**：
> **做 AI 系统时，数据合规决定「架构能不能这么设计」**（数据存哪、模型在哪跑）；
> **贸易合规决定「能不能跟这个人做生意」**（这是业务逻辑层的硬闸门）。

---

## 1. 数据跨境的三层问题

```
① 数据能不能出境？          → 数据本地化法规（国家级的硬要求）
        ↓
② 出境了，要满足什么条件？   → 传输机制（充分性 / 适当保障 / 评估）
        ↓
③ 境外处理者本身合规吗？     → 处理者义务（GDPR 等对境外处理者的要求）
```

> **三层要分开答。**
> **「我们有云服务在海外」回答不了任何一层**——
> 它只回答了「技术上出境了」。

---

## 2. 数据跨境：机制层（工程视角）

> **⚠️ 以下只讲机制框架，不给法条结论。**
> 具体适用哪条路径、门槛是多少，**必须由法务按适用法规确认**。

### 2.1 三条常见路径

| 路径 | 形态 | 适用（**须法务确认**） |
|---|---|---|
| **A 充分性认定** | 目的地国家/地区被认定为「充分」 | 目的地在认定名单内 → 机制最简 |
| **B 适当保障** | 标准合同条款（SCC）+ 影响评估（TIA） | 通用路径；**通常还需申报/备案** |
| **C 认证 / 保护认证** | 通过认可的认证 | 部分场景可用 |

### 2.2 工程上要落的四件事

| # | 事项 | 工程动作 |
|---|---|---|
| **1** | **数据流图** | 画清楚：数据从哪来 → 存哪 → 谁访问 → 出境到哪 → 谁处理 → 多久删 |
| **2** | **分类分级** | 哪些是个人信息、哪些是敏感/重要数据；**不同类别的出境要求不同** |
| **3** | **传输机制** | 合同条款、技术措施（加密、假名化）、**并写进数据处理协议** |
| **4** | **留档** | 影响评估记录、同意记录、跨境传输记录；**能对外交代** |

### 2.3 「数据本地化」的三个层次

| 层次 | 含义 | 典型要求 |
|---|---|---|
| **L1 存储本地化** | 数据必须存在境内 | 金融、医疗、关键信息基础设施 |
| **L2 处理本地化** | 数据可以出去但**处理**必须在境内 | 部分政务与关键行业 |
| **L3 访问控制** | 数据可以存在境外但**境内实体的访问**受控 | 常见于大企业的集团内跨境 |

> **L3 最容易被忽略**——
> 「数据存在境外」听起来违反本地化，
> 但很多法规真正限制的是**「境内主体能不能访问」**。
> **这个区别直接决定架构**：
> L3 允许用境外的模型服务（前提是访问被管控并留痕），
> L1/L2 则要求模型与存储都在境内。

> **⚠️ 这条判断对 AI 系统尤其关键**：
> **「能不能用海外的模型 API」不是技术问题，是数据出境问题**——
> 如果请求里带了个性信息，那这个请求就是一次跨境传输。

## 3. 贸易合规：制裁与出口管制

**这是外贸场景里最硬的闸门。**

### 3.1 名单体系

**多套名单并存，必须一起筛。**

| 名单 | 管辖区 | 内容 |
|---|---|---|
| **OFAC SDN** | 美国 | 特别指定国民清单 |
| **欧盟综合清单** | 欧盟 | 统一的综合金融制裁清单 |
| **BIS Entity List** | 美国 | 出口管制实体清单（与技术出口相关） |
| **UK OFSI** | 英国 | 金融制裁目标清单 |

> **工程上最关键的一条规则**：
> **四份名单必须一起做精确匹配，不能只筛一份。**
> 漏筛任何一份 = 合规缺口。
> **而且「名单没导入」应该「拦截」而不是「放行」**——
> 名单不全时，业务应该停下，而不是默认通过。

### 3.2 筛查的时机（不只是签约时）

| 时机 | 查什么 |
|---|---|
| **线索入库时** | 早期就筛，**避免给被制裁方投入资源** |
| **联系/报价前** | 交易对手 |
| **签约前** | 交易对手 + **最终用户/最终用途** |
| **付款环节** | 银行信息、受益所有人 |
| **定期复筛** | **名单会更新**——名单入库时的结论会过期 |

> **「定期复筛」最容易被漏**：
> 一个季度前合规的交易对手，
> 三个月后可能进了名单。
> **名单版本 + 筛查时间必须留档。**

### 3.3 匹配方式

| 方式 | 说明 | 局限 |
|---|---|---|
| **精确匹配** | 名单里的 ID / 名称全等 | 漏掉别名与拼写变体 |
| **归一化匹配** | 去空格/大小写/标点后比对 | **基线做法** |
| **模糊匹配** | 编辑距离、发音相似 | **误报多**——但漏报更致命 |
| **强关联筛查** | **实控人、股东、受益所有人、关联公司、银行账户** | **最容易被漏** |

**工程上常见的三段式**：

```
① 归一化精确匹配        → 高置信，直接命中/直接排除
② 模糊匹配（阈值高）    → 进人工复核队列
③ 人工裁决              → 记录理由，**命中不得人工放行**
```

> **「命中后不能人工放行」是外贸场景的关键规则**——
> 与本库 15 主线的「红线破线即停」是同一条原则：
> **有些闸门不给人「酌情处理」的余地。**

### 3.4 次级制裁（Secondary Sanctions）

**真正的难点不是直接命中，而是「关联」。**

| 关联类型 | 说明 |
|---|---|
| **50% 规则** | 被列名实体直接或间接拥有 ≥50% 的实体 → **一并受限** |
| **实控人** | 即使不在名单上，受被列名实体控制也受限 |
| **船舶/运输** | 特定船舶与运输服务受限 |
| **金融通道** | ** correspondent banking ** 受限——**钱根本汇不出去** |
| **转口** | 经第三国转运仍可能触发 |

> **实务结论**：**只做「交易对手在不在名单上」的筛查是不够的**——
> **受益所有人、关联公司、银行通道都要覆盖**，
> 否则会在付款环节被打回，而那时货已经发了。

### 3.5 出口管制（技术出口）

**AI/技术产品的额外维度**：不仅看交易对手，还看**物项本身**。

| 维度 | 说明 |
|---|---|
| **管制清单（CCL）** | 受控物项分类 |
| **最终用途** | 军事、监控、大规模监控等用途受限 |
| **最终用户** | 特定实体（尤其军工背景）受限 |
| **再出口** | 转口到第三国仍受原管辖权约束 |
| **技术支持** | **提供技术支持本身也可能被管制** |

> **「AI 服务算不算技术支持」是个真问题**——
> 这需要法务按具体物项与具体场景判断，**不能由工程自行决定**。

## 4. 地区化产品要求

**同一款产品在不同市场，标签、说明书、认证、数据处理都可能不同。**

| 项 | 典型差异 |
|---|---|
| **标签语言** | 强制要求本地语言；某些市场要求特定字体与位置 |
| **成分/材料披露** | 欧盟 REACH、美国加州 Prop 65 等 |
| **安全警示** | 图形符号（ISO 7010）、多语言警示语 |
| **认证标志** | CE / UKCA / FCC / 各国本地认证 |
| **说明书** | 语种、可读性（视障要求）、格式 |
| **能效标签** | 部分品类强制 |
| **数据驻留** | 是否要求数据存在本地 |
| **隐私政策** | 本地版本，且要符合当地披露要求 |

> **工程落地方式**：
> **把「地区要求」做成配置（region profile），而不是散落在代码里**——
> 和 [`03`](./03-跨文化改写而非直译.md) 的「市场画像卡」是同一个机制。

## 5. 工程落地的合规能力清单

### 5.1 数据侧

- [ ] **数据流图**完整且与实际架构一致（能对外交代）
- [ ] 数据分类分级完成（哪些能出境、哪些不能）
- [ ] 跨境传输的机制与合同条款已确定（法务确认）
- [ ] **影响评估记录**留存
- [ ] 用户同意的记录与撤回机制
- [ ] 访问控制与删除机制（**含境外副本的删除**）
- [ ] 处理者协议（DPA）与子处理者清单
- [ ] **模型调用的出网清单**（哪些 API 会把数据带出境）

### 5.2 贸易侧

- [ ] **四份名单都接入**，且有版本与更新机制
- [ ] **名单不可用时阻断业务**（不是放行）
- [ ] 归一化 + 模糊匹配 + 人工复核队列
- [ ] **实控人/受益所有人/关联公司**筛查
- [ ] 名单版本 + 筛查时间 + 筛查结果**留档**
- [ ] 定期复筛机制
- [ ] 命中后的处置流程（**无人工放行**）
- [ ] 银行信息也要筛查

### 5.3 地区化侧

- [ ] region profile 配置化（标签/警示/认证/隐私政策）
- [ ] 每个目标市场的清单（要哪些认证、哪些语言）
- [ ] 变更管理（法规变化 → 谁来更新 profile）

> **三条里最容易漏的是贸易侧的「名单不可用时阻断」**——
> 它是一个**可用性设计**：如果名单接口挂了业务就停，
> 那运营一定会要求「先放行再说」。**这个要求必须被拒绝。**
> 做法是**本地缓存 + 版本校验 + 明确的降级策略**（降级到「用最近一次同步的名单」，
> **而不是「不筛查」**）。

## 6. 工程结论

1. **数据合规与贸易合规是两套体系**：
   数据合规决定「架构能不能这么设计」，贸易合规决定「能不能跟这个人做生意」。
2. **数据跨境要答三层**：能不能出境 / 出境的条件 / 境外处理者是否合规。
3. **数据本地化有 L1/L2/L3 三层，L3（访问控制）最容易被忽略**——
   它决定「能不能用海外的模型 API」。
4. **AI 系统的每次模型调用都可能是跨境传输**——
   请求里带个人信息，就是一次出境。
5. **制裁筛查要覆盖四份名单**（OFAC SDN / 欧盟 / BIS / UK OFSI），
   **名单不可用时必须阻断业务**（降级到最近一次同步的名单，不是「不筛查」）。
6. **只筛交易对手不够**：受益所有人、实控人、关联公司、**银行通道**都要覆盖——
   **否则会在付款环节被打回，那时货已经发了**。
7. **名单会更新 → 定期复筛**，并留档「名单版本 + 筛查时间」。
8. **命中不得人工放行**——有些闸门不给人「酌情处理」的余地。
9. **出口管制看的不只是人，还有物项、最终用途、最终用户**——
   **「AI 服务算不算技术支持」需要法务判断，不能由工程自行决定**。
10. **地区化要求要配置化**（region profile），不要散落在代码里。
11. **工程上要落的四件事**：数据流图、分类分级、传输机制、留档。
