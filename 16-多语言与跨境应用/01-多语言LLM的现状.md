# 多语言 LLM 的现状

> **核心问题**：同一个模型换成另一种语言就变笨了？多语言到底难在哪？

---

## 0. 三个必须先分清的概念

| 概念 | 含义 | 难度 |
|---|---|---|
| **多语能力（Multilingual）** | 模型本身会多种语言 | **训练数据决定**，大部分开源模型已覆盖 100+ 语言 |
| **翻译（Translation）** | 把 A 语言的文本翻成 B 语言 | **相对容易**——翻译数据是高质量的平行语料 |
| **跨语言推理（Cross-lingual Reasoning）** | 用 B 语言思考，得出正确的答案 | **最难**——推理链条在语言间不通 |

> **关键认知**：
> **「模型会说法语」≠「模型用法语思考」。**
> 一个模型可能能写出通顺的法语营销文案，
> 但**让它用法语做多步推理或读懂法语技术文档**，效果会明显下降。

---

## 1. Token 效率：多语言的第一笔账

**同样内容，不同语言的 token 数差别很大。**

| 语言 | 相对 token 数（vs 英文） | 说明 |
|---|---|---|
| 英文 | 1.0× | 基准 |
| **中文** | **~1.5~2×** | 一个汉字常需 1~3 个 token |
| **日文** | ~1.5~2.5× | 汉字 + 假名混合 |
| **德文** | ~1.3× | 复合词长 |
| **阿拉伯文** | ~2~3× | 词根形态，形态变化多 |
| **俄文** | ~1.5× | 西里尔字母，形态变化多 |
| **印地语** | ~2~3× | 形态变化 + 音标 |
| **泰文** | ~2~3× | 无空格分词，需子词切分 |
| **代码** | ~2~3× | 符号碎片化（见 10 主线） |

> **影响**：同样 32K 的上下文窗口，
> **英文能塞 32K 词，中文可能只能塞 16~20K 字**。
> 跨语言系统的**成本与上下文容量**要按语言分别算。

### 1.1 一个实用做法

**在设计多语言系统时，用「目标语言的 tokenizer」做预算，而不是用「英文的 token 数 × 经验系数」**：

```python
for lang in ["en", "zh", "ar", "th"]:
    tok = AutoTokenizer.from_pretrained(model)
    n = len(tok.encode(sample[lang]))
    print(f"{lang}: {len(sample[lang])} chars -> {n} tokens")
```

> **同一条 prompt 的四种语言版本，token 数能差 2~3 倍**——
> 这直接决定了成本，也决定了「多语言版本要不要按语言分配不同预算」。

## 2. 多语言能力的分层

**模型的多语言能力不是「支持/不支持」的二元，而是分层的。**

| 层 | 能力 | 典型表现 |
|---|---|---|
| **L1 存在** | 见过这种语言 | 能输出像样的句子 |
| **L2 流畅** | 语法地道、用词自然 | **母语者看不出是机器写的**（营销文案能做到） |
| **L3 准确理解** | 能读懂技术文档、法律条款 | 中等资源语言开始掉点 |
| **L4 跨语言推理** | 用该语言多步推理 | **只在高资源语言上可靠** |

### 2.1 各层在业务里的对应

| 任务 | 需要哪一层 | 难度 |
|---|---|---|
| 分类 / 打标 | L1 | **低** |
| 翻译 | 翻译能力（独立于 L1~L4） | **低** |
| 客服话术 | L2 | 中 |
| **技术文档问答** | **L3** | **中高** |
| **多步推理 / 合同条款分析** | **L4** | **高** |

> **这是多语言项目最常见的错配**：
> 用 L2 的能力去做 L4 的任务——
> 「能写出通顺的阿拉伯语客服话术」不代表
> 「能读懂阿拉伯语的合同并找出风险条款」。

---

## 3. 三种做多语言的方式

### 3.1 方式一：直接用目标语言（Native）

```
用户输入（西班牙语） → 模型（多语言） → 输出（西班牙语）
```

| 优点 | 缺点 |
|---|---|
| **保留原文的细节与语气** | **受限于模型在该语言上的能力** |
| 一次调用，无翻译损耗 | 低资源语言质量差 |
| 延迟低（无翻译环节） | 需要该语言有足够训练数据 |

### 3.2 方式二：翻译中转（Translate-then-Respond）

```
源语言 → 翻译成英文 → 用英文 LLM 处理 → 翻译回目标语言
```

| 优点 | 缺点 |
|---|---|
| **用上了最强的英文能力** | **两次翻译损耗**：语义、语气、格式都可能丢 |
| 工具调用、逻辑推理都在英文空间里做 | 延迟翻倍 |
| 适合「英文语料为主的知识库」 | **文化适配几乎为零**（见 [`03`](./03-跨文化改写而非直译.md)） |

> **判断标准**：
> **任务的核心难度在「理解与推理」→ 方式二可能更稳**；
> **任务的核心难度在「表达与文化」→ 方式一必须**。

### 3.3 方式三：混合（推荐）

```
用户输入（目标语言）
   ↓
【意图/关键实体】抽取 → 用目标语言或结构化输出
   ↓
【需要强推理的部分】→ 翻译到英文处理（可选）
   ↓
【表达】→ 用目标语言 + 术语表 + 风格约束生成
```

> **混合方式是工程上最实用的**：
> **让每一步用它最擅长的语言**。

## 4. 术语一致性：多语言系统最隐蔽的坑

### 4.1 问题

```
同一个产品名，在系统里被翻译成三种：
  产品页：   "High-Performance Screwdriver"  (英文)
  报价单：   "Hochleistungs-Schraubenzieher" (德文)
  邮件模板： "高性能电动螺丝刀"               (中文)
```

**用户会认为这是三个不同的产品。**

### 4.2 影响的业务场景

| 场景 | 后果 |
|---|---|
| **报价与合同** | **术语不一致 = 条款指向不明 = 法律风险** |
| **认证与资质** | 认证名称必须与官方名称一致（否则验真失败） |
| **产品检索** | 用户用本地语言搜不到 |
| **工单流转** | 跨部门交接时信息丢失 |

### 4.3 解法：术语表（Glossary）作为一等公民

```
术语表条目 = {
  "zh": "高性能电动螺丝刀",
  "en": "High-Performance Electric Screwdriver",
  "de": "Hochleistungs-Elektroschraubenzieher",
  "ar": "مفكات كهربائي عالي الأداء",
  "canonical": "SCR-1024",          # ★ 内部唯一标识
  "do_not_translate": true,          # ★ 型号/认证号不翻译
  "notes": "德文用复合词；勿译为 'Hochleistungs-Schraubendreher'"
}
```

**三条规则**：

| # | 规则 | 说明 |
|---|---|---|
| **1** | **内部用唯一 ID 对齐**，各语言只是展示层 | 数据模型层面解耦 |
| **2** | **型号、认证号、代码不翻译** | 翻译了就找不到了 |
| **3** | **术语表进 prompt，并且是「强约束」** | 见 [`02`](./02-多语言Agent的术语一致性.md) |

## 5. 多语言评测

### 5.1 公开基准

| 基准 | 测什么 | 局限 |
|---|---|---|
| **MGSM / GSM8K 多语版** | 数学推理 | 题目翻译质量影响大 |
| **MMLU 多语版** | 知识 | 部分语言题目质量差 |
| **FLAME** | 多语言理解 | 小模型 |
| **MIRACL** | 多语言检索 | 检索场景 |
| **XNLI** | 跨语言 NLI | 旧但常用 |
| **CULTURE** | 文化理解 | 覆盖有限 |

### 5.2 公开基准测不出的四件事

| 测不出 | 为什么 |
|---|---|
| **术语一致性** | 公开集没有「你的产品名」 |
| **文化适配** | 「说得地道」≠「说得对（符合当地习惯）」 |
| **商业说服力** | 母语者觉得「像本地人写的」吗 |
| **专业领域准确性** | 技术术语、法律条款、认证名称 |

> **结论**：**多语言项目必须自建评测集**（见 [`04`](./04-多语言评测集构建.md)）。

### 5.3 翻译质量指标为什么不够

| 指标 | 问题 |
|---|---|
| **BLEU** | 与人类判断相关性差；**高分也能是坏翻译** |
| **chrF** | 比 BLEU 好，但仍只看字符重合 |
| **COMET / BERTScore** | 基于学习的语义相似度，**更接近人类判断** |
| **LLM-as-Judge** | 可用，但**要按语言分别校准**（判官在某些语言上本身就弱） |

> **翻译指标只能当「筛查」用，不能当「验收」用。**
> **验收要用任务级指标**（生成的回答是否解决了问题）。

## 6. 多语言 RAG

**检索侧的多语言问题与生成侧完全不同。**

| 问题 | 说明 | 对策 |
|---|---|---|
| **查询与文档语言不一致** | 用户用中文问，库里有英文文档 | **多语言嵌入模型**（如 multilingual-e5、bge-m3） |
| **检索召回不均** | 某些语言召回率显著低 | **按语言分别评测召回率**；必要时**双语 query 扩展** |
| **重排器语言偏置** | 交叉编码器重排对某些语言弱 | **评测重排后的分语言指标** |
| **术语匹配** | 搜「螺丝刀」找不到 "Screwdriver" | **术语表参与 query 改写** |

### 6.1 一个必须做的检查

```
按语言分别统计：Recall@K、MRR、nDCG@10
```

> **如果只报一个总的 Recall@K，低资源语言的严重下滑会被平均掉。**
> **这和 11 主线里「盲测对照」的思路一样：分语言看，不要看总体。**

---

## 7. 工程结论

1. **「会说法语」≠「会用法语思考」**——
   多语言能力分四层（L1 存在 / L2 流畅 / L3 准确理解 / L4 跨语言推理），
   **用 L2 的能力做 L4 的任务是常见的错配**。
2. **token 效率按语言差 2~3 倍**——**成本与上下文容量要按目标语言的 tokenizer 算**。
3. **翻译中转适合「理解与推理」难的任务；表达与文化类任务必须用目标语言直接生成。**
4. **术语一致性是多语言系统最隐蔽的坑**，且**在合同与报价里会变成法律风险**。
5. **术语表要作为一等公民**：内部唯一 ID + 各语言展示层 + `do_not_translate` 标记。
6. **公开基准测不出术语一致性、文化适配、商业说服力、专业准确性**——
   **必须自建评测集**。
7. **翻译指标（BLEU/chrF）只能筛查不能验收**；
   **LLM-as-Judge 要按语言分别校准**。
8. **多语言 RAG 要分语言统计召回率**——总体数字会掩盖低资源语言的严重下滑。
9. **最实用的架构是「混合式」**：让每一步用它最擅长的语言。
