# 多语言 Agent 的术语一致性

> **核心问题**：同一个产品在四种语言里叫四个名字，怎么保证它们指的是同一个东西？

---

## 0. 为什么 Agent 场景的术语问题更严重

| 场景 | 术语不一致的后果 |
|---|---|
| **静态文案**（产品页） | 用户困惑，但**影响有限** |
| **客服问答** | 用户拿到错误信息 → **信任崩塌** |
| **报价与合同** | **条款指向不明 → 法律风险** |
| **Agent 调工具** | **工具参数填错 → 直接操作错对象** ⭐ |
| **跨部门工单** | 信息在交接中丢失，**责任无法追溯** |

> **Agent 场景的特殊性**：
> 在文本场景里，术语错了只是「话说错了」；
> 在 Agent 场景里，**术语错了会让系统「对正确的人做了错的事」**。

```
用户（德语）："Wie ist der Status der Bestellung SCR-1024?"
    ↓
系统抽取订单号 → "SCR-1024"（型号不翻译 ✅）
    ↓
如果系统把型号也翻译成 "SCR-1024-Bestellung" 或误抽成别的
    ↓
工具调用查到了错误的订单 → **给用户报错状态**
```

## 1. 术语表的结构

**术语表是数据，不是提示词里的几句话。** 结构：

```json
{
  "canonical_id": "SCR-1024",
  "type": "product_model",
  "display_names": {
    "zh": "高性能电动螺丝刀 SCR-1024",
    "en": "High-Performance Electric Screwdriver SCR-1024",
    "de": "Hochleistungs-Elektroschraubenzieher SCR-1024",
    "ar": "مفكات كهربائي عالي الأداء SCR-1024"
  },
  "aliases": {
    "en": ["SCR-1024", "SCR1024", "Screwdriver SCR-1024", "旧型号 SCR-900"]
  },
  "do_not_translate": true,
  "specs": { "power": "450W", "certifications": ["CE", "RoHS", "UL"] },
  "notes": "德文市场用 'Elektroschraubenzieher'，勿用 'Schraubendreher'"
}
```

### 1.1 字段说明

| 字段 | 作用 |
|---|---|
| **`canonical_id`** | **内部唯一标识，永远不变**。所有语言、所有系统都用它对齐 |
| **`display_names`** | 各语言的**规范展示名**（唯一，不允许有第二个） |
| **`aliases`** | **别名**（旧型号、供应商叫法、口语叫法、拼写变体）——**用于识别，不用于展示** |
| **`do_not_translate`** | 型号/认证号/代码 → **任何语言下都不翻译** |
| **`specs`** | 结构化参数。**让模型引用参数而不是复述** |
| **`notes`** | 翻译注意事项（用词偏好、禁用词） |

> **`canonical_id` 与 `display_names` 分离是整个设计的关键**：
> 数据模型层面就解耦了「这是什么」和「这怎么说」。

## 2. 术语的四个层级

**不同层级的术语，处理方式完全不同。**

| 层级 | 例子 | 处理方式 |
|---|---|---|
| **L1 标识符** | 型号 `SCR-1024`、认证号 `CE 1234`、料号 `P/N-88` | **永不翻译**。正则可校验 |
| **L2 产品与品牌名** | 产品名、公司名、品牌 | **规范译名唯一**；品牌名一般保留原文 + 音译 |
| **L3 领域术语** | 「螺距」「扭矩」「IP65」「FOB」 | **有标准译法**（用行业术语表） |
| **L4 通用词** | 「快速」「可靠」「高质量」 | **交给模型**（但要风格约束） |

> **一个实用判断**：
> **L1/L2 用术语表强制；L3 用术语表辅助；L4 交给模型 + 风格约束。**
> **把 L4 也管起来是不现实的**（那是文案风格，不是术语一致性）。

### 2.1 L1 的正则校验（最容易做，也最有效）

```python
import re

# 从术语表生成「必须保持不变」的标识符集合
IMMUTABLE = {e["canonical_id"] for e in glossary if e["do_not_translate"]}

# 校验：输出中出现的型号类 token 必须都在术语表里
IDENTIFIER_RE = re.compile(r"\b[A-Z]{2,}-\d{2,}\b")

def check_identifiers(text: str) -> list[str]:
    found = set(IDENTIFIER_RE.findall(text))
    return sorted(found - IMMUTABLE)     # 空 = 通过
```

**这类断言可以进 CI**：
每次改 prompt 或换模型，都自动跑一遍——
**它比任何「提示模型保持一致」都可靠。**

## 3. 术语表怎么进 prompt

**三种方式，可组合。**

### 3.1 方式一：System Prompt 内嵌（术语少时）

```
<glossary>
- SCR-1024 = 高性能电动螺丝刀 (不可翻译)
- CE = 欧盟认证标志 (不可翻译)
- FOB = 船上交货 (使用行业标准译法)
</glossary>
```

| 优点 | 缺点 |
|---|---|
| 简单、**模型一定看得到** | 占 token；术语多了会稀释注意力 |
| 适合 **< 50 条**的稳定术语 | 每次请求都带全部术语，**浪费** |

### 3.2 方式二：检索注入（术语多时）

```
用户提到某实体 → 检索该实体的术语条目 → 注入到 prompt
```

| 优点 | 缺点 |
|---|---|
| **只带相关的**（省 token） | **依赖检索正确**——检索漏了就用错译名 |
| 术语表可以很大 | 需要实体链接（把用户输入里的提及映射到 canonical_id） |

> **实体链接是多语言的关键环节**：
> 用户可能说「那个1024的螺丝刀」「SCR1024」「老型号」——
> **都要映射到 `SCR-1024`**。这需要别名表 + 向量检索 + 规则（正则匹配型号）。

### 3.3 方式三：后处理替换（最可靠，但有代价）

```
生成完 → 用词典把非规范译名替换成规范译名
```

| 优点 | 缺点 |
|---|---|
| **100% 保证术语一致** | **可能破坏语法**（替换后词序/大小写不对） |
| 不依赖模型配合 | 需要维护「非规范译名 → 规范译名」的映射 |
| 可与前两种叠加 | 替换数量多时人工要复核 |

> **推荐组合**：
> **方式二（注入）+ 方式三（后处理校验与替换）**
> ——模型侧给正确的上下文，输出侧兜底。

### 3.4 后处理的三条规则

```python
def normalize_terms(text: str, glossary: list[dict], lang: str) -> str:
    # ① 规范译名 → 保留
    # ② 已知的非规范译名 → 替换为规范译名
    # ③ 同一段内出现的"其他语言的规范译名" → 替换为当前语言的
    for e in glossary:
        canonical = e["display_names"][lang]
        # 把其他语言的规范名也当作"需要替换"的
        for other_lang, name in e["display_names"].items():
            if other_lang != lang and name and name != canonical:
                text = text.replace(name, canonical)
        # 替换别名
        for alias in e.get("aliases", {}).get(lang, []):
            text = text.replace(alias, canonical)
    return text
```

> **第 ③ 条规则最有价值**：
> **模型偶尔会串语言**（在德语回复里夹一个英文产品名），
> 这条规则能自动把它改回来。

## 4. 多语言知识库的数据模型

**知识库的多语言不是「存多份文档」，而是「一份事实 + 多个语言视图」。**

```python
@dataclass
class LocalizedContent:
    canonical_id: str              # 全局唯一
    content: dict[str, str]        # {"zh": "...", "en": "...", "de": "..."}
    version: str                   # 事实版本（不随语言变）
    updated_at: str
    fallback_chain: list[str]      # ["en", "zh"]  ← 缺失语言的回退链
```

### 4.1 三条设计规则

| # | 规则 | 原因 |
|---|---|---|
| **1** | **事实只存一份**（结构化字段 + 版本号） | 避免各语言版本的事实漂移 |
| **2** | **长文本按语言存**，但**结构化字段全局唯一** | 长文本确实需要本地化；参数/价格不能有多个版本 |
| **3** | **缺失语言走回退链**（如 `ar` → `en` → `zh`），**并在输出里标注** | 静默回退会让用户拿到不对语言的答案 |

### 4.2 回退链要「明说」

```python
def get_content(cid: str, lang: str) -> tuple[str, str]:
    """返回 (内容, 实际使用的语言)"""
    for l in fallback_chain(lang):
        c = store.get((cid, l))
        if c:
            return c, l
    return "", lang
```

**然后在回答里说明**：

> 「以下内容来自英文版（该产品暂无阿拉伯语详情），如需其他语言请联系我们。」

> **静默回退是跨语言系统的经典事故源**——
> 用户以为拿到的是当地信息，实际是英文原文（可能是美国口径的价格或条款）。

## 5. 实体对齐与去重

**同一个东西在数据源里有多个名字。**

| 来源 | 叫法 |
|---|---|
| 官网 | `SCR-1024 Electric Screwdriver` |
| 供应商 A | `Schraubenzieher SCR-1024` |
| 供应商 B | `SCR1024-SD` |
| 老系统 | `电动螺丝刀A型` |

**对齐流程**：

```
① 规范化：去空格/大小写/连字符 → 得到候选键
② 精确匹配：型号正则命中 canonical_id
③ 别名表匹配：aliases 命中
④ 向量匹配：语义相似度（处理俗称、老名字）
⑤ 人工确认：低于阈值的一律进人工
```

> **第 ⑤ 步不能省**——
> **错误合并比未合并更危险**（两个产品被当成一个），
> **错误拆分只是效率损失**。

## 6. 工具调用里的术语

**这是最容易出事、也最少被讨论的地方。**

| 场景 | 风险 |
|---|---|
| **工具参数是自然语言** | 「查一下那个 1024 的螺丝刀」作为参数传进去 → **下游查不到** |
| **工具参数是 ID** | 模型需要先做实体链接 → **链接错了就调错对象** |
| **工具返回是自然语言** | 返回里的术语进入下一轮上下文 → **污染后续** |

### 6.1 三条设计规则

| # | 规则 | 说明 |
|---|---|---|
| **1** | **工具参数用 canonical_id，不用自然语言** | 让实体链接在**模型之外**做（确定性） |
| **2** | **工具返回值里的实体名也做规范化** | 防止污染下一轮 |
| **3** | **不可逆操作前用规范译名复述** | 「确认要删除订单 SCR-1024 吗？」——**用户看得懂那个 ID** |

> **第 1 条是最重要的**：
> **让模型输出「看起来对」的 ID 是不可靠的**——
> 它可能幻觉出一个不存在的型号。
> **更稳的做法是：模型输出提及，实体链接器输出 ID，工具只接受 ID。**

### 6.2 实体链接作为一道闸

```
用户输入 ──▶ [模型抽取提及] ──▶ [实体链接器：提及 → canonical_id]
                                        │
                          置信度够 ──────┼────── 置信度不够
                             │                     │
                        工具用 ID              ★ 转人工澄清
```

> **这一道闸同时解决了「术语不一致」和「幻觉 ID」两个问题**——
> 它是本库 15 主线「能力层」的又一个实例。

## 7. 一致性校验清单（可进 CI）

| # | 断言 | 怎么判 |
|---|---|---|
| 1 | **每个实体在每个目标语言都有且只有一个规范译名** | 术语表结构校验 |
| 2 | **型号/认证号在所有语言中保持不变** | 正则提取 + 集合比对 |
| 3 | **输出中出现的型号都在术语表里**（无幻觉 ID） | 正则 + 集合差 |
| 4 | **同一段落内同一实体不出现两个不同译名** | 同段扫描 + 别名归一 |
| 5 | **输出中没有混入其他语言的规范译名** | 跨语言名扫描 |
| 6 | **回退到其他语言时，输出里标注了实际语言** | 模板校验 |
| 7 | **数字、金额、单位的本地化格式正确**（小数点/千分位/货币符号） | 格式正则 |

> **第 7 条经常被漏**：
> 德语用 `1.234,56 €`，中文用 `1,234.56 元`——
> **数字格式错在跨境场景里是实实在在的商务事故。**

## 8. 工程结论

1. **术语一致性在 Agent 场景比文本场景严重**——
   **术语错 = 对正确的人做了错的事**。
2. **数据模型层面解耦**：`canonical_id`（内部唯一，永不变）+ `display_names`（各语言展示层）。
3. **四个层级分别处理**：L1 标识符永不翻译、L2 产品名规范唯一、L3 领域术语用行业表、
   L4 通用词交给模型 + 风格约束。
4. **三种注入方式组合用**：注入（system / 检索）+ **后处理替换兜底**。
   **后处理能 100% 保证一致，但可能破坏语法**。
5. **「其他语言的规范译名」也要纳入替换规则**——
   这能自动修掉模型串语言的问题。
6. **事实存一份，长文本按语言存，结构化字段全局唯一**。
7. **缺失语言走回退链，但必须「明说」**——
   **静默回退会让用户拿到不对口径的信息**。
8. **实体对齐要有人工确认环节**——**错误合并比未合并更危险**。
9. **工具参数用 canonical_id，实体链接放在模型之外做**——
   **这一道闸同时解决术语不一致与幻觉 ID**。
10. **一致性要靠机器可判的断言（7 条）保证，不要靠提示模型保持一致。**
