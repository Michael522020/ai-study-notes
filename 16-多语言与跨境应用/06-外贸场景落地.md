# 外贸场景落地

> **核心问题**：外贸的 AI 场景和别的行业有什么不同？哪些设计是「外贸特有」的？

---

## 0. 三个典型场景

| 场景 | 核心动作 | 最大的风险 |
|---|---|---|
| **① 询盘应答** | 收到询盘 → 识别语言与意图 → 检索产品/报价/认证 → **写回复草稿** | **发错**（不可逆 + 商务承诺） |
| **② 获客** | 采集线索 → 清洗去重 → 富化 → **ICP 评分** → 生成触达素材 → 询盘分级 | **骚扰**（合规与品牌） |
| **③ 投标/技术标** | 招标资料 → 拆要求 → 分章节 → 起草 → **证据核对与放行** | **承诺无依据**（法律风险） |

> **三个场景的共同点**：
> **AI 的产出都是「对外的」**——一旦发出去就收不回来。
> **所以它们的设计重点都不是「让 AI 更聪明」，而是「让 AI 更不敢」。**

---

## 1. 场景一 · 多语种询盘应答

### 1.1 链路

```
多渠道接入（平台 / 邮件 / IM）
        ↓
① 去重与反垃圾        ← ★ 幂等
        ↓
② 语言识别 + 客户识别
        ↓
③ 检索：产品 / 报价 / 认证
        ↓
④ 生成目标语言草稿
        ↓
⑤ 红线校验（N 条）
        ↓
⑥ 只写入待审队列  →  人工审阅 → 人工发送
```

### 1.2 三个关键设计

#### ① 去重与反垃圾放在最前

```
重复推送同一条询盘 → 直接返回 {"duplicate": true}
```

**为什么放最前**（三个理由）：

| 理由 | 说明 |
|---|---|
| **成本** | 重复询盘重复消耗 token、重复检索 |
| **数据质量** | 重复记录会污染评测集与统计 |
| **合规** | 重复的营销触达可能构成骚扰 |

> **「幂等 + 去重」是所有接入端点的必备设计**，不只是外贸场景。

#### ② 检索优先于生成

```
问题 → 检索结构化的产品/报价/认证数据 → 在检索结果上组织语言
```

> **不要让模型「凭记忆」报价与认证**——
> **报价与认证是事实，必须来自数据源。**
> 这与本库 03 主线的 RAG 原则一致，也是 [`02`](./02-多语言Agent的术语一致性.md)
> 术语表机制存在的前提。

#### ③ 红线校验（N 条）+ 只生成不发送

| 红线类型 | 例子 |
|---|---|
| **含报价** | 涉及具体价格、报价单、折扣 |
| **新客户** | 未经审核的新交易对手 |
| **承诺类表述** | 交期、赔付、保修、认证承诺 |
| **合规风险** | 制裁命中、禁运行业、受限物项 |
| **技术承诺** | 规格、性能、兼容性承诺 |

> **红线的设计原则：宁可多拦。**
> **一条误拦（多一次人工确认）的代价 << 一条漏拦（发错报价）的代价。**

**「只生成不发送」是这个场景的正确默认值**：

```
AI 产出 → 写入待审队列（状态 pending_review）→ 人工审 → 人工发送
```

> **这与本库 15 主线的「不可逆动作必须人工闸」是同一条原则。**

### 1.3 关键指标

| 指标 | 说明 |
|---|---|
| **草稿采纳率** | 人工审后直接用的比例（**最核心**） |
| **红线拦截率 / 误拦率** | 两条都要看 |
| **重复询盘识别准确率** | |
| **语言识别准确率** | 混合语言、多语言询盘是难点 |
| **响应时间**（从收到到草稿就绪） | |
| **人工修改幅度** | 改得越多 = 模型越没用 |

> **「人工修改幅度」比「采纳率」更能反映真实价值**——
> 采纳但大幅修改 = 模型只省了打字时间。

## 2. 场景二 · 外贸获客

### 2.1 依赖图（阶段之间有严格顺序）

```
P0 领域数据模型 + 状态机
  ├─→ P1 线索采集与清洗
  │      ├─→ P2 富化与 ICP 评分
  │      │      └─→ P3 触达素材（只生成不发送）
  │      └─→ P6 评估与回归
  ├─→ P4 询盘分级
  │      └─→ P5 报价辅助（必须人工签字）
  └─→ P3 触达素材
```

> **这张图的价值是「防止依赖倒挂」**：
> **P2 没做完就写开发信，只能得到通用模板**；
> **P5 的产出永远是待审草稿，不是对外报价。**

### 2.2 领域数据模型的三层（外贸特有）

#### ① 状态机：跟进状态是严格的单向流转

```
NO_REPLY → REPLIED → { POSITIVE | OBJECTION | MEETING_SET | NOT_INTERESTED | NURTURE }
                                          ↓
                          BOUNCED / UNSUBSCRIBED / WRONG_CONTACT
```

> **关键规则**：
> **`NOT_INTERESTED` 和 `NURTURE` 必须先有回复，只能从 `REPLIED` 进入。**
> 这不是技术约束，是**业务语义约束**——
> 「没回复过就标记为无意向」会污染数据，也会让后续的自动化决策出错。

#### ② 分档：规模用区间，不用绝对值

| 维度 | 分档方式 | 例子 |
|---|---|---|
| **员工人数** | 区间 + UNKNOWN | `UNKNOWN` / `1-10` / `11-50` / … / `10001+` |
| **年营收** | **人民币分档** | `UNDER_1M_CNY` / `1M_10M_CNY` / … / `OVER_1B_CNY` |

> **为什么要分档而不是精确值**：
> **① 数据源本身给的是区间**（领英/企业库），用精确值是假精确；
> **② 分档对评分更稳健**（营收 9500 万和 1.05 亿在商业上没区别）；
> **③ 区间可枚举、可做规则、可做阈值**。

**注意年营收分档用人民币计**——
这意味着**换算口径是固定的**（见 §4.1）。

#### ③ 评分权重：业务确认的、可追溯的

| 维度 | 权重 |
|---|---|
| 需求匹配 | 30 |
| 时间窗口 | 20 |
| 切换难度 | 15 |
| 角色 | 15 |
| 规模 | 10 |
| 可达性 | 10 |

> **「已确认的权重」和「待业务确认的示例值」要严格区分**——
> **代码里要标注哪些是确认值、哪些是占位**，
> 否则半年后没人知道哪个数字能改。

### 2.3 关键设计

| # | 设计 | 说明 |
|---|---|---|
| **1** | **只生成不发送** | 开发信只写入 `outbox/`，状态 `pending_review`；**代码里没有 SMTP/WhatsApp/LinkedIn 发送** |
| **2** | **询盘分级与报价辅助不依赖前面的阶段** | 没有真实样本时，那两步只会编出规则 → **明确「暂时不做」是专业判断** |
| **3** | **制裁筛查前置到入库** | 见 [`05`](./05-跨境合规与数据主权.md) §3 |
| **4** | **P1 的产出必须能直接喂 P2** | P2 依赖 P1 的 `icp_score`；**否则会拿到不干净的分数** |

> **第 2 条特别值得学**：
> **「这个功能暂时不做，因为没有真实样本支撑」是一个成熟的工程判断**——
> 硬做出来的规则在真实数据面前会立刻崩溃。

## 3. 场景三 · 多语言技术标 / 投标

**跨境版本的投标**（见本库 `biaoshu-desk` 的形态）。

### 3.1 核心链路与外贸版的差异

```
招标资料 → 拆要求（R-01 编号）→ 分派章节 → 起草 → 证据核对 → 人工放行 → 导出
```

**跨境版多出来的三件事**：

| # | 事项 | 说明 |
|---|---|---|
| **1** | **规范译名** | 招标要求里的**产品名、认证名必须用目标市场的规范名**（见 [`02`](./02-多语言Agent的术语一致性.md)） |
| **2** | **法规与标准引用** | 目标市场的标准编号（CE/UL/BS/GB）与认证要求**与投标要求逐条对应** |
| **3** | **本地格式** | 标书格式、页数限制、签字盖章、货币、语言 |

### 3.2 「待人工补充」是核心机制

```
资料里没有的资质、案例、数字和承诺 → 一律写成「待人工补充」
```

> **这与本库 03 主线的「证据必须可回指」是同一条原则**，
> 只是应用到了「**没有证据就不要写**」这个方向上。
>
> **跨境投标尤其危险**：
> 把中国的认证说成是目标市场认可的认证（CE vs UL vs 各国本地认证），
> **在投标阶段可能只是废标，在中标后是合规问题**。

### 3.3 多语言投标的一个额外检查

**规范名 + 认证对应表要单独维护**：

| 源（中文） | 目标市场用词 | 认证对应 |
|---|---|---|
| 「CE 认证」 | 「CE-Kennzeichnung」/「CE marking」 | **不是所有产品都要 CE**——按目标市场与品类核对 |
| 「ISO 9001」 | 各市场普遍认可 | 通常可用 |
| 「中国 3C」 | 目标市场**不认** | **必须说明是否需要等效认证** |

> **「把国内认证当作国际认证」是跨境投标的经典错误**——
> **而且它在评审时可能没人指出（评委也不一定懂），到交付时爆。**

## 4. 跨境业务特有的工程约束

### 4.1 汇率口径（最容易出错的一处）

```
fx_rate = 1 单位报价币种兑多少人民币
报价币种是人民币时，fx_rate 必须 = 1
```

> **这条规则看起来琐碎，但它是所有金额计算的地基**。
> **口径必须在数据模型里固定，且有单元测试覆盖**——
> 特别要测「报价币种 = 人民币」这个边界情况。

**三件必须一起定义的事**：

| # | 事项 | 说明 |
|---|---|---|
| **1** | **汇率的时点与来源** | 报价日汇率？当日汇率？哪个数据源？ |
| **2** | **汇率是否含税/运费** | 报价口径必须自洽 |
| **3** | **汇率有效期** | 报价单上的汇率什么时候失效 |

> **「汇率是多少」是采购与销售之间最常见的争议来源**——
> **它必须是一个可追溯的、带时点的数字，而不是一个模型算出来的估算。**

### 4.2 保险与贸易术语（Incoterms）

**CIF / DDP 等术语下，保险规则是硬性的**：

```
保险必须单独写在 insurance 字段
金额 > 0
且 = 发票金额 × 110% × 保险费率
```

> **这类「看起来是业务规则、实际上是公式」的东西，应该写成代码里的校验函数**，
> **而不是写在 prompt 里让模型记住**——
> **本库 15 主线说的「确定性的东西不要交给概率模型」。**

### 4.3 其他外贸特有的约束

| 事项 | 约束 |
|---|---|
| **交期与起订量** | 起订量 100 pcs、交期 30 days 这类参数是**业务确认值**，要能追溯 |
| **报价有效期** | 跨时区的客户需要当地时间 |
| **工作时间** | 消息时间戳用**客户当地时间**显示 |
| **节假日** | 各市场节假日不同 → 跟进节奏要按客户当地时间 |
| **单位与包装** | 装箱量、托盘尺寸（影响运费） |
| **危险品/受限品** | 品类决定能否发货与需要哪些文件 |

## 5. AI 产出的交接（跨团队）

**外贸业务里 AI 的产出经常要交给人继续处理。** 交接的质量决定价值。

| 产出 | 交接给谁 | 交接要求 |
|---|---|---|
| 询盘回复草稿 | 业务员 | **附依据**（引用了哪些产品/报价/认证条目） |
| 线索评分 | SDR | **给分项**（每个维度的分与理由），不要只给总分 |
| 触达素材 | SDR | **标注适用市场**（同一素材在德国和美国不同） |
| 规范译名表 | 内容/SEO | **带内部 ID**（见 [`02`](./02-多语言Agent的术语一致性.md)） |
| 报价草稿 | 商务 | **明确待确认项**（哪些参数是业务确认值、哪些是占位） |

> **一条通用原则**：
> **AI 的产出必须带「依据」和「不确定项」两样东西**——
> **依据让人能复核，不确定项让人知道要补什么。**
> 这与本库 08 主线的「证据回指」是同一条原则的跨场景应用。

## 6. 指标体系

| 类别 | 指标 | 目标 |
|---|---|---|
| **效果** | 草稿采纳率、**人工修改幅度**、询盘分级准确率 | 采纳率提升 + 修改幅度下降 |
| **效率** | 从收到询盘到草稿就绪的时间、每个询盘的成本 | 时延下降 |
| **护栏** | **红线漏拦率（红线）**、重复发送率、制裁漏筛率（红线） | **零漏拦** |
| **商业** | 询盘回复率、进入报价的比例、商机转化率 | **最终看这个** |

> **护栏指标里的两条是红线，不参与综合评分**——
> **破了就停**（同本库 12 主线）。

> **商业指标（回复率、转化率）要滞后看**：
> **AI 辅助回复和「回复得好不好」是两个不同的问题**，
> 而转化率的归因周期长、噪声大——
> **不要把转化率的小幅波动归因到 AI 上。**

## 7. 工程结论

1. **外贸 AI 场景的共同点是「产出都是对外的」**——
   **设计重点不是「让 AI 更聪明」，而是「让 AI 更不敢」**。
2. **去重与反垃圾放最前**（成本 + 数据质量 + 合规三 reasons）。
3. **报价与认证必须检索，不许模型凭记忆**——
   **它们是事实，不是文本**。
4. **红线宁可多拦**——误拦的代价远小于漏拦（发错报价）。
5. **「只生成不发送」是正确默认值**；代码里**不应存在发送能力**。
6. **状态机是单向的**（`NOT_INTERESTED` 只能从 `REPLIED` 进入）——
   **业务语义约束要写进模型与校验，不靠约定。**
7. **规模数据用分档不用精确值**（数据源给的就是区间）。
8. **「暂时不做某个功能，因为没有真实样本支撑」是专业判断**——
   硬做出来的规则在真实数据面前会崩。
9. **汇率口径要固定且有单元测试**（报价币种=人民币时汇率必须=1 这类边界）。
10. **保险这类公式写成代码里的校验函数**，不要写进 prompt。
11. **跨境投标的经典错误是把国内认证当国际认证**——
    **按目标市场与品类逐条核对认证对应表**。
12. **AI 的产出必须带「依据」和「不确定项」**——让人能复核、知道要补什么。
13. **商业指标滞后且噪声大**，**不要把转化率的小幅波动归因到 AI**。
