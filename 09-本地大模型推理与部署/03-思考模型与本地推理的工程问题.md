# 思考模型与本地推理的工程问题

> **核心问题**：qwen3 是「思考模型」，它的思考块到底怎么控制？同一个开关为什么在 CLI、交互模式、API 三处行为都不一样？多出来的思考 token 要怎么算账？

本章记录 2026-11-12 / 2026-11-14 在本机（Ollama 0.40.16 + qwen3:4b）上对思考模型的实测。

**数据口径**：本章 token 数与速度为**本机实测**，标注了测量日期；`--think` 参数的解析机制为**转述自 Ollama CLI 的帮助文本与 pflag 的 flag 语义**，可自行复核。**结论只对本机的模型版本与 Ollama 版本成立。**

---

## 1. 什么是「思考模型」

**思考模型（reasoning / thinking model）** 是在输出正式答案之前，先生成一段**内部分析文本**的模型。

```
用户问题
   │
   ├─► [ 思考块 ]  ← 内部分析，可能很长，可能自我修正
   │
   └─► [ 正式答案 ]
```

Qwen3、DeepSeek-R1、o 系列、QwQ 等都属于这一类。

本机模型元信息里明确标了这一点：

```json
"capabilities": ["completion", "tools", "thinking"]
```

`thinking` 出现在 `capabilities` 里，意味着这个模型**支持思考模式**。

### 1.1 为什么要管它

| 影响 | 说明 |
|---|---|
| **token 消耗** | 思考块也要生成，每个 token 都是钱（本地是电费和等待） |
| **输出延迟** | 同样一个问题，思考模型的总生成时间明显更长 |
| **输出解析** | 思考块混在回答里，下游正则 / JSON 解析会炸 |
| **流式渲染** | 前端要能把「思考中」和「正式回答」分开显示 |
| **评测口径** | 思考 token 算不算进评测？多数榜单**排除**思考部分 |

> 💡 **最实际的痛点是第三个。** 本地跑 4B 模型做抽取任务时，思考块混进 JSON 里，直接导致解析失败——而且失败得很隐蔽，因为「模型返回了看起来像 JSON 但前面有一段废话」的内容，肉眼扫过去很容易当成格式问题。

## 2. 三处开关，三种行为

这是本章的核心。**同一个「关闭思考」的意图，在三个入口上有三种不同的写法，而且其中一种理解是错的。**

### 2.1 CLI 非交互模式：`--think=false`，**必须带等号**

```bash
# ✅ 正确
ollama run qwen3:4b "你的问题" --think=false

# ❌ 错误：字符串 "false" 会漏进提示词
ollama run qwen3:4b "你的问题" --think false
```

**为什么会漏？** 看 `ollama run --help` 里这一行的写法：

```
--think string[="true"]   Enable thinking mode: true/false or high/medium/low for supported models
```

`string[="true"]` 是 pflag（Go 的 flag 库）的 **NoOptDefVal** 记法，含义是：**这个 flag 的值是可选的，不写值时默认取 `"true"`**。

NoOptDefVal 的副作用是：**用空格分隔的写法不会吃掉后面的参数**。所以

```
--think false
```

被解析成 —— `--think` 取默认值 `"true"`（于是思考**没被关掉**），而紧随其后的 `false` 变成了**位置参数**，也就是被当成提示词的一部分追加进 prompt。

模型看到的是一个以 `false` 开头的问题，于是真的会念叨「用户用了 false 开头」之类的话。**同时思考也没关掉。** 一条命令，两个错误。

而 `--think=false` 是**等号形式**，flag 的值被明确解析为 `"false"`，`false` 不会漏进 prompt。

> ⚠️ **这个坑之所以难发现，是因为它不报错。** 命令行正常退出，模型正常返回，只是「关思考」这个意图没生效，而且提示词里多了一句莫名其妙的话。

### 2.2 CLI 交互模式：`/set nothink`

```
/set nothink        ✅
/set think false    ❌ 同样会把 "false" 当成设置项的一部分
```

交互模式里 `notthink` 是**一个整体单词**，不是 `think` + `false` 两个词。写法风格和 CLI 完全相反，这也是第二个容易混的地方。

### 2.3 API 层：**`think: false` 并不关掉思考**

这是本章最重要的一条，也是**最反直觉的一条**。

2026-11-14 本机实测（同一模型、同一问题、`num_predict=500`、`temperature=0`，中文提示词完整送达——`prompt_tok` 24~28 属正常区间）：

| # | 提示词 | `think` 标志 | eval token | `response` 长度 | `thinking` 长度 | 推理文本落在哪 |
|---|---|---|---|---|---|---|
| A | 问题 **+ `/no_think`** | `false` | 500 | **848** | 0 | ⚠️ **`response`（答案字段）** |
| B | 问题 **+ `/no_think`** | `true` | 500 | **0** | **848** | ✅ `thinking`（思考字段） |
| C | 问题（无 `/no_think`） | `false` | 500 | **894** | 0 | ⚠️ **`response`（答案字段）** |
| D | 问题（无 `/no_think`） | `true` | 500 | **0** | **894** | ✅ `thinking`（思考字段） |

**A 和 B 的内容逐字相同（都是 848 字），C 和 D 也逐字相同（都是 894 字）。**

也就是说：

> **`think` 标志不改变模型「想什么」，只改变这段推理被放在哪个字段里。**
>
> - `think: true` → 推理进 `thinking` 字段，`response` 干净。
> - `think: false` → **推理原样留在 `response` 里**，`thinking` 字段是空的。

**所以「`think: false`」的真实语义不是「关闭思考」，而是「不要把它分流出去」。** 模型照样在思考，只是思考内容混进了你以为已经「干净」的答案字段。

**这条对下游的杀伤是直接的**：你在 `think: false` 之后直接拿 `response` 去解析 JSON / 正则抽取，拿到的是**推理前缀 + 答案**，解析必然失败——而且失败得很隐蔽。

### 2.4 提示词里的 `/no_think` 在 API 层**没有可靠效果**

A/C 两组的差别只有提示词末尾有没有 `/no_think`：

| | 推理文本长度 |
|---|---|
| 加了 `/no_think`（A / B） | 848 字 |
| 没加 `/no_think`（C / D） | 894 字 |

**两组基本同量级——`/no_think` 并没有把推理压下去。** 更能说明问题的是 A 组推理文本的原文：

> 「首先，用户要求用三点简要介绍人工智能在制造业的三个典型应用场景。关键点是"三点"和"简要"，所以我需要确保内容简洁、直接，每个点只有一句话或短语。**用户还指定了"/no_think"**」

模型**看见了** `/no_think` 这条指令，还专门在推理里点评了它——**然后照旧推理**。

> ⚠️ **这推翻了一个很流行的说法**：「在提示词里写 `/no_think` 是最可靠的方式」。
> **在本机这个模型 + 这个 Ollama 版本上，它并不可靠。**
>
> 它的可靠性**取决于模型是否把 `/no_think` 当成训练时学过的指令**——这在不同模型、不同版本、甚至不同量化档位上是不同的。本机的 Q4_K_M 档没有可靠执行它。
>
> **这同时说明：任何「关思考」的方法都必须实测验证，不能想当然。**

### 2.5 那么到底怎么关

把三种手段按本机实测结果排个序：

| 手段 | 本机实测效果 | 可靠性判断 |
|---|---|---|
| **API `think: true` + 读 `thinking` 字段** | 推理 100% 与答案分离 | ✅ **唯一可靠的分离方式**——不是「关掉」，是「分开拿」 |
| API `think: false` | ❌ 推理仍在 `response` 里 | ❌ 无效（但**至少字段结构是确定的**，你可以据此自己剥） |
| 提示词 `/no_think` | ❌ 推理照旧（848 vs 894 字） | ❌ 本机无效 |
| CLI `--think=false`（等号形式） | ✅ 记录显示不显示思考块（2026-11-12） | ⚠️ CLI 侧有效，**API 侧不能照搬** |

**推荐的工程做法**：

```python
# ✅ 显式要求分流，然后自己决定要不要用 thinking
resp = client.chat(
    model="qwen3:4b",
    messages=[...],
    think=True,
)
answer   = resp.message.content      # 干净
thinking = resp.message.thinking     # 单独拿，需要的话记进轨迹
```

**代价**：你仍然要付思考 token 的钱（§3）。**这一节解决的是「能不能把两段分开」，不是「要不要思考」。**

> 💡 **一个反向的推论**：如果你的应用**根本不需要思考**（分类、抽取、改写），那么最可靠的「关思考」方式不是任何开关，而是**换一个非思考模型**——或者用 `--think=false` 走 CLI 路径。**任何开关都是在跟模型的固有行为对抗，换模型是顺流而下。**

## 3. 思考 token 的成本账

### 3.1 本机实测

| 配置 | eval token | 生成速度 | 说明 |
|---|---|---|---|
| 2026-11-14，`think=false` + `/no_think`，`num_predict=500` | **500（撞上限）** | 13.09 tok/s | 推理文本在 `response` |
| 2026-11-14，`think=true` + `/no_think`，`num_predict=500` | **500（撞上限）** | 12.92 tok/s | 同样 848 字，移到了 `thinking` |
| 2026-11-14，`think=false`，无 `/no_think`，`num_predict=500` | **500（撞上限）** | 12.83 tok/s | 推理文本在 `response` |
| 2026-11-14，`think=true`，无 `/no_think`，`num_predict=500` | **500（撞上限）** | 13.09 tok/s | 同样 894 字，移到了 `thinking` |

**关键观察：**

1. **生成速度几乎不受影响**（12.8 ~ 13.1 tok/s，四组一致）。**思考 token 和答案 token 是同一个速率生成的**——它不享受任何加速。**你为思考付的每一分钱，都是按标准速率付的。**
2. **四组全部撞上 500 token 上限，而且都没给出答案。** 四次的 `response`（或 `thinking`）内容全是**对任务的分析**——「我需要确保回答是三点」「关键点：三点 / 简要」——**模型把整个预算都花在复述任务要求上，没有走到答案。**

> ⚠️ **第 2 点值得单独强调**：本机 qwen3:4b 对这条提示词的推理**在 500 token 内没有收敛**。这不是「思考模型天然慢」这么轻描淡写的事——**小模型的思考经常不收敛**，它会把预算耗在「我要做三点、每点要简要」这种复述上。
>
> **工程含义**：给小模型用思考模式，必须配 `num_predict` 上限 + 超时兜底，否则会得到「等了半天，一个字答案都没有」的请求。

### 3.2 2026-11-12 那次记录的另一组数字

同一天（2026-11-12）用不同设置测到的一组：

| 配置 | eval token |
|---|---|
| 默认（思考开启） | **327** |
| `--think=false` | **248** |

**思考占约 24%**（327 vs 248，差 79 token）。

> ⚠️ **注意这两组数字的口径差异**：2026-11-12 那组跑到了自然结束（`done_reason=stop`），2026-11-14 这组全部撞上 500 上限。**两组不可直接相减**——但它们共同说明的是同一件事：**思考 token 是纯开销，且按标准速率计费。**

### 3.3 怎么把这笔账算清楚

| 指标 | 公式 |
|---|---|
| **首 token 延迟（TTFT）** | 加载时间 + prompt 评估时间 + **（思考段长度 ÷ 生成速率）** |
| **单次请求总耗时** | TTFT + 答案长度 ÷ 生成速率 |
| **本地能耗** | 整机能耗 × 耗时 |

**思考模型真正吃掉的是 TTFT，不是吞吐。** 用户感知到的「慢」，大部分来自思考段——因为在思考完成之前，屏幕上什么都出不来。

> 💡 **流式输出能显著改善这个体感**：思考块本身也可以流式吐出来，用户看到「正在思考」比看到一片空白要友好得多。**如果你的应用用思考模型，一定要开流式。**

### 3.4 思考 token 算不算评测口径

| 场景 | 常规做法 |
|---|---|
| 能力榜单（如 AIME、MMLU-Pro） | **排除**思考部分，只评最终答案 |
| 端到端延迟测试 | **必须计入**思考 token——那是真实用户等待的时间 |
| 成本对比 | **必须计入**——思考 token 一样要花钱 |

**做「本地模型 vs 云端模型」的性价比对比时，最容易出的错就是只算答案 token。**

## 4. CLI 斜杠命令只在真 TTY 下生效

这是一个纯工程但很致命的坑。

```
# ❌ 管道喂 stdin：斜杠命令被绕过
echo "/help" | ollama run qwen3:4b
```

**现象**：交互模式的斜杠命令（`/set`、`/show`、`/save`、`/clear` 等）**只在真正的终端（TTY）下才被拦截**。一旦 stdin 是管道或重定向文件，CLI 就**把它当成普通提示词原样发给模型**。

**后果**：

| 你以为 | 实际发生 |
|---|---|
| `/set nothink` 关闭了思考 | **模型收到了一个叫 `/set nothink` 的问题**，并开始回答它 |
| `/help` 打印了帮助 | 模型开始解释「/help 是什么意思」 |
| `/save` 保存了对话 | 模型回答「好的，我帮你保存……」 |

**为什么危险**：这些命令在自动化脚本里**不会报错**，只会让模型「回答」一条本该被解释成命令的字符串。脚本跑完了，没有异常，但结果全错。

**规避**：

| 场景 | 做法 |
|---|---|
| 自动化脚本 | **不要用交互模式**，直接用 `ollama run MODEL "PROMPT"` 非交互形式，或直接调 API |
| 需要非交互改设置 | 用**环境变量 / API 字段 / 提示词指令**，不要用斜杠命令 |
| 必须用交互模式 | 用伪终端（`script`、`expect`、Windows 的 ConPTY） |

## 5. 工程结论

1. **API 的 `think: false` 不是「关掉思考」，是「不要分流」。** 推理文本原样留在 `response` 里——**本机四组实测逐字验证**。要干净的回答，**传 `think: true` 读 `thinking` 字段**，自己决定用不用。
2. **提示词里的 `/no_think` 在本机无效**（848 字 vs 894 字，模型甚至在推理里点评了这条指令却照旧推理）。**任何「关思考」的手段都必须实测验证。**
3. **CLI 侧 `--think=false` 必须带等号**——`--think false` 因 pflag 的 NoOptDefVal 语义把 `false` 漏进提示词，**且同时没关掉思考**。
4. **CLI 有效不等于 API 有效。** 两条路径的机制不同，**不要把一边的结论搬到另一边**。
5. **思考 token 是纯开销，按标准速率计费**（本机 ~12.8~13.1 tok/s，四组一致），且主要伤的是 **TTFT** 而非吞吐。用思考模型就一定要开流式。
6. **小模型的思考经常不收敛**——本机四组全部撞 500 token 上限仍未给出答案。**必须配 `num_predict` 上限 + 超时兜底。**
7. **自动化脚本里绝不用交互模式的斜杠命令**——非 TTY 下会被当成提示词发给模型，而且不报错。
