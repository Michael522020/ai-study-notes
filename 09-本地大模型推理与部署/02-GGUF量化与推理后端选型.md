# GGUF 量化与推理后端选型

> **核心问题**：同一份模型权重，存成不同的量化档位会差多少？Ollama、llama.cpp、vLLM 到底该选哪个？为什么在无独显的机器上，你能用的后端比想象中少？

本章讲清两件事：**「模型被压成了什么样」** 和 **「谁来跑这个被压过的模型」**。前者决定质量与体积，后者决定速度与并发能力。

**数据口径**：本章的量化档位与后端特性为**转述自 llama.cpp / Ollama / vLLM 官方文档与社区公开基准**；带「本机实测」标注的数字来自作者本机（i5-13500H + Iris Xe 核显）。**不同模型对量化的敏感度差别很大**，本表只作选型参考，具体模型请以自己的实测为准。

---

## 1. GGUF：为什么现在大家都用它

**GGUF**（**G**eneral **G**raph **U**nit **F**ormat）是 llama.cpp 生态的模型容器格式，取代了早期的 GGML。

```
┌─────────────────────────────────────────────┐
│  GGUF 容器                                  │
├─────────────────────────────────────────────┤
│  metadata (KV)   模型结构 / 超参 / tokenizer │
│  tensor data     量化后的权重块             │
└─────────────────────────────────────────────┘
```

**一个 GGUF 文件同时携带**：模型结构定义、全部超参（层数、头维度、RoPE 参数）、分词器（vocab + merges）、以及量化后的权重。

> 💡 **这一点值得单独强调**：GGUF 是**自包含**的。你不需要额外的 `config.json`、不需要 `tokenizer.json`、不需要 `model.safetensors.index.json`。**下载一个 `.gguf` 就是完整的模型**。
>
> 这就是为什么「用 Ollama 跑一个别人分享的 GGUF」只需要一条命令，而走 HF `transformers` 路线往往还要拼装一堆文件。

**GGUF vs safetensors**（HF 生态的 `.safetensors`）：

| | GGUF | safetensors |
|---|---|---|
| 内部结构 | **已量化**的权重块 + 元信息 | **浮点**权重张量（FP16/BF16） |
| 推理前是否需要额外转换 | 不需要 | 需要（转 ONNX / 转 TRT / 转自己的格式） |
| 典型使用者 | llama.cpp / Ollama / LM Studio / koboldcpp | vLLM / SGLang / TGI / transformers |
| 硬件依赖 | **CPU 就能跑** | 基本要求有 GPU |

**结论**：HF 上的 `safetensors` 是「训练/研究侧的原料」，GGUF 是「推理侧的成品」。

## 2. 量化档位：压多少、掉多少

### 2.1 档位全表

| 档位 | 权重位宽（平均） | 4B 模型体积（估） | 质量 | 说明 |
|---|---|---|---|---|
| **F32 / BF16 / F16** | 16–32 bit | ~8.0 GB | 基准 | BF16 是训练/大显存推理的默认档 |
| **Q8_0** | 8.5 bit | ~4.4 GB | 几乎无损 | 8-bit 逐块量化，体积减半 |
| **Q6_K** | 6.6 bit | ~3.4 GB | 极轻微损失 | K 量化，6-bit |
| **Q5_K_M** | 5.7 bit | ~2.9 GB | 轻微损失 | K 量化 + 重要性矩阵混合 |
| **Q4_K_M** | 5.1 bit | ~2.5 GB | **可接受**（社区最常用） | ⚠️ **本机 `qwen3:4b` 就是这一档** |
| **Q4_K_S** | 4.6 bit | ~2.3 GB | 略差于 Q4_K_M | 纯 4-bit K 量化 |
| **Q3_K_M / IQ3_XS** | 3.4 bit | ~1.8 GB | 明显下降 | 小模型可接受，大模型伤明显 |
| **Q2_K** | 2.6 bit | ~1.4 GB | **明显崩坏** | 只在极端省空间时用 |
| **IQ2_XXS** | ~2 bit | ~1.2 GB | 基本不可用 | 娱乐用途 |

**K 量化（k-quants）vs 传统量化**：llama.cpp 的 K 量化对每个 block 内的张量**按重要性分配不同位宽**，并引入 **IQ / 重要性矩阵**（imatrix，用校准集统计每个通道的激活重要性）来优化哪些通道值得多给比特。

**同一个"平均位宽"下，K 量化 + imatrix 的质量明显优于传统 round-to-nearest 量化**——这也是为什么 `Q4_K_M` 比同为 4 bit 的 `Q4_0` 好用得多。代价是量化要多跑一遍校准。

### 2.2 质量 vs 体积 vs 速度：三者不同步

这是最容易踩的误解：

> **量化主要省的是「显存/内存」，其次才是「速度」。**

| 你以为的 | 实际情况 |
|---|---|
| 「压到 Q4 就跑得快一倍」 | ❌ **内存带宽才是瓶颈**。权重要读进计算单元，压小后**读得更快**，但只有当原来被带宽卡住时才能体现为加速 |
| 「压到 Q4 质量掉一半」 | ❌ 通常**掉得很少**。4-bit 已经是「几乎无损」的甜点档 |
| 「压得越小越快」 | ❌ **有拐点**。低于 Q4 后质量掉得比速度涨得快 |

**经验阈值**（通用规律，具体模型要自己测）：

| 场景 | 建议档位 |
|---|---|
| 显存/内存很紧，质量优先 | `Q4_K_M` |
| 质量优先，速度次要 | `Q6_K` / `Q8_0` |
| 追求极限速度 | `Q4_K_M` 或 `Q5_K_M` —— **不要低于 Q4** |
| 只是跑个格式测试 / 逻辑验证 | `Q3_K_M` 可接受 |

### 2.3 本机的实例

本机 `qwen3:4b` 的元信息（`/api/tags` 返回）：

```json
"details": {
  "format": "gguf",
  "family": "qwen3",
  "parameter_size": "4.0B",
  "quantization_level": "Q4_K_M",
  "context_length": 262144,
  "embedding_length": 2560,
  "runner": "ggml"
}
```

| 项 | 值 | 解读 |
|---|---|---|
| 量化档位 | `Q4_K_M` | 甜点档，2.5 GB |
| 文件体积 | 2,497,293,931 B（≈ 2.33 GiB） | 4B 模型的 Q4 体积，符合预期 |
| 模型上下文上限 | 262144（256k） | **模型能力上限**，不是服务端生效值 |
| 嵌入维度 | 2560 | 4B 级别的典型值 |

## 3. 推理栈三选一：llama.cpp / Ollama / vLLM

这三者不是「同一个东西的三个版本」，是**三种不同的目标**。

| | **llama.cpp** | **Ollama** | **vLLM** |
|---|---|---|---|
| 定位 | **底层引擎**（C/C++ 库 + CLI） | **易用封装**（llama.cpp + 模型管理 + API） | **高并发服务**（PagedAttention 专用） |
| 主要语言 | C++ / Python 绑定 / Go / Rust | Go 守护进程 + llama.cpp | Python + CUDA |
| 硬件要求 | **CPU 就能跑** | CPU 就能跑 | **基本要求 GPU**（无 GPU 路径不成熟） |
| 模型格式 | GGUF | GGUF（自动转换） | safetensors（也支持 GGUF 但非主线） |
| 并发能力 | 弱（单请求为主） | 中（`OLLAMA_NUM_PARALLEL`） | **强（PagedAttention，KV Cache 分页管理）** |
| 显存管理 | 靠 OS | 靠 OS | **显存利用率显著更高** |
| 接口 | 无 HTTP 服务（CLI / 库） | **OpenAI 兼容 REST** | **OpenAI 兼容 REST** |
| 上手成本 | 高（自己拼） | **最低** | 中（要装 PyTorch + CUDA） |
| 典型场景 | 嵌入式 / 边缘设备 / 自研集成 | 个人本机 / 小团队 / 私有化 | 生产 API 服务 / 高并发 |

### 3.1 选型判据

```
                  你的负载是什么？
                        │
        ┌───────────────┼───────────────┐
        │               │               │
   本机/个人，       要 OpenAI 兼容    高并发生产服务
   离线和私有化        接口接现有 App    （几十 QPS+）
        │               │               │
   Ollama ◀─────────────┘               │
        │                                 │
   显存只有几 GB？                   有 A100/4090？
   想要最高质量？                        │
        │                          ┌─────┴─────┐
     llama.cpp + 手动启动         vLLM        llama.cpp
     （Q6_K/Q8_0 档）            （PagedAttention）
```

**一句话判据**：

- **没有 GPU，或者 GPU 只是核显** → **Ollama**。别碰 vLLM，它的显存调度逻辑在 CPU 路径上没有意义。
- **有独立显卡 + 多用户并发** → **vLLM**。
- **要嵌入自己的 C/C++/Rust 产品** → **llama.cpp**。

> ⚠️ **一个常见误区：以为 Ollama 和 vLLM 可以二选一「谁更快」。**
> 在**单请求单用户**场景下，**Ollama（底层就是 llama.cpp）和 vLLM 的速度差异很小**，瓶颈都是显存带宽。
> vLLM 的优势**只在多请求并发时体现**——它用 PagedAttention 让 KV Cache 像虚拟内存一样分页，避免「预留一大块连续显存给 KV Cache」导致的浪费。**单并发场景这个优势基本不存在。**

### 3.2 Ollama 的 OpenAI 兼容接口

这是 Ollama 最有工程价值的一点——它把本地模型暴露成一个 **OpenAI 风格的 REST API**：

```bash
# 原生接口
curl http://127.0.0.1:11434/api/chat -d '{"model":"qwen3:4b","messages":[...]}'

# OpenAI 兼容路径
curl http://127.0.0.1:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"qwen3:4b","messages":[{"role":"user","content":"..."}]}'
```

意味着**任何支持 OpenAI SDK 的框架（LangChain / LlamaIndex / OpenAI Python SDK / vLLM 客户端写法）都能零改动指过来**：

```python
from openai import OpenAI

client = OpenAI(base_url="http://127.0.0.1:11434/v1", api_key="ollama")  # api_key 随便填，占位用
resp = client.chat.completions.create(
    model="qwen3:4b",
    messages=[{"role": "user", "content": "用三点介绍向量数据库"}],
)
```

> 💡 **「接本地模型」这件事的难度，被 OpenAI 兼容接口压到了接近零。** 大部分框架默认往 OpenAI 兼容端点发请求，本地模型只是把 `base_url` 换成一个本机地址。**第 05 章会把这个接进本仓库的 provider 抽象。**

## 4. 后端矩阵：你的机器实际能用哪几个

llama.cpp / Ollama 底层用 ggml，ggml 会探测可用的计算后端，**按优先级选一个**。

| 后端 | 需要什么 | 本机可用？ | 典型性能 |
|---|---|---|---|
| **CUDA** | NVIDIA 独显 + CUDA | ❌ 无 NVIDIA 卡 | 最快（主流选择） |
| **ROCm / HIP** | AMD 独显 | ❌ 无 AMD 卡 | 与 CUDA 接近 |
| **Vulkan** | 任意厂商 GPU（含核显） | ✅ **本机唯一可用的加速后端** | 略慢于 CUDA，但**核显可用** |
| **Metal** | Apple Silicon | ❌ 非 Mac | 与 CUDA 接近 |
| **SYCL / oneAPI** | Intel 独显 | ❌ 无 Intel 独显 | Intel 路线 |
| **CPU（AVX2 / AVX512）** | x86-64 CPU | ✅ **兜底路径** | 取决于内存带宽 |
| **BLAS** | 通用 | ✅ 作为 CPU 路径的补充 | 部分算子加速 |

本机的探测日志（`runner.go`）印证了这条路径：

```
msg="dropping integrated GPU; to enable, set OLLAMA_IGPU_ENABLE=1"
  id=0 library=Vulkan compute=0.0 name=Vulkan0 description="Intel(R) Iris(R) Xe Graphics"
msg="inference compute" id=cpu library=cpu name=cpu total="31.7 GiB" available="16.1 GiB"
```

`library=Vulkan` 说明 **Vulkan 后端成功识别了 Iris Xe**，只是被默认策略丢弃了。设上 `OLLAMA_IGPU_ENABLE=1` 它就能用。

### 4.1 CPU 后端靠什么加速

在 CPU 上，推理速度几乎完全由**内存带宽**决定，而不是由「算力」决定：

```
token/s ≈ 内存带宽 ÷ 每 token 需要读取的权重字节数
```

几个推论：

| 观察 | 原因 |
|---|---|
| **量化到 Q4 提速明显，Q4 → Q3 提速有限** | 权重读取量已不是瓶颈，前向计算和 KV Cache 开始接管 |
| **核显和 CPU 共享内存带宽 → 速度接近** | 它们读的是同一块内存 |
| **换 DDR4 内存比换 CPU 提升更明显** | 带宽瓶颈 |
| **上下文越长越慢** | 每生成一个 token 要读写一遍 KV Cache |

**这也解释了第 01 章的核心现象**：核显只快 5%，因为它没有多出一条独立带宽通道。

### 4.2 KV Cache 量化

`OLLAMA_KV_CACHE_TYPE` 默认 `f16`。改成 `q8_0` 可以把 KV Cache 占用减半，在**长上下文**场景下收益明显（KV Cache 大小随 `层数 × 序列长度 × 头维度 × 2(K,V)` 线性增长）。

| 设置 | KV Cache 精度 | 占用 | 影响 |
|---|---|---|---|
| `f16`（默认） | 16 bit | 基准 | 质量最稳 |
| `q8_0` | 8 bit | **减半** | 质量损失很小，长上下文推荐 |

> ⚠️ **别在短上下文时折腾这个**。上下文只有几千 token 时，KV Cache 占的内存相比模型权重可以忽略不计，改了也没感觉。**只有当你为了塞下长上下文而爆显存时，它才有意义。**

## 5. 上下文长度：一个被反复误解的参数

模型文件里的 `context_length: 262144` 和服务端的实际生效值**是两件事**：

| | 含义 | 谁决定 |
|---|---|---|
| 模型上下文上限 | 架构能支持的最大序列长度（RoPE 训练时的长度外推能力） | **模型权重本身**（GGUF 头） |
| 服务端生效上下文 | 每次请求实际使用的 `num_ctx` | **`OLLAMA_CONTEXT_LENGTH` / 请求参数 / 按显存自动分配** |

Ollama 的默认策略是**按显存分配**：

```
msg="vram-based default context" total_vram="0 B" default_num_ctx=4096
```

`4k/32k/256k based on VRAM` —— 有显存给 256k，独显给 32k，**没有显存就给 4k**。

**所以本机不修好核显那件事，上下文就永远是 4k。** 修好之后按 256k 分配，但那是**上限**，实际用多少由请求里的 `num_ctx` 或 `OLLAMA_CONTEXT_LENGTH` 决定。

> ⚠️ **这个坑的特点是「不报错」**：服务端不会告诉你「你的文档被截断了」，只会返回一段看起来通顺、但少了后半截信息的答案。
> **排查口诀**：凡是「模型好像没看完我给的东西」，先查生效的 `num_ctx`，再查检索质量。

## 6. 工程结论

1. **先定量化档位，再定推理栈**。顺序反了会做无用功——选错推理栈（比如在核显机器上装 vLLM）解决不了档位选错的问题。
2. **Q4_K_M 是甜点档**。想要更高质量上 Q6_K / Q8_0，**不要低于 Q4**——低于 Q4 后质量掉得比速度涨得快。
3. **Ollama vs vLLM 的选择取决于「并发」而不是「速度」**。单请求场景两者几乎没差别；vLLM 的 PagedAttention 只在多请求下兑现。
4. **没有 GPU 就别碰 vLLM**，没有独显就用 Ollama，嵌入产品用 llama.cpp。
5. **量化省的是内存带宽，不是「算力」**。这解释了为什么核显≈CPU、为什么换内存比换 CPU 划算、为什么长上下文会变慢。
6. **上下文长度看服务端生效值，不看模型元信息**。`context_length: 262144` 不等于你能用 256k。
