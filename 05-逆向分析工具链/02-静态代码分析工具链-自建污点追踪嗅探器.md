# 静态代码分析工具链：自建一个污点追踪嗅探器

> **核心问题**：静态扫描网页代码里的危险 API，为什么必然误报？为什么「有污点追踪」和「没污点追踪」是两种工具？自己写一个够用的版本，难点到底在哪？

本章记录 2026-11-11 自建的一个零依赖静态分析工具（**WebVulnSniffer**）的完整设计。

**数据口径**：本章的规则数量、严重度分布、各靶页面的发现数、字段结构均为**作者本机实测**（2026-11-14 在本机运行该工具取得）。**本章不收录该工具的源码**——只讲设计与取舍。工具本身不发送任何写请求、不执行目标提供的脚本、不尝试利用任何漏洞。

---

## 1. 定位：它不是生产工具，是学习载体

先说清楚它是什么、不是什么，否则后面的取舍会看不懂。

| | |
|---|---|
| ✅ **是** | 一个**够用**的静态分析器：57 条规则、污点追踪、三种报告、CI 可用 |
| ✅ **是** | 一份**刻意保留中间产物**的学习材料——掩码后的代码、作用域树、数据流链路都留着 |
| ❌ **不是** | 生产级扫描器（不处理混淆、无跨函数过程间分析、无服务端逻辑） |
| ❌ **不是** | 动态扫描器（`--render` 只补上浏览器里跑出来的那部分） |
| ❌ **不是** | 攻击工具（不发送写请求、不执行目标脚本、不尝试利用） |

**为什么值得单独写一章**：这个仓库的 05 主线讲的是「怎么把别人做好的东西拆开看」——用的是**现成的大工具链**（[`01` REA 逆向工程工具链配置实录](./01-REA-逆向工程工具链配置实录.md)）。而这一章讲**反方向**：当通用工具链不够细时，自己造一个专注的小工具。

> 💡 **这也是理解污点分析最省力的方式**——自己实现一遍，才知道它在哪些地方必然会出错。

## 2. 为什么正则 grep 必然误报

### 2.1 两个方向的错

朴素做法是「匹配危险 API 名字」。它在**两个方向同时出错**：

```js
var tip = "别用 innerHTML";   // ← 误报：字符串里出现了关键字
// eval(x)                   // ← 漏报：注释里的危险调用
```

| 方向 | 例子 | 后果 |
|---|---|---|
| **误报（假阳性）** | 字符串字面量、注释里出现了 `innerHTML` / `eval` | 报告里 80% 是噪声，**用两周之后没人看它** |
| **漏报（假阴性）** | 危险调用在注释里、被拆开写、或者真正的问题形态不是「关键字出现」 | **漏掉的恰恰是最危险的那类** |

**更关键的是：即使没有上面两种噪声，正则也答不出真正的问题。**

### 2.2 真正的问题是「数据流」，不是「关键字」

```js
var q = location.search;     // source：用户可控
var id = q;                  // 传播
el.innerHTML = id;           // sink：危险汇聚点 ⇒ 确认可利用
```

对比：

```js
el.innerHTML = sanitized(id);  // 同一个 sink，但数据是干净的 ⇒ 不是漏洞
```

**这两段代码里有完全相同的 `innerHTML`，但一个是漏洞、一个不是。** 差别在**数据从哪来、经过了什么处理**——**正则原理上无法表达这件事**。

> **这就是「有污点追踪」和「没污点追踪」的分水岭**：
> 没有污点追踪的工具只能告诉你「这里用了 `innerHTML`」；有污点追踪的工具能告诉你「**这里的 `innerHTML` 真的能被用户输入控制**」。

### 2.3 两档严重度，以及「严重度取自汇聚点」

本工具把「危险 API 出现」和「真的可利用」分成两个等级：

| 规则 | 规则声明的严重度 | 含义 |
|---|---|---|
| `WVS-JS-000` | **HIGH**（置信度 85%） | **污点数据流入危险汇聚点，确认可利用** |
| `WVS-JS-001` | **LOW**（置信度 40%） | 出现了 DOM XSS 危险汇聚点（`innerHTML` / `document.write` 等），但**未确认数据流** |

**注意一个容易看错的细节**：`WVS-JS-000` 这条**规则**声明的是 HIGH，但它产出的 **finding 的严重度取自汇聚点（sink）**，不是取自规则：

```python
out.append(emit(
    RULE_TAINT.id, unit.location(flow.sink.offset, len(flow.sink.name)),
    ...
    severity=flow.sink.severity,      # ← 取 sink 的严重度
    confidence=flow.confidence,
    source=" → ".join(flow.chain),
    extra_tags=["taint-confirmed"],
))
```

而每个 sink 自己带严重度：

| 汇聚点 | 声明的严重度 | 置信度 |
|---|---|---|
| `eval` / `new Function` | **CRITICAL** | 0.6 |
| `iframe.srcdoc` | HIGH | 0.45 |
| `setTimeout(字符串)` / `setInterval(字符串)` | HIGH | 0.5 |

**所以同一 `WVS-JS-000`，流到 `eval` 会报 CRITICAL，流到 `iframe.srcdoc` 会报 HIGH。**

> 💡 **这个设计值得记住**：**「确认可利用」是同一条规则，但它的危险程度取决于被命中的汇聚点有多危险。**
> 污点确认解决的是「是不是真的能注入」，**汇聚点决定的是「注入了有多严重」**——**两个维度必须分开表达**。
> 如果把严重度写死在规则上，所有污点确认都会被拉平成同一个级别。

这个分层是整个工具的价值所在：**把「值得今天就修」和「顺手看看」分开。**

本机实测的一条 `WVS-JS-000` 完整记录：

```json
{
  "rule_id": "WVS-JS-000",
  "title": "污点数据流入危险汇聚点（确认可利用）",
  "severity": "CRITICAL",
  "cwe": "CWE-79",
  "owasp": "A03:2021 Injection",
  "confidence": 0.85,
  "location": { "line": 95, "column": 18,
                "snippet": "  if (payload) { eval(payload); }" },
  "evidence": "eval(payload",
  "source": "URLSearchParams → eval",
  "remediation": "使用 textContent 代替 innerHTML；或用 DOMPurify 等库做白名单净化后再写入。",
  "tags": ["xss", "taint", "confirmed", "taint-confirmed"]
}
```

**`"source": "URLSearchParams → eval"` 这一行是整个工具的核心输出**——它不只告诉你「哪一行有问题」，而是告诉你**数据是怎么流过去的**。审阅的人可以直接判断这个结论对不对。

## 3. 掩码：让偏移量与原文件 1:1 对应

### 3.1 做法

掩码器把注释、字符串字面量、正则字面量的**内容**替换成空格，**但保持长度和换行不变**。

```
原始:  var tip = "别用 innerHTML";
掩码:  var tip = "                  ";
```

**「长度不变」是这个设计的全部要点**：

| 性质 | 后果 |
|---|---|
| 偏移量 1:1 对应 | 所有行列号计算都能直接用原文件偏移量，**不会累积误差** |
| 换行保留 | 行号不会因为掩码而错位 |
| 字符串内容被抹掉 | `innerHTML` 出现在字符串里不再会被当成代码 |

**对比一下常见做法**：很多工具用「替换成 `<STR>` 之类的占位符」——**长度变了**，后面所有偏移量都要重新映射，**行列号就会漂**。本工具刻意避开了这个坑。

### 3.2 两个视图：这条坑值得单独记

掩码之后，**你需要看到字面量内容的时候怎么办**？于是有两个视图：

| 视图 | 数据源 | 用途 |
|---|---|---|
| `iter_matches` | **掩码后**的代码 | 只看代码结构，避免字符串里的关键字造成误报 |
| `iter_raw` | **原始源码** | 需要判断字面量**内容**时用（`'md5'`、`'AKIA…'`、`'message'`） |

> ⚠️ **这个坑的代价是 12 条规则集体漏报。**
>
> 当初一批规则（查硬编码密钥、查弱加密算法名、查特定字符串常量）需要看字面量内容，但它们当时用的是 `iter_matches`——**而 `iter_matches` 里字面量已经被抹成空格了**，所以规则永远匹配不上。
>
> **12 条规则同时失灵，而不是零星几条**——这是很强的信号：**当一批不相关的规则同时不出结果时，先怀疑共享的基础设施，而不是逐条查规则逻辑。**

### 3.3 怎么选

| 规则要查什么 | 用哪个视图 |
|---|---|
| 「代码里出现了 `eval(` 这个调用」 | `iter_matches` |
| 「字符串字面量的**内容**是 `md5` / `sha1`」 | `iter_raw` |
| 「代码里出现了 `AKIA` 开头的字符串」 | `iter_raw` |
| 「这段代码调用了 `document.write`」 | `iter_matches` |

**判断标准很简单：你要看的是「代码结构」还是「数据」**。前者掩码后看，后者必须回原文。

## 4. 污点追踪引擎

### 4.1 数据流模型

```
  Source（location.search / DOM 存储 / postMessage / URLSearchParams …）
        │
        ├──赋值──▶ 变量 ──传播──▶ 变量
        │                          │
        └──────────▶ Sink（innerHTML / eval / document.write …）  ⇒ 确认可利用
```

**污点只在「同一函数作用域」内传播**（靠 `JsCode.function_scopes` 建立的作用域索引）。所以：

```js
function a() { var x = location.search; /* 污点 */ }
function b() { var x = "hello";       /* 干净 */ }
```

**函数 A 的局部变量不会污染函数 B 的同名变量。** 这一条是误报控制的关键——不做作用域隔离的话，满页的同名 `x` 会让污点传播到不该去的地方。

### 4.2 弱污点：不确定的来源要降级

形参名可疑时（`userInput`、`keyword`、`query` 这类），按**弱污点**处理，**置信度降级**。

```js
function render(userInput) { el.innerHTML = userInput; }
```

这里 `userInput` 是不是真的来自用户，静态分析**无法确定**——它可能来自调用方传进来的常量。所以：

| | 强污点 | 弱污点 |
|---|---|---|
| 来源 | 明确可判定的 source API | 形参名可疑 |
| 置信度 | 按规则基准（如 85%） | **降级** |
| 报告级别 | CRITICAL | 降一档 |

### 4.3 行号换算：内联脚本要换算回 HTML

内联 `<script>` 的代码行号是**相对 script 标签的**，而报告要的是**相对整个 HTML 文档的**行号。

`CodeBlock.doc_line()` 专门处理这次换算；独立的 `.js` 文件则直接用它自己的行号。

> **这类「坐标系不一致」的问题在静态分析工具里非常常见**，而它对可用性的影响极大：**行号错位，用户点进去发现对不上，这个工具就废了。**
> 顺带一句——`08-dynamic.html` 这类页面里，内联脚本和动态注入的脚本混在一起，行号换算更容易出错，所以它同时也是行号换算的测试用例。

## 5. 规则体系

### 5.1 57 条规则的分布（本机实测）

| 前缀 | 数量 | 覆盖内容 |
|---|---|---|
| `WVS-JS-*` | **18** | DOM XSS 汇聚点、eval、开放重定向、postMessage、原型污染、SQL / 命令 / 路径注入、不安全随机数、localStorage 存凭据、Cookie 属性、ReDoS、调试残留、Source Map |
| `WVS-HTML-*` | **16** | 事件处理器属性、`javascript:` 伪协议、GET 提交口令、缺 CSRF、hidden 存敏感值、iframe sandbox/srcdoc、`<base>` 劫持、跨域表单、CSP meta、`target=_blank`、可路径、meta refresh、口令字段类型、CSS 表达式 |
| `WVS-HTTP-*` | **10** | HSTS、nosniff、点击劫持防护、CSP、Referrer-Policy、Permissions-Policy、版本泄露、Set-Cookie 属性、CORS 通配与凭据 |
| `WVS-SEC-*` | **8** | AWS Key、私钥、硬编码密钥 / 口令、JWT、含口令的连接串、注释里的遗留凭据、第三方服务密钥 |
| `WVS-CRYPTO-*` | **5** | MD5/SHA-1、DES/RC4、ECB、硬编码 IV/nonce、PBKDF2 迭代不足 |
| **合计** | **57** | |

**规则声明的严重度分布（本机实测）**：CRITICAL **4** / HIGH **10** / MEDIUM **27** / LOW **12** / INFO **4**。

> **注意分布**：MEDIUM 有 27 条，占了近一半。这是**有意的**——一条工具如果全是高危，等于没有优先级分层。**CRITICAL 只有 4 条**，因为「确认可利用」的标准本来就应该很严。

### 5.2 每条规则都带的元数据

```python
RULE_MY = Rule(
    id="WVS-MY-001",
    title="示例：禁用了某个危险 API",
    severity=Severity.MEDIUM,
    cwe="CWE-1004",
    description="说明这条规则查的是什么。",
    remediation="说明怎么改。",
    tags=["custom"],
)
```

**每条规则都带 CWE 编号、OWASP 分类、置信度、修复建议**。

**置信度是可选字段**——这一点很重要：

| 规则类型 | 置信度 |
|---|---|
| 污点确认（`JS-000`） | 85% |
| 危险 API 出现（`JS-001`） | 40% |
| 硬编码密钥（`SEC-*`） | 高（模式匹配确定） |

**没有置信度，报告就只是一堆排序不明的告警。**

### 5.3 加一条规则的模板

```python
# wvs/rules/my_rules.py
from ..models import Rule, Severity
from .base import ScanContext, emit, iter_raw, register

RULE_MY = Rule(
    id="WVS-MY-001",
    title="示例：禁用了某个危险 API",
    severity=Severity.MEDIUM,
    cwe="CWE-1004",
    description="说明这条规则查的是什么。",
    remediation="说明怎么改。",
    tags=["custom"],
)

@register(RULE_MY)
def check_my_rule(ctx: ScanContext) -> list:
    out = []
    for idx, unit in enumerate(ctx.units):
        for m in iter_raw(unit, r"\bmyDangerousApi\s*\("):
            out.append(emit(RULE_MY.id, unit.location(m.start(), m.end() - m.start()),
                            evidence=unit.text(m.start(), m.end())))
    return out
```

在 `wvs/rules/__init__.py` 里 `from . import my_rules` 即可注册。**规则 ID 重复会直接报错**，避免互相覆盖。

> 💡 **「规则 ID 重复直接报错」这个小设计值得抄。** 规则一多，ID 撞车几乎必然发生；而撞车的后果是**一条规则静默覆盖另一条**——工具报告里少了一类问题，而你完全不知道为什么。

## 6. 工程化：让它真的能被用起来

### 6.1 三种报告

| 格式 | 用途 |
|---|---|
| `console` | 终端彩色分组，默认 |
| `json` | 接 CI / 其它工具 |
| `html` | **单文件**，可以直接发给同事 |

### 6.2 CI 接入

```
python -m wvs scan <target> --fail-on high
```

| 退出码 | 含义 |
|---|---|
| 0 | 正常结束（未命中 `--fail-on` 阈值） |
| 1 | **命中 `--fail-on` 指定级别及以上的问题** |
| 2 | 参数错误 / 目标无法加载 |

**把「发现了高危问题」映射成一个非零退出码，是让静态检查进入 CI 的唯一方式。** 否则它永远只是「报告里的一页」。

### 6.3 靶站与误报回归基线

`lab/` 下每个文件都是**故意写得不安全**的，同时**每个文件里都嵌了「不该报」的对照组**。

本机实测的各靶页面扫描结果：

| 靶页面 | 发现数 | 命中规则数 | 说明 |
|---|---|---|---|
| `01-dom-xss.html` | **10** | 3（JS-000 / JS-001 / JS-004） | 8 种 XSS 数据流 + 2 组对照组 |
| `02-secrets.html` | **14** | 8（SEC-001 ~ 008） | AWS Key / Stripe Key / JWT / 私钥 / 连接串 + 占位符对照组 |
| `03-crypto.html` | **11** | 6（CRYPTO-001 ~ 005 + JS-009） | MD5、SHA-1、DES、ECB、静态 IV、低迭代 PBKDF2 |
| `04-forms.html` | **24** | 16（HTML-001 ~ 016） | GET 提交口令、缺 CSRF、跨域表单、`javascript:`、iframe |
| `05-api.js` | **21** | 12（JS-000、002 ~ 008、011 ~ 014） | eval、postMessage、原型污染、SQL 拼接、命令注入、路径穿越、ReDoS |
| `06-spa.html` | 0 | 0 | 外部脚本抓取 / 渲染后 DOM（需 http 目标） |
| **`07-clean.html`** | **0** | **0** | ✅ **规范写法的对照组——误报回归基线** |
| `08-dynamic.html` | 0 | 0 | 动态注入的 `<script>`（需 http 目标 + `--render`） |

**`07-clean.html` 必须零发现**——这是整个工具的**误报回归基线**。**改任何一条规则之后，先跑它。**

> 💡 **「每个靶页面里都嵌对照组」是这类工具的核心方法论**：
> 只写「必须报」的用例，规则写错了方向（该报的不报）测试也会通过；
> **只有同时写「不该报」的用例，才能抓住规则写反了、或者写宽了**。
> 这和本仓库 04 主线里「跨后端结果对齐」是同一个思路——**只验证正例的工具，等于没有验证。**

### 6.4 一个实测发现的静默失败

本机实测：`--render` 扫 `08-dynamic.html` 得到 **0 条发现，且没有任何警告**。

读代码才找到原因——`cli.py:140`：

```python
if args.render and args.target.startswith(("http://", "https://")):
    ...
    dom = render_dom(args.target, timeout=max(30.0, args.timeout))
```

**`--render` 只对 http/https 目标生效。** 扫本地文件时它是**静默空操作**——不报错、不警告，报告里只是「没有发现」。

> ⚠️ **这类静默失败是这个仓库反复强调的那类问题的又一例**（见 04 主线「旧 sdkconfig 会盖掉 defaults」）：
> **工具不报错，只让结果变得不对。**
>
> **改进方向**：渲染失败时应当产生一条 `warnings` 记录（JSON 报告里本来就有 `warnings` 字段，只是没被用上），而不是当作「扫描完成、没发现问题」。

## 7. 已知限制

这一节是这个工具最有价值的部分——**明确说出边界，比多报几条规则重要得多**。

| 限制 | 说明 |
|---|---|
| **静态分析看不到服务端逻辑** | 前端代码里的 `fetch('/api/xxx')` 到底查了什么，静态分析无从判断 |
| **污点分析是「过程内」的** | 跨函数调用（`f(x)` 把参数传进 `f`）**不做完整的过程间分析**；弱污点规则是对这一块的**近似补偿**，不是完整解法 |
| **正则与除号的区分靠启发式** | `a / b / c` 与正则字面量 `/ab+c/` 的区分是启发式的，**极端写法会误判** |
| **混淆代码不处理** | 这是所有静态嗅探器的固有边界，不是本工具独有的问题 |
| **`--render` 对本地文件静默空操作** | 见 §6.4 |

> **关于「过程内」这一条值得多说几句**：真正的过程间分析需要构建调用图、解析参数与返回值的污点传播——那是编译器分析的活。一个纯 Python 零依赖工具不可能做好。
> **所以正确的做法不是硬做，而是明说边界，再用弱污点做保守近似**——**宁可报得可疑一点，也不要让用户以为覆盖是完整的。**

---

## 8. 工程结论

1. **「有污点追踪」和「没污点追踪」是两种工具。** 正则只能回答「用了危险 API」，污点分析才能回答「**这里真的能被用户输入控制**」。
2. **两级严重度是关键设计**：CRITICAL = 确认可利用（带数据流链路），LOW = 只是出现了危险汇聚点。**置信度字段让报告有优先级。**
3. **掩码必须「长度不变」**，否则行列号会漂——**行列号错了，工具就废了**。
4. **掩码后和原文是两个视图**（`iter_matches` / `iter_raw`），**用错视图会让规则静默失灵**。本工具曾因此让 12 条规则集体漏报。
5. **一批不相关的规则同时不出结果时，先查共享基础设施**（掩码视图、作用域索引、行号换算），而不是逐条查规则逻辑。
6. **污点传播必须限定在同一函数作用域内**；不确定的来源（可疑形参名）按弱污点降级。
7. **每个靶页面里都要写「不该报」的对照组**，`07-clean.html` 作为误报回归基线，**改规则后必跑**。
8. **把「命中高危」映射成非零退出码**，否则工具进不了 CI。
9. **静默失败比崩溃更危险**——`--render` 对本地文件空操作却不报错，就是典型。**工具应该把「我没能做这件事」明确说出来。**
10. **明确说出边界**（过程内分析、看不到服务端、不处理混淆），比多报几条规则更能建立信任。
