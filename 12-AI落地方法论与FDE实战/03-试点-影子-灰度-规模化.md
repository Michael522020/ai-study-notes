# 试点 → 影子 → 灰度 → 规模化

> **核心问题**：Demo 之后怎么安全地上线？每个阶段的出口标准是什么？什么时候能停？

---

## 0. 为什么必须有这四步

**Demo 成功 ≠ 系统可用。** 差别在四处：

| | Demo | 可用系统 |
|---|---|---|
| **输入** | 你精心挑的几条 | 全量、含脏数据、含攻击 |
| **输出** | 你重试到满意为止 | 一次过、有兜底 |
| **责任** | 你在看 | 别人在看，出错有人承担 |
| **数据** | 静态 | 活的，会漂移 |

> **这四步的本质是「逐级增加风险敞口」。**
> 每一步的出口标准都是**可测量的**，不是「感觉还行」。

```
   试点            影子              灰度              规模化
  PoC          Shadow Run        Canary          Full Rollout
  ─────       ───────────       ───────         ─────────────
  跑通闭环      跑但不做决定       少量真实流量      全量
  你在看        积累对照数据       小流量真决策       常态运行
     │             │                │                │
  风险敞口:    0  →  0          1% → 10%        100%
```

## 1. 阶段一 · 试点（PoC / Pilot）

### 1.1 目标

**验证「这件事模型能不能做」，不是验证「这个方案好不好」。**

### 1.2 做什么

| 项 | 说明 |
|---|---|
| **小样本集** | 100~500 条真实样本（不是 demo 数据） |
| **最小闭环** | 端到端跑通：输入 → 模型 → 输出 → 人工看 |
| **基线对照** | 同时跑一个**规则/人工基线**，用于对比 |
| **错误分类** | 把错误按类型归类（漏/错/格式/幻觉/超时） |
| **成本测量** | 真实的 token 数、延迟、单次成本 |

### 1.3 出口标准（建议）

| 指标 | 阈值示例 | 说明 |
|---|---|---|
| **任务级成功率** | ≥ 80% | 端到端成功，不是单步准确率 |
| **效果指标** | 达到基线 **+X%** | X 由业务定 |
| **单次成本** | ≤ 目标值 | 用实测均值 |
| **p95 延迟** | ≤ 目标值 | 含首 token |
| **错误可归类** | 100% 能归入预定义类别 | **不能归类的错误 = 还没搞懂系统** |

### 1.4 试点阶段的三个禁区

| 禁区 | 为什么 |
|---|---|
| **不许用 demo 数据** | demo 数据是你挑的，分布是理想化的 |
| **不许跳过基线** | 没有基线，你不知道 AI 到底带来了什么 |
| **不许在试点阶段承诺上线时间** | 试点的目的是**发现你没想到的问题** |

> **试点的产出不是「可以上线了」，而是「我们知道了系统会在哪里失败」。**
> 这句话写进阶段说明里，能防止试点被草率收尾。

## 2. 阶段二 · 影子运行（Shadow Run）

### 2.1 这是整个流程里最被低估的一步

**核心思想：AI 真实运行，但它的输出不参与决策。**
人工照常做原来的流程，AI 在旁边跑，同时记录两边的结果用于对比。

### 2.2 影子运行解决什么问题

| 问题 | 影子运行怎么解决 |
|---|---|
| **真实分布是什么样的** | Demo 数据永远反映不了真实输入的脏乱程度 |
| **真实失败率是多少** | 连续跑几百条，统计任务级成功率 |
| **人工和 AI 的分歧在哪** | 找出「AI 对但人错」和「人会对但 AI 错」的分布 |
| **哪些情况 AI 完全不行** | 收集 hard case，决定要不要加规则兜底 |
| **真实成本** | 真实 token 分布，而不是估算 |

### 2.3 影子运行的操作要点

```
① 线上真实请求 → 复制一份 → 送到 AI 链路 → AI 结果丢弃但记录
② 人工的真实决策 → 记录
③ 定期对比：一致 / AI 对人错 / 人对AI错 / 双方都错
④ 把「人错 AI 对」的案例单独拎出来 —— 那是系统的价值
⑤ 把「AI 错人错」的案例归类 —— 那是能力边界
```

### 2.4 出口标准

| 指标 | 阈值示例 |
|---|---|
| **样本量** | ≥ 500 条（**低于这个数，任何比率的置信区间都很宽**） |
| **与人工的一致率** | ≥ 85%（视任务） |
| **严重错误率** | 0（**红线**：会导致不可逆后果的错误必须为 0） |
| **真实 p95 延迟** | ≤ 目标值 |
| **真实单次成本** | ≤ 目标值 |
| **未归类错误** | 0（都归上类了） |

> **500 条不是玄学**：比例估计的置信区间宽度随样本量平方根下降。
> 100 条样本上「准确率 90%」的 95% 置信区间大约是 [82%, 95%]——
> **这个宽度不足以支撑上线决策**。

### 2.5 影子运行的关键指标：一致率的分解

**不要只看一个总一致率。** 要拆成四格：

| | AI 对 | AI 错 |
|---|---|---|
| **人工对** | ✅ 一致（真·正确） | ❗ **人比 AI 强** → 能力缺口 |
| **人工错** | ❗ **AI 比人强** → 价值证明 | ⚠️ 双方都错 → 任务本身有问题 |

- **右上格大** → 模型不行，回去改
- **左下格大** → **这就是你的价值证明**，写进汇报材料
- **右下格大** → 任务定义或流程有问题，**先改流程**

> **汇报时最有说服力的一张图就是这个四格表。**
> 它同时回答了「能不能用」和「值不值」。

## 3. 阶段三 · 灰度（Canary）

### 3.1 核心变化

**AI 的输出开始真正参与决策，但只对一小部分流量。**

### 3.2 灰度维度

| 维度 | 切法 | 注意 |
|---|---|---|
| **按用户** | 5% → 20% → 50% → 100% | 最常用。**要固定用户集合**（同一用户始终在同一组），避免体验跳变 |
| **按场景** | 先切简单的场景，再切复杂的 | **推荐**：先切「错了代价低」的 |
| **按时间** | 先在低峰时段 | 适合对实时性不敏感的批处理 |

### 3.3 灰度期的必备机制

| 机制 | 说明 |
|---|---|
| **一键回滚** | 必须是**一个开关**，不能是一串操作。**回滚时间目标 < 5 分钟** |
| **实时看板** | 效果 / 效率 / 护栏三类指标，分钟级刷新 |
| **自动告警** | 护栏指标破线 → 自动降级到人工/规则路径 |
| **人工兜底通道** | 用户可以随时转人工，且不丢失上下文 |
| **对照日志** | 灰度组 vs 对照组，同口径指标 |

### 3.4 放量节奏（建议）

```
5%  ──(观察 1~2 天)──▶  20%  ──(观察 3~5 天)──▶  50%  ──▶  100%
 │                        │                        │
 └─ 严重错误出现：立即回滚   └─ 指标持平但未改善：停下来做 A/B 实验
```

**每一档的停留时间按「能收集到足够样本量」来定**，不是按日历。
如果 5% 档每天只有 50 次调用，那 5% 档至少要待 2 天才有 500 条样本。

### 3.5 出口标准

| 指标 | 要求 |
|---|---|
| 护栏指标 | **全程零红线**（一次都不能破） |
| 效果指标 | 灰度组 **显著优于**对照组（不是「持平」） |
| 效率指标 | p95 延迟、单次成本达标 |
| 人工负担 | 复核工时在预算内（**如果 AI 让人更忙了，这就是失败的灰度**） |
| 用户反馈 | 无集中负面 |

> **「人工负担上升」是最容易被忽略的失败信号。**
> 如果 AI 让审核员每条都要改一遍，系统的总人力成本可能不降反升。

## 4. 阶段四 · 规模化

### 4.1 规模化的重点不是性能，是**可持续**

| 维度 | 要做的事 |
|---|---|
| **容量** | 峰值 QPS、扩容预案、降级策略 |
| **SLA** | 可用性目标、故障响应时限、值班安排 |
| **监控** | 业务指标 + 系统指标 + **模型指标**（见下） |
| **变更管理** | Prompt 改动、模型升级的准入流程 |
| **文档** | 操作手册、事故预案、**「模型升级后要重跑什么」的清单** |
| **成本治理** | 月度成本看板 + 超预算告警 |

### 4.2 模型专属的监控项

**这是普通系统没有的，也是最容易被漏的：**

| 监控项 | 为什么 |
|---|---|
| **输入分布漂移** | 用户行为变了，输入的分布也变了，模型效果悄悄下降 |
| **输出分布漂移** | 模型开始输出不同的模式（格式变了、长度变了） |
| **拒答率变化** | 突然上升 = 输入分布变了或模型退化了 |
| **工具调用失败率** | Agent 链路的关键健康指标 |
| **人工推翻率** | **最重要的单一指标**——人推翻 AI 的比例 |
| **成本/延迟趋势** | 突增通常意味着有人在改 prompt 或数据分布变了 |

> **人工推翻率是唯一一个「业务真相」指标。**
> 其他指标都可以在模型退化初期毫无反应（模型会自信地给出错误答案），
> 但**人会立刻发现不对并推翻**。

### 4.3 变更管理：模型是最容易「悄悄坏掉」的组件

```
任何变更都必须回答：
① 改了之后要不要重跑评测集？（Prompt 改动 → 必须）
② 评测分数下降多少算可接受？（提前定好阈值，别临时讨论）
③ 灰度怎么放？（和功能发布一样）
④ 怎么回滚？（Prompt 版本化，保留旧版本）
```

> **Prompt 必须版本化。** 它是代码的一部分，
> 要有 diff、能回滚、能追溯「线上跑的是哪个版本的 prompt」。

## 5. 四阶段门禁汇总表

| 阶段 | 风险敞口 | 关键产出 | 出口条件 |
|---|---|---|---|
| **试点** | 0（离线） | 错误分类表、真实成本、基线对比 | 任务级成功率 ≥ 目标；错误 100% 可归类 |
| **影子** | 0（不决策） | 对照四格表、500+ 条真实记录 | 一致率 ≥ 目标；严重错误 = 0；成本/延迟达标 |
| **灰度** | 1% → 100% | 实时看板、回滚开关、告警 | 护栏零红线；效果显著优于对照；人工负担不升 |
| **规模化** | 100% | SLA、运维手册、变更流程 | 连续 N 天稳定；成本在预算内；监控齐全 |

> **每一阶段的出口条件都必须是「数字 + 口径」，不能是「评审通过」。**

## 6. 回滚机制

### 6.1 回滚开关的三层

```
① 功能开关     ← 关掉 AI 入口，用户走老流程
② 降级开关     ← 关掉某个环节（如自动发送 → 只生成草稿）
③ 模型回滚     ← 切回上一个版本的 prompt / 模型
```

**三层要独立**。只有「模型回滚」而没有「功能开关」是不够的——
新 prompt 引入了新逻辑时，回滚模型不够，得能整体关掉。

### 6.2 自动降级的触发条件

| 触发 | 动作 |
|---|---|
| 护栏指标破线 | 自动切到人工路径 + 告警 |
| 错误率超阈值 | 缩小灰度比例 |
| 成本超预算 | 切到小模型 / 关掉高成本功能 |
| 延迟劣化 | 限流 / 排队 |
| 依赖服务挂 | 降级到规则基线 |

> **降级路径必须在上线前演练过。**
> 没演练过的降级方案，出事时大概率也是坏的。

---

## 7. 规模化阶段的必备文档

| 文档 | 内容 | 缺失后果 |
|---|---|---|
| **操作手册** | 日常操作、参数调整、常见问题 | 依赖某一个人 |
| **事故预案** | 每类故障的现象、定位路径、处置动作、回滚 | 出事时乱抓 |
| **模型升级清单** | 升级后必须重跑什么、谁批准、阈值多少 | 升级即事故 |
| **评测集说明** | 怎么加用例、怎么跑、分数怎么解读 | 评测集腐烂 |
| **成本看板说明** | 每个指标的口径和归因 | 成本说不清 |
| **数据处理说明** | 数据从哪来、谁能看、怎么删 | 合规风险 |
| **变更记录** | 每次改了什么、为什么、谁批的 | 无法追溯 |

> **这七份文档是「系统从个人产物变成组织资产」的标志。**
> 没有它们，系统只能靠某个人撑着——**那个人一走，系统就废了**。

## 8. 常见错误

| 错误 | 表现 | 纠正 |
|---|---|---|
| **跳过影子直接灰度** | 真实分布完全没测过 | 影子是零风险的信息来源，**没有理由跳过** |
| **影子样本量不够就下结论** | 100 条上测出 90% 一致率就上线 | 至少 500 条；报告置信区间 |
| **灰度只看效果不看人工负担** | 审核员工作量翻倍 | 复核工时是灰度的一级指标 |
| **回滚不是一键** | 出事要改 5 个配置 | 功能开关 + 降级开关 + 模型回滚三层 |
| **降级方案没演练** | 真降级时发现链路是断的 | 上线前演练一次完整降级 |
| **Prompt 没版本化** | 不知道线上跑的是哪版 | prompt 进版本库 |
| **只看系统指标不看模型指标** | 模型悄悄退化三个月才发现 | 监控拒答率、推翻率、输出分布 |
| **规模化=加机器** | 忽略了运维与文档 | 规模化是可持续性 |

---

## 9. 工程结论

1. **四阶段是逐级放大风险敞口**：0 → 0 → 1% → 100%。**影子阶段是零风险的免费信息源，没有理由跳过。**
2. **影子至少 500 条。** 低于这个数，任何比率的置信区间都宽到不能支撑决策。
3. **影子阶段最有价值的产出是那个四格表**——它同时回答「能不能用」和「值不值」。
4. **灰度看三类指标**，其中「人工负担」最容易被漏——**AI 让人更忙就是失败的灰度**。
5. **回滚要三层独立**：功能开关 / 降级开关 / 模型回滚。降级方案必须演练过。
6. **模型是最容易悄悄坏掉的组件**——Prompt 要版本化，升级要有清单和阈值。
7. **「人工推翻率」是最重要的单一监控指标**，因为其他指标在模型退化初期毫无反应。
8. **规模化的重点是可持续，不是性能。** 七份文档是系统从个人产物变成组织资产的标志。
