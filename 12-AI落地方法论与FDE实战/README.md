# 12 · AI 落地方法论与 FDE 实战

> **从「这个方案该不该做」到「怎么证明它做成了」——一套可以照着走的交付流程。**

前面十一条主线讲的是**技术**：模型怎么跑、检索怎么做、Agent 怎么编排、检测怎么部署。
这一条讲的是**怎么把技术变成一个能交付、能验收、能持续运行的业务系统**。

**它不是又一份「最佳实践」清单。** 它是一套有顺序、有闸门、有出口标准的流程，
外加三个公开仓库形态的真实案例拆解。

> **为什么单独开一条线**：模型能力会变、框架会变、价格会变，
> 但**「该不该做 / 边界在哪 / 做成什么样算成功」这三件事的判断方式是不变的**。
> 这条线讲的就是这些不变的东西。

## 🚦 五道闸

```
        业务需求
           │
    ┌──────┴──────┐
    │  ① 需求闸   │  这事该用 AI 吗？        ← 80% 的项目死在这
    └──────┬──────┘
    ┌──────┴──────┐
    │  ② 边界闸   │  AI 做什么、不做什么？
    └──────┬──────┘
    ┌──────┴──────┐
    │  ③ 数据闸   │  数据在哪、多少、能不能用？
    └──────┬──────┘
    ┌──────┴──────┐
    │  ④ 方案闸   │  模型/架构/部署形态怎么选？
    └──────┬──────┘
    ┌──────┴──────┐
    │  ⑤ 验收闸   │  做成什么样算成功？谁来判？
    └──────┬──────┘
           ▼
        排期与交付
```

> **关键：按顺序过，不能跳。** 跳过 ① 直接做 ③ 的项目，
> 最后会发现数据攒了很久，但需求本身不成立。

## 💰 成本五项（常被算漏四项）

| # | 成本项 | 常被忽略 |
|---|---|---|
| ① | **数据成本**（采集/清洗/标注） | ⭐ 几乎总是被忽略 |
| ② | **开发成本** | |
| ③ | **推理成本** | 唯一被认真算的那项 |
| ④ | **人工审核成本** | ⭐ 最常被漏 |
| ⑤ | **运维成本** | ⭐ 自托管时很高 |

> **一个测算靠不靠谱，只看一件事**：
> 「失败重试的成本、人工复核的成本、标注的成本算进去了吗？」

## 📊 四个阶段与出口标准

| 阶段 | 风险敞口 | 出口条件（核心） |
|---|---|---|
| **试点** | 0（离线） | 任务级成功率达标 + **错误 100% 可归类** |
| **影子** | 0（不决策） | ≥500 条真实记录 + 一致率达标 + **严重错误 = 0** |
| **灰度** | 1% → 100% | **护栏零红线** + 效果显著优于对照 + **人工负担不上升** |
| **规模化** | 100% | 连续稳定 + 成本在预算内 + **模型监控齐全** |

## 🔑 从三个案例抽出的四个模式

| 模式 | 一句话 |
|---|---|
| **1 · 边界用机制表达** | 把规范从文档里删掉，系统行为不变——那才叫边界 |
| **2 · 能规则判定的，不交给模型** | 模型负责生成，代码负责约束；代价从「事故」降级为「一次被拦截的调用」 |
| **3 · 把「不确定」变成状态** | 「待人工补充」比编造的资质更值钱——状态可审核、可统计、可放行 |
| **4 · 最小必要上下文** | 只发当前任务需要的 → 同时省 token + 降泄露面 + 降噪音 |

## 💡 工程结论（浓缩版）

1. **五道闸按顺序过。** 80% 的项目死在需求闸，却把时间花在了写代码上。
2. **边界是最重要的商业决策**，且必须同时是一条可机器判定的验收标准。
3. **数据永远先小样本验证**——100~500 条就能回答「模型能不能做这件事」。
4. **成本要算五项**，尤其人工复核与失败重试。
5. **影子阶段至少 500 条**，低于这个数任何比率的置信区间都太宽。
6. **「人工负担不上升」是灰度的一级指标**——AI 让人更忙就是失败的灰度。
7. **AI 项目往往不是交付时死的，是交付后 3~6 个月慢慢死的**——早期信号在早期就能看到。
8. **Prompt 是代码**，需要版本管理、回归测试和 review。
9. **边界用机制表达**：生成交给模型，约束交给代码。
10. **采购先答「哪个环节值得买」**，混合是大多数场景的正确答案。
