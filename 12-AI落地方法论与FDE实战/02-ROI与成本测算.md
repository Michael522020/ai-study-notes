# ROI 与成本测算

> **核心问题**：这个 AI 方案一年省多少钱？给客户报的数字，他能不能自己算一遍？

---

## 0. 成本不止推理成本

**最常见的测算错误：只算推理成本。**

真实的项目成本有五项：

| # | 成本项 | 一次性 | 持续 | 典型量级 |
|---|---|---|---|---|
| **①** | **数据成本** | 采集、清洗、标注 | 增量标注 | **常被完全忽略** |
| **②** | **开发成本** | 方案设计、编码、评测集 | — | 通常是最大项 |
| **③** | **推理成本** | — | 按调用量 | 唯一「性感」的那项 |
| **④** | **人工审核成本** | — | 按复核量 | **最常被漏算** |
| **⑤** | **运维成本** | 部署、监控、文档 | 值守、升级、故障 | 自托管时很高 |

> **判断一个测算靠不靠谱，只需要问一句：**
> **「失败重试的成本、人工复核的成本、标注的成本算进去了吗？」**
> 三样都算了，基本靠谱；一样没算，就是拍的。

## 1. 推理成本：先把口径定死

### 1.1 单次调用成本

```
单次成本 = 输入 token × 输入单价 + 输出 token × 输出单价
```

**必须同时写明四个口径**，否则数字无法复现：

| 口径项 | 为什么必须写 |
|---|---|
| **输入 token 数** | 含系统提示？含检索到的文档？含工具定义？ |
| **输出 token 数** | 是上限还是实测均值？**实测均值通常只有上限的 1/3** |
| **是否命中缓存** | 命中与未命中单价可能差一个量级 |
| **调用来源** | 同一家厂商的不同模型档位差很多 |

> **输出 token 用实测均值，不要用上限。**
> 报上限会让客户觉得贵，且在真实系统里本来就是错的。

### 1.2 一个可直接抄的测算函数

```python
from dataclasses import dataclass

@dataclass
class Price:
    input_per_m: float          # 每百万输入 token 单价
    output_per_m: float         # 每百万输出 token 单价
    cache_read_per_m: float     # 缓存命中价（无则填 None）
    cache_write_per_m: float    # 缓存写入价（无则填 None）

def call_cost(p: Price, in_tok: int, out_tok: int,
              cached_in_tok: int = 0) -> float:
    """单次调用成本（美元）"""
    fresh = in_tok - cached_in_tok
    c = fresh / 1e6 * p.input_per_m + out_tok / 1e6 * p.output_per_m
    if cached_in_tok and p.cache_read_per_m is not None:
        c += cached_in_tok / 1e6 * p.cache_read_per_m
    return c


def daily_cost(p: Price, calls_per_day: int, in_tok: int, out_tok: int,
               cache_hit_rate: float = 0.0) -> float:
    """日成本；cache_hit_rate 应用于「可缓存的前缀」部分"""
    cached = int(in_tok * cache_hit_rate)
    return calls_per_day * call_cost(p, in_tok, out_tok, cached)
```

### 1.3 影响推理成本的四个杠杆

| 杠杆 | 做法 | 效果 |
|---|---|---|
| **模型分级** | 简单任务用小模型，复杂才上大模型 | 通常能降 50%+ |
| **缓存** | 稳定前缀（系统提示 + 知识库 + 工具定义）命中缓存 | 输入成本可降一个量级 |
| **压缩上下文** | 裁剪历史、摘要、只放相关片段 | 输入 token 直接降 |
| **批处理** | 非实时任务走批量接口 | 通常有折扣 |

> **杠杆的优先级**：先做**分级**（架构改动最小），再做**缓存**（要求前缀稳定），
> 最后做**压缩**（影响效果，要评测）。

## 2. 三张成本表

### 2.1 表一：单次调用成本

| 场景 | 输入 token | 输出 token | 缓存命中 | 单次成本 | 备注 |
|---|---|---|---|---|---|
| 简单分类 | 800 | 100 | 0% | $x | 无检索、无工具 |
| 带检索问答 | 3,000 | 500 | 40% | $y | 知识库前缀稳定 |
| Agent 多步（均摊 4 步） | 2,000×4 | 300×4 | 60% | $z | **按整次任务算，不是按步** |
| 人工复核（**别漏**） | — | — | — | **人时 × 单价** | 见 §4.2 |

> **Agent 场景必须按「一次任务」而不是「一次 API 调用」报成本。**
> 用户感受到的是任务，不是调用。

### 2.2 表二：月度运行成本

```
月成本 = 月调用量 × 单次成本
       + 月复核工时 × 工时单价
       + 基础设施月摊销
       + 月度运维工时 × 工时单价
```

**必须列出三个场景**（业务量会变）：

| 场景 | 月调用量 | 月复核工时 | 基础设施 | 运维 | **合计** |
|---|---|---|---|---|---|
| 保守（当前量） | | | | | |
| 基准（3 个月后预期） | | | | | |
| 乐观（满负荷） | | | | | |

> **给客户报「保守」和「基准」两个数**，并说明乐观数的前提。
> 只报乐观数 = 后期超支必然引发纠纷。

### 2.3 表三：三年 TCO

```
三年 TCO = 一次性投入 + 3 × 月成本 + 升级/迁移成本 + 退出成本
```

| 项 | 第 0 年 | 第 1 年 | 第 2 年 | 第 3 年 | 合计 |
|---|---|---|---|---|---|
| 数据采集与标注 | | | | | |
| 开发（含评测集） | | | | | |
| 基础设施（自托管） | | | | | |
| 推理（API 或自托管） | | | | | |
| 人工复核 | | | | | |
| 运维与值守 | | | | | |
| 模型升级与再评测 | | | | | |
| **合计** | | | | | |

**三个容易漏的项**：

| 项 | 说明 |
|---|---|
| **模型升级成本** | 每次换模型都要重新跑评测集、重新校准阈值。**这是持续成本，不是意外** |
| **再标注成本** | 生产中的 bad case 修正要回流到训练集，形成长期标注义务 |
| **退出成本** | 数据迁出、接口适配、用户迁移（见 [`05`](./05-采购与选型清单.md) §6） |

## 3. ROI 模型：两种算法，别混

### 3.1 模型 A：人力替代（AI 顶掉人）

```
年节省 = 被替代的人力 × 单价
ROI = (年节省 - 年增量成本) / 年增量成本
```

**前提**：被替代的人力**真的能减少**。

> ⚠️ **最常见的失败**：AI 节省了 70% 的审核时间，但**没有人因此离职**，
> 那这 70% 的时间是**变成了做别的事**，不是变成了成本节省。
> **替代型 ROI 只有在真的减编/减外包时才成立。**

### 3.2 模型 B：人力增效（AI 让人更快）

```
年节省 = 人力数量 × 单价 × (原耗时 - 新耗时) / 原耗时
```

**这个模型几乎总是成立**，因为人没有被替代，只是产能提高。

**但要注意**：增效产出的价值**需要业务侧真的把它兑现**
（多接单、多服务客户、多做项目）。**如果业务量不变，增效就不产生财务价值。**

> **FDE 的判断**：增效型 ROI 更真实，但更难说服人；
> 替代型 ROI 更漂亮，但通常不成立。
> **诚实做法：两个都算，把前提写清楚。**

### 3.3 回收期

```
回收期（月） = 一次性投入 ÷ (月节省 - 月增量成本)
```

**如果月节省 ≤ 月增量成本，这个项目永远不回本。**
这句话必须出现在测算表里，而不是只给一个正的 ROI 数字。

## 4. 三个最常漏算的成本

### 4.1 失败重试的成本

```
有效调用率 = 成功调用数 ÷ 总调用数
实际成本 = 名义调用数 × 单次成本 ÷ 有效调用率
```

| 场景 | 名义调用 | 有效调用率 | 实际成本倍数 |
|---|---|---|---|
| 格式校验失败重试 | 1000 | 95% | 1.05× |
| 检索为空需降级重试 | 1000 | 80% | 1.25× |
| 多步 Agent 某步失败重跑 | 1000 | 60% | **1.67×** |

> **Agent 的有效调用率是最容易被忽略的乘数。**
> 一个平均 5 步的 Agent，每步 90% 成功率 → 任务级成功率只有 59%。
> 这直接推高了 §1 的单次任务成本。

### 4.2 人工审核的成本（最常被漏）

**如果有人工闸，就必须算这道成本。**

```
月复核成本 = 月任务量 × 平均复核时长 × 复核单价
```

| 复核模式 | 平均复核时长 | 说明 |
|---|---|---|
| **抽检**（抽 10%） | 任务量 × 10% × 全量时长 | 便宜但发现不了小比例严重错误 |
| **全检**（100%） | 任务量 × 全量时长 | 贵，但高风险场景通常必须 |
| **只审高风险** | 按比例筛 | 需要风险分类器 |
| **审核 = 改写** | 任务量 × 编辑时长 | 产出直接可用，ROI 最高 |

> **「只审不改」是最贵的模式**：既付了审核成本，
> 又没把审核结果转化为产出价值。**能改成「审核即编辑」通常能省一半成本。**

### 4.3 数据成本

```
一次性数据成本 = 采集 + 清洗 + 标注单价 × 标注量
持续数据成本 = 月增量 bad case 标注 + 主动学习采样标注
```

| 标注方式 | 单价量级 | 说明 |
|---|---|---|
| 自标 | 工程师工时 | 慢但口径一致 |
| 外包 | 低于工程师工时 | 需仲裁机制与规范文档 |
| 主动学习 | **每条价值更高** | 只标模型最不确定的样本 |

> **主动学习是数据成本的最优解**：同样预算下，标注量可以少 3~5 倍，
> 因为标的是「最有信息量的样本」。但前提是你已经有第一版模型。

## 5. 规模效应

**成本不是线性的。** 有三个反直觉的点：

### 5.1 规模变大后，单次成本会下降

| 机制 | 原因 |
|---|---|
| **模型分级** | 调用量越大，越能把「简单请求」分流到小模型 |
| **缓存命中率上升** | 知识库和工具定义被更多请求共享 |
| **批处理** | 非实时场景占比上升，可用批量接口 |
| **专用硬件摊销** | 自托管时，GPU 利用率从 30% 提到 70%，单位成本降一半 |

### 5.2 规模变大后，运维成本会**上升**

| 机制 | 原因 |
|---|---|
| 容量管理 | 高峰期要扩容，低谷要缩容 |
| 故障影响面 | 一个请求拖垮一批 |
| 值班 | 7×24 有人 |
| 版本管理 | 每次模型升级影响面变大 |

> **所以「量大就便宜」是错的。**
> 正确的说法是：**量大会摊薄推理成本，但抬高运维成本。**
> 两个拐点之间的区间是最优规模。

### 5.3 拐点在哪里

```
总成本 = 固定成本 + 变动成本

固定成本（开发 + 部署 + 评测）      变动成本（推理 + 复核 + 运维）
        │                                        │
        └──────── 交叉点 = 盈亏平衡量 ────────────┘
```

**测算表里应该画出这张图**——客户最关心的就是「我的量够不够过这个点」。

## 6. 敏感性分析

**只给一个数字的测算表是不可信的。** 至少给出三档：

| 变量 | 保守 | 基准 | 乐观 |
|---|---|---|---|
| 月调用量 | 实际量 | 3× 实际 | 10× 实际 |
| 单次输入 token | 实测 P90 | 实测均值 | 实测均值 |
| 缓存命中率 | 0% | 实测 | 理想 |
| 有效调用率 | 实测最低 | 实测均值 | 100% |
| 人工复核比例 | 全检 | 抽检 20% | 审核即编辑 |

```
三年 TCO（保守）= $X
三年 TCO（基准） = $Y   ← 报这个
三年 TCO（乐观） = $Z
```

> **报 Y，但把 X 和 Z 也摆出来。**
> 客户自己会判断哪个更接近他的场景——**你给出区间，他做决策，这比单点数字有说服力得多。**

## 8. 常见算错的地方

| 错误 | 正确做法 |
|---|---|
| 只报推理成本 | 五项成本都列 |
| 用输出 token 上限而不是实测均值 | 跑一遍真实流量统计 P50/P90 |
| 忘了失败重试 | 乘上有效调用率的倒数 |
| 忘了人工复核 | 按复核模式和工时算 |
| 忘了数据标注 | 一次性 + 持续标注都列 |
| 用「人力替代」但实际不减人 | 老实算增效型 |
| 报了单点数字 | 给三档 + 敏感性分析 |
| 隐瞒未计入项 | 明示，并说明原因 |
| 价格没写查询日期 | 必须写（价格随时会变） |

> **最后一条特别重要**：**给客户的成本表必须带定价查询日期。**
> 三个月后价格变了，客户拿旧数字来质疑，责任在你。

## 9. 工程结论

1. **成本五项**：数据 / 开发 / 推理 / 人工复核 / 运维。**只算推理的测算一律不可信。**
2. **三个漏算项**：失败重试、人工复核、数据标注。前两个最常被漏。
3. **Agent 必须按「一次任务」报成本**，不是按 API 调用；并乘上任务级有效调用率。
4. **输出 token 用实测均值，不用上限。**
5. **人力替代型 ROI 通常不成立**（人没减编）；增效型几乎成立但需要业务量兑现。**两个都算。**
6. **量大不等于便宜**：推理成本被摊薄，运维成本被抬高，有最优规模区间。
7. **报三档而不是一个数字**，并画出盈亏平衡点。
8. **成本表必须带定价查询日期和「未计入项」清单。**
