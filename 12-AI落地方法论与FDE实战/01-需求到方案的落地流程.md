# 需求到方案的落地流程

> **核心问题**：一个业务需求摆在面前，我凭什么判断「这事该做 AI」？从需求到第一版方案，中间要过几道闸？

---

## 0. 一句话立场

> **FDE 的核心产出不是代码，是「这个方案该不该做、做成什么样算成功」的判断。**
> 代码是执行，判断才是价值。

绝大多数失败的 AI 项目，死在**第一道闸**（需求闸），却把时间花在了第五道闸（实现）。

---

## 1. 五道闸

```
        业务需求
           │
    ┌──────┴──────┐
    │  ① 需求闸   │  ← 这事该用 AI 吗？（80% 的项目死在这）
    └──────┬──────┘
           │
    ┌──────┴──────┐
    │  ② 边界闸   │  ← AI 做什么、不做什么？
    └──────┬──────┘
           │
    ┌──────┴──────┐
    │  ③ 数据闸   │  ← 数据在哪、多少、能不能用？
    └──────┬──────┘
           │
    ┌──────┴──────┐
    │  ④ 方案闸   │  ← 模型/架构/部署形态怎么选？
    └──────┬──────┘
           │
    ┌──────┴──────┐
    │  ⑤ 验收闸   │  ← 做成什么样算成功？谁来判？
    └──────┬──────┘
           │
           ▼
        排期与交付
```

**关键：五道闸必须按顺序过，不能跳。**
跳过 ① 直接做 ③ 的项目，最后会发现数据攒了很久，但需求本身不成立。

---

## 2. ① 需求闸：这事该用 AI 吗

### 2.1 判断标准

**AI 擅长的是「处理无法穷举规则的模糊信息」**。三类信号：

| 信号 | 说明 | 例子 |
|---|---|---|
| **非结构化输入** | 文本/图像/音频/文档，需要理解语义 | 简历筛选、合同审阅、病历归类 |
| **输出需要多样性** | 正确答案不唯一，需要生成 | 营销文案、回复草稿、摘要 |
| **规则会持续增长** | 穷举规则的维护成本 > 模型成本 | 客服意图分类、询盘分级 |

### 2.2 反向判断表（更实用）

| 场景 | 该不该上 AI | 为什么 |
|---|---|---|
| 规则能穷举且稳定 | ❌ **不该** | 规则更快、更准、更便宜、可审计 |
| 规则能穷举但持续变 | ⚠️ **谨慎** | 考虑「规则 + 兜底」或先做小模型分类 |
| 需要理解语义但输出固定 | ✅ **该** | 结构化抽取（LLM 做 NER） |
| 需要生成且允许人工改 | ✅ **该** | 草稿类场景（对应人审闸） |
| 需要生成且**不允许**人工改 | ⚠️ **高风险** | 见 §3.1 的边界约束 |
| 高频低价值单点 | ❌ **不该** | 一次调用能解决的，不要上系统 |
| 一次性任务 | ❠️ **看情况** | 建系统的成本可能超过手工做 |

### 2.3 三个「伪需求」信号

| 伪需求信号 | 真实需求可能是 |
|---|---|
| 「我们想做个 AI 系统」 | 某个具体环节人力太贵 |
| 「AI 能自动做这个」 | 这个环节有大量非标准化的判断 |
| 「竞品有 AI 功能」 | 竞品用它做获客/展示，不是用它省钱 |

> **问对第一个问题**：「如果不考虑 AI，这个流程现在是怎么做的？哪一步最贵？」
> 答不上来的需求，不要开始做。

### 2.4 需求闸的输出物

一份**《需求澄清单》**，必须包含：

- [ ] 当前流程图（AI 介入前的）
- [ ] 哪一步的人力成本最高（量化到人/小时）
- [ ] 期望的产出是什么（产物形态：分类结果 / 草稿 / 决策）
- [ ] **产出错误的代价**（错一次的代价决定要不要人工闸）
- [ ] 谁是最终使用者、谁为结果负责

## 3. ② 边界闸：AI 做什么、不做什么

**这是整条流程里最重要的商业决策，也是最容易被跳过的一步。**

### 3.1 三种边界形态

| 边界 | AI 的角色 | 决策者 | 合规友好度 | 典型场景 |
|---|---|---|---|---|
| **工具型** | 只产出量化指标/标记，**不出结论** | 人 | **最高** | 医学影像辅助标注、缺陷面积计算 |
| **辅助决策型** | 出建议/草稿，人确认后生效 | 人 | 中 | 简历初筛、客服回复草稿 |
| **自动决策型** | 直接出结论并生效 | AI | **最低** | 自动审批、自动放行 |

> **高风险领域（医疗诊断、招聘录用、信贷审批、司法）通常只允许前两种。**
> 不是因为技术做不到，而是因为**责任无法被算法承担**。

### 3.2 边界该怎么写

**用一句话写死，并让它出现在产品界面和合同里。**

范例（来自一个真实的影像项目形态）：

> **AI 只做辅助标记与量化指标（分割/测量/三维重建），不出具诊断结论。**
> 诊断结论由执业医师确认并以 CA 数字证书电子签名后方可生效。

这句话同时解决了三个问题：
1. **责任边界**：谁签字谁负责
2. **产品边界**：AI 产出物的法律性质（辅助信息 vs 结论）
3. **验收边界**：AI 的指标就是分割精度/测量误差，不是诊断准确率

### 3.3 边界闸的三个必答问题

| 问题 | 为什么必须答 |
|---|---|
| **AI 出错时谁承担后果？** | 决定要不要人工闸、要不要多级复核 |
| **AI 的产出物在法律上是什么？** | 「参考信息」和「诊断结论」的监管要求完全不同 |
| **用户能不能绕过 AI 直接看原始数据？** | 决定「可解释性」和「可回溯」的设计深度 |

### 3.4 常见错误

| 错误 | 后果 |
|---|---|
| 边界只写在 PPT 上，不进产品和合同 | 上线后责任真空 |
| 边界写成「AI 辅助决策」这种模糊话 | 合规审查过不了 |
| 边界留了「可选项」 | 实际使用中 AI 变成默认，人不再复核 → **闸门失效** |
| 没有把边界变成**验收指标** | 验收时变成「感觉还行」 |

> **推论**：**边界必须同时是一条验收标准。**
> 比如「系统输出的每一条结论都能逐字回指到原始证据，回指率 100%」。

## 4. ③ 数据闸：数据在哪、多少、能不能用

### 4.1 数据三问

| 问题 | 判定 | 不满足怎么办 |
|---|---|---|
| **有多少？** | 与任务难度匹配 | 少 → 用预训练模型 + 小样本；或先做规则基线 |
| **质量如何？** | 有标注？有噪声吗？ | 差 → 先治理数据，**这是最容易被跳过、也最致命的一步** |
| **能不能用？** | 许可 + 合规 + 权限 | 不能 → 见 [`../appendix/数据集与许可索引.md`](../appendix/数据集与许可索引.md) |

### 4.2 冷启动的三条路

| 路线 | 做法 | 适合 |
|---|---|---|
| **规则先行** | 先用规则跑通全流程，AI 只替换其中最贵的一步 | 流程尚未定型、需求还在变 |
| **小样本先行** | 标注 100~500 条 → 验证「能不能学」→ 再决定要不要标更多 | 有明确任务边界 |
| **通用模型先行** | 用现成大模型 + 提示词，不训练 | 任务通用、容错高、无合规限制 |

> **工程结论**：**永远不要一上来就标 1 万条数据。**
> 先用 100~500 条验证「这件事模型能不能做」，再决定投入规模。
> 这是本项目里**性价比最高的一个决策**。

### 4.3 数据闸的输出物

- [ ] 数据清单（来源 / 规模 / 质量抽检结果 / 许可 / 敏感字段）
- [ ] **数据泄漏检查**（训练/验证/测试是否有重叠；视频按序列划分）
- [ ] 标注规范（多人标注时的仲裁规则）
- [ ] 数据版本管理方式（改了数据能不能追溯到模型版本）

## 5. ④ 方案闸：三层选型

### 5.1 三层决策

```
应用层：要不要 Agent？      → 07/01、07/02、07/03
         ↑ 判据：单次调用能解决 / 路径已知 → 不要上 Agent
         │
模型层：直接调 API / 微调 / 从头训 / 用小模型
         ↑ 判据：通用任务 → API；领域术语多、格式稳定 → 微调；特殊模态/端侧 → 小模型
         │
部署层：云 API / 私有化 / 端侧
         ↑ 判据：数据不能出院 → 私有化；延迟/成本 → 端侧或自建
```

### 5.2 模型层选型表

| 情况 | 选择 | 成本量级 |
|---|---|---|
| 任务通用、格式灵活 | **大模型 API + 提示词** | 最低（按量付费） |
| 任务通用但量大 | **自托管开源模型** | 中（一次性硬件 + 运维） |
| 领域术语密集、输出格式固定 | **微调**（LoRA 优先） | 中高（数据 + 训练） |
| 有特殊模态（图像/语音/端侧） | **专用小模型** | 中（数据 + 训练 + 部署） |
| 需要极致能力与知识 | **大模型 API + 混合检索** | 中（API + 检索系统） |

> **默认答案是「大模型 API + 提示词 + 检索」**。
> 微调和训练都是在**提示词扛不住**时才需要的。

### 5.3 部署层选型表

| 判据 | 云 API | 私有化 | 端侧 |
|---|---|---|---|
| 数据能否出院 | ❌ 不能 | ✅ | ✅ |
| 初始投入 | 最低 | 高（硬件+改造） | 中 |
| 单位成本（量大时） | 高 | 低 | 低（但受限于硬件） |
| 运维复杂度 | 最低 | 高 | 高（现场运维） |
| 延迟 | 受网络影响 | 低 | 最低 |
| 可审计性 | 差（依赖厂商） | **好** | **好** |

### 5.4 方案闸的输出物

一份**《技术选型说明》**，每条决策必须写「**为什么选它，而不是另一个**」：
> 选私有化部署而非云 API：因为业务数据不得离开医院内网，且客户为等保测评要求提供完整审计日志。
> 选 7B 私有模型而非调用外部 API：成本在日均 2000 次调用后回本，且避免数据出院。

**只写结论不写理由的选型文档，等于没写。**

## 6. ⑤ 验收闸：做成什么样算成功

### 6.1 验收标准必须机器可判

**「效果不错」不是验收标准。** 每一条验收标准都要能被程序检查。

| 差的写法 | 好的写法 |
|---|---|
| 模型回答质量好 | 每条结论都能回指原文，**回指率 100%** |
| 速度快 | p95 延迟 < 3 秒（口径：并发 8，含首 token） |
| 成本可接受 | 单次调用成本 ≤ $0.05（口径：输入 2K / 输出 500 token） |
| 分类准 | 人工复核一致率 ≥ 85%（口径：50 条金标准集，2 名标注者仲裁） |

### 6.2 三类指标必须一起定

| 指标类 | 例子 | 缺失的后果 |
|---|---|---|
| **效果指标** | 准确率 / 回指率 / 检索召回 | 模型无用的也能上线 |
| **效率指标** | 延迟 / 吞吐 / 单次成本 | 上线后发现用不起 |
| **护栏指标** | 越权率 / 敏感信息泄露率 / 拒答率 | 出一次事就全线停 |

> **护栏指标是红线**：一旦破线立刻回滚，不参与「综合评分」。
> 详见 [`../07-Agent与智能体/02-Agent-Bot-产品化.md`](../07-Agent与智能体/02-Agent-Bot-产品化.md)。

### 6.3 验收闸的输出物

- [ ] 验收标准表（效果 / 效率 / 护栏，各有明确数字与口径）
- [ ] **金标准评测集**（建议 ≥ 50 条，人工标注，双人仲裁）
- [ ] 评测脚本（可重复运行、输出可对比的分数）
- [ ] 影子运行方案（见 [`03-试点-影子-灰度-规模化.md`](./03-试点-影子-灰度-规模化.md)）

## 7. 交付物清单

过完五道闸，应该产出这七份东西：

| # | 交付物 | 关键内容 | 常见缺失 |
|---|---|---|---|
| 1 | 需求澄清单 | 现状流程、痛点量化、产出形态 | 只写「想要 AI」 |
| 2 | 边界说明书 | AI 做什么/不做什么、责任人、法律性质 | **完全缺失** |
| 3 | 数据清单与质量报告 | 来源、规模、抽检、泄漏检查、许可 | 只写「我们有 XX 万条」 |
| 4 | 技术选型说明 | 每个决策的理由与放弃的选项 | 只有结论没有理由 |
| 5 | 验收标准表 | 效果/效率/护栏三类指标 + 口径 | 只有效果指标 |
| 6 | 评测集与脚本 | 金标准集 + 可重复的评测 | 用 demo 代替评测 |
| 7 | 成本测算表 | 五项成本 + 敏感性分析 | 只算推理成本 |

> **这七份东西就是 FDE 的交付物。**
> 它们加起来可能比代码更值钱——**因为它们让项目不会做错方向**。

## 8. 常见错误清单

| 错误 | 表现 | 纠正 |
|---|---|---|
| **跳过需求闸** | 一上来就选模型、标数据 | 先算「哪一步最贵」 |
| **边界不清** | 上线后不知道谁负责 | 一句话写死，进产品进合同 |
| **过早标数据** | 标了 5000 条才发现任务定义不清 | 先用 100~500 条验证 |
| **选型只有结论** | 半年后无法解释为什么这么选 | 每个决策写「为什么不是另一个」 |
| **验收指标模糊** | 上线后各部门各说各话 | 效果/效率/护栏三类，各有数字 |
| **没有评测集** | 每次改动都在猜有没有变好 | 先建 50 条金标准 |
| **忽略成本** | demo 很美，生产用不起 | 见 [`02`](./02-ROI与成本测算.md) |
| **忽略兜底** | 模型一失败整条链路断 | 见 [`../07-Agent与智能体/03-Super-Agent-长任务自治.md`](../07-Agent与智能体/03-Super-Agent-长任务自治.md) |

## 9. 工程结论

1. **五道闸按顺序过，跳过第一步最危险。** 80% 的失败项目死在需求闸，却把时间花在了写代码上。
2. **需求闸的第一个问题永远是「现在这一步的人力成本是多少」。** 答不上来就别做。
3. **边界闸是商业决策不是技术决策。** 「AI 不出结论、人签字」这类边界必须写进产品界面和合同。
4. **边界必须同时是一条可机器判定的验收标准。** 否则验收会变成扯皮。
5. **数据永远先小样本验证。** 100~500 条就能回答「模型能不能做这件事」。
6. **模型层默认选「大模型 API + 提示词 + 检索」**，微调和训练是提示词扛不住时的退路。
7. **选型文档要写「为什么不是另一个」。** 只写结论的文档半年后无法解释。
8. **效果 / 效率 / 护栏三类指标一起定。** 护栏是红线，不参与综合评分。
