# 案例拆解

> **核心问题**：方法论听起来都对，具体项目里长什么样？三个真实形态的项目，能不能抽出可复用的模式？

---

## 0. 说明

本章拆解三个**公开仓库形态**的项目：

| 案例 | 仓库 | 形态 |
|---|---|---|
| **A** | `medplan` | 合规驱动的私有化部署（医疗影像） |
| **B** | `eva` | 多语种外贸询盘应答 Agent |
| **C** | `biaoshu-desk` | 本地优先的投标工作台 |

**拆解的目的不是介绍项目，而是从三个不同约束的项目里抽方法论。**
每个案例都按同一个模板拆：

```
背景与约束 → 五道闸怎么过的 → 关键工程决策（带取舍） → 踩过的坑 → 可复用的方法论
```

> **说明**：三个仓库都是**工程实现与设计参考**，
> 里面的数据是合成的/占位的，**不是真实生产部署的记录**。
> 本章从中提炼的是**架构与决策模式**，不是性能结论。

## 1. 案例 A · 合规驱动的私有化部署

### 1.1 背景与约束

| 维度 | 约束 |
|---|---|
| **场景** | 院内影像科：阅片 + 手术规划 |
| **部署** | **院内私有化 Kubernetes，无外网依赖**（数据不出院） |
| **合规** | 等保 2.0 三级 + 卫健委电子病历应用管理规范 |
| **核心链路** | DICOM 调阅 → 多平面阅片 → AI 自动分割 → 三维入路规划 → 结构化报告 → 医师电子签名 → 归档留痕 |
| **AI 边界** | **只做辅助标记与量化指标，不出具诊断结论** |

### 1.2 五道闸怎么过的

| 闸 | 这个项目的答案 |
|---|---|
| **① 需求闸** | 痛点不是「没有 AI」，而是**影像科的阅片与规划流程有大量非标准化测量与标注**——规则穷举不了 |
| **② 边界闸** | **AI 只做辅助标记与量化指标**（分割/测量/三维重建）；诊断结论由执业医师确认并**以 CA 数字证书电子签名**后方可生效。这句话进了 README、进了产品、进了合规说明 |
| **③ 数据闸** | 数据是院内 DICOM，**不出院**；因此部署形态被合规倒推为私有化 |
| **④ 方案闸** | 开源做内核、自建合规壳：**Cornerstone3D（阅片）+ 自研 NestJS（业务）+ PostgreSQL 18（审计）** |
| **⑤ 验收闸** | 不是「AI 诊断准确率」，而是**合规条款逐条可验证**：980 条静态断言 + 13 条编译期负向断言 + 23 组真实数据库执行验证 |

### 1.3 关键工程决策（带取舍）

#### 决策 1：审计表「物理不可改」——三层递进

| 层 | 手段 | 防住什么 |
|---|---|---|
| 1 | **权限层**：`REVOKE` | 应用账号直接改/删 |
| 2 | **触发器层**（含 `TRUNCATE` 语句级） | 绕过权限的直连写、整表清空 |
| 3 | **hash chain** | **整表重建**（把所有记录删掉重插一遍） |

> **取舍**：三层递进意味着性能开销和实现复杂度都上升。
> 但**「审计表可被重建」是合规审计一定会问的问题**——
> 只有前两层是不够的。

#### 决策 2：越权响应「不可区分」

同一个接口对「用户不存在」和「密码错误」返回**相同的状态码、相同的响应体大小、相近的响应时间**（10004 与 10005）。

> **为什么**：如果两者可区分，这个接口就成了**「患者存在性预言机」**——
> 攻击者可以用它枚举「院内是否有某个患者」。**这本身就是合规问题。**

#### 决策 3：AI 合规边界「编译期强制」

用 `additionalProperties: false`（JSON Schema 严格化）+ 13 条 `@ts-expect-error` **负向断言**，
让**编译器**守住「AI 输出字段不能超出允许范围」这条边界。

> **取舍**：比运行时校验更早失败、更难绕过，但要求团队接受「类型即约束」的开发方式。
> **对比**：用运行时校验也能做，但**运行时校验是「人记得加的」，编译期是「加不了就编译不过」**。

#### 决策 4：设计 Token 单一数据源

JSON 是唯一权威，CSS **由脚本生成**，三处副本由 CI 门禁校验不漂移。

> **可迁移的方法论**：**凡是要在多处保持一致的东西，必须有单一数据源 + 自动校验。**
> 这条在设计系统、Prompt 模板、多语言文案、评测集上完全通用。

#### 决策 5：签名绑定与防绕过

电子签名用 **SM3 摘要绑定正文**——正文改一个字符，签名即失效；
服务端保存权威锁定标志，防止前端绕过。

### 1.4 踩过的坑（从设计里能反推出来的）

| 坑 | 表现 | 修法 |
|---|---|---|
| **审计表能被整表重建** | 前两层防线都拦不住「删了重插」 | 加 hash chain |
| **越权响应可区分** | 变成患者存在性预言机 | 三者（时间/状态码/体大小）对齐 |
| **AI 边界靠人守** | 有人加了个字段就突破边界了 | 编译期负向断言 |
| **Token 三处副本漂移** | 改了一处忘了另两处 | 单一数据源 + 门禁 |
| **前端能绕过签名校验** | 前端说「已签名」但服务端没锁 | 服务端权威标志 |

### 1.5 可复用的方法论

1. **合规不是最后加的检查项，它会倒推架构。** 「数据不出院」直接决定了部署形态、依赖清单和模型选型。
2. **边界要写成一句话，并在三个地方出现**：产品界面、对外文档、验收标准。
3. **能用编译期/构建期守住的约束，不要留到运行时。**
4. **合规敏感系统要过一遍「攻击者视角」**：存在性预言机、审计可重建、日志可篡改。
5. **把「一致性」交给机器**：单一数据源 + 自动校验。

## 2. 案例 B · 多语种外贸询盘应答 Agent

### 2.1 背景与约束

| 维度 | 约束 |
|---|---|
| **场景** | 阿里国际站 / 邮件 / WhatsApp 询盘应答 |
| **语言** | 简中 / 繁中 / 英 / 法 / 西 / 葡 / 阿 / 德（9 种） |
| **链路** | webhook → 去重与反垃圾 → 语言与客户识别 → 报价与认证检索 → 目标语言草稿 → **12 条红线校验** |
| **红线** | 含报价、新客户，或任何红线命中 → **都不自动发出** |
| **发送** | **自动发送被强制关闭**，草稿只能进人审 |

### 2.2 五道闸怎么过的

| 闸 | 答案 |
|---|---|
| **① 需求闸** | 询盘语言杂、格式乱、产品与认证信息分散 → 规则穷举不了 |
| **② 边界闸** | **AI 只写草稿，绝不自动发出**。报价、新客户、红线命中三个条件都进人工 |
| **③ 数据闸** | 全部用**合成/占位数据**（价格、认证、证书号都是虚构的，读取时打 `[SYNTHETIC DATA]` 标记）→ 许可问题在源头就消除了 |
| **④ 方案闸** | 多语种 + 结构化业务数据 → **检索优先**（查产品/报价/认证）再生成 |
| **⑤ 验收闸** | **12 条红线**是机器可判的验收标准；另有 `judge_calibration.md` 做判官校准 |

### 2.3 关键工程决策（带取舍）

#### 决策 1：把「不能做什么」做成代码里的强制

> **自动发送被强制关闭**，草稿只能进人审。

**取舍**：这让系统的「自动化程度」看起来低了，但**它让整条链路不需要为「发错」的代价负责**——
这是外贸场景里最正确的默认值。

#### 决策 2：红线是**多条独立判定**，不是一个大模型判断

「含报价 / 新客户 / 任何红线命中」是**结构性条件**，不是让模型「自己判断有没有红线」。

> **可迁移的方法论**：**能用规则判定的，不要交给模型判定。**
> 模型负责「生成」，规则负责「拦截」，两者职责分离。

#### 决策 3：去重与反垃圾在最前面

重复推送同一条阿里询盘，第二次直接返回 `{"duplicate": true}`。

> **为什么放最前**：重复询盘会重复消耗 token、重复触发检索、重复生成草稿，
> 也会污染评测集。**去重是成本控制的第一道闸，也是数据质量的第一道闸。**

#### 决策 4：多语言的难点不在「翻译」在「术语一致性」

产品名、认证名、报价条款在 9 种语言里必须**指同一个东西**。
解法是**检索回来的结构化数据里就是多语的**——不是翻译出来的，是**存的时候就分语言存的**。

> **可迁移的方法论**：**多语言系统的坑在「翻译质量」之前，在「术语与数据的一致性」。**
> 优先解决数据层的语言建模，再谈生成层的语言能力。

#### 决策 5：Prompt 工具包与判官校准

仓库里单独有 `docs/prompt_kit.md`（提示词工具包）和 `docs/judge_calibration.md`（判官校准）。

> **判官校准是评测环节的关键动作**：
> LLM-as-Judge 的分数在**没有校准**时是没有意义的——
> 需要用一批人工标注的样本去测判官本身的一致性，**校准后才敢用它的分数做决策**。

### 2.4 踩过的坑（可推断的）

| 坑 | 表现 | 修法 |
|---|---|---|
| **自动发送** | 一次误发就是事故 | 强制关闭，代码里锁死 |
| **红线靠模型判** | 模型漏判一次就出事 | 改成结构性条件 |
| **去重放在后面** | 重复询盘重复消耗、污染评测 | 去重前置 |
| **多语言靠翻译** | 术语前后不一致 | 数据层分语言存储 |
| **判官未校准** | 分数波动大，无法做上线决策 | 人工标注集校准判官 |

### 2.5 可复用的方法论

1. **「只生成不发送」是外贸类 AI 的正确默认值。** 把不可逆动作从系统里拿掉，比优化它更划算。
2. **生成交给模型，拦截交给规则。** 两者职责分离，不要让模型既生成又自检。
3. **去重、反垃圾、幂等要放在最前面。** 它们既是成本闸也是数据质量闸。
4. **多语言先解决数据层一致性，再解决生成层。**
5. **LLM-as-Judge 必须先校准再用。** 判官本身需要被评测。

## 3. 案例 C · 本地优先的投标工作台

### 3.1 背景与约束

| 维度 | 约束 |
|---|---|
| **场景** | 投标文件起草与收口（要求 → 章节 → 证据 → 放行 → 导出） |
| **形态** | **纯浏览器本地应用**（Vite + React），数据在 IndexedDB，**没有账号、不上传** |
| **核心模型** | 资料 → 整理要求（`R-01` 编号）→ 分派章节 → 起草 → **核对证据与人工放行** → 导出 Word |
| **模型接入** | 预置 DeepSeek / 硅基流动 / 本机 Ollama / OpenAI，也可自定义 Chat Completions 地址 |

### 3.2 五道闸怎么过的

| 闸 | 答案 |
|---|---|
| **① 需求闸** | 技术标的核心痛点是**「每条招标要求都要能找到章节，每句承诺都要能回到资料」**——这是可验证的工程问题，不是「智能写作」 |
| **② 边界闸** | **没有资料支撑的资质、案例、数字和承诺，一律写成「待人工补充」**；**正式稿由人放行** |
| **③ 数据闸** | 投标资料是客户机密 → **默认留在本机**；内置示例是虚构数据 |
| **④ 方案闸** | 浏览器本地 + 可选云模型/本机模型 → **数据边界由「本地优先 + 显式调用」保证** |
| **⑤ 验收闸** | **放行清单**：核心要求、证据、正文、人工放行**四项全完成**才能导出正式 Word；审核稿随时可导 |

### 3.3 关键工程决策（带取舍）

#### 决策 1：数据默认不出本机，且「不点按钮就不外发」

> 应用本身没有账号，不上传；**没有点击「调用模型」时，不会向外发送资料**。

**取舍**：牺牲了「开箱即用的云端体验」，换来**数据边界是可证明的**（不是承诺，是机制）。

#### 决策 2：密钥只留在当前浏览器会话

API 密钥写在 `sessionStorage`，**关掉浏览器会话就消失**；
项目库（IndexedDB）里只存接口地址、模型名、是否本机服务。

> **可迁移的方法论**：**敏感配置与业务数据的存储位置要分离。**
> 「关掉浏览器就没了」是用户能理解、能验证的安全承诺。

#### 决策 3：模型只收到「当前任务需要的摘录」

调用模型时，请求只包含：系统提示 + **本章要回应的要求** + 资料正文的一段摘录（最长约 8000 字）。
**检索也只在当前项目内**（最多返回 30 条），**检索词不会发给模型**。

> **可迁移的方法论**：**这是「最小必要上下文」原则的完整实现。**
> 它同时做到了三件事：省 token、降低泄露面、降低噪音。

#### 决策 4：「没有依据就不写成确定事实」

本地提纲和模型提示都要求：**资料里没有的资质、案例、数字和承诺，必须标成「待人工补充」**。

> **这是把「幻觉」变成「一个可数的状态」。**
> 与其在生成后检测幻觉，不如**在生成前规定「没有依据就不许写」**，
> 并让「待人工补充」成为一个显式的、可以被审核的状态。

#### 决策 5：报价与正文分开，但用同一套项目数据

报价单独一页、按分取整再汇总，**不代替盖章的商务报价文件**。

> **可迁移的方法论**：**把「AI 生成的」和「对外承诺的」在产品形态上分开。**
> 技术方案草稿可以由 AI 起草；报价单必须走商务流程。

#### 决策 6：正式稿的导出被四道条件锁住

> 核心要求 + 证据 + 正文 + 人工放行，**四项全完成**才能导出正式 Word；审核稿随时可导出。

**取舍**：这让「一键导出」变得不那么方便，但**让「未经核对就发出去」在产品层面不可能**。

### 3.4 踩过的坑（可推断的）

| 坑 | 表现 | 修法 |
|---|---|---|
| **默认上传云端** | 客户资料出境/出院 | 本地优先 + 显式调用 |
| **密钥持久化** | 密钥留在机器上 | 只在 sessionStorage |
| **整篇资料进上下文** | token 爆炸 + 噪音 + 泄露面大 | 最小必要摘录 |
| **模型编造资质案例** | 出现不存在的案例 | 「待人工补充」状态化 |
| **一键导出无闸门** | 未核对就发出去 | 四条件锁导出 |

### 3.5 可复用的方法论

1. **数据边界要靠机制而不是承诺。** 「默认不出本机 + 不点不外发」比任何隐私政策都有效。
2. **敏感配置与业务数据分开存储。**
3. **最小必要上下文**同时省 token、降泄露面、降噪音——**三个目标一次达成**。
4. **把「不确定」变成一个可数的状态**（「待人工补充」），而不是让模型硬编。
5. **把不可逆的出口用产品形态锁住**（四条件锁导出）。

## 5. 抽象出来的四个模式

**三个项目约束完全不同，但反复出现四个模式。**

### 模式 1：边界用「机制」表达，不用「规范」表达

| 弱（规范） | 强（机制） |
|---|---|
| 「正式发送前必须人工审核」写在文档里 | 代码里**强制关闭发送**，草稿只能进人审 |
| 「AI 输出字段不能超范围」靠 code review | `additionalProperties: false` + **编译期负向断言** |
| 「未核对的稿子不要导出」写在规范里 | **四条件不满足则导出按钮不可用** |

> **判据**：把规范从文档里删掉，系统行为会变吗？
> **不会变 → 那是机制；会变 → 那只是规范。**

### 模式 2：凡是能规则判定的，不交给模型判定

- 红线（报价 / 新客户 / 命中）→ 结构性条件
- 导出条件（四项全满足）→ 状态机
- 敏感字段 → 进模型前屏蔽
- 权限 → 检索层过滤

> **模型负责「生成」，代码负责「约束」。**
> 这条把「模型出错的代价」从「事故」降级为「一次被拦截的调用」。

### 模式 3：把「不确定」变成状态，而不是让它变成幻觉

- 「待人工补充」代替编造的资质与案例
- 「待补证据」代替没有出处的承诺
- 「未响应 / 待补证据 / 已响应」代替模糊的完成度

> **可数的状态 > 不可数的质量。**
> 状态能被审核、能被统计、能在放行清单上被检查。

### 模式 4：最小必要上下文，同时达成三个目标

```
只发当前任务需要的  →  省 token  +  降低泄露面  +  降低噪音
```

三个项目都在做同一件事，只是载体不同：
- A：只输出量化指标，不出结论
- B：检索结构化数据再生成，不自由发挥
- C：只发当前章节的摘录

---

## 6. 三个项目共同的「不该做」

| 不该做 | 为什么 |
|---|---|
| **让 AI 做不可逆动作** | 发出去 / 导出 / 提交——一旦出错无法撤回 |
| **把判断交给模型的「自己判断」** | 「你觉得这有没有风险」不是风控 |
| **用承诺代替机制** | 「我们承诺数据不出院」不如「架构上没有出院路径」 |
| **把上下文塞满** | 塞满 = 贵 + 噪 + 危险 |
| **用演示代替评测** | 演示是挑过的，评测是测出来的 |

---

## 7. 工程结论

1. **三个项目最强的约束都来自「不可逆性」**——数据出院、消息发出、稿子导出。
   **约束决定架构，不是反过来。**
2. **边界用机制表达**：把规范从文档删掉，系统行为不变，那才叫边界。
3. **生成交给模型，约束交给代码。**
4. **把「不确定」变成可数的状态**，而不是让模型硬编。
5. **最小必要上下文同时省 token、降泄露、降噪音。**
6. **凡是能自动校验的一致性，交给构建期校验**（单一数据源 + 门禁）。
7. **LLM-as-Judge 必须先校准再用**（案例 B 的 `judge_calibration`）。
8. **合规会倒推架构**——但反过来，**架构里没有的那条路径，靠文档补不上**。
