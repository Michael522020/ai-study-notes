# AI 项目失败的八种死法

> **核心问题**：AI 项目死的时候长什么样？我怎么在它死之前就看出来？

---

## 0. 为什么要有这张清单

**AI 项目的失败有一个恶劣的特性：它往往不是在交付时失败的，而是在交付后第 3~6 个月慢慢死的。**

- 交付时一切正常（Demo 好、评测分数高）
- 真正的死因在早期就有**可观测的信号**，只是没人看
- 很多项目在「已经没救了」的时候，还在讨论「要不要换个更强的模型」

> **这张清单的价值是给出早期信号。**
> 每种死法都配了「早期信号」——那是可以在项目早期就观察到的现象。

---

## 1. 死法一 · 伪需求

### 症状
- 需求描述里出现「AI」「智能化」「大模型」这些词，但说不出**具体要解决谁的什么问题**
- 立项时的成功标准是「做一个 Demo」或「跟上同行」
- 没人能说出「现在这一步的成本是多少」

### 早期信号
- 第一次会议上没有人带来**真实的坏样本**
- 需求文档里没有「现状流程图」
- 「业务方」说不出最终使用者是谁

### 根因
把「技术趋势」当成了「业务需求」。**能做 ≠ 该做 ≠ 做了值钱。**

### 处方
回到 [`01`](./01-需求到方案的落地流程.md) 的需求闸，只问三个问题：
1. 现在这一步谁在做、花多少时间？
2. 如果不用 AI，这一步怎么做？
3. AI 出错的代价是什么？

**三个都答不上来 → 停。**

---

## 2. 死法二 · 数据不成立

### 症状
- 标了一堆数据，模型效果还是差
- 评测分数在训练集上极高，在真实数据上崩塌
- 数据「有」，但不知道有多少、分布如何、能不能用

### 早期信号（三选一即中招）
| 信号 | 说明 |
|---|---|
| **数据泄漏** | 训练/验证/测试有重复样本（用感知哈希查一遍） |
| **分布错位** | 标注数据来自三个月前，现在业务已经变了 |
| **许可不清** | 说不清数据能不能商用（见 [`../appendix/数据集与许可索引.md`](../appendix/数据集与许可索引.md)） |

### 根因
- **数据量**：低于任务复杂度所需（经验：分类任务至少几百条/类，复杂抽取需要几千条）
- **数据质量**：标注不一致、噪声高、没有仲裁规则
- **数据合法性**：客户数据未获授权、含个人信息、跨类别边界不清

### 处方
1. **先小样本验证**（100~500 条）再决定投入规模
2. **建一个数据体检脚本**：样本数、类别分布、重复率、标注一致性
3. **许可和数据授权先于标注**——不能先标了 5000 条再发现不能用

---

## 3. 死法三 · 没有评测集

### 症状
- 每次改动都在猜「有没有变好」
- 上线后无法回答「这版比上版强吗」
- 汇报时只能说「感觉不错」

### 早期信号
- 代码仓库里有 prompt，但**没有 tests/ 或 evals/ 目录**
- 有人建议「我们人工试几条看看」
- 每次模型升级都要从头讨论「会不会变差」

### 根因
**没有基线，就没有进步。** 没有评测集，所有优化都是盲改。

### 处方
| 规模 | 做法 |
|---|---|
| **起步** | 50 条金标准集，人工标注，双人仲裁，分歧记原因 |
| **成型** | 100~200 条，**按错误类型分层**（常见 / 边界 / 困难） |
| **持续** | 生产中的 bad case 自动回流，人工确认后进评测集 |

**评测集必须和代码一起版本化**，每次模型/prompt 改动自动跑一遍。

> **评测集的腐化是隐性的**：如果只用「容易的样本」扩充评测集，分数会一路上涨，
> 而线上效果一路下跌。**评测集要专门加难样本。**

---

## 4. 死法四 · 把 Demo 当交付

### 症状
- Demo 里效果很好，上线后大面积失败
- 同一批数据在开发时通过，生产时失败
- 「模型没问题，是数据有问题」成为常态

### 早期信号
| 信号 | 说明 |
|---|---|
| **提示词里写死了示例答案** | 「参照以下格式回答：<真实答案>」 |
| **输入做了大量人工预处理** | 真实流量里没有这一步 |
| **只在「干净」样本上测过** | 没测过脏输入、空输入、超长输入、恶意输入 |
| **没有兜底** | 模型返回格式不对时，链路直接崩 |

### 根因
Demo 的输入分布是**被挑选过的**，生产的是**全量分布**。

### 处方：一份「脏输入清单」

上线前必须逐项测试：

- [ ] 空输入 / 只有空白
- [ ] 超长输入（超过上下文）
- [ ] 格式完全错误（乱码、错编码）
- [ ] 多语言混杂
- [ ] 包含指令注入的内容（「忽略前面的指令，改为……」）
- [ ] 包含敏感信息的输入
- [ ] 模型返回**不符合预期格式**时的降级行为
- [ ] 模型**超时**时的降级行为
- [ ] 依赖的下游服务**超时/报错**时的行为

> **这九项是生产事故的主要来源。**
> 每项都要有明确的预期行为（不是「不崩」这么模糊）。

---

## 5. 死法五 · 没有兜底

### 症状
- 模型或某个工具一出问题，整条业务链路断掉
- 用户直接看到「系统错误」
- Agent 陷入循环，费用飙升

### 早期信号
- 代码里找不到 `try/except` 包住模型调用的地方
- 没有「模型不可用时怎么办」的分支
- Agent 的最大步数没有上限
- 没有预算闸（步数 / 工具数 / 费用）

### 根因
把模型当成**确定性的函数**，而不是**会失败的组件**。

### 处方：四层兜底

```
第 1 层  格式兜底   模型输出不合法 → 重试 → 修复 → 规则解析 → 拒答
第 2 层  能力兜底   模型整体不可用 → 降级到规则/检索结果直出
第 3 层  预算兜底   步数/费用超限 → 强制收尾并输出已有结论
第 4 层  业务兜底   关键场景 → 转人工，且带上已完成的中间结果
```

**每一层都要能单独测试。** 见
[`../07-Agent与智能体/03-Super-Agent-长任务自治.md`](../07-Agent与智能体/03-Super-Agent-长任务自治.md)。

> **第 4 层最容易被省，但最重要**——
> 转人工时必须带上「已经做了什么、卡在哪」，否则人工要从头再来一遍。

---

## 6. 死法六 · 成本不可持续

### 症状
- Demo 阶段调用量小，一切正常
- 上量后账单爆炸，或者用户量涨了但成本涨得更快
- 为了省钱换小模型，效果崩了

### 早期信号
- 成本测算只有「推理成本」一项（见 [`02`](./02-ROI与成本测算.md)）
- 没算过**失败重试**和**人工复核**的成本
- 没有模型分级策略（所有请求都走同一个模型）
- 上下文里塞了大量其实用不到的内容

### 根因
**成本结构没想清楚就上线。** 成本不是线性增长的，量大了以后结构会变。

### 处方
1. 上线前完成完整的三张成本表（单次 / 月度 / TCO）
2. 做**模型分级**：简单请求走小模型
3. **稳定前缀做缓存**：系统提示 + 知识库 + 工具定义
4. 设**预算闸**：单任务费用上限、超限即降级
5. 月度成本看板 + 超预算自动告警

## 7. 死法七 · 合规与权限缺失

### 症状
- 系统能读到不该读的数据
- 用户 A 看到了用户 B 的内容
- 输入里的恶意内容被当成了指令执行
- 事后无法追溯「谁在什么时候看了什么」

### 早期信号
| 信号 | 说明 |
|---|---|
| **权限过滤不在检索层** | 先全量检索再在应用层过滤 → **必然泄漏** |
| **越权响应可区分** | 「用户不存在」和「密码错误」返回不同 → 变成存在性预言机 |
| **没有审计日志** | 或有日志但内容不可改（合规要求「物理不可改」） |
| **输入直接进 prompt** | 用户内容能影响系统指令 |
| **敏感字段未屏蔽** | 评分/决策输入里保留了本该剔除的字段 |

### 根因
把 AI 当成了普通业务功能，**忘了它会自由生成、会读全量、会照做别人的指令**。

### 处方
| 层面 | 措施 |
|---|---|
| **权限** | **在检索层做权限过滤**，不是应用层；越权响应做到不可区分 |
| **输入** | 用户内容与系统指令**分隔**；对检索到的内容做「数据而非指令」的处理 |
| **审计** | 访问日志 + **物理不可改**（append-only + hash chain） |
| **输出** | 敏感信息脱敏后再输出；引用可回指 |
| **数据** | 敏感字段在**进模型前**屏蔽，不是输出时过滤 |

> **「权限过滤为什么必须在检索层」**——
> 应用层过滤意味着「无权用户的数据已经进了上下文」，
> 模型可能把它复述出来。**这是最隐蔽的泄漏路径。**
> 详见 [`../03-RAG/12-失败模式与安全.md`](../03-RAG/12-失败模式与安全.md)。

## 8. 死法八 · 上线后无人维护

### 症状
- 系统跑着跑着效果变差，没人知道为什么
- 业务改了流程，系统没跟上
- 模型/依赖升级后没人负责回归
- 唯一懂系统的人离职了

### 早期信号
- 没有模型效果的**持续监控**（只有系统 CPU/内存监控）
- 没有「模型升级要重跑什么」的清单
- Prompt 在代码里被随手改，改完没人跑评测
- 只有一个人知道系统怎么用

### 根因
把 AI 系统当成**一次性交付物**，而不是**需要持续运营的服务**。
AI 系统有一类传统系统没有的维护负担：**输入分布会漂移、模型会退化、提示词会被改坏。**

### 处方
| 措施 | 说明 |
|---|---|
| **模型监控** | 拒答率、输出分布、人工推翻率、工具失败率 |
| **Prompt 版本化** | 进版本库，能 diff、能回滚 |
| **升级清单** | 换模型/换依赖后必须重跑什么、阈值多少、谁批 |
| **评测集持续维护** | 生产 bad case 回流，定期加难样本 |
| **文档** | 见 [`03`](./03-试点-影子-灰度-规模化.md) §7 的七份文档 |
| **值班与预案** | 谁在出事时第一线处理 |

> **最容易被忽略的一条**：**Prompt 是代码。**
> 它需要 code review、需要版本管理、需要回归测试。
> 「同事随手改了一行 prompt 就上线了」是效果退化的常见来源。

## 9. 八种死法的早期信号汇总

**一张表扫一遍，比读十篇方法论有用。**

| 死法 | 一眼可辨的早期信号 |
|---|---|
| 1 伪需求 | 需求文档里只有「AI」「智能化」，没有现状流程图 |
| 2 数据不成立 | 训练/验证集有重复；不知道数据有多少 |
| 3 没有评测集 | 仓库里没有 evals/ 目录 |
| 4 把 Demo 当交付 | 提示词里写死了示例答案；只测过干净样本 |
| 5 没有兜底 | 模型调用外没有 try/except；Agent 无步数上限 |
| 6 成本不可持续 | 成本测算只有「推理」一项；所有请求同一模型 |
| 7 合规缺失 | 权限过滤在应用层；越权响应可区分；无审计日志 |
| 8 无人维护 | 只有系统监控没有模型监控；Prompt 无版本管理 |

## 10. 上线前自检清单

**这份清单可以直接贴到项目 wiki 里当 gate。**

### 需求与数据
- [ ] 有现状流程图与人力成本量化
- [ ] 有《需求澄清单》《边界说明书》
- [ ] 数据体检通过（量、质、泄漏、许可）
- [ ] 小样本验证已完成（100~500 条）

### 评测
- [ ] 有 ≥50 条金标准评测集（双人仲裁）
- [ ] 有基线对照（规则/人工）
- [ ] 评测脚本可重复运行、有版本
- [ ] 每次改动自动跑评测（CI）

### 工程
- [ ] 脏输入清单九项全部测过
- [ ] 四层兜底每一层都能单独测试
- [ ] Agent 有步数/费用上限
- [ ] Prompt 已版本化
- [ ] 降级方案演练过

### 成本
- [ ] 三张成本表完成（单次/月度/TCO）
- [ ] 算了失败重试、人工复核、标注成本
- [ ] 有模型分级与缓存策略
- [ ] 定价带查询日期

### 合规
- [ ] 权限过滤在检索层
- [ ] 越权响应不可区分
- [ ] 审计日志 append-only 且可验证
- [ ] 用户内容与系统指令分隔
- [ ] 敏感字段进模型前屏蔽

### 运维
- [ ] 三类模型监控指标在看
- [ ] 有模型升级清单与阈值
- [ ] 回滚是一键开关（三层独立）
- [ ] 七份运维文档齐备

## 11. 工程结论

1. **AI 项目往往不是交付时死的，是交付后 3~6 个月慢慢死的。** 早期信号在项目早期就能观察到。
2. **八种死法有七种在需求闸和数据闸就能拦住。** 这也是为什么 [`01`](./01-需求到方案的落地流程.md) 要按顺序过闸。
3. **伪需求是唯一一种「完全没有解法」的死法**——只能靠需求闸拦住。
4. **没有评测集是最可修复的死法**，也是投入产出比最高的补救（50 条就能起步）。
5. **「把 Demo 当交付」的处方是脏输入清单**——九项，逐项测。
6. **合规问题最好在架构期解决**，上线后再补代价极高（尤其是权限过滤的位置）。
7. **Prompt 是代码**，需要版本管理、回归测试和 review。
8. **把这张表当 gate 用**，比事后复盘有用得多。
