# 采购与选型清单

> **核心问题**：自建还是买？选谁？怎么谈？怎么不被锁死？

---

## 0. 先把问题拆对

「我们要做一个 AI 系统」拆成四个独立决策：

| 决策 | 选项 | 决定什么 |
|---|---|---|
| **① 模型从哪来** | 调 API / 开源自托管 / 采购成品 | 能力、成本、数据边界 |
| **② 谁来做** | 自研 / 外包实施 / 采购整套 | 组织成本、可控性 |
| **③ 部署在哪** | 云 / 私有化 / 端侧 | 合规、延迟、成本结构 |
| **④ 知识从哪来** | 自建库 / 买第三方 / 混合 | 长期资产 vs 租 |

> **很多项目在「要不要买」这个问题上纠缠，其实该先答「哪个环节值得买」。**
> 常见的合理答案是**混合**：买能力、自建数据与流程。

---

## 1. 买 vs 自建 vs 混合

### 1.1 决策表

| 维度 | **采购成品** | **自建** | **混合** |
|---|---|---|---|
| 上线速度 | **最快**（周） | 慢（月~季） | 中 |
| 初始成本 | 低（订阅/许可） | 高（人力 + 硬件） | 中 |
| 单位成本（量大） | **高** | **低** | 中 |
| 可控性 | 差 | **完全可控** | 关键环节可控 |
| 适配业务 | 差（要迁就） | **好** | 好 |
| 知识资产归属 | 弱 | **完全自有** | **核心自有** |
| 合规风险 | 高（依赖厂商） | **低** | 中（看边界） |
| 退出难度 | **高**（锁定） | 低 | 中 |
| 适合 | 非核心、快速试错 | 核心能力、特殊合规 | **大多数情况** |

### 1.2 混合的标准形态（推荐）

```
┌────────────────────────────────────────────┐
│  自建（核心资产）                             │
│   · 业务数据与知识库                           │
│   · 提示词与编排逻辑                           │
│   · 评测集与验收标准                           │
│   · 与业务流程的集成                           │
├────────────────────────────────────────────┤
│  采购（通用能力）                             │
│   · 基础模型 API                               │
│   · 向量数据库 / 文档解析                      │
│   · 通用 OCR / 语音                             │
└────────────────────────────────────────────┘
```

> **判断标准：凡是构成「你的业务壁垒」的部分，必须自建且自有。**
> 凡是「通用且可替换」的部分，可以买。

### 1.3 一个决策流程

```
这一步是通用能力吗（行业里买得到现成的）？
  ├─ 是 ──▶ 买
  │         └─ 量小 → 直接买 API
  │            量大 → 对比「API vs 自托管」的 TCO（§5）
  └─ 否 ──▶ 涉及核心业务逻辑或特殊合规吗？
            ├─ 是 ──▶ 必须自建（哪怕慢）
            └─ 否 ──▶ 自研有把握吗？
                      ├─ 有 ──▶ 自研
                      └─ 没 ──▶ 买/外包实施，但要拿到源码或可迁移性保证
```

## 2. 选型 Checklist

### 2.1 模型层

| # | 检查项 | 关键问题 |
|---|---|---|
| 1 | **能力是否匹配** | 你的任务在它的评测集上表现如何？**自己拿真实样本测** |
| 2 | **语言与领域** | 中英混排？专业术语？行业术语的表现 |
| 3 | **上下文长度** | **够用就行**——长上下文比短上下文贵且更容易出错 |
| 4 | **输出稳定性** | 同一输入多次调用是否一致（影响是否需要缓存与重试） |
| 5 | **结构化输出** | JSON schema 支持好不好（直接影响 Agent 工具调用可靠性） |
| 6 | **速度与延迟** | 首 token 延迟、吞吐（**用你的真实 prompt 长度测**） |
| 7 | **价格与缓存** | 输入/输出/缓存三档价格，以及**前缀缓存命中规则** |
| 8 | **版本策略** | 会不会静默更新？更新后行为是否变化？ |

### 2.2 平台层（向量库 / 编排框架 / Agent 平台）

| # | 检查项 | 关键问题 |
|---|---|---|
| 1 | **部署形态** | 能不能私有化？依赖哪些外部服务？ |
| 2 | **权限模型** | 是否支持行列级权限？**权限能不能在检索层执行**？ |
| 3 | **数据可导出** | 能不能完整导出（**避免锁定**）？什么格式？ |
| 4 | **可观测性** | 有没有 trace、有没有成本统计 |
| 5 | **运维复杂度** | 要几个人维护？依赖多少组件？ |
| 6 | **版本节奏** | 更新频率、破坏性变更频率 |

### 2.3 工程层

| # | 检查项 |
|---|---|
| 1 | 有没有**评测集**和**回归能力** |
| 2 | 有没有**成本核算**（按请求/按 token） |
| 3 | 有没有**降级开关**和**回滚机制** |
| 4 | 有没有**审计日志**（append-only） |
| 5 | Prompt **能不能版本化**、能不能热更新 |
| 6 | 错误信息的可读性（出错时能不能定位） |

## 3. 供应商评估：十二个必问的问题

**这十二个问题应该在签约前问完并写进合同。**

### 3.1 数据类

| # | 问题 | 为什么必须问 |
|---|---|---|
| 1 | **我的数据会不会被用来训练模型？** | 这是隐私条款里最关键的一句。有些默认会。 |
| 2 | **数据存在哪、存多久？怎么删？** | 「按需删除」和「30 天内自动删除」差很多 |
| 3 | **能不能给我数据删除证明？** | 没有证明就无法向监管/客户交代 |
| 4 | **有没有子处理者？清单在哪？** | 你在跟谁共享数据 |

### 3.2 合规类

| # | 问题 |
|---|---|
| 5 | **部署在哪个法域？**（境内外） |
| 6 | **能不能满足等保/密评/数据本地化要求？** |
| 7 | **有没有审计日志？日志保留多久？谁能看到？** |

### 3.3 服务类

| # | 问题 |
|---|---|
| 8 | **模型会不会静默更新？更新前多久通知？** |
| 9 | **SLA 是什么？未达标怎么赔？** |
| 10 | **出安全事故谁负责？**（这不是法律问题，是「找谁」的问题） |

### 3.4 资产与退出类

| # | 问题 |
|---|---|
| 11 | **微调/定制模型的知识产权归谁？** |
| 12 | **停止服务后，多久能完成数据迁移和删除？协助义务写了吗？** |

> **第 1 题和第 12 题最常被跳过，也最贵。**
> 前者关系到合规，后者关系到你被锁死的程度。

## 4. 合规审查项

### 4.1 采购方要问的（清单）

| # | 审查项 | 交付证据 |
|---|---|---|
| 1 | **数据处理协议（DPA）** | 签署的协议，明确处理目的、方式、期限 |
| 2 | **子处理者清单** | 完整名单 + 变更通知机制 |
| 3 | **数据存储位置** | 境内外具体位置，是否满足数据本地化要求 |
| 4 | **数据删除机制** | 删除流程 + 证明样例 |
| 5 | **模型训练使用声明** | 书面声明「不使用客户数据训练」 |
| 6 | **审计日志能力** | 字段清单、保留期、导出方式 |
| 7 | **安全认证** | ISO 27001 / SOC 2 / 等保测评报告 |
| 8 | **渗透测试报告** | 近一年，且覆盖当前版本 |
| 9 | **个人信息保护影响评估（PIPIA）** | 自有系统也要做，见国内《个人信息保护法》要求 |
| 10 | **生成式 AI 服务备案** | 若面向公众提供服务，境内需完成备案（**须以监管最新要求为准**） |
| 11 | **知识产权担保** | 训练数据来源合法性的担保条款 |
| 12 | **分包商风险** | 是否转包、转给谁 |

### 4.2 自研方要自查的（同一批问题反过来问自己）

- [ ] 我的数据流经了哪些环节？每个环节谁在管？
- [ ] 我有没有**数据处理活动清单**（对外提供、共同处理、委托处理）
- [ ] 我有没有做过 PIPIA
- [ ] 我的审计日志能证明「谁在什么时候访问了什么」吗？
- [ ] 用户能不能导出/删除自己的数据？链路通吗？

> **采购方和自研方要问的问题是一样的。**
> 这也说明：**合规不是「买的时候才需要考虑的事」，是所有系统的基本要求。**

## 5. 私有化 vs API 的 TCO 对比

### 5.1 对比维度

| 维度 | 云 API | 私有化自托管 |
|---|---|---|
| **一次性** | 集成成本（小） | 硬件 + 部署 + 改造（**大**） |
| **月固定** | 0 | 硬件摊销 + 运维 + 值守 + 机房 |
| **月变动** | 按调用量 | 电费 + 带宽（+ 少量调用成本） |
| **规模效应** | 线性增加 | 阶梯式（跨过利用率台阶后很便宜） |
| **峰值弹性** | **好** | 差（要提前扩容） |
| **数据边界** | 数据出院 | **数据不出院** |
| **模型能力** | 最新的 | 取决于你选的开源权重（**滞后 3~12 个月**） |
| **可定制** | 弱（提示词层） | **强**（可微调、可改结构） |
| **运维负担** | 低 | **高**（要有懂的人） |

### 5.2 交叉点

```
        API 月成本
        │  ╱
        │ ╱
        │╱  ← 交叉点 = 盈亏平衡调用量
        ├───────────── 私有化月固定成本
        │ ╲
        │  ╲ 私有化（阶梯）
        └──────────────────────── 调用量
```

**交叉点通常在几十万到几百万次/月的量级**（取决于硬件成本与 token 单价）。
**做之前必须用自己真实的 token 长度算一遍。**

### 5.3 一个被忽略的中间选项

| 选项 | 适用 |
|---|---|
| **云上专属实例** | 需要数据不出「云厂商的机房」但不需要自己运维 |
| **混合路由** | 简单请求走本地小模型，复杂请求走云 API |
| **多云 / 地域双活** | 有合规或可用性要求时 |

## 6. 退出成本（Lock-in）评估

**「买」的最大代价不是钱，是退不出。**

### 6.1 锁定强度的四个维度

| 维度 | 低锁定 | 高锁定 |
|---|---|---|
| **数据** | 标准格式可完整导出 | 只能在厂商后台看，导不出 |
| **接口** | 标准 API（OpenAI 兼容等） | 私有 SDK / 私有协议 |
| **Prompt / 逻辑** | 存在自家代码里 | 存在厂商平台的编排器里 |
| **评测集** | 自有 | 依赖厂商的评测环境 |

### 6.2 三个必须问的退出问题

| # | 问题 | 答不上来的风险 |
|---|---|---|
| 1 | **停止服务后，我的数据和定制内容多久能全部拿回来？什么格式？** | 数据被锁在厂商手里 |
| 2 | **换一个供应商要多久？**（估：接口适配 + 效果回归 + 数据迁移） | 换不了 = 永久绑定 |
| 3 | **如果厂商倒闭或被收购，我的系统还能跑吗？** | 供应商风险 |

### 6.3 降低锁定的具体做法

- **Prompt 存在自家代码库里**（不要只存在厂商的 prompt 面板）
- **知识库用开放格式**（向量能导出成 npy/parquet，文档能导出原文）
- **评测集自有**（不能只在厂商的 playground 里跑）
- **接口层做一层适配**（自家一层薄封装，换供应商只改这一层）
- **合同里写退出协助义务和时限**

> **第 1 条最常被忽略。**
> 很多团队把 prompt 只存在厂商后台，几年后想换供应商，
> 才发现当初的 prompt 工程全部沉没。

## 7. 合同该写进去的条款

| 条款 | 内容 |
|---|---|
| **SLA 与赔付** | 可用性、延迟、错误率、未达标的赔偿 |
| **变更通知** | 模型更新、接口变更、价格调整的**提前通知期**（建议 ≥ 30 天） |
| **数据删除** | 终止后的删除时限 + **书面删除证明** |
| **审计权** | 客户有权审计数据处理与安全措施 |
| **IP 归属** | 输入数据、输出内容、定制模型的归属 |
| **不用于训练** | 明确承诺不使用客户数据训练通用模型 |
| **退出协助** | 数据迁移格式、时限、协助义务 |
| **涨价上限** | 年度涨幅上限或调整公式 |
| **责任划分** | 事故责任、赔偿上限、下游责任 |
| **分包披露** | 转包需事先同意 |

> **「变更通知期」是最有性价比的一条。**
> 模型静默更新导致效果变化的排查成本极高，
> 一条 30 天的通知期能把大部分风险消掉。

## 8. 常见坑

| 坑 | 表现 | 规避 |
|---|---|---|
| **只看 Demo 选型** | 供应商用精心挑的样本演示 | **用自己的真实样本盲测** |
| **忽略版本变化** | 半年后效果变了，说不清原因 | 合同里写变更通知 + 锁版本 |
| **Prompt 沉在厂商** | 换不了供应商 | Prompt 存自家代码库 |
| **没有删除证明** | 合规过不了 | 合同条款 + 验收时索取样例 |
| **低估运维** | 私有化后没人会维护 | 上线前确认运维归属与预算 |
| **成本没算复核** | 上线后比人工还贵 | 用 §2 的三张表 |
| **没有降级方案** | 厂商故障业务全断 | 合同里要 SLA + 自建降级路径 |
| **被「定制开发」绑架** | 定制部分没有源码 | 合同里写源码/可维护性归属 |

## 9. 工程结论

1. **先答「哪个环节值得买」，别纠缠「买还是自建」。** 混合是大多数场景的正确答案。
2. **构成业务壁垒的部分必须自建且自有**（数据、Prompt、评测集、集成逻辑）。
3. **通用能力买之前先算交叉点**：量大自托管划算，量小直接买。
4. **供应商十二问在签约前问完并写进合同**，尤其第 1 问（数据是否用于训练）和第 12 问（退出协助）。
5. **合规审查清单自研方也要自查**——合规不是采购才有的事。
6. **降低锁定的第一件事：把 Prompt 存进自家代码库。**
7. **变更通知期 ≥ 30 天**是性价比最高的一条合同条款。
8. **永远用自己的真实样本盲测**，不要用供应商的 Demo 数据。
