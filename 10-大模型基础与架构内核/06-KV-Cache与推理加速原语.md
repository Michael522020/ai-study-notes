# KV Cache 与推理加速原语

> **核心问题**：推理慢在哪一环？TTFT 和吞吐怎么同时优化？投机解码什么时候真的有用？

---

## 0. 为什么需要 KV Cache

自回归解码每一步只生成**一个** token。但这一步需要：

```
1. 读全部历史 token 的 K 和 V      ← 必需
2. 算一次 attention（Q 只有 1 个）
3. 算一次 FFN（1 个 token）
```

**关键观察**：第 2、3 步只处理**新 token**（Q 的长度 = 1），
但第 1 步要读**全部历史**的 K/V。

而**历史 token 的 K/V 在生成过程中是不变的**（因果掩码，新 token 不影响旧的 K/V）。

> **所以：把算过的 K/V 缓存起来，每步只需为新 token 计算并追加。**

**没有 KV Cache 时**（朴素实现）：
```
生成第 t 个 token → 重算 t 个 token 的 K/V → 总计算量 O(T²)
```

**有 KV Cache**：
```
生成第 t 个 token → 只算 1 个 token 的 K/V → 总计算量 O(T)
```

**代价**：KV Cache 占显存，且随序列长度**线性增长**。
**这就是长上下文推理的核心矛盾：省算力和占显存是对立的。**

---

## 1. 显存账：把公式记死

```
KV Cache 字节数 = 2 × L × H_kv × d_head × S × bytes_per_element
```

### 1.1 Llama-3-8B 实测口径（GQA, H_kv=8, d_head=128, L=32, bf16）

```
每 token = 2 × 32 × 8 × 128 × 2 = 131,072 字节 = 128 KiB
```

| 序列长度 | 单序列 KV | 单序列总显存（+15GB 权重） |
|---|---|---|
| 2K | 256 MB | 15.3 GB |
| 4K | 512 MB | 15.5 GB |
| 8K | **1 GB** | 16 GB |
| 32K | **4 GB** | 19 GB |
| 128K | **16 GB** | 31 GB |

> **单序列 128K 就吃掉 16 GB 显存——比模型权重还多。**
> 这是长上下文服务规划的第一张表。

### 1.2 并发的放大

```
总 KV 显存 = 单序列 KV × 并发数（考虑 prefix 共享后略小）
```

| 场景 | KV 显存 |
|---|---|
| 8K × 8 并发 | 8 GB |
| 32K × 8 并发 | 32 GB |
| 32K × 32 并发 | **128 GB** ⚠️ |

> **结论：长上下文 + 高并发时，KV Cache 是绝对瓶颈，模型权重不是。**

### 1.3 端侧（llama.cpp）

llama.cpp 用 **GGUF 量化格式存 KV Cache**：

| KV 量化类型 | 每 token 字节 | 8K 序列 |
|---|---|---|
| F16（默认） | 128 KiB | 1 GB |
| **Q8_0** | 64 KiB | 512 MB |
| **Q4_0** | 32 KiB | 256 MB |

> 端侧长上下文时，**KV 量化比权重量化更值得先做**——
> 因为权重已经压到 4 bit 了，KV 往往还是 16 bit。

## 2. 减少 KV 的六个手段

| 手段 | 原理 | 效果 | 代价 |
|---|---|---|---|
| **MQA / GQA** | 减少 KV 头数 | 4~32× | 质量略降（GQA 几乎无损） |
| **KV 量化** | K/V 存低精度 | 2~4× | 精度损失（K 比 V 敏感） |
| **滑动窗口** | 只保留最近 W 个 | W/S 倍 | 丢失远距离信息 |
| **KV 淘汰** | 按重要性丢弃旧 KV | 动态 | 需要打分机制，有开销 |
| **PagedAttention** | 分页管理，碎片不浪费 | 显存利用率 2~4× | 需要框架支持（vLLM） |
| **Prefix 共享** | 相同前缀共用 KV | 取决于共享率 | 需要前缀树结构 |

### 2.1 KV 量化的关键细节

**K 和 V 的敏感度不一样**：

- **V**（value）：直接参与加权求和，量化误差直接加到输出上 → 敏感
- **K**（key）：参与计算 attention 分数，误差会被 softmax 平滑 → 相对不敏感

所以主流做法是 **K 用 int8、保留 V 为 fp16**（或 K4V16）。

| 方案 | 说明 |
|---|---|
| **K8V16** | K 存 int8，V 存 fp16。**收益/损失比最好的起点** |
| **K4V16** | K 存 int4。收益更大，但需要 per-channel/per-token 的 scale |
| **KIVI** | K 用 per-channel、V 用 per-token 的分组量化 |
| **llama.cpp Q8_0** | 端侧最简单，K/V 都量化 |

> **工程结论**：需要长上下文时，**先量化 KV，再考虑别的**。
> 8K→32K 的上下文扩展，KV 量化往往比换模型更划算。

### 2.2 KV 淘汰（H2O / SnapKV）

**思路**：不是每个历史 token 的 KV 都重要。统计每个 token 累积的注意力分数，**只保留重要的 + 最近的**。

| 方法 | 策略 |
|---|---|
| **H2O** | 保留「历史累计注意力高」+「最近」的 token。**注意它会破坏位置编码的连续性** |
| **SnapKV** | 用「观察窗口」（最近若干 token）的注意力模式，投票决定保留哪些历史 KV。**更稳** |

> **代价**：丢弃 KV 会让模型「忘记」被丢的内容——**这不是无损优化**。
> 在需要精确引用长文档的场景要谨慎。

## 3. PagedAttention：vLLM 的核心

### 3.1 问题：内存碎片

传统 KV Cache 管理是**连续分配**（每个序列一段连续显存）：

```
请求 A 结束 → 留下 512 token 的空洞
请求 B 需要 800 token → 找不到连续 800 的空间 → 只能等，或重新分配+复制（慢）
```

**结果**：显存利用率可能只有 30~50%。

### 3.2 分页方案

借鉴操作系统虚拟内存：**把 KV Cache 切成固定大小的 block（如 16 token / block），
用「页表」映射逻辑块 → 物理块**。

```
逻辑块 0 → 物理块 7
逻辑块 1 → 物理块 2
逻辑块 2 → 物理块 11     （物理块可以不连续）
```

**收益**：

| 收益 | 量级 |
|---|---|
| 显存利用率 | **提升 2~4×** |
| 消除「碎片导致的等待」 | 吞吐提升明显 |
| 支持前缀共享 | 相同前缀直接共用物理块，**零拷贝** |
| 支持抢占 | 显存不足时把序列换出到 CPU 磁盘 |

### 3.3 RadixAttention（SGLang）

**在分页之上加一棵基数树（Radix Tree）**，按 token 前缀组织：

- 相同前缀的请求**自动共享** KV block
- 典型的 Agent 场景（系统提示相同、工具定义相同）**共享率很高**

```
系统提示 + 工具定义（共用）
├── 会话 A 的对话历史
├── 会话 B 的对话历史
└── 会话 C 的对话历史
```

> **工程结论**：如果你的场景有大量**共享长前缀**（Agent、RAG 系统提示），
> RadixAttention / Prefix Cache 能把 KV 显存降一个数量级。
> 这是 2024 年之后推理框架最重要的能力之一。

## 4. 投机解码（Speculative Decoding）

### 4.1 原理：草稿 + 验稿

```
第 1 步：小模型（draft）快速生成 γ 个候选 token        (γ=4~8)
第 2 步：大模型（target）一次性并行验证这 γ 个 token    (1 次前向)
第 3 步：接受连续的前缀，把第一个不匹配的位置用 target 的输出替换
```

**关键性质：无损（lossless）**。
最终输出的**概率分布与直接用 target 模型采样完全一致**——
只是加速了采样过程，不改变结果分布。

### 4.2 数学：加速比从哪来

设：
- `α` = 草稿 token 被接受的概率（接受率）
- `γ` = 每轮草稿长度

**每轮 target 前向期望产出 token 数**：

```
E[tokens] = (1 - α^(γ+1)) / (1 - α)
```

**加速比**（草稿和 target 成本相同时）：

```
speedup = E[tokens] / γ
```

**真实加速比**（草稿模型便宜得多时）：

```
speedup = E[tokens] / (γ · c_draft + 1)
         其中 c_draft = 草稿模型单 token 成本 / target 单 token 成本
```

**实例**（α=0.8, γ=4, c_draft=0.1）：

```
E[tokens] = (1 - 0.8^5) / 0.2 = 3.36
cost      = 4 × 0.1 + 1 = 1.4
speedup   = 3.36 / 1.4 ≈ 2.4×
```

### 4.3 接受率的影响（关键）

| α（接受率） | γ=4 时的 E[tokens] | 加速比（c_draft=0.1） |
|---|---|---|
| 0.6 | 1.64 | 1.0× ❌ |
| 0.7 | 2.14 | 1.36× |
| **0.8** | **3.36** | **2.4×** ✅ |
| 0.9 | 4.10 | 2.6× |
| 0.95 | 4.78 | 2.8× |

> **接受率低于 0.7 基本白干。**
> 接受率取决于「草稿模型和 target 的行为差异」——
> **两者越像（同系列、同 tokenizer、蒸馏得来），接受率越高。**

### 4.4 什么时候有用

| 场景 | 判断 |
|---|---|
| **草稿模型很便宜**（小 5~10 倍） | ✅ 推荐 |
| **接受率高**（> 0.8） | ✅ 推荐 |
| **输出很长**（生成 1000+ token） | ✅ 推荐——摊薄了草稿的固定开销 |
| **输出很短**（10~20 token） | ❌ 不划算，固定开销占比太大 |
| **batch 已经很高** | ❌ GPU 已算力饱和，加速收益被摊薄 |
| **草稿和 target 差异大** | ❌ 接受率低 |

### 4.5 多 token 预测（Medusa / EAGLE）

投机解码需要**一个独立的草稿模型**（占显存）。多 token 预测方案**不需要额外模型**：

| 方法 | 做法 |
|---|---|
| **Medusa** | 在 target 上加几个轻量「头」，直接预测未来第 2/3/4 个 token |
| **EAGLE** | 用一个小的自回归模块在**特征层**（不是 token 层）预测未来 |

| 优点 | 缺点 |
|---|---|
| **不占额外显存** | 需要训练/微调（Medusa 的头要训） |
| 接受率比独立草稿模型更高（同源） | 增加 target 的复杂度 |

> **端侧场景特别值得注意**：独立草稿模型要额外占显存，
> 而端侧最缺的就是显存 → **Medusa/EAGLE 路线更适合端侧**。

## 5. 并行解码：一次出多个 token

| 方法 | 机制 | 质量 |
|---|---|---|
| **Beam Search** | 维护多条候选路径 | ⚠️ 会重复、且**改变输出分布** |
| **多序列采样** | 同时跑 n 个独立序列 | ✅ 不改变单条分布 |
| **N-gram / Lookahead Decoding** | 用 n-gram 匹配草稿（**不需要模型**） | ✅ 无损 |
| **Lookahead Decoding** | 用「前瞻」分支产生 n-gram 候选 | ✅ 无损 |

> **Lookahead / N-gram 方案在 llama.cpp 等端侧推理器里很常见**，
> 因为它零额外显存、零额外模型，对重复性输出（代码、格式化文本）特别有效。

## 6. 连续批处理（Continuous Batching）

### 6.1 静态批处理的浪费

```
传统（静态）批处理：
  凑满 32 个请求一起跑 → 其中 31 个早结束，1 个还在生成
  → GPU 在等最慢的那个，剩下的算力全浪费
```

### 6.2 连续批处理

```
每一步（每生成一个 token）：
  1. 把已完成的序列踢出批次
  2. 立刻把等待队列里的新请求加进来
  3. 用新的批大小继续下一步
```

**收益**：在高并发场景下 **吞吐提升 10~20×**。

> **工程结论**：**连续批处理是推理框架的「必选项」。**
> 没有它，vLLM 之类的框架就没有意义。
> 评估推理服务能力时，**并发吞吐**比单请求延迟更能说明问题。

## 7. 算子层加速

| 技术 | 做什么 | 收益 |
|---|---|---|
| **CUDA Graph** | 把一串 kernel 启动固化成一次图启动 | 消除 kernel launch 开销，小模型/短序列收益大 |
| **torch.compile** | 自动融合算子 + 生成 Triton kernel | 端到端 10~50%（视模型） |
| **算子融合** | QKV 合并、SwiGLU 融合、RMSNorm 融合 | 减少 HBM 往返 |
| **量化（权重）** | INT8 / INT4 | 见下 |
| **张量并行 / 流水并行** | 多卡切分 | 见下 |

### 7.1 量化对不同平台的影响不同

| 平台 | 权重量化收益 | 说明 |
|---|---|---|
| **GPU（TensorRT / vLLM）** | 大 | 有专门的 INT4/FP8 kernel，能实打实加速 |
| **CPU** | 中 | 取决于是否有 AVX-512 / AMX 指令集支持 |
| **Apple Silicon** | **大** | Metal 后端对量化支持好（llama.cpp 的 MLX / Metal 路径） |
| **ARM 边缘** | 小 | 很多 MCU/NPU 无低精度算子，量化后反而要额外解量化开销 |

> **⚠️ 与 YOLO 量化的本质区别**：视觉模型的量化目标是**塞进 NPU**（显存优先），
> LLM 的量化目标是**提速/省显存**（吞吐优先）。两者的「精度可接受」标准完全不同。
> 见 [`../01-YOLO/08-导出部署与推理加速.md`](../01-YOLO/08-导出部署与推理加速.md)。

### 7.2 张量并行 vs 流水并行

| | 张量并行 (TP) | 流水并行 (PP) |
|---|---|---|
| 切什么 | 单层内的矩阵 | 层 |
| 通信 | 每层 all-reduce | 少（只在 stage 边界传激活） |
| 通信量 | **大** | 小 |
| 额外显存 | 小 | **大**（流水气泡） |
| 适合 | 单机能装下 | 模型大到单机装不下 |

> **不要自己实现 TP。** 用 Ray / DeepSpeed / Megatron 这类成熟框架，
> 或直接用 vLLM 的 `--tensor-parallel-size`。

## 8. 端到端延迟拆解

**「延迟 2 秒」这个数字没有任何信息量。** 必须拆开：

```
用户感知延迟 = 排队时间 + 预填充时间 + 解码时间 + 网络时间
```

### 8.1 三个关键指标

| 指标 | 定义 | 影响因素 |
|---|---|---|
| **TTFT**（Time To First Token） | 从请求到第一个 token | 排队 + **预填充**（处理输入 prompt） |
| **TPOT**（Time Per Output Token） | 后续每个 token 的间隔 | **解码**速度（受 KV 读取带宽约束） |
| **吞吐** | 全系统每秒总 token 数 | 并发数 × batch |

### 8.2 三个阶段各自的瓶颈

| 阶段 | 瓶颈 | 优化手段 |
|---|---|---|
| **排队** | 调度策略、并发上限 | 连续批处理、优先级队列 |
| **预填充（prefill）** | **算力**（矩阵乘，compute-bound） | chunked prefill、FlashAttention、更高 batch |
| **解码（decode）** | **显存带宽**（memory-bound） | GQA、KV 量化、投机解码、CUDA Graph |

> **关键认知：预填充是算力密集，解码是带宽密集。**
> 这两个阶段的优化方向完全不同——
> **把它们混在一个 batch 里算，反而互相拖累**（这就是 chunked prefill 的由来）。

### 8.3 chunked prefill

长 prompt（预填充）会一次性占满 GPU，导致**已有的解码请求被卡住**（首 token 延迟暴涨）。

**解法**：把长 prompt 切成若干块，和解码请求交替执行。

```
[prefill chunk 1][decode 1][prefill chunk 2][decode 1][prefill chunk 3][decode 1]...
```

| 收益 | 代价 |
|---|---|
| 解码请求不再被长 prompt 饿死 | 预填充总时长略增（chunk 边界开销） |
| TTFT 和 TPOT 更均衡 | 需要框架支持 |

> **工程结论**：**混合负载场景（既有长文档问答又有短对话）必须开 chunked prefill。**
> 否则一个 500 页 PDF 的请求会把整个服务的短请求延迟拉高 10 倍。

## 9. 选型决策树

```
推理慢，先定位瓶颈
  ↓
测出 TTFT 和 TPOT 分别是多少
  ↓
TPOT 高（每 token 慢）→ 解码是瓶颈
  ├─ 检查 FlashAttention 有没有生效（head_dim / dtype）
  ├─ KV 显存占太多？→ GQA / KV 量化 / KV 淘汰
  ├─ 显存带宽打满？→ 投机解码 / 多 token 预测
  ├─ 输出很短？→ 投机解码不划算，改用 batching
  └─ 小模型？→ CUDA Graph / torch.compile
  ↓
TTFT 高（首 token 慢）→ 预填充或排队是瓶颈
  ├─ 排队久？→ 扩并发 / 连续批处理 / prefix cache
  ├─ prompt 很长？→ chunked prefill / 减少 prompt 长度
  ├─ prefix 能复用吗？→ Prefix Cache / RadixAttention
  └─ prompt 能缓存吗？→ prompt caching（厂商侧）
  ↓
吞吐低（并发上不去）
  ├─ KV 显存占满？→ 量化 / 滑窗 / 降低上下文
  ├─ 连续批处理开了吗？
  └─ 多卡？→ TP / PP
```

## 10. 工程结论

1. **KV Cache 是长上下文推理的真瓶颈**，不是模型权重。8K 上下文 = 1 GB 显存（8B 模型）。
2. **省 KV 的六个手段**：GQA、KV 量化、滑动窗口、KV 淘汰、PagedAttention、前缀共享。
3. **KV 量化对 K 用 int8、V 留 fp16** 是收益/损失比最好的起点。
4. **PagedAttention 消除内存碎片**，vLLM 的核心；**RadixAttention 再叠加前缀共享**。
5. **投机解码是无损的**，但需要接受率 > 0.7 且草稿模型便宜；
   **Medusa/EAGLE 不占额外显存，端侧更适合**。
6. **连续批处理是推理框架的必选项**，高并发下吞吐差 10~20 倍。
7. **预填充是算力密集，解码是带宽密集**——混合负载要开 chunked prefill。
8. **永远报 TTFT 和 TPOT 两个数**，只报「总延迟」的报告没有信息量。
9. **端侧先量化 KV，再考虑权重**——权重已经压到 4 bit 时，KV 往往还是 16 bit。
