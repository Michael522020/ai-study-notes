## ⚡ 一张表看懂现代配方

```
现代开源 dense LLM 的骨架（2023 年之后基本收敛）：

  Embedding(V×d) ──┬── RMSNorm ── Attention(GQA) ──┬── +x
                   │      (Pre-Norm)                 │
                   │                                  ▼
                   │                            RMSNorm ── SwiGLU FFN ── +x
                   │                                  │
                   └──────────────────────────────────┴── Final Norm ── LM Head
```

| 组件 | 默认选择 | 不这么做的后果 |
|---|---|---|
| 归一化 | **RMSNorm** | LayerNorm 更慢但等价；BatchNorm 在变长推理时行为漂移 |
| 归一化位置 | **Pre-Norm** | Post-LN 需要精细 warmup，深层容易发散 |
| FFN 激活 | **SwiGLU**（3 矩阵） | GELU 少 1/3 参数，同预算下容量更小 |
| FFN 扩展 | `d_ffn ≈ 8d/3` | 写成 4d 会让参数量多 33% |
| 位置编码 | **RoPE** | 正弦外推失效；ALiBi 生态不兼容 |
| 注意力 | **GQA**（`H_kv = H/4`） | MHA 的 KV 显存是 GQA 的 4 倍 |
| 残差分支 | **加缩放初始化** | 深层模型 final loss 变差 |
| QK 归一化 | **有** | 长训练后 attention 饱和、梯度消失 |
| bias | **全部去掉** | 冗余参数，推理显存白占 |

> **自己实现 Transformer 时照抄这一列，不要照抄 2017 年的原始论文。**

## 📐 三个必须记死的公式

### ① 参数量

```
Embedding + LM Head = 2 × V × d
每层                = 4d²  (Attention) + 3·d·d_ffn  (SwiGLU)
总参数              = 2Vd + L·(4d² + 3·d·d_ffn)
```

### ② KV Cache 显存

```
KV 字节 = 2 × L × H_kv × d_head × S × bytes/元素

Llama-3-8B（bf16）→ 128 KiB/token
  8K → 1 GB    32K → 4 GB    128K → 16 GB
```

### ③ 算力

```
训练 FLOPs ≈ 6 × N × D          （N=参数量, D=训练 token 数）
推理 FLOPs / token ≈ 2 × N
```

> **这三个公式能回答 FDE 最常被问的三个问题**：
> 这个模型多大？带 32K 上下文要多少显存？训练它要多少算力？

## 🔍 从 config.json 反读架构

**最快的架构学习方式不是读论文，是读 `config.json`。**

```json
{
  "hidden_size": 4096,
  "intermediate_size": 14336,
  "num_hidden_layers": 32,
  "num_attention_heads": 32,
  "num_key_value_heads": 8,        ← GQA 分组数（=H 是 MHA，=1 是 MQA）
  "head_dim": 128,
  "max_position_embeddings": 131072,
  "rope_theta": 500000.0,          ← 老模型是 10000
  "vocab_size": 128256
}
```

**三个快速诊断**：

| 现象 | 从 config 看出的原因 |
|---|---|
| 长上下文很吃显存 | `num_key_value_heads = H`（MHA）→ KV 显存是 GQA 的 4 倍 |
| 中文 token 消耗多 | `vocab_size` 小（< 64K） |
| 长文本质量差 | `rope_theta` 小 + `max_position_embeddings` 小 |

完整解读见 [`07`](./07-论文索引与工程结论.md) §3。

## 🚦 三个最容易混淆的判断

| 混淆 | 真相 |
|---|---|
| 「FlashAttention 减少了计算量」 | **没有**。它多算了（重算），省的是**显存带宽**。GPU 上带宽才是瓶颈 |
| 「MoE 的模型更省显存」 | **反了**。显存按**总参数**算，算力按**激活参数**算。MoE 是训练期省算力，部署期更费显存 |
| 「上下文越长效果越好」 | **不是**。Lost in the Middle + Power of Noise 决定了「塞进去」和「用得上」是两件事。**先做检索，再考虑扩窗** |

## 💡 工程结论（浓缩版）

1. **参数量 87% 在 FFN 里。** 记住这一条，LoRA / MoE / 量化三个技术都能挂上去。
2. **Decoder-only 赢在任务统一和规模化**，不是「更先进」。Encoder-only 在检索上仍是主力。
3. **KV Cache 是长上下文推理的真瓶颈**，不是模型权重。
4. **算子层优化（FlashAttention / PagedAttention / CUDA Graph）是免费午餐**；
   架构层改动（MQA/GQA/MoE）等于换模型。**分清这两层是本领域最重要的判断力。**
5. **MoE 的推理速度像激活参数模型，显存像总参数模型。** 单卡部署直接出局。
6. **Chinchilla 的 20× 规则**：数据不够时堆参数是浪费。**效果不好的第一检查项是数据量。**
7. **永远用 `apply_chat_template()`。** 手拼字符串是「模型突然变傻」的头号原因。
8. **永远报 TTFT 和 TPOT 两个数。** 只报「总延迟」的报告没有信息量。
