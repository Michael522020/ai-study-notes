# MoE 稀疏专家

> **核心问题**：MoE 凭什么用「激活 37B」的算力做出「总参数 671B」的能力？这个模型在生产上怎么部署？

---

## 0. 动机：87% 的参数在 FFN 里

回看 [`02-Transformer结构演进.md`](./02-Transformer结构演进.md) §1 的参数量分布：

```
7B 级模型（d=4096, L=32, d_ffn=11008, V=128K）：

  嵌入 + LM Head   1.05B   ████░░░░░░░░░░░░░░░░░░░░  14%
  Attention 层     0.88B   ███░░░░░░░░░░░░░░░░░░░░  12%
  FFN 层          5.60B    ████████████████████░░░░░  74%  ← 大头
```

**两个推论**：

1. **想让模型更强，最直接的办法是加大 FFN** → 但这会线性增加算力和显存
2. **MoE 的赌注是：绝大多数 token 根本不需要用上所有 FFN 容量**

> **MoE = 把「稠密 FFN」换成「多个专家 + 一个路由器」，每个 token 只激活少数几个。**
> **参数量（知识）涨，算力（成本）不涨。**

---

## 1. 结构：把 FFN 换成专家池

```
稠密 FFN（每个 token 都过）：
   x → [ W_gate_up: d×2d_ffn ] → act → [ W_down: d_ffn×d ] → x'

MoE FFN（每个 token 只过 top-k 个专家）：
   x → Router → {Expert_1, Expert_2, ..., Expert_N}
                     ↓ 只选中 k 个
              加权求和
```

| 组件 | 说明 |
|---|---|
| **Router（门控网络）** | 一个很小的线性层（`d → N`），给每个专家打分 |
| **Expert** | 每个专家就是一个普通 FFN（通常 SwiGLU） |
| **Top-k 路由** | 每个 token 选 k 个专家，k 通常 1~8 |

**参数量对比**（N 个专家，每个大小等于原 FFN）：

```
稠密:   FFN 参数 = 3 · d · d_ffn
MoE:    FFN 参数 = N · 3 · d · d_ffn      ← N 倍

但每个 token 只经过 k 个专家：
        每 token 实际计算量 = k · 3 · d · d_ffn
```

> **这就是 MoE 的全部魔法：参数 ×N，计算量 ×k。**
> 前提是 **N ≫ k**（通常 N/k 在 10~100 量级）。

---

## 2. Router：怎么选专家

```python
def moe_router(x, gate_weight, n_experts, top_k, capacity_factor):
    # x: [T, d]  T = token 总数（batch × seq_len）
    logits = x @ gate_weight                      # [T, N]
    probs = softmax(logits, dim=-1)               # [T, N]

    # top-k 选择（注意：路由用 softmax 概率做加权）
    topk_probs, topk_idx = torch.topk(probs, top_k, dim=-1)
    topk_probs = topk_probs / topk_probs.sum(dim=-1, keepdim=True)  # 归一化

    # 容量限制：每个专家最多处理 capacity 个 token
    capacity = ceil(capacity_factor * T * top_k / n_experts)
    # 超容量的 token 被丢弃（→ 需要 aux loss 惩罚）
    return topk_idx, topk_probs, capacity
```

### 2.1 Router 本身很小

```
Router 参数 = d × N
```

对 d=7168, N=256 → 1.8M 参数。**相比 671B 的总参数可以忽略。**

但它**极其关键**：Router 决定每个 token 的知识路径。**Router 训练不好，整个 MoE 就废了。**

### 2.2 负载不均是最常见的问题

**实际训练中，Router 极易坍缩**：
- 少数几个专家被大量 token 选中（**专家坍缩 / 专家退化**）
- 其他专家几乎收不到 token → 训不出来 → 更没人用 → 死循环

**后果**：参数浪费了（显存照占），能力没提升。

### 2.3 路由的梯度从哪来

```
总损失 = 主任务损失 + λ × 负载均衡损失
```

Router 的梯度**只来自均衡损失**（因为 top-k 是离散选择，梯度无法穿过）。

> **关键理解**：Router 不直接学「哪个专家最适合这个 token」，
> 它学的是「怎么分配才能让所有专家都被用上」。
> **「专家适合什么」是通过专家自己的训练学出来的，Router 只是搬运工。**

---

## 3. 负载均衡：两条路线

### 3.1 路线 A：辅助损失（Switch Transformer / GShard）

```
L_aux = N · Σ_i (f_i · P_i)

f_i = 本批中分给专家 i 的 token 比例
P_i = router 给专家 i 的平均概率
```

- `f_i` 和 `P_i` 越接近越均衡（理想情况都是 1/N）
- **需要调 λ**，且 λ 和主任务损失会「打架」

**缺点**：
- 引入新的超参
- 均衡项和任务项相互干扰（有的任务需要一定的不均衡）
- 路由权重被「拉向均匀」，牺牲了路由的自由度

### 3.2 路线 B：无辅助损失的均衡（DeepSeek-V3 路线）

**思路**：不改损失函数，**改 Router 的实现**：

```
每层做一次「专家选择偏置」修正：
  1. 统计本批每个专家的 token 负载
  2. 对选得多的专家，减去一个 bias（后续批次倾向少选它）
  3. 对选得少的专家，加上 bias
  → 负载自然回到均衡
```

| 优点 | 缺点 |
|---|---|
| **不引入额外损失项**，主任务信号不被污染 | 需要额外的同步通信 |
| 训练更稳定 | 实现复杂度高 |

### 3.3 其他辅助机制

| 机制 | 做法 |
|---|---|
| **容量限制（drop）** | 每个专家最多接 `capacity` 个 token，超了就**丢**（token 直接过残差） |
| **容量因子上调** | 宁可多算也不要丢（牺牲一点算力换质量） |
| **Token 选择（dropless）** | 超容量的 token 在专家之间「排队」而不是丢弃（Tutel 等） |
| **专家容量预测** | 用一个小网络预测每层的负载，动态分配容量 |

## 4. 专家并行：通信是硬约束

### 4.1 三种并行方式

```
数据并行 (DP)：切 batch，各卡持有全部模型
  └─ 模型必须能放进一张卡 → MoE 做不到（模型太大）

张量并行 (TP)：切权重矩阵
  └─ 每层都要 all-reduce → 通信密集

专家并行 (EP)：切专家
  └─ 每层一次 all-to-all → 只在 MoE 层通信
```

**MoE 的标准组合**：`专家并行 (EP) + 数据并行 (DP)`，
通信只在 **MoE FFN 层**发生（而非每层）。

### 4.2 all-to-all 通信

```
每个 GPU 持有部分专家。所有 token 需要被送到它们各自的专家所在的 GPU。

  Token Routing (all-to-all)  →  专家计算  →  Token Return (all-to-all)
```

**这是 MoE 训练最痛的地方**：
- 通信量与 `激活参数 × batch × seq_len` 成正比
- 需要高速互联（NVLink / InfiniBand）
- **跨节点 EP 极易成为瓶颈**

> **工程结论**：MoE 训练的硬件门槛极高。**没有高速互联的多机训练 MoE 基本跑不动。**
> 这直接决定了 MoE 只存在于少数几家大厂。

### 4.3 推理时的并行

推理的并行策略与训练不同：

| 策略 | 说明 |
|---|---|
| **专家并行** | 和训练一样，需要 all-to-all；延迟高 |
| **专家并行 + 副本** | 每卡放一份完整模型，按 expert 亲和性路由 |
| **纯数据并行** | 每卡放完整模型，batch 切分。**显存要求极高** |
| **专家卸载（offload）** | 专家放 CPU/磁盘，按需加载。**延迟抖动大** |

## 5. 共享专家与细粒度专家

### 5.1 共享专家（Shared Experts）

**动机**：每个 token 都会激活的少数专家，负责**通用知识**（如句法、常识）。
路由专家负责**专门知识**。

```
输出 = Σ(路由专家输出) + 共享专家输出
```

**收益**：路由专家可以更专门；通用知识不用在每个专家里冗余存储。

### 5.2 细粒度专家（Fine-grained Experts）

**DeepSeek-V3 的关键设计**：

```
粗粒度：8 个大专家，每个 top-2 激活      → 2 个专家被激活
细粒度：256 个小专家，每个 top-8 激活    → 8 个专家被激活
```

**收益**：
1. **同样的激活参数量下，组合更多** → 表达力更强
2. 每个专家更小 → 更容易专业化
3. 每个 token 可以从更多「不同的角度」聚合信息

**代价**：
- 路由计算更复杂
- all-to-all 通信的分组更多

## 6. 关键区分：总参数 vs 激活参数

**这是理解 MoE 最重要的一件事，也是最容易被宣传话术带偏的地方。**

| 指标 | 含义 | 影响什么 |
|---|---|---|
| **总参数** | 所有专家 + 共享部分的总和 | **显存**（必须全部加载） |
| **激活参数** | 每个 token 实际经过的参数 | **算力**（单 token 计算量） |

### 6.1 实例对照

| 模型 | 总参数 | 激活参数 | 比率 |
|---|---|---|---|
| **Mixtral 8×7B** | 46.7B | 12.9B | 3.6× |
| **DeepSeek-V2** | 236B | 21B | 11.2× |
| **DeepSeek-V3** | 671B | **37B** | **18.1×** |
| 对比：Dense 70B | 70B | 70B | 1× |

### 6.2 部署账（本节最重要）

**DeepSeek-V3 的部署账**：

```
权重显存（bf16） = 671B × 2 bytes = 1.34 TB
激活参数（单 token 计算量）= 37B  → 和一个 37B 的 dense 模型相当
```

> **结论非常反直觉**：
> **MoE 模型的推理速度像 37B，但显存需求像 671B。**

| 场景 | 影响 |
|---|---|
| **单卡部署** | **完全不可行**（1.34 TB） |
| **多卡部署** | 需要 8× H100 (640GB) / 更多 |
| **小 batch 推理** | **灾难性低效**——batch=1 时，每个 token 只激活 8/256 个专家，**绝大部分显存是闲的** |
| **大 batch 推理** | 效率接近 dense 37B |
| **API 服务** | 需要按 token 负载做专家亲和路由，否则跨节点通信爆炸 |

### 6.3 三个必须记住的推论

```
① 推理速度 ≈ 激活参数  →  MoE 相对 dense 同激活参数模型**没有速度优势**
② 显存 ≈ 总参数        →  MoE 相对 dense 同总参数模型**显存没有优势**
③ 质量 ≈ 总参数（近似）→  MoE 相对 dense 同总参数模型**质量有优势**
```

> **所以 MoE 的真实价值是「训练期的算力效率」，不是「推理期的部署效率」。**
> 它的产出物是**一个质量高但部署很重的模型**。
> 如果你的目标是「在 1 张卡上跑」，MoE 帮不上忙。

## 7. 训练难点清单

| 难点 | 表现 | 对策 |
|---|---|---|
| **专家坍缩** | 少数专家吃掉全部 token | 负载均衡机制（辅助损失 / bias 修正） |
| **路由不稳定** | 相似 token 路由到不同专家，训练抖动 | 限制路由容量、辅助损失 |
| **通信瓶颈** | all-to-all 占了大半训练时间 | 高速互联；专家本地化 |
| **微调数据不足** | MoE 在小数据集上**明显不如 dense** | **MoE 必须有大数据**（DeepSeek-V3 用 14.8T token） |
| **专家数量与 batch size** | batch 太小，装不满专家（浪费容量） | 大 batch + 梯度累积 |
| **推理时的负载不均** | 某些专家排队 | 容量因子上调 / dropless |

> **最反直觉的一条**：**MoE 对数据量的需求远高于 dense。**
> 很多团队上 MoE 效果不如预期，根因是**数据不够**——
> 每个专家要专门化，需要足够多的样本来喂饱它。

---

## 8. 什么时候**不要**上 MoE

| 条件 | 建议 |
|---|---|
| **数据量 < 百亿 token** | **不要上**。用 dense，把参数加在 FFN 上更划算 |
| **单卡/边缘部署** | **不要上**。显存按总参数算，直接劝退 |
| **小 batch 推理** | **不要上**。专家利用率极低 |
| **没有高速互联** | **不要上**。all-to-all 会成为训练瓶颈 |
| **团队规模小** | **不要上**。调参和故障排查成本高（专家级问题定位很难） |
| **任务需要严格的一致性** | 谨慎。路由的随机性会增加输出方差 |

**替代方案**：
- **dense + 更深/更宽**（同样的算力预算下，小数据场景下通常更好）
- **LoRA/QLoRA 微调大模型**（见 [`../06-大模型训练/03-LoRA.md`](../06-大模型训练/03-LoRA.md)）
- **量化 + 蒸馏**（见 [`../09-本地大模型推理与部署/`](../09-本地大模型推理与部署/)）

## 9. 主流模型的架构选择速查

| 模型 | 架构 | 专家数 / top-k | 备注 |
|---|---|---|---|
| Llama 2/3 | **Dense** | — | 无 MoE |
| Qwen2/3 | **Dense**（部分小尺寸有 MoE） | — | 主力是 dense |
| Mixtral 8×7B | MoE | 8 / 2 | 首个开源 MoE 主流模型 |
| DeepSeek-V2 | MoE | 160+ / 6 | 细粒度 + 共享专家 |
| DeepSeek-V3 | MoE | 256 / 8 | 细粒度 + 无辅助损失均衡 |
| GPT-4（公开信息） | 未公开 | — | 有传闻称用了 MoE，未确认 |
| 各类 70B~400B 开源模型 | **多数 dense** | — | **MoE 在开源生态仍非主流** |

> **现实判断**：**MoE 是大厂在超大规模（千亿 token 级数据 + 千卡集群）下的选择。**
> 对于绝大多数团队（数据 < 千亿 token、硬件 < 百卡），**dense + 更好的数据仍是正解**。

## 10. 工程结论

1. **MoE 的赌注是「大部分 token 用不上全部 FFN 容量」。** 赌赢了参数涨 N 倍、算力只涨 k 倍。
2. **总参数 = 显存，激活参数 = 算力。** 这两件事千万别混。
3. **MoE 的推理速度像激活参数模型，显存像总参数模型。**
   671B/37B 的 DeepSeek-V3 需要 1.34 TB 显存——**单卡部署直接出局**。
4. **MoE 对数据量要求极高。** 小数据场景下，dense 几乎总是更好。
5. **负载均衡是 MoE 训练的第一难题**，辅助损失和 bias 修正两种路线各有取舍。
6. **all-to-all 通信是 MoE 的硬件门槛。** 没有 NVLink 级别的互联别碰。
7. **推理端要按专家亲和性路由**，否则跨节点通信会把延迟吃掉。
8. **除非你有百亿 token 级数据和百卡集群，否则不要上 MoE。**
