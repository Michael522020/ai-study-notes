## 3. 从 checkpoint 反读架构

**最快的架构学习方式：读 `config.json`，不要读论文。**

```bash
# Llama / Qwen / Mistral 系
cat config.json
```

```json
{
  "architectures": ["LlamaForCausalLM"],
  "hidden_size": 4096,
  "intermediate_size": 14336,
  "num_hidden_layers": 32,
  "num_attention_heads": 32,
  "num_key_value_heads": 8,
  "head_dim": 128,
  "max_position_embeddings": 131072,
  "rope_theta": 500000.0,
  "rms_norm_eps": 1e-05,
  "vocab_size": 128256,
  "tie_word_embeddings": false,
  "hidden_act": "silu"
}
```

### 3.1 逐字段翻译

| 字段 | 含义 | 读出什么 |
|---|---|---|
| `hidden_size` | d_model | 模型宽度 |
| `intermediate_size` | d_ffn | FFN 扩展比 = 14336/4096 = **3.5×**（SwiGLU 的 8/3×2 形式） |
| `num_hidden_layers` | L | 深度 |
| `num_attention_heads` | H | Q 头数 |
| **`num_key_value_heads`** | H_kv | **GQA 的分组数**（= H 是 MHA，= 1 是 MQA） |
| `head_dim` | d_head | 通常 = hidden_size / H |
| `max_position_embeddings` | S_max | 训练时的最大长度 |
| **`rope_theta`** | base | **RoPE base**（10000 = 老式；500000 = 为长上下文调过） |
| `vocab_size` | V | 词表大小 |
| `tie_word_embeddings` | — | 小模型常 true（省参数） |
| `hidden_act` | — | `silu` → SwiGLU；`gelu` → 老式 |

### 3.2 由此算出的三件事

```
① KV Cache 每 token 字节 = 2 × L × H_kv × d_head × bytes
② 权重显存 ≈ (V×d×2 + L×(4d² + 3·d·d_ffn)) × bytes
③ 注意力复杂度 = O(S²·d) 每层，prefill 阶段主导
```

**例（上面的 Llama-3-8B 配置）**：
```
KV/token = 2 × 32 × 8 × 128 × 2 = 128 KiB   → 8K 序列 = 1 GB
权重 ≈ (128256×4096×2 + 32×(4×4096² + 3×4096×14336)) × 2B
     ≈ (1.05B + 8.03B) × 2B ≈ 18 GB (bf16)
```

### 3.3 三个快速诊断

| 现象 | 从 config 能看出的原因 |
|---|---|
| **长上下文很吃显存** | `num_key_value_heads` = H（MHA）→ 换 GQA 模型或量化 KV |
| **短文本也慢** | `rope_theta` 小 + `max_position_embeddings` 小 → 可能是老架构 |
| **tokenizer 效率差** | `vocab_size` 小（< 64K）→ 中文场景 token 数多 |

## 4. 可直接抄的配置

### 4.1 一个 7B 级的现代 dense 配方

```yaml
# 架构
d_model: 4096
n_layers: 32
n_heads: 32
n_kv_heads: 8          # GQA
d_head: 128
d_ffn: 14336           # ≈ 8d/3，SwiGLU 3 矩阵
vocab_size: 128256
rope_theta: 10000      # 若要 >32K 上下文 → 500000
qk_norm: true

# 训练
optimizer: adamw
lr: 3e-4               # 峰值
betas: [0.9, 0.95]
weight_decay: 0.1
warmup_ratio: 0.01
lr_schedule: cosine
min_lr_ratio: 0.1
grad_clip: 1.0
precision: bf16
micro_batch: 4         # 按显存调
grad_accum: 16         # 有效 batch = 4 × 16 × seq_len
seq_len: 8192
checkpointing: full    # 激活检查点
```

### 4.2 几个「不要改」的默认值

| 参数 | 默认 | 为什么 |
|---|---|---|
| `weight_decay` | **0.1** | 0.0 会让模型更容易过拟合小数据 |
| `betas` | **(0.9, 0.95)** | 0.999 在 LLM 上偏保守 |
| `warmup_ratio` | **0.01~0.03** | Pre-LN 也建议留 warmup |
| `grad_clip` | **1.0** | 便宜的安全网 |
| `min_lr_ratio` | **0.1** | 余弦退到 0 会在最后阶段抖动 |
| `seq_len` | **≥ 2048** | 短序列训练的模型长文本能力差 |

### 4.3 数据配比（Chinchilla 结论）

```
训练 token 数 ≈ 20 × 参数量
```

| 参数量 | 建议训练 token |
|---|---|
| 1B | 20B |
| 7B | 140B |
| 13B | 260B |
| 70B | 1.4T |

> **数据不够时，堆参数是浪费。** 一个 7B 模型用 20B token 训练，
> 效果不如 4B 模型用 80B token 训练。
> **这是「你的模型效果不好」最常见的根因。**

## 5. 预训练 vs 推理的检查清单

### 5.1 拿到一个 checkpoint，30 秒判断它是什么

```
1. 读 config.json          → 架构、上下文长度、RoPE base
2. 读 tokenizer_config.json → 词表大小、chat template 是否存在
3. 读 generation_config.json → 采样默认值、stop token
4. 看 model.safetensors.index.json → 参数量、分片数
5. 算 KV Cache 每 token 字节 → 决定并发上限
```

### 5.2 推理前必须确认的三件事

| 检查 | 为什么 |
|---|---|
| **chat template 存在且与模型匹配** | 答非所问的头号原因 |
| **`eos_token_id` 正确** | 否则模型停不下来，token 疯狂刷屏 |
| **KV Cache dtype 与量化设置** | 决定能用多长的上下文 |

## 6. 工程结论

1. **先读 `config.json` 再读论文。** 架构的一切信息都在那 12 个字段里。
2. **现代 dense 配方是收敛的**：RMSNorm + SwiGLU + RoPE + GQA + Pre-LN + QK-Norm + 无 bias。
   **自己实现时照抄，不要照抄 2017 年原始论文。**
3. **GQA 的 `num_key_value_heads` 是最重要的一个字段**——它直接决定你的 KV 显存。
4. **Chinchilla 的 20× 规则**：数据不够时堆参数是浪费。
   **模型效果不好的第一检查项是数据量，不是模型大小。**
5. **FlashAttention 不改数学。** 没启用就查 backend，不是模型的问题。
6. **投机解码要看接受率**，< 0.7 白干；**Medusa/EAGLE 不占额外显存，端侧更合适**。
7. **MoE 的显存按总参数算。** 671B/37B 的模型需要 1.34 TB——单卡部署直接出局。
8. **训练稳定性靠 RMSNorm + Pre-LN + QK-Norm + bf16 四件套**，别自己发明。
