# 位置编码与长上下文

> **核心问题**：模型怎么知道「谁在谁前面」？为什么 4K 训练的模型放到 32K 就开始胡说？长上下文真正的成本在哪？

---

## 0. 为什么需要位置编码

**自回归注意力的本质是「内容寻址」**——attention 的权重只由 Q·K 的**内容相似度**决定：

```
scores[i][j] = q_i · k_j     ← 只看内容，不看位置
```

所以两个**词完全相同但位置不同**的 token，对注意力层来说是**完全一样的输入**。

```
"猫 追 狗"  和  "狗 追 猫"
```

如果不给位置信息，模型看到的是同一个 bag of tokens，无法区分。

> **位置编码要解决的是：把「顺序」这个一维信息注入到「内容」的高维表示里。**

---

## 1. 六种方案

| 方案 | 年份 | 机制 | 相对位置 | 外推能力 |
|---|---|---|---|---|
| **正弦绝对** | 2017 | 固定 sin/cos 频率 | ❌ | ✅ 理论上可外推 |
| **可学习绝对** | 2018 | 可训练的 embedding 表 | ❌ | ❌ 超出表长即失效 |
| **相对位置（Shaw）** | 2019 | 距离 bias 加到 attention logit | ✅ | 中等 |
| **T5 相对偏置** | 2020 | 分桶的相对距离 bias | ✅ | 中等 |
| **ALiBi** | 2022 | 线性负偏置，斜率随头递减 | ✅ | ✅ 优秀 |
| **RoPE** | 2021 | **旋转位置编码** | ✅ | ⚠️ 需要插值技巧 |

### 1.1 正弦绝对（原始 Transformer）

```python
PE(pos, 2i)     = sin(pos / 10000^(2i/d))
PE(pos, 2i + 1) = cos(pos / 10000^(2i/d))
```

- 高维用高频（相邻位置可区分），低维用低频（远距离位置可区分）
- **不需要训练** → 理论上可以外推到训练时没见过的位置
- **但实践效果差**：模型学到的还是「绝对位置 → 绝对表示」的映射，
  外推时表示落在训练分布外 → 失效

### 1.2 ALiBi（Pressplay et al., 2022）

**思路**：不给位置表示，**直接给 attention 加一个线性惩罚**：

```
scores[i][j] += -m(i - j) · slope_h
```

每个头有一个不同的 `slope_h`，**按几何级数递减**：
前面的头惩罚陡（关注局部），后面的头惩罚缓（关注全局）。

| 优点 | 缺点 |
|---|---|
| **外推能力优秀**——位置信息是线性的，天然可延 | 不携带绝对位置信息，理论上表达力略弱 |
| 实现极简，零额外参数 | 与主流生态不兼容（几乎没被采用） |
| 训练极稳 | 与 RoPE 组合的收益不明显 |

> ALiBi 证明了「位置信息不一定要靠 embedding 承载」，
> 但因为生态兼容性，它没有取代 RoPE。

## 2. RoPE：现代事实标准

### 2.1 核心思想：把位置变成旋转

**不是给 embedding 加东西，而是对 Q 和 K 按位置做旋转。**

```
给位置 m 的 query 和 key 分别施加旋转矩阵 R_m：

  q'_m = R_m · q_m
  k'_n = R_n · k_n

其中 R_m 是由位置 m 决定的分块旋转矩阵（2D 平面上按不同频率转不同角度）。
```

### 2.2 为什么旋转能编码相对位置

旋转矩阵的性质：`R_mᵀ · R_n = R_{n-m}`

于是 attention logit 变成：

```
q'_m · k'_n = (R_m q_m)ᵀ (R_n k_n)
            = q_mᵀ R_mᵀ R_n k_n
            = q_mᵀ R_{n-m} k_n
                    ↑
              只依赖相对距离 n - m
```

> **这是 RoPE 最漂亮的地方**：
> 它不像绝对位置编码那样「附加」信息，而是**把相对位置关系直接编码进了内积**。
> 模型的相似度计算天然变成了相对位置敏感的。

### 2.3 实现

```python
import torch

def apply_rope(x, pos_ids, base=10000.0):
    """
    x:      [B, H, S, D]   D 必须是偶数
    pos_ids:[B, S]         每个 token 的绝对位置
    """
    B, H, S, D = x.shape
    half = D // 2

    # 频率：第 i 组 (i, i+half) 共用频率 base^(-2i/half)
    inv_freq = 1.0 / (base ** (torch.arange(0, half, device=x.device).float() / half))
    freqs = pos_ids.float().unsqueeze(-1) * inv_freq.unsqueeze(0)   # [B, S, half]

    cos = freqs.cos().unsqueeze(1)   # [B, 1, S, half]
    sin = freqs.sin().unsqueeze(1)

    x1, x2 = x[..., :half], x[..., half:]
    out1 = x1 * cos - x2 * sin
    out2 = x1 * sin + x2 * cos
    return torch.cat([out1, out2], dim=-1)
```

> **注意实现细节**：现代实现通常**只对 Q 和 K 应用 RoPE**，**不对 V 应用**——
> 因为 V 参与的是「加权求和」，不需要位置信息。

### 2.4 频率基数的含义

```python
base = 10000.0    # 默认
inv_freq = base ** (-2i / d)
```

| base | 效果 |
|---|---|
| 1000 | 高频更多，能分辨近距离，但最长可辨距离短 |
| **10000** | **默认平衡** |
| 500000~1000000 | 低频更多，**长距离分辨力更好**（Llama-3 用 500000） |

> **Llama-3 把 RoPE base 从 10000 提到 500000**，就是为了配合 128K 上下文。

## 3. RoPE 的外推困境

### 3.1 现象

模型在 4K 上训练，直接喂 32K：

```
短文本（< 4K）    →  正常
中等（4K~8K）    →  开始重复、逻辑混乱
超过训练长度      →  完全崩坏（重复 token、语法碎片）
```

### 3.2 原因

RoPE 的旋转角度是位置的**线性函数**：

```
θ(pos) = pos × inv_freq
```

在训练长度 `L` 内，模型见过 `θ ∈ [0, L·inv_freq]` 的所有旋转。
超出后，角度进入了**从未见过的区域**：

```
低频维度（i 大）：inv_freq 极小 → pos 增大时角度变化很小 → 外推相对安全 ✅
高频维度（i 小）：inv_freq 较大 → pos 增大时角度转过很多圈 → 落进未见区域 ❌
```

**同时**：注意力权重是由 Q·K 决定的，而 Q/K 的**幅值**（norm）也在位置外推时失配。

### 3.3 三种外推方法

#### ① 位置插值（Position Interpolation, PI）

**思路**：把位置 m 压缩到训练范围 L 内：

```
θ_new(m) = m × (L / S) × inv_freq        （S = 目标长度）
```

| 优点 | 缺点 |
|---|---|
| 简单有效，**不需重训或少量重训** | 位置分辨率下降（S/L 倍），**短文本精度也降** |
| 兼容性最好 | 高频维度被过度压缩，损失近距离分辨力 |

#### ② NTK-aware 插值

**思路**：**不缩放位置，而是缩放频率**：

```
base' = base × s^(d / (d - 2))      其中 s = S / L
θ_new(m) = m × inv_freq(base')
```

等价于「把低频维度多留一点，高频维度少压一点」。

| 优点 | 缺点 |
|---|---|
| **短文本精度几乎不掉**（高频维度基本不动） | 需要少量微调才能完全恢复 |
| 长文本质量明显优于 PI | 实现比 PI 复杂一点 |

#### ③ YaRN

**思路**：把 NTK 分块（by-parts）+ **注意力温度补偿** + ** ramp 函数** 组合起来：

1. **NTK-by-parts**：对不同频率段用不同的插值比例（高频不插值、中频部分插值、低频全插值）
2. **注意力温度缩放**：`1/t` 补偿——外推后注意力熵变大（更分散），需要锐化
3. **ramp 混合**：训练长度内用原 RoPE，外推区用 YaRN，中间平滑过渡

> **工程结论**：YaRN 目前是**长上下文外推的最佳实践**。
> 但更常见的做法是：**训练时就把长上下文训进去**（比如 32K 训练 + 分段续训到 128K），
> 而不是纯靠推理时的插值技巧。

## 4. 长上下文的三个真问题

**很多人以为「长上下文 = 把窗口调大」，实际上有三个独立的问题。**

| # | 问题 | 性质 | 解法 |
|---|---|---|---|
| **1** | **位置外推** | 模型没见过那么长的位置 | 插值技巧 / 长上下文训练 |
| **2** | **注意力稀释** | 上下文越长，单个 token 分到的注意力越少 | 见 §5 |
| **3** | **KV Cache 显存** | 线性增长 | GQA / 量化 / 淘汰 / 分页 |

**这三个问题互相独立，解决一个不影响另外两个。**
一个模型可以「不崩」但「用不好」，也可以「用得好」但「装不下」。

## 5. 注意力稀释与位置效应

### 5.1 Lost in the Middle

**现象**：把关键信息放在上下文中部，模型的表现**显著差于**放在开头或结尾。

```
┌─────────────────────────────────────────┐
│ [开头]   问题   [中部:关键事实]   [结尾]  │
│   ✓          ✓           ✗          ✓   │
└─────────────────────────────────────────┘
```

**这不是「模型读不到」，而是「模型给中部的注意力权重更低」。**

### 5.2 The Power of Noise（对 RAG 尤其重要）

**结论**：检索到**无关内容**的负面影响，**远大于**检索到**相关但覆盖不全**的内容。

> 这颠覆了「召回率越高越好」的直觉：
> **减少噪音（少而精）比提高召回更重要。**

### 5.3 上下文预算怎么分配

```
┌──────────────────────────────────────────────┐
│ 系统提示（稳定，可缓存）          ~500 token   │
├──────────────────────────────────────────────┤
│ 工具定义（稳定，可缓存）        ~2000 token   │
├──────────────────────────────────────────────┤
│ 历史对话（滚动窗口）            ~4000 token   │
├──────────────────────────────────────────────┤
│ 检索到的知识片段                ~4000 token   │
├──────────────────────────────────────────────┤
│ 当前问题 + 最近观察（放最前）   ~1000 token   │
└──────────────────────────────────────────────┘
```

**排序原则**：
1. **最重要的放两端**（开头和结尾）
2. **最不重要的放中间**
3. **最易变的信息放最后**（破坏前缀缓存的代价最小）

> 见 [`../07-Agent与智能体/06-记忆与上下文工程.md`](../07-Agent与智能体/06-记忆与上下文工程.md)。

## 6. KV Cache 显存：长上下文的真实账单

### 6.1 公式

```
KV Cache 字节数 = 2 × L × H_kv × d_head × S × bytes_per_element
                   │   │    │      │      │   │
                   │   │    │      │      │   └─ bf16=2, fp8=1, int4=0.5
                   │   │    │      │      └──── 序列长度
                   │   │    │      └─────────── 每头维度
                   │   │    └────────────────── KV 头数
                   │   └─────────────────────── 层数
                   └─────────────────────────── K 和 V 两份
```

### 6.2 实例：Llama-3-8B（GQA，H_kv=8, d_head=128, L=32）

```
每 token = 2 × 32 × 8 × 128 × 2 bytes = 131,072 bytes = 128 KiB
```

| 上下文长度 | 单序列 KV Cache |
|---|---|
| 2K | 256 MB |
| **4K** | **512 MB** |
| **8K** | **1 GB** |
| **32K** | **4 GB** |
| **128K** | **16 GB** |

### 6.3 对比 MHA

如果用 MHA（`H_kv=32`），上面所有数字 **×4**：

| 上下文长度 | MHA | GQA | 节省 |
|---|---|---|---|
| 8K | 4 GB | 1 GB | 4× |
| 32K | 16 GB | 4 GB | 4× |
| 128K | 64 GB | 16 GB | 4× |

> **这张表是长上下文规划的第一张表。**
> 128K 上下文 + GQA + bf16，单序列就要 16 GB 显存——
> 这就是为什么长上下文服务**必须**配合 KV 量化或分页管理。

### 6.4 batch 的影响

```
总 KV 显存 = 单序列 KV × 并发序列数
```

128K 上下文、并发 8 路 → 128 GB。**这通常比模型权重还大。**

> **工程结论**：长上下文服务的瓶颈**几乎总是 KV Cache，不是模型权重**。
> 选型时先算 `128K × 并发数 × 每 token KV 字节`，再决定要不要量化。

## 7. 怎么正确评测长上下文

**绝大多数「模型支持 128K」的宣传是不可信的**，因为评测方式有问题。

### 7.1 常见的三种作弊

| 作弊 | 表现 |
|---|---|
| **大海捞针（Needle in a Haystack）** | 在长文本里插一句事实，检索它。**这只测了「能不能找到」，没测「能不能用」** |
| **只测长度不测深度** | 关键信息永远在开头或结尾 |
| **多次采样取最好** | 掩盖了真实波动 |

### 7.2 一个更靠谱的评测设计

```
1. 多个深度位置（10% / 30% / 50% / 70% / 90%）
2. 多个信息条数（1 / 3 / 5 个分散的知识点）
3. 需要**组合**多个知识点才能回答的问题（而非单点检索）
4. 有干扰项（语料里放相似但不相关的段落）
5. 固定随机种子，报告多次运行的均值和方差
6. 同时报 TTFT 与 TPOT（长上下文常常 TTFT 爆炸）
```

### 7.3 必报的口径

| 口径项 | 说明 |
|---|---|
| **KV Cache 精度** | bf16 / fp8 / int4 —— 直接影响可用上下文长度 |
| **是否 chunked prefill** | 长 prompt 会被切块，长上下文服务通常开启 |
| **并发数** | 上下文长度和并发是**此消彼长**的 |
| **位置分布** | 只测开头等于没测 |

## 8. 工程建议

### 8.1 选位置编码

| 场景 | 选择 |
|---|---|
| **自己训模型** | **RoPE**（base 10000；计划支持 >32K 则用 500000+） |
| **从 checkpoint 续训长上下文** | RoPE + 分段扩窗（4K → 16K → 64K → 256K），每段用上一段的最优 |
| **推理时临时扩窗** | **YaRN** 或 NTK-aware；**同时必须下调 attention 温度或换 YaRN 的温度补偿** |
| **流式长文档** | RoPE + 滑动窗口 + **保留 sink token** |
| **极端省事** | 直接用官方长上下文 checkpoint，不要自己插值 |

### 8.2 什么时候**不要**追求长上下文

| 情况 | 更好的方案 |
|---|---|
| 文档可以切块 | **RAG**（检索 + 拼接）——见 [`../03-RAG/`](../03-RAG/) |
| 需要精确引用原文位置 | **RAG + 位置标注**（长上下文里模型说不清引自哪里） |
| 成本敏感 | RAG（只送相关片段） |
| 上下文 > 256K | RAG / 层级摘要（GraphRAG、RAPTOR） |

> **一个反直觉但可靠的判断**：
> **「上下文越长」不等于「效果越好」。**
> 很多论文显示，**恰当检索 + 短上下文**的效果**超过**长上下文塞满。
> 这是因为长上下文引入了噪音（Power of Noise）、位置效应（Lost in the Middle）、
> 和成本上升三连。**先做检索，再考虑扩窗。**

### 8.3 续训扩窗的标准做法

```
阶段 1: 4K → 16K    （1 epoch，lr 降到原来的 1/10）
阶段 2: 16K → 64K   （1 epoch，lr 继续降）
阶段 3: 64K → 256K  （1 epoch）
每阶段：保持其余超参不变，batch 按 token 数动态调整
```

**注意**：每阶段都要**重新测位置分布下的表现**，不能只测大海捞针。

## 9. 工程结论

1. **位置编码必须让模型知道顺序**，因为注意力本身只做内容匹配。
2. **RoPE 是现代事实标准**：它把相对位置关系直接编码进内积，而不是「附加」信息。
3. **RoPE 外推要靠技巧**：PI 简单但伤短文本精度；NTK-aware 更好；**YaRN 最优**。
4. **长上下文有三个独立问题**（外推 / 稀释 / 显存），解决一个不等于解决全部。
5. **KV Cache 显存 = `2 × L × H_kv × d_head × S × 字节`**，长上下文的账主要在这。
6. **长上下文不等于长上下文效果。** Lost in the Middle + Power of Noise 决定了
   「塞进去」和「用得上」是两件事。
7. **优先做检索，再考虑扩窗。** 恰当检索 + 短上下文常常赢过长上下文塞满。
8. **评测长上下文必须多点、多干扰、多次运行**，只测大海捞针等于没测。
