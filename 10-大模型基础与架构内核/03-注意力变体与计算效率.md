# 注意力变体与计算效率

> **核心问题**：MHA / MQA / GQA 到底差在哪？FlashAttention 改了模型还是只改了算子？为什么推理时显存总是卡在 KV Cache 上？

---

## 0. 从一个瓶颈说起

自回归解码时，每生成一个 token 都要：

```
① 读一遍全部 K 和 V（旧 token 的）  ← 带宽瓶颈
② 算一次 attention                  ← 算力其实很闲
③ 算一次 FFN                        ← 算力很闲
```

**第 ① 步是真正的瓶颈**。原因：

- 每层要读 `2 × S × H_kv × d_head` 个元素
- **序列越长，读得越多**；而 FFN 的计算量与序列长度无关

> **所以推理优化的核心命题是：怎么少读 KV。**
> 这一章的所有变体，本质都在回答这一个问题。

---

## 1. MHA → MQA → GQA：减少 KV 头数

### 1.1 三者的区别

关键在于 **K/V 的头数（`H_kv`）可以和 Q 的头数（`H`）不一样**。

```
MHA (Multi-Head Attention):     Q: 32 头   K: 32 头   V: 32 头
MQA (Multi-Query Attention):    Q: 32 头   K:  1 头   V:  1 头
GQA (Grouped-Query Attention):  Q: 32 头   K:  8 头   V:  8 头
                                ↑
                        每 4 个 Q 头共享 1 组 K/V
```

**实现方式**：把 Q 的 32 个头分成 8 组，每组 4 个 Q 头共享同一个 K/V 头。
推理时 K/V 只算 8 份，但 Q 仍然 32 份。

### 1.2 KV Cache 的缩减倍数

```
KV Cache 显存 ∝ H_kv
```

| 转换 | KV 头数 | 显存缩减 |
|---|---|---|
| MHA (32) → MQA (1) | 1 | **32×** |
| MHA (32) → GQA (8) | 8 | **4×** |
| GQA (8) → GQA (4) | 4 | 8× |

**真实例子**：Llama-2-7B（MHA，32 KV 头）→ Llama-3-8B（GQA，8 KV 头），
在**上下文长度相同时 KV Cache 显存降到 1/4**。这就是为什么新模型普遍换 GQA。

### 1.3 质量代价

| 方案 | 质量 | 说明 |
|---|---|---|
| MHA | 基准 | KV 显存最大 |
| GQA | **≈ MHA** | 经验上几乎无损，是工业界默认 |
| MQA | 略降 | 最早的 GQA 论文报告在部分任务上有小幅下降，但**后续研究普遍显示可接受** |
| MQA + 分组 KV 头（MLA 的做法） | ≈ GQA | 见 §2 |

> **工程结论**：**选 GQA，不要选 MQA。**
> 除非你的场景是**极端显存受限**（比如单卡小显存跑长上下文），否则 MQA 省下的那点显存
> 换来的质量损失不划算。

### 1.4 代价在推理端而非训练端

GQA/MQA 的好处**只在推理（尤其是 batch=1 解码）时体现**：

| 场景 | 影响 |
|---|---|
| **训练 / 预填充**（算 QK^T） | KV 头数减少 → **计算量也减少**（Q 头多，K 头少要广播） |
| **解码**（读 KV） | KV 头数减少 → **显存和带宽都减少** ✅ |
| **大 batch 推理** | 算力瓶颈为主，KV 显存占比下降，收益变小 |

## 2. MLA（Multi-head Latent Attention，DeepSeek）

GQA 的折中方案：**不减少 KV 头数，而是把 K/V 先低秩压缩再缓存**。

```
传统 MHA:
   K = W_k · x        → 缓存 32 头 × 128 维 = 4096 维
   V = W_v · x        → 缓存 32 头 × 128 维 = 4096 维

MLA:
   c_kv = W_dkv · x   → 缓存 1 个低维向量（如 512 维）
   K = W_uk · c_kv    → 用时再「解压」回 32 头
   V = W_uv · c_kv
```

**收益**：KV Cache 从 4096×2 维降到 512 维 → **8× 缩减**，比 GQA 更狠。

**难点**：**解压需要重新投影**，意味着推理时要么
1. 缓存解压后的 K/V（省了显存但没省计算），或
2. 缓存低维向量 + 每步做投影（省显存但增加了计算）

DeepSeek 的解法：**RoPE 与低秩解耦**——K 的一部分（承载位置信息）
单独走一条全维路径，其余走低秩路径。工程复杂度显著高于 GQA。

> **工程结论**：MLA 是**大模型厂商在超大参数量下的选择**。
> 如果你部署的模型是 7B~70B 级别，主流开源模型基本都给了 GQA，不需要自己实现 MLA。

## 3. 滑动窗口注意力（Mistral）

```
每个 token 只看前 W 个 token（W 通常 4096）+ 少量 sink token
```

| 收益 | 代价 |
|---|---|
| KV Cache 变成 **O(W)** 而非 O(S) | **信息传递要靠多层堆叠**（每层 W 步，理论感受野 L×W） |
| 长上下文显存不随长度增长 | 短距离依赖多、远距离依赖弱的场景可能掉点 |
| 推理速度显著提升（KV 读取量固定） | 需要「重复 KV」（相邻层共享窗口）才能真正省 |

**适用**：长文档流式处理、目标是对话流做局部理解。

---

## 4. 稀疏注意力

**思路**：不是每个 token 都看所有 token，只看一部分。

| 方法 | 稀疏模式 | 代表 |
|---|---|---|
| **Longformer** | 滑窗 + 膨胀（dilated）+ 全局 token | 长文档分类 |
| **BigBird** | 随机 + 滑窗 + 全局 + 局部块 | 长序列任务 |
| **Sparse Transformer** | 跨步长度的 strided attention | 早期稀疏化 |

**通用结论**（有理论保证）：**局部 + 少量全局 + 随机，三者组合足以表达大多数任务依赖**。

> **但它们在今天的 LLM 里基本被淘汰了**——
> 因为 RoPE + GQA + FlashAttention 这套组合已经足够便宜，
> 稀疏注意力带来的**质量损失**（尤其对推理任务）不划算。

---

## 5. 线性注意力

**思路**：用核技巧把 `softmax(QKᵀ)V` 的复杂度从 O(S²d) 降到 O(Sd²)。

```
标准注意力:  softmax(QKᵀ)V     →  O(S²d)
线性注意力:  φ(Q)(φ(K)ᵀV)      →  O(Sd²)
```

| 方法 | 做法 |
|---|---|
| **Performer** | 随机特征近似 softmax 核（FAVOR+） |
| **Linformer** | 对 K/V 沿序列维做低维投影 |
| **Transformers are RNNs** | 核化 + 累积状态量 |

**致命缺陷**：**改变了注意力的数学定义**，是近似而非等价。
在需要精确检索的任务上掉点明显，而且**长序列下状态量会「挤爆」**（信息被平均掉）。

> **工程结论**：线性注意力在学术上有意义，在生产上基本不用。
> 原因很简单——**真正的瓶颈是访存，不是算力**，而线性注意力省的是算力。

---

## 6. FlashAttention：最重要的认知纠偏

> **⚠️ 这是本章最容易被误解的地方，请务必读清楚。**

**FlashAttention 没有改模型的数学定义。它是精确注意力（exact attention），不是近似。**

```
标准注意力（naive）:
   1. 把 Q, K, V 从 HBM 读到 SRAM
   2. 算 QK^T → 把 S×S 的注意力矩阵**写回 HBM**
   3. 再读回注意力矩阵 → 算 ×V
   → HBM 读写量 ∝ S²   ← 瓶颈

FlashAttention:
   1. 分块（tile）处理，永不把完整注意力矩阵写回 HBM
   2. 在 SRAM 里完成 softmax 的增量更新
   3. 反向时从输入**重算**中间值，而不是存下来
   → HBM 读写量 ∝ S   ← 降一个数量级
```

### 6.1 三个关键技巧

| 技巧 | 做什么 |
|---|---|
| **IO 感知分块** | 把 Q/K/V 分成能放进 SRAM 的 tile，tile 间用 online softmax 合并 |
| **反向重计算** | 反向传播时重算 S×S 矩阵而不是存着 → 用计算换显存 |
| **避免非 matmul 的 HBM 往返** | softmax、mask、dropout 全部在 SRAM 内完成 |

### 6.2 收益

| 指标 | 变化 |
|---|---|
| **显存** | 从 O(S²) 降到 **O(S)**（不分块写回） |
| **速度** | **2~4×**（A100/H100 上更明显） |
| **精度** | **完全一致**（与 naive 实现 bit-level 或 fp32 参考一致） |

### 6.3 FlashAttention-2 / -3 的改进

- **FA-2**：优化并行划分（按序列而非按头分块）、减少非 matmul 操作、更好的 warp 利用
- **FA-3**：针对 Hopper 的 **FP8 与异步** 支持，进一步压低 HBM 往返

### 6.4 怎么用

```python
# PyTorch 内置（PyTorch 2.0+）
with torch.nn.attention.sdpa_kernel(SDPABackend.FLASH_ATTENTION):
    out = F.scaled_dot_product_attention(q, k, v, is_causal=True)

# 框架通常自动调用
# vLLM / SGLang / transformers 都会在条件满足时选 FlashAttention
```

**什么时候不生效**（导致静默回退到慢路径）：

| 条件 | 原因 |
|---|---|
| head_dim 不是 8 的倍数（如 80、96 以外的奇数） | FA 要求 head_dim ∈ {32, 64, 96, 128, 256} |
| fp32 输入 | FA 需要 fp16/bf16 |
| 需要输出注意力权重 | FA **不返回**注意力矩阵 |
| 有自定义 mask（除 causal 外） | 部分版本不支持 |

> **工程结论**：**FlashAttention 是「免费的午餐」——不改数学、不掉精度、还更快更省显存。**
> 如果你的推理框架没启用它，那是配置问题，去查 backend 选择逻辑。

## 7. 算子层 vs 架构层：一张必须记住的表

这是本章最有价值的区分。**混淆这两层是新手最常犯的判断错误。**

| | **算子层** | **架构层** |
|---|---|---|
| 改什么 | **计算顺序 / 数据搬运** | **模型定义** |
| 数学 | **完全等价** | 改变了 |
| 旧权重能用吗 | **能** | **不能**（要重训） |
| 代表 | **FlashAttention、CUDA Graph、算子融合、torch.compile、KV Cache 分页** | **MHA/MQA/GQA、RoPE、MoE、滑动窗口、MLA、线性注意力** |
| 收益来源 | **访存与调度** | **参数/计算/显存结构** |
| 风险 | 极低（数值等价） | 高（掉点、需重训） |

**推论**：

1. **优先做算子层优化**——收益大、风险低、不用重训。
2. **改架构层意味着换模型**——不是「优化」，是「换一个模型来部署」。
3. 看到有人说「我们优化了注意力」，先问：**数学变了吗？**

> **一个常见误解**：有人以为 FlashAttention 「减少了计算量」。实际上
> **FlashAttention 的计算量反而略增**（因为重算），它省的是**显存带宽**。
> 在 GPU 上带宽是瓶颈，所以净收益为正。

## 8. 注意力 sink

**现象**：训练好的模型里，前几个 token（通常是 BOS）会**吸收大量注意力权重**，
哪怕它们没有实际内容。

**原因**：softmax 必须在所有位置上分配概率和。当某个 head「这一层没什么想看的」时，
它需要一个**垃圾桶**——BOS 就是那个垃圾桶。没有 sink 的话，
注意力会被强行分配到无意义的位置上，反而干扰了真正的注意力。

**StreamingLLM 的发现**：只要**保留最开始的 4 个 sink token + 最近的窗口**，
就能在流式生成中保持模型不退化，**不训练、不改模型**。

> **工程结论**：做流式/长上下文裁剪时，**不要只保留最近窗口，要保留开头几个 token**。
> 这是个只要几行代码但效果显著的区别。

## 9. 选型决策树

```
要选注意力方案
  ↓
模型已经训好了？
  ├─ 是 → 【算子层】确认 FlashAttention 生效
  │         → 检查 head_dim / dtype / 显存够不够放 KV Cache
  │         → 不够就上 KV Cache 量化 / 滑窗 / KV 淘汰
  └─ 否（要自己训）
        ↓
     目标是什么？
        ├─ 通用 LLM，最大化质量 → **GQA**
        ├─ 极致显存（边缘/单卡）→ MQA + KV 量化，或 MLA
        ├─ 超大参数（100B+）→ MLA（DeepSeek 路线）
        ├─ 超长流式文档 → 滑窗 + sink + KV 淘汰
        └─ 学术/特殊结构 → 稀疏/线性注意力（**注意掉点**）
```

### 9.1 训练自己模型时的默认答案

| 参数量 | 推荐 |
|---|---|
| < 1B | MQA 也行，省显存 |
| 1B ~ 70B | **GQA**，`G = H/4` 或 `H/8` |
| > 70B | GQA 或 MLA；MoE 见 [`05`](./05-MoE稀疏专家.md) |

## 10. 工程结论

1. **MQA/GQA 减少的是 KV 头数，不是注意力头数。** Q 头数不变，质量几乎不掉。
2. **默认选 GQA。** MQA 省的那点显存换来的质量损失通常不划算。
3. **FlashAttention 是算子层优化：数学完全等价、不掉精度、更快更省显存。**
   没启用就去查 backend，不是模型的问题。
4. **区分「算子层」和「架构层」是本领域最重要的判断力之一。**
   算子层优化=免费午餐；架构层改动=换模型。
5. **稀疏/线性注意力在生产上基本不用。** 因为真瓶颈是访存，而它们省的是算力。
6. **长上下文裁剪要保留开头的 sink token。** 只要几行代码，差别很大。
7. **FlashAttention 有静默回退的坑**：head_dim 不对齐、fp32、要输出注意力权重，
   都会回退到慢路径，而且**不报错**。
