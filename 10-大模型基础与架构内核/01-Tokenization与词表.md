# Tokenization 与词表

> **核心问题**：模型看到的到底是「字」还是「token」？为什么同样的中文句子，不同模型算出来的 token 数能差一倍？换 tokenizer 到底影响什么？

---

## 0. 一个必须先建立的直觉

**LLM 的基本单位不是字，也不是词，是 token。**

token 是 tokenizer 把文本切分后的最小单元。它可能是：

- 一个完整的常见词（`the`、`hello`）
- 一个词的一部分（`un` + `bel` + `ievable`）
- 一个汉字（多数中文 tokenizer 的常态）
- **半个汉字**（更细的 tokenizer 会把 UTF-8 字节拆开）
- 一个字节（极端情况）
- 一个空格（`Ġ` 这种带前缀标记的形式）
- **一个数字字符**（`2026` 通常被切成 `202` + `6` 或 `2`+`0`+`2`+`6`）

**为什么这件事重要**——因为它同时决定三个东西：

| 影响 | 机制 |
|---|---|
| **成本** | 计费按 token 数；同样一段话，token 多的模型更贵 |
| **上下文长度** | 上下文按 token 计；同样 32K 窗口，token 效率高的模型能塞更多内容 |
| **能力上限** | 被切成两半的词，模型要先「拼」才能理解；数字被拆散则直接损害算术能力 |

> **一句话**：tokenizer 是**整条流水线上最不起眼但影响最广的一环**。
> 换 tokenizer 换来的收益，常常被误以为是「模型变强了」。

---

## 1. 三种切分粒度

| 粒度 | 例子 | 优点 | 致命缺陷 |
|---|---|---|---|
| **字符级** | `h` `e` `l` `l` `o` | 无 OOV（未登录词）问题；中文天然友好 | **序列过长**，同一句话要几十上百个 token，注意力成本爆炸 |
| **词级** | `hello` `world` | 最短 | **OOV 问题**：词表装不下所有词，生僻词/人名/URL 直接变 UNK |
| **子词级** | `play` `ing` | 兼顾：无 OOV + 序列短 | 训练复杂度高，跨语言不均衡 |

**现代 LLM 全部用子词级。** 下面所有算法都是子词级算法的变体。

---

## 2. 三种子词算法

### 2.1 BPE（Byte-Pair Encoding）

GPT-2 起的事实标准。核心是**反复合并最高频的相邻符号对**：

```
起始：h e l l o _ w o r l d
      ↓ 统计频次，合并最高频对 "l"+"l" → "ll"
h e ll o _ w o r l d
      ↓ 继续合并 "o"+"r" → "or"
h e ll o _ w or l d
      ↓ ...
最终：hello _ world  （3 个 token）
```

**Byte-level BPE（GPT-2 的关键改进）**：不在 UTF-8 字符上做 BPE，而在**字节**上做。

```
"你好" → UTF-8: E4 BD A0 E5 A5 BD  (6 字节)
        → 常见组合被合并 → 可能 2~4 个 token
```

好处：
1. **永远不会 OOV**——任何字节序列都能被表示
2. **跨语言共享词表**——罕见语言的词可以退化成字节组合，不丢信息

### 2.2 WordPiece（BERT 系）

和 BPE 的区别：
- 不用频率，用**似然度**（合并后语言模型似然提升多少）
- 续接标记用 `##` 前缀：`play` + `##ing`
- 词表通常 30K 级别

### 2.3 SentencePiece / Unigram LM

Google 系（T5、Gemma、Qwen 部分版本）用的方案：

- **Unigram Language Model**（反向）：从**大词表**出发，**不断删除**贡献最小的子词
- 优点：
  - 训练可以用 EM 算法，比 BPE 快
  - 天然支持**多语言共享词表**（SentencePiece 的招牌能力）
  - 输出是概率，可以做多种切分（n-best / lattice）
- SentencePiece 同时支持 BPE 和 Unigram 两种模式

### 2.4 三者对比

| | BPE | WordPiece | SentencePiece(Unigram) |
|---|---|---|---|
| 合并方向 | 合并（正向） | 合并（正向） | **删除（反向）** |
| 合并依据 | 频率 | 语言模型似然 | 语言模型似然 |
| 训练速度 | 中 | 慢 | **快** |
| 多语言 | 需自行平衡 | 需自行平衡 | **原生支持** |
| 代表模型 | GPT-2~4、Llama、Qwen | BERT、DistilBERT | T5、Gemma、Qwen(部分) |
| 词表大小 | 32K~256K | 30K | 32K~256K |

> **实际差异没你想的那么大。** 大多数情况下，Llama 的 BPE 和 Qwen 的 Unigram 在中文上的表现差别，
> **远小于模型规模差异带来的差别**。不要为 tokenizer 过度优化。

## 3. 词表大小：一个被低估的工程参数

### 3.1 三角权衡

```
       词表大 (256K)
          ↓              ↑ 序列短（同样的文本 token 更少）
   ┌──────┴──────┐       │
   │  未知 token  │       │
   │  更少        │       │
   └──────┬──────┘       │
          ↓              │ 词表大
   词表小 (32K)    嵌入层参数 = 词表 × d_model
          ↓
   嵌入层巨大、罕见 token 训练不足、上下文占用高
```

**具体数字**（d_model=4096）：

| 词表大小 | Embedding + LM Head 参数 | 占 7B 模型比例 |
|---|---|---|
| 32K | 0.13B + 0.13B | ~3.7% |
| 128K | 0.52B + 0.52B | ~14.9% |
| 256K | 1.05B + 1.05B | ~30% ⚠️ |

> **256K 词表的模型里，约 30% 的参数在管 token 嵌入**——
> 这解释了为什么有些大词表模型的「小模型档位」性价比反而很差。

### 3.2 词表大小的真实收益

词表从 32K 涨到 128K：
- 英文：平均 token 数下降 ~15~25%
- **中文：下降可达 40~50%**（中文更需要细粒度）
- 推理成本：**几乎线性下降**（同样的问题，token 少 → prompt 缓存命中率高 → 便宜）

### 3.3 常见误区

| 误区 | 事实 |
|---|---|
| 「大词表 = 更好的模型」 | 词表只影响**效率**，不影响「智能」。质量由训练数据和训练方法决定 |
| 「换个 tokenizer 模型就变强了」 | 变的是**成本和上下文容量**。智能不变 |
| 「小模型也要用大词表」 | 小模型 embedding 层占比过高，**挤压了真正的推理层参数** |

## 4. 中文场景的特殊性

### 4.1 UTF-8 回退

中文常用字在 UTF-8 里是 3 字节。如果 tokenizer 的词表没覆盖到这个字，
它会退化成 **3 个字节 token**（或 2 个 token 的组合）。

```
"你好" 
  好词表覆盖 → 2 tokens（你好 各 1）
  词表未覆盖 → 最多 6 tokens（E4 BD A0 | E5 A5 BD）
```

**这就是为什么不同模型的中文成本能差 2~3 倍。**

### 4.2 中英混排的碎片化

```
"使用 YOLO 训练模型"
→ 有词表覆盖时：使用 | YOLO | 训练 | 模型    （4 tokens）
→ 无覆盖时：  使用 | Y | OL | O | 训练 | 模型  （6 tokens）
```

**英文缩写、技术术语、代码符号是碎片化重灾区**。做 RAG 或 Agent 时，
上下文里全是技术词，token 效率的差异会被放大。

### 4.3 一段实测参考（口径：`tokenizer` 自带 `encode`）

> **⚠️ 口径警告**：下表为**示例值**，不同 tokenizer 版本、不同
> `add_special_tokens` 设置会不同。**请用自己模型的 tokenizer 实测。**

| 文本 | 字符数 | Byte 级 BPE | 细粒度中文词表 |
|---|---|---|---|
| `你好，世界` | 5 | 6~9 | 2~3 |
| `使用 YOLO 训练模型` | 15 | 8~12 | 6~9 |
| `def forward(self, x):` | 20 | 7~9 | 7~9 |
| `https://example.com/docs?q=1` | 29 | 12~16 | 12~16 |
| 一段中文技术文档（1000 字） | 1000 | ~1000~1400 | ~600~900 |

**规律**：**纯中文 + 大词表最划算；英文/代码几乎不划算**（因为英文本来就该按词切）。

## 5. 数字：一个容易被忽略的坑

**几乎所有主流 tokenizer 都会把连续数字拆成单个数字 token。**

```
"2026" → ["202", "6"]  或  ["2", "0", "2", "6"]
```

**为什么**：数字是**开放类**——你无法枚举所有可能的数字。
按频率合并会让 `12345` 和 `99999` 各占一个词表位置（组合爆炸），
而且合并后的数字 token **无法自然地表示未见过的数字**。

**代价**：
1. **算术能力受损**——`1+1` 变成 4 个 token，模型要学「逐位加法」
2. **数字 token 多**——一串 ID（订单号、手机号）会消耗大量 token
3. **数字对齐在下游任务上会掉点**

### 5.1 缓解手段

| 手段 | 说明 |
|---|---|
| **按位数分段** | 部分 tokenizer 对 3 位数字整体建词（`123`），兼顾对齐与组合数 |
| **预处理** | 把长数字串用分隔符切开（如订单号每 4 位插 `_`），让模型学「按段读」 |
| **字符级算术任务** | 算术任务直接用字符级输入，绕开数字分词 |
| **工具外置** | **最佳解**：算术交给 Python/计算器工具，模型只负责决定「要不要算」 |

> **这正是 Agent 工具调用的价值所在之一**：把精确计算从「模型能力」变成「工具能力」。
> 见 [`../07-Agent与智能体/05-工具调用与MCP协议.md`](../07-Agent与智能体/05-工具调用与MCP协议.md)。

## 6. 特殊 token 与 chat template

### 6.1 常见特殊 token

| token | 作用 |
|---|---|
| `<pad>` | 补齐到固定长度（训练用，推理一般不用） |
| `<bos>` / `<s>` | 序列开始 |
| `<eos>` / `</s>` | 序列结束，**生成时用它停止** |
| `<unk>` | 未知词（byte-level BPE 下基本不会出现） |
| `<mask>` | 掩码（BERT 系预训练用） |
| `<|im_start|>` / `<|im_end|>` | 对话轮次边界（ChatML 格式） |
| `<|user|>` / `<|assistant|>` / `<|system|>` | 角色标记 |
| 工具调用标记 | 部分模型用专用 token 序列化 function call |

### 6.2 chat template 是什么

**对话格式不是模型自己发明的，是 tokenizer 配套的模板。**

```python
# 伪代码
messages = [
    {"role": "system", "content": "你是一个助手"},
    {"role": "user", "content": "你好"},
]
text = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
```

**用错模板的后果**（这是模型「答非所问」的高频原因）：

| 错误 | 表现 |
|---|---|
| 忘了加 generation prompt | 模型继续扮演用户，不回答 |
| 用了别的模型的模板 | 角色混乱、格式崩坏、**输出不收敛** |
| 模板版本对不上 | 官方升级模板后旧 prompt 全部失配 |

> **工程结论**：**永远用 `tokenizer.apply_chat_template()`，不要手拼字符串。**
> 模板变了模型就变了，这是最容易踩的「版本陷阱」之一。

### 6.3 停在哪：停止 token 的选择

| 策略 | 说明 |
|---|---|
| **`<eos>`** | 最常见。模型训练时学会在回答结束处输出它 |
| **`<|im_end|>`** | ChatML 系 |
| **专用 stop string** | 文本级停止串，如 `\n\nHuman:`。**依赖模型学到停止符** |
| **max_tokens 兜底** | 必设。否则模型可能永不停止 |

## 7. 换 tokenizer 的坑

### 7.1 扩展词表的正确做法

**加新 token ≠ 加几行代码。** 完整步骤：

```
1. 统计业务语料的新 token 频率
2. 扩展词表（vocab_size += N）
3. **随机初始化** 新 token 的输入 embedding 和 LM head 行
4. 重训（至少部分层），否则新 token 的 embedding 是噪声
5. 重新校准（必要时调整 RMSNorm 与 lm_head 的初始化尺度）
```

**只扩词表不重训 = 模型输出乱码。** 新 token 的 embedding 初始是随机的，
模型从没见过，等价于给了一条随机指令。

### 7.2 换 tokenizer 的代价

| 影响 | 说明 |
|---|---|
| **embedding 层不兼容** | 老 embedding 不能直接用（词表 id 语义变了） |
| **序列长度变化** | 同一批数据 token 数变了 → 训练时的 packing 策略要重调 |
| **评测基线失效** | 旧的 mAP / perplexity 不能直接对比 |
| **成本重算** | 所有成本估算要按新 tokenizer 重算 |

## 8. 实操：用 tokenizer 做成本预估

这是 FDE / 落地场景里最高频的估算需求。

```python
from transformers import AutoTokenizer

tok = AutoTokenizer.from_pretrained("你的模型")

def estimate_cost(prompt: str, output_tokens: int, price_in: float, price_out: float):
    n = len(tok.encode(prompt))
    return {
        "input_tokens": n,
        "output_tokens": output_tokens,
        "total_tokens": n + output_tokens,
        "cost": n / 1e6 * price_in + output_tokens / 1e6 * price_out,
    }

# 关键：同一个问题，在不同模型上的 token 数差多少
prompt = "请阅读以下技术文档并回答问题：\n" + doc + "\n问题：..."
for model in ["模型A", "模型B", "模型C"]:
    tok = AutoTokenizer.from_pretrained(model)
    print(model, len(tok.encode(prompt)))
```

### 8.1 估算时必须带上 tokenizer

**「10 万 token 的上下文」这句话是没意义的**，除非说清楚：
- 哪个模型的哪个 tokenizer
- 中文还是英文
- 什么内容（代码 / 自然语言 / JSON）

**报告模板**：

> 上下文占用：`<文档名>` 共 12,400 token（`<模型>` / `<tokenizer>`，含系统提示 380 token）。

### 8.2 提示缓存的影响

| 场景 | 缓存命中 | 成本影响 |
|---|---|---|
| 多轮对话 | 前缀稳定 → 命中率高 | 输入成本可降到 1/10 量级（视厂商） |
| RAG 固定知识库 | 系统提示 + 知识库稳定 → 命中 | **必须把变化的部分放最后** |
| Agent 多步 | 每步的观察不同 → 前缀稳定 | 工具定义放前面 |

> **tokenizer 决定了「前缀边界」在哪**：改一个字都会让后面全部缓存失效。
> 见 [`../07-Agent与智能体/06-记忆与上下文工程.md`](../07-Agent与智能体/06-记忆与上下文工程.md)。

## 9. 评测 tokenizer 的四个指标

选型或换词表时，看这四个：

| 指标 | 怎么测 | 为什么重要 |
|---|---|---|
| **压缩率** | `字符数 / token 数` | 直接决定成本 |
| **跨语言一致性** | 中/英/代码各自的压缩率是否接近 | 决定多语言场景的公平性 |
| **未登录率** | 语料中落到 byte 回退的比例 | 太高说明词表覆盖不足 |
| **下游掉点** | 换 tokenizer 重训后评测集分数 | 唯一真正重要的指标 |

### 9.1 压缩率实测脚本

```python
def compression(tok, texts):
    ratios = []
    for t in texts:
        n = len(tok.encode(t))
        ratios.append(len(t) / max(n, 1))
    return sum(ratios) / len(ratios)

print("中文压缩率:", compression(tok, chinese_samples))
print("英文压缩率:", compression(tok, english_samples))
print("代码压缩率:", compression(tok, code_samples))
```

> **判据**：中英压缩率差异 > 2 倍 → 词表对某一语言明显偏斜；
> 代码压缩率 < 3 → 技术文档场景成本会很高。

## 10. 工程结论

1. **token 是计费单位、上下文单位、也是能力单位。** 谈「多少 token」时必须说清 tokenizer。
2. **词表大小影响效率不影响智能。** 大词表省 token，但小模型的 embedding 层会被撑大。
3. **中文 + 大词表最划算；英文和代码几乎不划算。** 代码符号天然碎片化。
4. **数字被拆散是算术能力差的根因之一。** 精确计算应该交给工具，不是交给模型。
5. **永远用 `apply_chat_template()`。** 手拼字符串是「模型突然变傻」的高频原因。
6. **换 tokenizer 必须重训 embedding。** 只扩词表 = 给模型塞随机指令。
7. **成本预估必须连 tokenizer 一起报。** 否则数字无法复现。
8. **前缀稳定性比上下文长度更值钱。** 缓存命中率的收益通常大于多买几个 token 的窗口。
