# VLM 推理优化与端侧可行性

> **核心问题**：VLM 推理慢在哪？端侧到底能不能跑 VLM？如果不能，那应该跑什么？

---

## 0. 三段延迟拆解

```
用户请求
   │
   ├─ ① 视觉编码器前向     ← 与图片数量 × 分辨率成正比（近似线性）
   ├─ ② LLM prefill        ← O(S²)，S = 视觉 token + 文本 token
   ├─ ③ LLM decode         ← 与输出长度成正比，带宽密集
   └─ ④ 视觉特征缓存命中？  ← **命中则跳过 ①**
```

| 阶段 | 瓶颈 | 主要优化 |
|---|---|---|
| **① 视觉编码** | **算力**（ViT 的 attention 有 flash 优化） | 量化、剪枝、**缓存**、降分辨率 |
| **② prefill** | **算力**（O(S²)） | 减 token、FlashAttention、chunked prefill |
| **③ decode** | **显存带宽** | GQA、KV 量化、投机解码（见 [`../10`](../10-大模型基础与架构内核/)） |

> **一个关键的结构差异**：
> VLM 的 prefill **天然比纯文本重得多**（S 里有几千个视觉 token），
> 所以 **TTFT 是 VLM 的主要瓶颈**，而纯文本场景的瓶颈在 decode。

## 1. 视觉侧的五种优化

### 1.1 权重量化

| 精度 | 体积 | 加速 | 精度影响 |
|---|---|---|---|
| FP16/BF16 | 1.0× | 1.0× | 基准 |
| **INT8** | 0.5× | 1.2~2× | 很小（视觉编码器对量化较鲁棒） |
| **INT4** | 0.25× | 1.5~3× | 中（密集特征任务影响更大） |

> **视觉编码器是「量化友好」的**——它只做特征提取，
> 不直接输出结论。**INT8 通常是安全的选择**。

### 1.2 视觉 token 压缩

见 [`03`](./03-视觉token化与数量级代价.md) §1.6：
Pixel Shuffle（固定 4×）、Token Pruning（动态 30~70%）、Token Merging。

> **推理端的动态剪枝比训练端更划算**——
> 它不需要重训模型，可以在运行时按注意力分数挑 token。

### 1.3 分辨率自适应

**按任务/按输入动态选分辨率**，而不是固定最高：

```
先跑一遍低分辨率（577 token）
  → 置信度够 → 直接返回
  → 置信度不够 → 重新用高分辨率跑一遍
```

> **「级联推理」模式**：简单输入便宜，疑难输入才上高分辨率。
> 这在批量业务场景里能省下大部分成本。

### 1.4 视觉编码器剪枝

**按层剪**：早期层是通用低级特征，可以剪掉一部分；
或者用更小的视觉编码器（MobileCLIP / EfficientViT）替换。

### 1.5 视觉特征缓存 ★

**这是 VLM 场景下最容易被忽略、也最有效的一条。**

**原理**：视觉编码器是**确定性的**——同一张图编码多次结果完全一样。

| 场景 | 缓存收益 |
|---|---|
| **多轮追问同一张图** | **省掉 ②×N 次视觉编码** |
| **RAG / 批量处理里图片重复** | 按图片哈希命中 |
| **同一文档多页被反复引用** | 按页缓存 |
| **Agent 循环里反复看同一图** | **直接消除循环里的视觉开销** |

**缓存的键与空间**：

```python
# 键：图片内容哈希（不是 URL，URL 可能变）
key = sha256(image_bytes)

# 值：Projector 之后的特征（LLM 嵌入空间的 token）
# 577 token × 4096 dim × 2 bytes ≈ 4.7 MB / 图
# 2880 token × 4096 dim × 2 bytes ≈ 23.6 MB / 图
```

> **注意缓存的空间账**：高分辨率图的特征缓存很占空间。
> 要么限制缓存大小（LRU），要么**用低分辨率特征做缓存**。

### 1.6 视觉 token 的 KV 缓存

**更进一步**：如果视觉 token 放在 prompt 开头，
那么**整个前缀（含视觉 token）的 KV 可以被前缀缓存复用**。

```
[视觉 token 577][系统提示][历史对话][当前问题]
└──────────── 前缀稳定 ────────────┘
       ↓
   厂商的 prompt caching 直接命中
```

> **所以「图片放最前面」不只是位置效应考虑，也是缓存考虑。**
> 这与 [`../07-Agent与智能体/06-记忆与上下文工程.md`](../07-Agent与智能体/06-记忆与上下文工程.md)
> 的「前缀稳定性」原则完全一致。

## 2. 端侧可行性：算三笔账

**判断端侧能不能跑 VLM，要算三笔账：**

```
① 显存够吗？   权重 + KV Cache + 激活 ≤ 设备内存
② 速度够吗？   用户能接受多少秒？
③ 质量够吗？   小模型在业务任务上够用吗？
```

### 2.1 三类设备的账

| 设备 | 内存 | NPU 算力 | 可跑什么 | 判断 |
|---|---|---|---|---|
| **ESP32-P4** | 32 MB PSRAM + 数百 KB SRAM | **无 NPU**（仅 RISC-V 向量扩展） | **专用小 CNN**（目标检测、分类、唤醒词） | **不能跑 LLM，更不能跑 VLM** |
| **RK3588S** | 8 GB LPDDR4/4GB | ~6 TOPS NPU | **0.5~2B 小 LLM**（量化后）、小 VLM（极慢） | **能跑极小的，多模态基本不现实** |
| **手机 / 平板** | 4~12 GB | 10~40 TOPS NPU | **1~3B 量化 VLM**（几秒级） | **可做离线助手，不适合实时** |
| **树莓派类 SBC** | 4~8 GB | 无/弱 | CPU 量化 LLM（**token/s 个位数**） | **勉强能用，体验差** |

> **ESP32-P4 的定位必须说清楚**：
> 它是**视觉前端**（摄像头 + 小 CNN 检测 + 特征提取），
> **不是 VLM 主机**。
> 它和 VLM 的正确关系是：**端侧出结构化事件，云端做理解**。

### 2.2 一个具体的可行性算例

**假设要在 RK3588S 上跑一个 1.5B 的量化模型：**

| 项 | 计算 | 结果 |
|---|---|---|
| 权重（INT4） | 1.5B × 0.5 B | 0.75 GB |
| KV Cache（2K 上下文） | 2048 × ~64 KiB | 128 MB |
| 激活与工作区 | — | ~500 MB |
| **合计** | | **~1.4 GB** ✅ 装得下 |

**速度**：NPU 上小模型的生成速度通常是**个位数到十几 token/s**
（取决于模型、算子支持度、量化格式）。

> **结论：装得下，但慢。**
> **端侧 VLM 只适合「离线、无强实时要求、低频」的场景。**

### 2.3 质量这一关

**小模型在多模态上的掉点比纯文本更严重**：

| 能力 | 小模型（1~2B） | 大模型（7B+） |
|---|---|---|
| 整体描述 | 尚可 | 好 |
| 细粒度定位 | **差** | 好 |
| OCR | **差很多** | 好 |
| 复杂推理 | **差** | 好 |
| 指令跟随 | 中 | 好 |

> **结论**：**端侧小 VLM 的能力上限很低**，
> 复杂视觉推理任务基本不适用。

## 3. 更好的端侧架构：检测器 + 文本 LLM

**这是本库最该被强调的一个架构判断。**

```
┌──────────────── 端侧（便宜、低延迟、离线）────────────────┐
│  摄像头                                                          │
│    ↓                                                             │
│  专用视觉模型（YOLO / 分类 / 分割，INT8 量化）                    │
│    ↓  输出结构化事件                                             │
│  结构化事件 = {类别、置信度、坐标、数量、跟踪ID、区域特征}          │
└─────────────────────────────┬──────────────────────────────────┘
                              ↓  （窄带宽、可信、可缓存）
┌──────────────── 云端 / 边缘服务器（贵、强）───────────────────┐
│  文本 LLM（或 VLM）                                              │
│    输入：结构化事件 + 业务上下文 + 规则知识                       │
│    输出：判断、建议、报告、工单                                     │
└──────────────────────────────────────────────────────────────────┘
```

### 3.1 为什么这个架构更好

| 维度 | 「端侧 VLM」 | 「检测器 + 文本 LLM」 |
|---|---|---|
| **端侧显存** | 1.4 GB+（含 LLM） | **几十 MB**（只放检测器） |
| **端侧算力** | 勉强 | **宽裕**（小 CNN 很快） |
| **延迟** | 几秒~几十秒 | **端侧 <100ms**，云端按需 |
| **网络依赖** | 强（否则能力受限） | **弱**（只传结构化事件） |
| **可审计** | 差（黑箱） | **好**（有明确的检测结果可查） |
| **可回溯** | 难（说不清模型看到了什么） | **好**（有坐标和置信度） |
| **隐私** | 原图可能上传 | **只传结构化事件，原图不出端** |
| **扩展性** | 换任务要换模型 | **云端改提示词即可** |

> **最后两行是决定性的**：
> 「检测器 + 文本 LLM」把**感知**与**理解**分开，
> 感知可验证、可追溯、可在端侧离线完成，理解可以随时升级。

### 3.2 这正是本库 04 主线在做的事

[`../04-边缘部署与端侧AI/`](../04-边缘部署与端侧AI/) 整条主线——
ESP32 端侧视觉栈、RK3588S 的 NPU 部署、ESP-DL 推理框架、
农业病虫害的端云协同——**全部是这个架构**。

> **所以当有人问「要不要在端侧上 VLM」时，
> 正确的回答通常是：「先把检测器做到位，把结构化事件传好，
> 云端用文本 LLM 做判断。」**

### 3.3 什么时候端侧真的需要 VLM

| 情况 | 判断 |
|---|---|
| **需要「看图理解」而非「识别」** | 端侧 VLM 有意义 |
| **完全离线、无网** | 端侧小模型 + 简单任务 |
| **隐私要求原图不能出院** | 用结构化事件方案（更好） |
| **实时性要求 <1s** | 检测器方案；VLM 做不到 |
| **任务是固定类目** | 检测器方案；VLM 是浪费 |

## 4. 边缘-云协同的三种模式

| 模式 | 端侧做什么 | 云端做什么 | 适用 |
|---|---|---|---|
| **A 全端侧** | 检测 + 规则 + 小模型 | 无 | 无网、隐私极致 |
| **B 端侧感知 + 云端理解** | 检测/跟踪/提取 | LLM/VLM 判断 | **最常用** |
| **C 端侧初筛 + 云端复核** | 便宜模型过滤 | 强模型处理疑难 | 成本敏感 |

### 4.1 模式 B 的接口设计

**端云之间传的应该是「结构化事件」，不是原图，也不是自由文本。**

```json
{
  "ts": "2026-11-16T10:00:00Z",
  "device_id": "<设备 ID>",
  "scene": "assembly_line_3",
  "events": [
    {
      "type": "defect",
      "label": "scratch",
      "confidence": 0.91,
      "bbox": [120, 340, 80, 22],
      "severity_hint": null,
      "crop_ref": "<可选：裁剪图引用>"
    }
  ],
  "counts": {"total": 12, "by_label": {"scratch": 1, "dent": 0}}
}
```

**设计要点**：

| 要点 | 原因 |
|---|---|
| **结构化优先** | 云端 LLM 处理结构化数据的准确率远高于处理自由描述 |
| **带置信度** | 云端据此决定是否需要看原图或复核 |
| **带坐标** | 支持「区域级」的追问 |
| **事件而非帧** | 降低带宽与噪声（同一目标在多帧里重复） |
| **可增量** | 事件流天然适合增量处理 |

> **「事件而非帧」是一个关键设计**：
> 摄像头每帧 1 张图，30fps 就是 30 张/秒；
> 但真正有意义的事件可能几分钟才一个。
> **传事件把带宽降一到三个数量级。**

## 5. 一个完整的 VLM 推理优化清单

```
① 视觉侧
   □ 视觉编码器 INT8 量化
   □ 视觉特征缓存（按图片哈希）
   □ 视觉 token 压缩（Pixel Shuffle / 动态剪枝）
   □ 分辨率自适应 / 级联推理
   □ 图片放 prompt 开头（利于前缀缓存）

② LLM 侧（见 10 主线）
   □ FlashAttention 生效
   □ GQA 模型优先
   □ KV Cache 量化
   □ 连续批处理 + chunked prefill
   □ 投机解码（接受率 > 0.7 才有意义）

③ 架构侧
   □ 前缀缓存 / RadixAttention（Agent 场景）
   □ 视觉 token 与文本 token 分预算
   □ 文档场景先 OCR
   □ 端侧用「检测器 + 结构化事件」而非 VLM

④ 工程侧
   □ 视觉特征缓存的容量上限（LRU）
   □ 超时与降级（视觉编码失败 → 规则路径）
   □ 单次调用的 token 预算硬上限
   □ 成本看板：按「请求数 × 视觉 token 数」维度
```

## 6. 工程结论

1. **VLM 的主要瓶颈是 TTFT（prefill）**，因为视觉 token 让序列长一到两个数量级。
2. **视觉特征缓存是 VLM 场景性价比最高的优化**——
   视觉编码器是确定性的，多轮追问同一张图可以完全跳过它。
3. **图片放 prompt 开头**，既利于位置效应，也利于前缀缓存命中。
4. **端侧跑完整 VLM 不可行**：ESP32-P4 只能做视觉前端，RK3588S 只能跑 0.5~2B 的小模型且很慢。
5. **「检测器 + 结构化事件 + 云端文本 LLM」是更好的架构**——
   显存、延迟、可审计、可回溯、隐私、扩展性六项全面占优。
6. **端云之间传「事件」而不是「帧」**，带宽能降一到三个数量级。
7. **视觉编码器量化友好**（INT8 安全）；但**小模型的多模态掉点比纯文本严重**
   （OCR、定位、复杂推理尤其明显）。
8. **文档场景先 OCR**，不要直接喂高分辨率图。
9. **级联推理（先低分辨率，不够再高）**在批量业务里能省大部分成本。
