# 视觉 token 化与数量级代价

> **核心问题**：一张图变成多少 token？这些 token 有多贵？为什么「给 VLM 看高清图」经常不划算？

---

## 0. 一条公式定全局

```
LLM 序列长度 = 视觉 token 数 N + 文本 token 数 T
```

**视觉 token 数由三件事共同决定**：

```
N = f( 视觉编码器输出粒度 , 分辨率策略 , 压缩层 )
```

| 方案 | 典型 N |
|---|---|
| 全图 224px（ViT-L/14） | 257 |
| 全图 336px | 577 |
| 切片 2×2 + 全局（LLaVA-1.5） | **2880** |
| 动态分辨率（Qwen-VL / InternVL，上限 1024~2048） | 1024~2048 |
| 像素级降采样（Pixel Shuffle 4:1） | 256~512 |
| 区域/目标级（Set-of-Mark） | **50~200** |

> **注意这个跨度：从 50 到 2880，差 57 倍。**
> 而模型的「看图能力」提升**远没有** 57 倍。
> **这就是全部成本讨论的起点。**

---

## 1. 六种 token 化方案

### 1.1 方案一：全图固定分辨率

```
整张图缩放到 224×224 → ViT → 257 个 token
```

| 优点 | 缺点 |
|---|---|
| 最简单、最快、最便宜 | **细节丢失严重**——小字、小物体直接没了 |
| token 数可预测 | 对文档/图表基本不可用 |

> **适合**：整体场景理解、粗分类、「图里有什么」。

### 1.2 方案二：切片（Tiling）

```
原图 → 切成 2×2 块 → 每块独立编码 → 拼成一个序列
     + 额外加一张整体缩略图（提供全局上下文）
```

**LLaVA-1.5 的方案**：4 个 336px 局部 + 1 个 336px 全局 = **5×576 = 2880 token**。

| 优点 | 缺点 |
|---|---|
| 局部细节保留好（OCR、小物体） | **token 数暴增** |
| 实现简单（几乎不用改代码） | 切片边界可能切断物体 |
| 全局图提供上下文 | 全局+局部有冗余 |

**切片数量的权衡**：

| 切片数 | token 数 | 何时用 |
|---|---|---|
| 1（无切片） | 576 | 粗粒度场景 |
| 2×2 + 全局 | 2880 | 通用 |
| 3×3 + 全局 | 3456 | 文档/图表 |
| 4×4 + 全局 | 6912 | 高分辨率文档（**贵**） |

> **切片数从 4 涨到 16，token 数翻 2.5 倍，效果提升通常远小于 2.5 倍。**

### 1.3 方案三：动态分辨率

**保持原始宽高比**，按比例缩放到 token 预算内：

```
原图 800×600 → 缩放到 (W', H') 使 (W'/P)×(H'/P) ≤ budget
              → token 数 = (W'/P)×(H'/P) + 1
```

| 优点 | 缺点 |
|---|---|
| **不拉伸变形**（长宽比保持） | 需要模型支持变长位置编码 |
| token 数可控（设预算） | 极端长宽比下细节仍不足 |
| 无冗余（不像切片要额外全局图） | **实现复杂度高**（动态分辨率的 position embedding 要插值） |

**这是现代 VLM 的主流方案**（Qwen-VL、InternVL）。

### 1.4 方案四：区域/目标级（Set-of-Mark）

**思路**：不把整张图塞进去，而是：
1. 用检测器/分割器找出图里的**显著目标**
2. 给每个目标画一个**带编号的标记框**
3. 把「带标记的图」+「每个标记的裁剪图」给 VLM

| 优点 | 缺点 |
|---|---|
| **token 数极小（50~200）** | **依赖前端检测器**——检测漏了，模型就看不见 |
| 目标区域细节最好（裁剪后可以高分辨率） | 前端检测器成了新的瓶颈与失败点 |
| 天然支持「回答里有几个」「左边那个是什么」 | 多一次检测的延迟与成本 |

> **这是一个「架构上把问题外包出去」的方案**：
> 用一个**便宜的专用模型**（检测器）替代**贵的大模型 token**。
> 这正好呼应 [`../02-视觉检测模型/`](../02-视觉检测模型/) 整条主线的存在意义。

### 1.5 方案五：目标符号（Object Symbol）

**Kosmos-2 式的做法**：把每个检测目标编码成**一个专门的 token**（`<obj_1>`），
和它的「属性描述」一起放进序列。

```
<image> <obj_1> 一只橘猫 <obj_2> 一张木桌 <obj_3> 一个杯子
```

| 优点 | 缺点 |
|---|---|
| token 数极小且**语义化** | **只能表达「有什么」，不能表达「长什么样」** |
| 与文本 token 天然融合 | 视觉细节完全依赖属性描述文本 |
| 适合做「检测 + 属性问答」 | 空间关系需要额外编码 |

> **对象符号 + 裁剪图**（方案四 + 五的组合）是很多「结构化视觉问答」系统的实际做法。

### 1.6 方案六：压缩与剪枝

**在进入 LLM 之前把 token 数量降下来。**

| 方法 | 做法 | 压缩比 |
|---|---|---|
| **Pixel Shuffle** | 空间相邻的 2×2 或 4×4 patch 合并成 1 个 token | 4× / 16× |
| **Token Pooling** | 相邻 token 池化 | 2×~4× |
| **Token Merging** | 相似 token 合并（类似 ToMe） | 动态 |
| **Token Pruning** | 按重要性丢弃冗余 token（如 LLaVA-PruMerge） | 动态 30~70% |
| **Importance-based** | 用 attention 分数挑重要 token | 动态 |

> **Pixel Shuffle 是最省事的**：不改变架构、不需要训练、压缩比固定。
> 代价是**空间精度下降**——「这个像素在哪」的精度下降 2~4 倍。

## 2. 数量级账（一张表看清代价）

**以 Llama-3-8B（GQA, 128 KiB KV/token）为例。**

| 场景 | 视觉 token | 文本 token | 序列总长 | **单图 KV Cache** |
|---|---|---|---|---|
| 全图 224 | 257 | 100 | 357 | 44 MB |
| 全图 336 | 577 | 100 | 677 | 85 MB |
| 切片 2×2+全局 | 2880 | 100 | 2980 | **373 MB** |
| 动态 1024 | 1024 | 100 | 1124 | 141 MB |
| 动态 4096 | 4096 | 100 | 4196 | **525 MB** |
| 区域级（50） | 50 | 100 | 150 | 19 MB |

> **关键观察**：
> **一张 2880 token 的图，光 KV Cache 就 373 MB**——
> 比模型权重的一半还多。
> **多图、多轮对话场景下，KV Cache 会直接爆掉。**

### 2.1 多图场景的放大

| 场景 | 视觉 token 合计 | KV Cache |
|---|---|---|
| 单图问答（577） | 577 | 72 MB |
| **5 图对比**（577×5） | 2885 | **353 MB** |
| **10 页文档**（2880×10） | 28800 | **3.5 GB** ⚠️ |
| 多轮追问 ×5 轮（同一图，**不缓存**） | 2880×5 | 1.8 GB ⚠️ |

> **最后一行是最冤的**：同一张图的视觉 token 被**重复编码了 5 次**。
> **缓存视觉特征就能省掉 80% 的视觉侧计算**（见 [`05`](./05-VLM推理优化与端侧可行性.md)）。

## 3. 边际收益递减

**这是本章最重要的判断。**

```
视觉 token:   256  →  576  →  1440  →  2880  →  5760
任务效果:     ↑        ↑          ↑          ↑
边际收益:   高      中         低        很低       接近 0
成本:        1×     2.25×     5.6×     11.25×    22.5×
```

**为什么收益递减**：

| 原因 | 说明 |
|---|---|
| **冗余** | 天空、墙面等大面积区域产出大量几乎相同的 token |
| **注意力稀释** | token 越多，**单个 token 分到的注意力越少**（Lost in the Middle 的多模态版） |
| **上下文位置效应** | 关键信息在中间时更容易被忽略 |
| **模型已学会压缩** | 视觉编码器本身已经做了特征抽象，再堆 token 是重复劳动 |

> **一个反直觉但可靠的结论**：
> **对大多数业务场景，「视觉 token 数量」应该按任务需求定，而不是按「分辨率越高越好」定。**
> 问「这是什么型号的设备」用 577 token 就够；
> 问「这张发票上的金额是多少」才需要 2880+。

## 4. OCR vs 视觉 token：文档场景的岔路口

**处理文档/表格/票据时，有两条完全不同的路：**

| | **路线 A：视觉 token** | **路线 B：先 OCR 再文本** |
|---|---|---|
| 做法 | 图直接给 VLM | 先用 OCR 引擎转成文本，再喂文本 LLM |
| token 数 | 1000~6000 | **200~500**（纯文本） |
| 精度 | 版面复杂的表格容易错位 | **数字与文字精确**（OCR 专门优化过） |
| 布局信息 | **保留**（模型能看到排版） | **丢失**（除非专门编码版面） |
| 成本 | 高 | **低** |
| 延迟 | 高 | 中（多一次 OCR） |

### 4.1 怎么选

| 文档类型 | 建议 | 原因 |
|---|---|---|
| **合同 / 报告 / 说明书**（文字为主） | **路线 B（OCR + 文本 LLM）** | 文字量大、成本敏感、文本 LLM 更强 |
| **表格 / 票据 / 财报** | **路线 B + 版面编码** | 数字精度是第一位 |
| **图表 / 示意图 / 照片** | **路线 A（视觉）** | OCR 读不了图表的语义 |
| **混合** | **两者都做，分流** | 按页/按块判断 |

> **一个被低估的组合**：
> **OCR 文本 + 视觉 token 一起喂**（双通道）。
> 文本保证精确，视觉补回版式与图表语义。token 成本翻倍但精度明显更好。

### 4.2 一个重要的成本对比

| 方案 | 200 页 PDF 的 token 总量（估） |
|---|---|
| 全视觉（每页 2880） | **576,000** ⚠️ |
| 全 OCR 文本 | **~120,000** |
| 分流（70% OCR + 30% 视觉） | **~260,000** |

> **长文档场景，「先 OCR」常常能省 4~5 倍成本**，而且数字更准。

## 5. 计算与显存代价

### 5.1 三个环节的耗时

```
① 视觉编码器前向   ← 与图片数量成正比，与分辨率成正比（平方）
② LLM prefill      ← O(S²)，S = 视觉 token + 文本 token
③ LLM decode       ← 与输出长度成正比
```

**关键**：
- **① 是线性于 token 数**（ViT 的 attention 有 flash 优化，接近线性）
- **② 是平方于 token 数**（即使有 FlashAttention 也是 O(S²) 计算，只是省了显存）

> **所以 token 从 1000 涨到 2000：视觉编码慢 2×，prefill 慢 4×。**
> **prefill 是超线性的，这决定了 token 预算不能太大。**

### 5.2 显存

| 项 | 计算 | 1K 视觉 token | 4K 视觉 token |
|---|---|---|---|
| 视觉编码器中间激活 | ∝ 分辨率 | 小 | 大 |
| **视觉 token 的 KV Cache** | 128 KiB/token | **128 MB** | **512 MB** |
| Projector 激活 | ∝ token 数 | 小 | 中 |

> **KV Cache 是主导项**，而且它**一直占着**（直到会话结束）。

## 6. 选型决策树

```
要处理图像
  ↓
任务是「整体理解」还是「细节/定位/计数」？
  ├─ 整体理解 → 全图固定分辨率（257~577 token）
  ├─ 细节/OCR/计数
  │     ↓
  │   文档类（文字为主）？→ **先 OCR 转文本**（+ 版面编码）
  │   实物类（零件/病灶/虫卵）？
  │     ↓
  │     有没有可靠的前端检测器？
  │     ├─ 有 → **区域级 token 化**（Set-of-Mark，50~200 token）★ 最省
  │     └─ 没有 → 切片 + 动态分辨率（1024~2880 token）
  └─ 多图/多轮？→ **必须缓存视觉特征**（否则重复编码）
```

### 6.1 一个实用的 token 预算表

| 任务 | 建议视觉 token 预算 | 理由 |
|---|---|---|
| 场景分类 / 审核过滤 | 256~577 | 够用 |
| 通用图像问答 | 577~1440 | 平衡点 |
| 计数 / 定位 / 属性 | 1440~2880 | 需要空间精度 |
| 文档 / 表格 / OCR | **优先 OCR**，视觉 ≤ 1440 | 文本更准更便宜 |
| 多图对比 | **每图 ≤ 576** | 数量乘以预算 |
| 端侧 | **≤ 256** | 显存与延迟硬约束 |

## 7. 工程结论

1. **LLM 序列长度 = 视觉 token + 文本 token**，视觉通常占 90% 以上。
2. **视觉 token 数由「编码器 + 分辨率 + 压缩层」决定，不由 LLM 决定。**
3. **跨度从 50（区域级）到 2880（切片）是 57 倍**，而效果提升远小于此——
   **token 数量级决定成本，不是决定质量**。
4. **边际收益递减**：注意力稀释 + 冗余 + 位置效应，三者共同作用。
5. **KV Cache 是主导成本**：2880 token 的图 ≈ 373 MB KV（8B 模型）。
   **多图、多轮场景必须缓存视觉特征。**
6. **prefill 是超线性的**（O(S²)），token 翻倍 prefill 慢 4 倍——
   这决定了 token 预算不能太大。
7. **文档类场景先 OCR**：200 页 PDF 能省 4~5 倍成本，且数字更准；
   **OCR 文本 + 视觉双通道**是精度优先时的组合。
8. **区域级 token 化（检测器 + 裁剪）是最省的方案**——
   它用便宜的前端模型替代贵的大模型 token。
9. **token 预算要按任务定**，不要按「分辨率越高越好」定。
