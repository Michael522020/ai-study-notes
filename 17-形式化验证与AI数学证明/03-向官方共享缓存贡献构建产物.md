# 03 · 向官方共享缓存贡献构建产物

> **本章要回答的问题**：公共缓存里那 175,187 个压缩产物是谁放进去的？我能不能也放一份进去？硬件门槛在哪？凭证怎么流转？有哪些会让机器「几小时后才以一条误导性错误失败」的坑？

**本章口径**：全部机制描述来自上游仓库的 `verification/CACHE.md`、`verification/CI-RUNNERS.md`、`verification/PORTABLE-CACHE.md`、`scripts/rh-buildq/README.md` 与 `scripts/ci-runner.py` 源码（均为 2026-11-24 读取）。**本机没有执行过其中任何一步**（本机是 Windows 11，没有符合要求的 Linux 机器），凡属推断的地方都已标注。

## 1. 缓存里装的是什么

| 项 | 值 |
|---|---|
| 服务地址 | `https://rh-cache.taucetiproject.org` |
| 协议 | S3 兼容（Cloudflare R2），bucket `riemann-hypothesis-cache` |
| 产物格式 | **LTAR**（Lake 的 tar 变体，把模块的 `.olean` 等产物打包压缩） |
| 产物数量 | 175,187（对应原版提交的模块数） |
| 索引 | 一张「输入哈希 → 产物」映射表 + 一份模块清单（`modules.jsonl.gz`） |
| 寻址 | 内容寻址，SHA-256 |
| 客户端入口 | `lake exe cache get` |

`lakefile.toml` 末尾三行就是接入点（服务名 / 端点 / revision 端点）。裸的 `lake cache get` 是 Lake 自带的另一套命令——**它不检查 receipt 和 sha256，而且慢得多**，上游明确建议用项目自己的 `lake exe cache get`。

### 1.1 客户端读取流程（`scripts/ci-cache-get.py`）

```
lake exe cache get
  └─ scripts/Cache.lean → scripts/lake-cache-get.sh
       ├─ 先跑 Mathlib 官方的 mathlib/cache（只取依赖）
       └─ 再跑 scripts/ci-cache-get.py（取本项目）
            ├─ 找一个「成功的公开 CI receipt」：
            │    必须匹配当前干净的 Git 源码树 + 实际的 lakefile /
            │    lake-manifest / lean-toolchain 字节
            ├─ 查输入指纹索引，再查一组「等价的祖先」
            │    → 只改文档的提交可以复用旧缓存
            ├─ 兜底：当前工具链在 scripts/cache-baselines.json 里的钉死的基线
            ├─ 拿到 receipt → 选出不可变、按 SHA-256 寻址的 map 与 module-manifest
            │    「绝不拿一个可变的 PR revision map 顶替」
            └─ 校验：manifest 必须**恰好**覆盖 map，一个输入哈希对应一个模块
            ↓
         恢复阶段（两件事并行）：
            ├─ lake cache add  → 16 个分片注册映射（Lake 一个映射一个文件，故不能冲突）
            └─ fetch-artifacts.py → 一个 curl 进程最多 500 路并发下载，带重试
            ↓
         校验与解包：
            ├─ 每个产物（无论是刚下的还是已在 .lake/cache/artifacts 的）
            │    都必须对上 manifest 里的 SHA-256；对不上就丢弃重下
            ├─ 检查每个源路径和输出路径（不许有符号链接）
            ├─ 删掉被替换产物对应的 Lake .hash 文件
            └─ 用一个 stock leantar 进程解包全部模块（24 workers）
            ↓
         lake build --no-build   ← 确认没有任何模块需要重新编译
```

**读缓存失败时的退出码**：`ci-cache-get.py` 找不到 receipt 或 receipt 不匹配时**退出码 3**；元数据损坏或归档不匹配则直接报错停止。

> **「一个输入哈希对应一个模块」这条约束是整个缓存的正确性基石。** 它保证了「拿到产物 A 就一定对应源码 B」，从而让增量构建可以跳过 Lean 的检查。这也是为什么发布端要做那么多校验——见 §3.3。

### 1.2 工具链是分代的

`scripts/cache-baselines.json` 里同时钉着两个工具链的基线：

| 工具链 | 基线 revision |
|---|---|
| `leanprover/lean4:v4.36.0` | `d4663eed405af528c67a3b1213021373cf8c0a5c` |
| `leanprover/lean4:v4.37.0-rc1`（当前 `active_toolchain`） | `2ef232d2992c67d457089833b7ec9e0c262f9370` |

每个基线钉着三个值：manifest 的 sha256、map 的 sha256、revision。**「一个未配置的工具链不能回退到另一个工具链的归档」**——这条规则防止用 4.36 的产物去喂 4.37 的构建。

## 2. 谁能往缓存里放东西

| 通道 | 谁执行 | 凭证在哪 | 适合谁 |
|---|---|---|---|

**所以「我在本地跑通了」不构成贡献。** 你要么真的把压缩产物喂进缓存（通道 B/C），要么去 Riemann@home 登记自己的构建（通道 D）。

## 3. 三条通道的具体流程

### 3.1 通道 B：`fragment` 分片构建（登记在册的 runner）

`scripts/rh-buildq/README.md` 的完整流程：

```
gh workflow run build-pr.yml --ref main -f mode=fragment -f pr_number=0 \
  -f fragment_commit=<sha> -f fragment_targets='Mod.A Mod.B' -f fragment_runner=<label> \
  [-f fragment_publish=false]
```

每个 job 的五步：

| 步 | 动作 |
|---|---|
| 0 `fragment.py probe` | 起沙箱，从里面确认 `$HOME`、runner 的文件和网络都够不着。**bwrap 建不起命名空间就直接失败，没有不带沙箱的兜底。** |
| 1 `fragment.py restore` | 每个 run 一棵树；首次运行时 clone 仓库并挑一个「有已发布 CI 记录」的第一父祖先；校验该提交的 `lean-toolchain` 和 `lake-manifest.json` 与 `main` **完全相同**（不同就拒绝）；装工具链；用 `main` 自己的配置准备依赖和 Mathlib 缓存；然后合并三张 map（CI map + `rh-buildq/pool` + 本提交的 `rh-buildq/maps` + stock revision map），下载缺失产物 |
| 2 `fragment.py build` | 在离线沙箱里 `lake build -v -o .lake/rh-fragment-outputs-<run>.jsonl <targets>` |
| 3 `fragment.py stage` | **构建失败或被取消时也会跑**。把 Lake 已完成、且恢复的 map 里没有的模块的 `.ltar` + 输入哈希 + SHA-256 拷进 stage 目录 |
| 4 `fragment.py result` | 写出 `result.json`：构建了、重放了、失败了哪些模块；stage 了多少；耗时 |
| 5 `fragment_publish` | 校验 stage → 上传为内容寻址对象 → 记进 `rh-buildq/maps/<sha>.jsonl` 和 `rh-buildq/pool/<toolchain>.jsonl`（**compare-and-swap** 更新） |

**重跑会续跑**：Lake 会重放已构建的，stage 会跳过恢复阶段已找到的。

### 3.2 通道 C：完整构建交付（一次性捐赠）

这条路径**不需要注册 runner**，适合「我有一台大机器，想把它的一次完整构建贡献出去」：

```
# 1. 在最终提交的干净 checkout 上，跑完整 stock 默认目标构建
python3 scripts/run-complete-build.py \
  --release leanprover/lean4:v4.36.0 --project "$PROJECT" \
  --build-map "$PRODUCER/outputs.jsonl" --build-log "$PRODUCER/full-build.log" \
  --receipt "$PRODUCER/build-receipt.json" --jobs 8

# 2. 打包压缩产物（不再编译任何证明）
python3 scripts/stage-completed-build.py \
  --release leanprover/lean4:v4.36.0 --project "$PROJECT" \
  --build-map "$PRODUCER/outputs.jsonl" --build-log "$PRODUCER/full-build.log" \
  --build-receipt "$PRODUCER/build-receipt.json" \
  --output "$PRODUCER/native" --metadata "$PRODUCER/metadata"

# 3. 把 native/ 和 metadata/ 交给维护者的发布主机
```

`run-complete-build.py` 的产物是一份 **receipt**（收据）：它把「最终的源码/配置/工具链身份 + 完整的默认目标范围 + 命令 + 日志 + 输出映射」绑在一起。`stage-completed-build.py` **不做任何证明编译**，它只验证原生内容哈希和 SHA-256，然后 stage 压缩缓存。

> **关键设计：receipt 是一份「可审计的身份记录」。** 上游 `PORTABLE-CACHE.md` 强调：发布的是**最终合并候选提交**的缓存，而**原作者原始提交/源码树必须作为一份独立的审计记录保留**，「永远不要把一个 fork 的缓存头重新标注成合并后的源码」。

`stage-completed-build.py` 还有个 `--cache-dir` 参数：给那些「本地没有 IR 目录副本、但有完整 native 缓存」的模块提供 LTAR 别名。

### 3.3 通道 A 的发布端校验

`publish-lake-cache.py`（在**持有凭证的发布主机**上跑）会：

- 读一个 mode-0600 的账户 R2 token（`~/.riemann-hypothesis-tauceti-r2-token`），或一个含 accessKeyId/secretAccessKey 的 JSON；
- **通过匿名端点验证 revision map**；
- 拒绝不完整的映射、多余的文件、以及任何链接（符号链接等）；
- 支持「先同步产物、最后才发布 map」的渐进式上传（`sync-cache-artifacts.py --watch` + `--map-only-after-sync`，后者会检查每个远端产物的存在性和大小后才发布 map）。

`publish-fragment.py`（分片发布的校验器）会：

- **重新计算**目标提交（对于 `SHA BASE HEAD DATE PR` 形式的确定性合并提交，重新合并并核对 SHA）；
- 要求 **每个 staged 模块都必须是该提交的源文件**；
- 要求每个输入哈希合法且唯一；
- 校验每个产物的**大小、SHA-256、以及 stock Lake 内容哈希**（用官方工具链重算）；
- **只增不删**地更新 map。

## 4. 凭证模型：上传凭证永远不在构建机上

这是整套流水线里**最值得学的安全设计**。上游 `CACHE.md` 的原话：

> Upload credentials never go to a machine that builds pull requests.

展开成四条：

| # | 规则 | 实现 |
|---|---|---|
| 1 | **构建机不持有任何 R2 凭证** | `fragment` job 没有 environment、读不到任何 secret；只把产物作为 GitHub Actions artifact 上传 |
| 2 | **发布发生在另一台机器上** | 一个全新的 `ubuntu-latest` job，在 `ci-cache-publish` environment 里，用 `R2_ACCOUNT_TOKEN` 派生密钥 |
| 3 | **密钥是 environment secret，不是 repository secret** | 「`R2_ACCOUNT_TOKEN` 永远是 `ci-cache-publish` 的环境密钥，永远不是仓库密钥」 |
| 4 | **发布器不执行被构建的代码** | 「它不运行被构建提交里的任何东西，只把它当 Git 对象读」 |

### 4.1 沙箱的规格

| 维度 | 规格 |
|---|---|
| 工具 | bubblewrap |
| 命名空间 | `--unshare-all`（user / PID / IPC / UTS / cgroup / network），支持时再加 `--disable-userns` |
| 会话 | `--die-with-parent`、`--new-session`、`--clearenv` + 显式环境 |
| 可见性 | `/usr`、`/bin`、`/lib*`、`/nix/store` 只读；`/etc` 里若干单文件只读（CA bundle、resolv.conf、hosts、nsswitch.conf、passwd、group、localtime、ld.so.cache）；工具链只读挂在 `/opt/lean`；下载的产物只读 |
| 可写 | **只有 job 自己的 work tree**（`.git` 除外，只读） |
| `/tmp` | 私有 tmpfs；`$HOME` = `/tmp/home` |
| 网络 | **没有**。独立 network namespace，到不了互联网、局域网、宿主 loopback、云元数据地址 `169.254.169.244`、宿主 abstract unix socket |
| 分组 | 受信任的宿主代码（clone、fetch、checkout、校验 toolchain/manifest、准备依赖、下载产物、stage）**不碰目标提交的 lakefile、不跑目标里的任何东西**；一切联网的都在这一组 |

### 4.2 一个必须知道的诚实限制

上游自己写明了这个模型**不能**防住什么：

> 发布器无法检查「一个 staged 产物真的就是某个模块的输入哈希产出的」——因为构建里的代码会写携带这些哈希的 `.trace` 文件。所以一个恶意的提交可以把自己模块的产物挂到**另一个**提交的模块的输入哈希下，**污染共享缓存池**。

应对方式不是技术性的，是政策性的：

> **共享缓存按策略是完全可信的：构建出来的东西都发布。** 分片构建默认发布。

所以：**只有在你能确认提交是可信的时候，才让你的机器去构建它。** 这也是为什么 donor runner 必须用**专用账号**——你让别人的 PR 代码跑在你的机器上。

## 5. 通道 D：Riemann@home（面向个人的自助通道）

如果你的目标不是「给官方缓存供料」，而是「**我自己独立复现一次全量构建，并公开我的记录**」，有一个门槛低得多的社区项目：[`Riemann-at-home/riemann-at-home`](https://github.com/Riemann-at-home/riemann-at-home)。

它的定位（README 原文大意）：

> 在你自己的电脑上构建黎曼猜想的 Lean 证明，并把你的构建加入一张全局地图。

**它的机制**：一个纯标准库的 Python CLI（`cli/riemann-at-home`），在你本机跑**官方未改动的** `lake build Main`；每约 10 分钟自动更新一个公开 PR（`submissions/<login>/<build_id>.json`），记录你的 GitHub 用户名、操作系统、芯片、核数，以及你已经构建了哪些模块。

**它的门槛**（README 自己列的）：

| 项 | 要求 |
|---|---|
| 系统 | macOS 或 Linux |
| 磁盘 | 约 150 GB 空闲（全量构建约 120 GB） |
| 内存 | 构建本身不需要特别多；**可选的 export 步骤需要很多**（峰值约 145 GB） |
| 时间 | 16～64 核桌面约 9～19 小时；12 核 M2 Max 约 2 天 |
| 权限 | `gh auth login -s workflow`（workflow 权限让更新能通过——仓库里有 bot 的 Actions 文件，GitHub 不允许在未授权时 push 触碰它们） |

**它明确写了边界**：

> 结果是自报的，绑定你的 GitHub 账号。一个 bot 会检查每次更新（钉死的归档与版本、进度只增不减、速度合理、已编译文件的指纹）之后才计入。**它无法证明你真的跑了。**

以及最重要的一句：

> 构建证明并不能证明数学命题成立。Lean 的陈述是否就是数学家所说的 RH、以及 Lean 本身有没有 bug，是专家的工作。

**签名机制**（Level 2，可选）：当全量构建完成，`export` 会导出编译后的证明（61.6 GB，边流式边哈希，不落盘）并**逐字节比对参考导出**；一致才可以签联合声明。内存需求：140 GB 以上舒适，96～140 GB 能跑但尾部很慢，96 GB 以下可能永远跑不完。

## 6. 通道 B 的硬件门槛：登记一个 donor runner

上游 `verification/CI-RUNNERS.md` 全文很短，就四步：

| # | 步骤 |
|---|---|
| 1 | **硬件**：Linux，理想 128 GiB 内存；至少 250 GiB 空闲 SSD；`vm.max_map_count` 至少 1048576，且**持久化在 `/etc/sysctl.d`** |
| 2 | **联系维护者**：在 Lean 社区的 Zulip 上私信 Kim Morrison，说明 CPU/内存、架构、空闲磁盘、可用时间 |
| 3 | **用专用账号**：job 会跑不受信任的 PR 代码 |
| 4 | **前置**：Git、Python 3.11+、C 编译器、Bubblewrap、Elan。下载 `scripts/ci-runner.py`，跑 `doctor` 把输出发给 Kim，跑 `install`，Kim 提供私有登记文件和启动命令 |

### 6.1 `ci-runner.py doctor` 到底查什么

源码里的 `failed_checks()` 逐条列出了**硬失败项**：

| 检查 | 不满足时的后果 |
|---|---|
| `platform.system() != "linux"` | 直接拒绝 |
| `os.getuid() == 0` | 「uid 是 0：请用专用非特权账号」 |
| 缺 `git` / `cc` / `python3` / `bwrap` / `elan` | 逐个点名 |
| `bwrap` 离线探针失败 | 「离线 bwrap 探针失败：沙箱可能不是离线的」 |
| 空闲磁盘 < 250 GiB | 「不够 250 GiB 给构建状态目录」（并提示可以把它挪到别的盘） |
| `vm.max_map_count` 不可读或 < 1048576 | 「需要至少 1048576」 |

另外它还会**报告**（但不作为硬失败）：物理内存 GiB、cgroup v2 是否可用、systemd user session 是否可用。

> ⚠️ **探针的判定很讲究**：它不是「网络不通」就算过，而是**要求连接尝试被明确拒绝为不可达**（`ENETUNREACH` / `EHOSTUNREACH` / `EADDRNOTAVAIL`）。如果连接被别的错误拒绝（本地防火墙的 `EPERM`/`EACCES`），探针**判为失败**——因为「本地防火墙挡了一下」不等于「沙箱没有出口」。这个设计很值得抄。

### 6.2 `vm.max_map_count`：那个「几小时后才以误导性错误失败」的坑

`ci-runner.py` 的注释把原因写得很清楚：

> Lean maps every imported `.olean`; Main imports all 175,186 other modules. The Linux default of 65530 fails with "failed to read file" on modules high in the import graph (issue #29).

拆开说：

| 项 | 值 |
|---|---|
| Linux 默认 `vm.max_map_count` | **65,530** |
| 需要的值 | **1,048,576** |
| 差距 | 16 倍 |

**为什么**：Lean's 编译器把每个 import 的 `.olean` 都 mmap 进内存。`Main` import 了全部 175,186 个其他模块，每个模块又会 import 一堆——**进程需要一个巨大的虚拟地址空间映射**。映射数超过 `max_map_count` 时，`mmap` 返回 `ENOMEM`，Lean 会报一个**和真实原因毫无关系**的错误。

**为什么「几小时后才失败」**：模块是按依赖顺序编译的，映射数随编译进度单调增长。**只有编译到导入图很深的模块时才会撞上限**——也就是**跑了几小时之后**。而且错误信息是「failed to read file」，任何人第一次看到都会去查文件路径，查不出任何东西。

**持久化**：`sysctl -w` 只在本次开机有效，重启就丢。要写进 `/etc/sysctl.d/60-rh-ci-max-map-count.conf`（`ci-runner.py` 里写死了这个路径）再 `sysctl --system`。

> **这条坑值得单独记住，因为它对任何「在 Linux 上构建大型 Lean 项目」都成立**，不只是这个仓库：默认的 65,530 对大多数人是够的，但对这种「一个模块 import 几万个模块」的项目不够。

### 6.3 磁盘落在哪个盘上

`doctor` 的 `--work-directory` 默认是 `$HOME`，它测量的是**这个路径所在的文件系统**。但 job 实际写盘的位置是构建状态目录（默认 `~/.local/share/riemann-build-state`，可用 `RH_CI_STATE_DIR` 改）。

上游脚本里的提示：

> doctor 只测一个文件系统，但 job 会往构建状态目录写盘，目录在哪就在哪测。**有一个/home 小、/data 大的志愿者应该挪目录，而不是重跑 doctor。**

### 6.4 云主机可行吗

（**以下是推断，不是上游文档**。上游只说「Linux、理想 128 GiB 内存、至少 250 GiB SSD」。）

按这个门槛筛，市面上够格的机器大致是「32 核 / 128 GiB 内存 / 大容量 NVMe」这一档，主流公有云里都有。成本集中在内存而不是 CPU。**价格随时间变动，请自行核对当期报价。**

要注意的额外几点：

| 项 | 说明 |
|---|---|
| **非特权用户命名空间** | `bwrap --unshare-user` 需要内核允许非特权 user namespace。有些云镜像默认关闭，需要换内核参数或换发行版。**这是云主机上最可能卡住的一步**，建议开通后第一件事就跑 `ci-runner.py doctor` |
| **`vm.max_map_count`** | 云主机的 `sysctl` 一般可以改，但要确认能写 `/etc/sysctl.d` |
| **不能是 root** | `doctor` 明确拒绝 uid 0，需要建一个专用非特权账号 |
| **账单周期** | 一次全量构建是小时级到天级的任务；**按小时计费的机型，用完立刻销毁**，别包月 |
| **带宽** | 构建要下载 Mathlib 缓存 + 上游依赖，是几百 GB 量级的流量 |
