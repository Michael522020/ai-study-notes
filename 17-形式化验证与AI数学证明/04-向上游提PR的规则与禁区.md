# 04 · 向上游提 PR 的规则与禁区

> **本章要回答的问题**：这个仓库到底收什么、不收什么？`AGENTS.md` 里那 6 条「常见错误」是怎么来的、为什么？怎样写一个能进维护者队列的 PR？

**本章口径**：全部来自上游 `AGENTS.md` 与 `README.md`（2026-11-24 读取），以及已合并 PR 的实际标题。为避免逐字复制上游文档，本章用中文转述并保留关键标识符（`nlinarith`、`grind`、`lia`、`set_option backward` 等），**原文请直接读上游 `AGENTS.md`**。

---

## 1. 先搞清楚这个仓库是什么

上游 README 的自我定位是：

> 一个社区主导的工作：清理并维护黎曼猜想（以及 Dirichlet L 函数的 GRH）的 Lean 形式化。

目标有三个词：

| 目标 | 含义 |
|---|---|
| **accessible** | 改善构建性能与模块化，让**没有大量算力**的研究者也能上手 |
| **readable** | 在保持证明「逻辑」不变的前提下改善代码质量，向 Mathlib 水平看齐：引理组织、格式、惯用风格、消除 linter 警告、无 slop 的文档 |
| **integrated with the community** | 在合适的地方补上文献引用，尽可能复用已有的形式化项目 |

**这三条目标直接决定了什么样的 PR 会被接受。** 一份「我加了个新工具链」的 PR 与这三条都无关；一份「把某个 5000 行的模块拆成 3 个可复用的引理模块」的 PR 三条都沾。

### 1.1 明确的「不收什么」

上游 README 用加粗列了三条不欢迎的贡献（中文转述）：

1. **沿着实质不同的证明路径做的大改**——不是「重构」，是「重写」；
2. **关于你自己机器上的构建 / Comparator 运行结果的声明**；
3. **加入证明本身用不到的文件**。

第 2 条是很多贡献者的第一反应就踩的：「我在我机器上跑通了！」——**上游明确不收这种声明**，因为维护者自己会构建每一个 PR，写这种话只会增加噪音。正确做法是：**自己确认能编译，但不要在 PR 里写「它在我机器上构建通过了」。**

第 3 条同样常被违反：顺手加一个自己的小工具、格式化脚本、写个分析报告——在**证明仓库**里这些都是负担。上游的第二条 `Do not` 也重复了这一点：`or add files the proof does not need`。

## 2. `AGENTS.md`：写给 AI agent 的规范

`AGENTS.md` 的开头就把读者定位说清楚了：

> 先读 README.md。它说明这个仓库是干什么的、哪些改动受欢迎、证明是怎么被检查的。下面这些规则，是 agent 最容易违反的那些。

**这个开头本身就是一条设计经验**：如果你知道读者可能是 LLM，就不要写「通用规范」，要写「**你最容易犯的那几条**」。规范的价值不在覆盖面，在命中率。

文件分四块：

```
## Building          先取缓存，再构建
## Pull requests     什么时候开 PR、怎么进队列、标题和正文怎么写
## Do not            硬性禁令（CI 会拒）
## Mistakes we keep seeing   6 条反复出现的错误
```

---

## 3. PR 的生命周期

### 3.1 开之前

| 要求 | 说明 |
|---|---|
| **基线是 `main`** | `original` 分支只保留 2026-11-20 最初发布的版本，**不要基于它提 PR** |
| **改完并确认能编译之后再开** | Lake 会重建你改过的文件**以及所有 import 它们的下游**——所以这一步还能抓到「你删掉了一个还在别处被用的引理」 |
| **要开早了就开 draft** | draft 不会进入维护者的审阅队列；完成后再转 ready |

验证命令：

```bash
git fetch upstream && git rebase upstream/main   # 先跟上 main
lake exe cache get                                # 取缓存
lake build                                       # 必须无错结束
```

> **「必须无错结束」是硬要求**，不是「基本能过」。

### 3.2 进队列

上游用一套标签 + 一条约定命令来管理队列：

| 事件 | 状态 |
|---|---|
| 维护者把 PR 打回给你 | 打上 `awaiting-author` 标签，**离开**审阅队列 |
| 你按要求改完（或回答了问题） | 在 PR 下**只**评论 `ready`（不带任何其他内容） |
| 机器人响应 | 去掉 `awaiting-author` 标签，PR **回到**队列 |

**「只评论 `ready`」这个约束很有意思**：它让一个命令式的信号不会被和讨论混在一起，机器人可以精确匹配。对 agent 来说，这意味着**不要在评论里写「ready, 我已经改好了，见下」**——多一个字，匹配就失败。

### 3.3 一个 PR 只做一件事

> Keep each pull request to one change. Small pull requests are quicker to review and easier to combine into a batch than one large one.

**小 PR 不是礼貌，是策略。** 一个 3 行的改动，审阅者 30 秒看完就过了；一个 3000 行的改动，审阅者要排进日程、可能拖到几周后。**维护者会把你打回，让你拆开。**

## 4. 标题与正文

### 4.1 标题：沿用 Mathlib 的约定

```
<type>(<optional-scope>): <subject>
```

| 部分 | 规则 |
|---|---|
| `type` | `feat` / `fix` / `doc` / `style` / `refactor` / `test` / `chore` / `perf` / `ci` |
| `scope` | 可选，是目录或文件名，**不带 `src/` 前缀** |
| `subject` | 祈使句（imperative），**首字母小写**，**结尾不要句号** |

上游给的三个真实例子：

```
refactor: reuse Mathlib lemmas in the primitive-character reflection proof
perf(GroundTheory/ArithmeticGeometry): speed up the acyclic Čech comparison in RelativeSerre
doc: document the Schrödinger and metaplectic representations over ℝ
```

**实际已合并的 PR 标题也确实是这个形状**，例如：

- `perf(ThirdPlaceSeries): avoid 12-field PSigma projection blowup in ExistsRowsKCColPins (1.86x / -56.7s CPU)`
- `refactor(imports): prune 125.7k redundant private Mathlib imports across ReciprocityTheory, CompanionTheory, PositivityTheory & Lemmata (−60.7 CPU-min)`
- `chore: remove the unused private lemma 'transpose_mul_mul_map_cc_eq_of_isUStab'' from PonStatementPfC`

**注意第三个例子**：标题里点名了要删的声明名。**这说明上游期望你在标题里就说清楚动了什么**——因为一个删掉 3000 行证明的 PR，审阅者首先想知道的是「删的是什么」。

### 4.2 正文模板

上游给的模板：

```markdown
<这次 PR 改了什么、为什么改，几句话。点名任何被删除、改名或移动的声明。>

---

- [ ] depends on: #123
```

**「点名任何被删除、改名或移动的声明」是硬要求。** 在 1700 万行的仓库里，审阅者不可能自己 diff 出你动了什么。

`depends on:` 那行是**堆叠 PR** 的声明——如果你的 PR 基于另一个还没合并的 PR，就写上它的编号。

## 5. 硬性禁令（CI 会拒）

上游 `Do not` 一节列的，加上 README 的 CI 检查，一共是这些：

| # | 禁令 | 后果 |
|---|---|---|
| 1 | 改 Comparator 的挑战文件 | **CI 直接拒绝这个 PR** |
| 2 | 加公理或 `sorry` | 证明失效 |
| 3 | 沿着实质不同的路径重写证明 | 会被打回 |
| 4 | 加证明用不到的文件 | 会被打回 |
| 5 | 在 PR 里报告自己机器的构建结果 | 会被打回 |

第 1 条点名的**六个不可改文件**：

```
src/Challenge.lean
comparator.json
export-targets.txt
comparator/FormalConjecturesChallenge.lean
comparator/formal-conjectures.json
comparator/formal-conjectures-export-targets.txt
```

**为什么这六个文件被冻结？** 因为它们定义了「什么叫证对了」。改掉任何一个，你就不再是在检验那个命题，而是在检验你自己定义的命题。**这是一条研究诚信线，不是代码风格线。**

第 2 条的技术细节：`src/Main.lean` 只能使用 `propext`、`Quot.sound`、`Classical.choice` 三条公理（见 [`01` §4.1](./01-Riemann-Hypothesis-Lean形式化工程解剖.md#41-公理白名单这条检查抓什么)）。

## 6. 「我们反复看到的错误」：6 条

上游这一节的定位写得很好：

> 这些都是 agent 经常做、而我们不想要的改动。**它们大多把问题藏在一个文件里，而不是在问题产生的地方修。** 我们每发现一些就往这个列表里加。

**「它们大多把问题藏在一个文件里，而不是在问题产生的地方修」——这一句是整节的钥匙。** 6 条里有 5 条是同一个病：**局部打补丁，代价转嫁给全局。**

### 6.1 手写改写 `nlinarith`

| | |
|---|---|
| ✅ 允许 | 当 `linarith` 或 `positivity` 就够时，把 `nlinarith` 换成它们 |
| ❌ 禁止 | 为了省一两秒，把 `nlinarith` 换成几个 `have` 步骤或一个 `calc` 块 |
| ✅ 推荐 | 先给 `nlinarith` 它需要的乘积；或者试一下 `grind` |

**理由**：后者更长 = 更难读，**对人难读，对其他 agent 也难读**。

> **这条的普适价值很高**：在一个 1700 万行的仓库里，「可读性」不是审美偏好，是**协作带宽**。每个 PR 平均改动多少行，决定了这个仓库能容纳多少个并行贡献者。

### 6.2 用旧 tactic

| | |
|---|---|
| 原因 | 「你的训练数据比这个仓库用的 Lean 和 Mathlib **旧**」 |
| 建议 | 线性算术（ℕ / ℤ）用 `lia` 而不是 `omega`；写长证明前先试 `grind` |
| ❌ 禁止 | 「只把一个 tactic 换成另一个 tactic」的 PR |

**上游这句话直接说给了 LLM 听**——它假设读者会凭记忆写出旧版本 Lean 的 API。

**可迁移的做法**：在写证明前先查 `lean-toolchain` 和 `lake-manifest.json` 里钉的版本，再查那个版本里到底有什么。**「先查版本再写代码」是 agent 最该养成的习惯。**

### 6.3 绕开慢的 instance search

这是 6 条里技术含量最高的一条。上游禁止的做法：

- `attribute [-instance]` 关掉实例；
- 加 `local instance`；
- 加一个快捷实例（如直接给某个类型指定 `CommRing`）；
- 证明一份私有副本（比如自己写一遍 `map_add`）让搜索根本不用跑。

**上游把这条的机制讲得非常透**：

> 这些做法让**一个文件**变快，却让搜索**在其他所有地方保持原来的慢**。

为什么？因为慢的根源是**那个类型上被错误声明的实例**。在**声明它的地方**修，别处自然就快了。

**上游给出的正确诊断流程**（值得抄）：

```lean
set_option trace.Meta.synthInstance true in
set_option trace.profiler true in
-- 放在慢的声明前面
```

然后**顺着时间找到那个把搜索带偏的实例，在它的声明处修掉**。

> **这一条是整个 `AGENTS.md` 里最有教学价值的一条。** 它教的不是 Lean，是**「不要在症状处治疗」**：
> **局部优化在局部有效，在全局是负的。** 一个 `local instance` 让你的文件编译时间从 40 分钟降到 5 分钟，同时让**另外 60,000 个文件**里的每一个搜索都多花同样的时间——因为搜索是沿 import 图传播的。
>
> 在 1700 万行的项目里，**一个文件的 5 分钟 × 60,000 个文件 = 不可接受**。所以社区必须把这种「假优化」明确列为错误。

### 6.4 用 `set_option backward` 复活旧行为

具体指的是 `set_option backward.isDefEq.respectTransparency false` 这类。

| | |
|---|---|
| 危害 | 「把旧版 Lean 的行为带回来，而 Lean 后续会移除它——所以依赖它的证明在将来的一次升级后会坏掉」 |
| 现实 | 「很多文件里还有这类选项，是以前升级时留下的；**别照抄那些**」 |
| 正解 | 「通常只要改写成用一个引理，而不是依赖 Lean 去展开一个定义就够了」 |

**这条对 AI 特别危险**：模型见过大量带 `set_option` 的旧代码，而且旧代码在训练数据里比例更高。**模型会自然地「抄」旧写法**，而上游明确说「别抄那些」。

**防御方法**：写之前先确认这个选项在当前钉死的版本里**还需要**——大部分不需要。

### 6.5 用 `exact` / `rfl` 之外的自写 tactic

上游的禁令非常具体：

> 不要用 `elab` 或 `run_tac` 写一个**就地**关掉目标的 tactic 来代替 `exact` 或 `rfl`——**无论是它不检查项的类型就赋值，还是它用 `Kernel.isDefEq` 检查**。

**为什么两种都不行？**

- 不检查类型的那种：把一个错的项留给后面，**只会在声明的最后以一个内核错误的形式暴露**——错误信息离错误原因十万八千里；
- 用 `Kernel.isDefEq` 检查的那种：**它把一次慢的合一藏起来了，而不是修好它**。

上游还加了一句：**有些文件里已经有一个这样的 tactic（叫 `exact_by_kernel`），别照抄那些。**

正解同样是「改写成用一个引理」。

> **注意这条和 [`01` §6](./01-Riemann-Hypothesis-Lean形式化工程解剖.md#6-元编程的暗角kexactbkcopyrun_tac) 的呼应**：这个证明本身就在用 `kexactB` / `kcopy`（原作者的手法）。**但上游禁止贡献者用同样的手法写新证明。**
>
> 这个差别很重要，值得想清楚：
> - **原作者的用法**：在一个 17 万模块、每个模块平均 100 行的证明里，`kexactB` 可能是唯一可行的写法（它绕过的正是「逐字写出那个巨大的推导式」这件事）；
> - **贡献者的用法**：在能被 `exact` 写清楚的 20 行里用 `kexactB`，是纯粹的伤害。
>
> **同一个手法，在「规模迫使」和「图省事」两种动机下，正确性天差地别。**

### 6.6 给 CI 脚本做微优化

上游收到大量这样的 PR：把 `scripts/` 或 `tools/ci_native/` 里的脚本优化掉零点几秒（比如把读两次文件改成读一次、把几次 `git` 调用合并成一次）。

**上游的拒绝理由有三条，每条都值得学**：

| # | 理由 |
|---|---|
| 1 | 「每一个这样的改动都需要一个懂 CI 的人来审」 |
| 2 | 「省下的时间在一次几小时的构建里就消失了」 |
| 3 | 「**CI 的改动是欢迎的——当它们修一个 bug、补上一个检查缺口，或者省下有人会注意到的**时间****——而且要以这个步骤真正处理的数据来衡量，而不是拿一个小 fixture 来衡量」 |

**第 3 条给出了 CI 改动的准入标准**：修 bug / 补缺口 / 省下可感知的收益，**且衡量口径要对**。

**「别拿小 fixture 衡量」这一条尤其重要**：一个在 10 个文件的 fixture 上快 0.3 秒的优化，在 175,187 个文件的真实数据上可能什么都不省。**用错误的样本优化，你会优化掉不存在的问题。**

## 7. 实操清单：怎样提一个能进队列的 PR

```
① 读 README.md（知道边界）→ 读 AGENTS.md（知道禁区）
② git fetch upstream && git checkout -b <你的分支> upstream/main
③ lake exe cache get && lake build          ← 先确认基线是干净的
④ 只做一件事；跟着 upstream/main 的风格
⑤ lake build                                 ← 改完再跑一次
⑥ 开 PR（draft 或正式），标题 <type>(<scope>): <subject>
   正文：改了什么 + 为什么 + 点名被删/改名/移动的声明
⑦ 等维护者打回 → 改 → 只评论 "ready"
```

### 7.1 一个新贡献者最容易忽略的三件事

| # | 忽略的后果 |
|---|---|
| ① 没先 `lake exe cache get` 就开分支 | 每个 PR 从零编译几小时，你以为是自己机器慢，其实是流程问题 |
| ② 在 PR 里写「已在我机器上构建通过」 | 上游明确不收这种声明，会被打回 |
| ③ 一个 PR 里改了三个不相关的东西 | 会被要求拆开，拖慢合并 |

## 8. 这套治理方式的可迁移经验

抛开 Lean 和 RH，这个仓库的治理设计对**任何「大规模 + 自动生成 + 多人协作」的代码库**都适用：

| 经验 | 做法 |
|---|---|
| **先建缓存，再开协作** | 让人能在几分钟内开始干活，而不是先编译几小时 |
| **把「不收什么」写得和「收什么」一样显眼** | 上游 README 专门用加粗列了三条不欢迎的贡献 |
| **给 agent 写「你最容易犯的错」，而不是「通用规范」** | `AGENTS.md` 的开头直接说明这个定位 |
| **用机器可判定的规则做门禁** | 六个挑战文件由 CI 拒绝改动，不靠人自觉 |
| **用一条命令做状态信号** | `ready` 单独一条评论，机器人精确匹配 |
| **禁止局部优化，要求在源头修** | 6 条错误里 5 条是同一个病 |
| **评价优化要看真实数据** | 「以这个步骤真正处理的数据来衡量，而不是小 fixture」 |

> **最后一条是这套治理里最反直觉、也最重要的一条。**
>
> 大多数工程实践默认「让东西变快」是好事。但在这个仓库里，「让一个脚本快 0.3 秒」是**明确被拒绝的**，因为：审阅成本 > 收益，且收益要用错误的样本衡量。
>
> **在一个有 583 个 PR、1700 万行的仓库里，最稀缺的不是算力，是「审阅带宽」。** 所有治理规则最终都在回答同一个问题：**如何把审阅带宽花在真正重要的地方。**
