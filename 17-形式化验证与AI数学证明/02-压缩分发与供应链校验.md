# 02 · 压缩分发与供应链校验

> **本章要回答的问题**：1.05 GiB 的 Lean 源码怎么压、压多少、怎么验证？「打个包发出去」这件事本身有哪些讲究？为什么「压缩一份证明」和「压缩它的文本」不是一回事？

**本章全部数字为本机 2026-11-24 实测**，测量对象是上游 `leanprover-community/riemann-hypothesis` 仓库的两个固定提交：

| 提交 | 含义 | `.lean` 文件数 | 源码字节数 |
|---|---|---:|---:|
| `40e56bab026552e089d7afcfeff08d2defb9c005` | **原版提交**：Alpöge 2026-11-20 公开归档的逐字节副本 | 175,187 | 1,030,531,854 |
| `26c37b400bc9cfd43c81d798aa5e798af5c55b94` | **当前 main**：社区整理 4 天后的状态 | 60,493 | 1,097,434,609 |

## 1. 为什么 1 GB 的证明需要「分发工程」

先把约束摆清楚：

| 事实 | 数值 | 来源 |
|---|---|---|
| 官方归档 `alpo.ge/lean.tar.gz` | 239,275,554 B（228.2 MiB） | 上游 `verification/NOTES.md` |
| 官方归档的分段数 | **14 段**（`lean.tar.gz.part01` … `part14`） | 同上 |
| 官方归档 sha256 | `9631b4f020199e580ba86178cb56c6e9b09f690c2369a80dc4334aa93f49c7fc` | 同上 |
| 上游 Git 仓库体积 | 976,257 KB ≈ 953 MiB | GitHub API，2026-11-24 |
| 上游的 release / tag | **0 个 / 0 个** | `gh release list`，2026-11-24 |

**切成 14 段这件事本身就说明了问题的规模。** 单个文件 228 MiB 在很多下载通道里是硬伤——HTTP 服务端有 body 大小限制、浏览器有内存上限、企业网关有单文件阈值。所以发布方把它切成 14 段，让用户 `cat` 起来。

于是形成了今天的三种获取方式，各有各的毛病：

| 方式 | 拿到什么 | 毛病 |
|---|---|---|
| `git clone` | 完整历史 | 953 MiB，而且 `main` 会动，你没法证明自己拿到的是哪一版 |
| codeload tar.gz | 一个快照 | **浮动的**，内容随 `main` 变化，没有自洽的校验值 |
| 官方 14 段归档 | 原始发布 | 是 4 天前的状态，不含社区后续整理；且要手工拼接 + 手工验 sha256 |

**所以「把内容钉死在一个提交上，并给出可复核的校验链」这件事本身是有价值的。** 这就是本仓库 [`Michael522020/riemann-hypothesis-pack`](https://github.com/Michael522020/riemann-hypothesis-pack) 做的事。

## 2. 实测：三种算法、两份内容

全部用同一套 tar 参数（见 §3），只换压缩器：

### 2.1 原版提交 `40e56bab`（175,187 文件 / 1,030,531,854 B）

| 算法 | 产物大小 | 压缩比 | 相对 gzip |
|---|---:|---:|---:|
| 原始（不压缩） | 1,030,531,854 | 1.00× | — |
| **gzip -9** | 235,815,509 | 4.37× | 基准 |
| **zstd -19** | 157,670,738 | **6.54×** | **−33.1%** |
| **xz -9** | 144,258,320 | **7.14×** | **−38.8%** |
| *官方 `alpo.ge/lean.tar.gz`* | *239,275,554* | *4.31×* | *+1.5%* |

### 2.2 当前 main `26c37b40`（60,493 文件 / 1,097,434,609 B）

| 算法 | 产物大小 | 压缩比 | 相对 gzip（原版） |
|---|---:|---:|---:|
| 原始（不压缩） | 1,097,434,609 | 1.00× | — |
| **zstd -19** | 128,500,935 | **8.54×** | **−45.5%** |
| **xz -9** | 120,232,252 | **9.13×** | **−49.6%** |

### 2.3 三个值得单独拎出来的结论

**① 我的 gzip -9 结果与官方归档只差 1.5%。**

我用同一套参数压原版提交得到 235,815,509 B，官方归档是 239,275,554 B，差 3,460,045 B（1.46%）。差在哪？可能是官方用了 gzip 默认级别（−6）而不是 −9、tar 根目录名不同（官方是 `lean/`，我是 `src/`）、以及 tar 版本的 header 差异。

**这个「差 1.5%」不是误差，是验证。** 它说明：**(a) 我拿到的原版提交确实就是官方归档的内容**（否则尺寸不会这么接近）；**(b) 官方归档就是一份普通 gzip，没有做任何特殊封装**。

**② zstd -19 比 gzip -9 在同一份内容上小 33.1%。**

这个数字和内容无关，是算法的差距。对一份高度重复的 Lean 源码，gzip 的 32 KB 窗口是主要瓶颈——zstd 的窗口和匹配策略在长程重复上强得多。

**③ 模块合并让压缩比从 6.54× 涨到 8.54×，但原始体积反而涨了 6.5%。**

原始字节：1,030,531,854 → 1,097,434,609（**+6.5%**）
压缩后（zstd -19）：157,670,738 → 128,500,935（**−18.5%**）

**同一份「数学内容」，压缩后小了 18.5%，原始却大了 6.5%。** 原因在 [`01` §5.1](./01-Riemann-Hypothesis-Lean形式化工程解剖.md#51-库级分布2026-11-24-实测)：社区把 175,187 个小模块合并成 60,493 个大模块，**平均行长从 59.3 字节涨到 65.7 字节**（更长的标识符 = 更可读）。

对压缩器来说，**更长的行意味着更好的局部重复率**（同一个变量名在同一个证明里反复出现），而**更少的文件意味着更少的 tar header**（每个 header 约 512 B + 文件名，175,187 × ~600 B ≈ 105 MB 的纯 header 开销！）。

> **这是本章最重要的一条认知**：
> **对 Lean 项目做「压缩」，真正的压缩单位是模块粒度，不是字节。**
> 字节级压缩（zstd/xz）最多给你 1.5× 的额外收益；
> 而把 175,187 个模块合并成 60,493 个，省下的是 **100 MB 级的 tar header + 更好的重复率**。

## 3. 可复现打包：那些 tar 参数为什么是那些参数

要「同样的输入得到逐字节相同的输出」，必须干掉三类不确定性：

| 不确定性来源 | 处理 |
|---|---|
| 目录遍历顺序（`readdir` 顺序随文件系统而变） | `tar --sort=name` |
| 文件 mtime（打包时刻） | `tar --mtime="@<epoch>"`，epoch 取上游该提交的 committer 时间 |
| 打包者的用户名 / 组名 | `tar --owner=0 --group=0 --numeric-owner` |
| tar 格式版本（ustar / pax / gnu 的 header 布局不同） | `tar --format=gnu` |
| gzip 头里写入的文件名和时间戳 | `gzip -n` |

完整命令：

```bash
EPOCH=$(gh api repos/leanprover-community/riemann-hypothesis/commits/<SHA> \
          --jq '.commit.committer.date' | date -u -d %s +%s)

tar --sort=name --format=gnu --owner=0 --group=0 --numeric-owner \
    --mtime="@$EPOCH" -cf - src \
  | zstd -19 -T0 -q -o rh-lean-src-<short-sha>.tar.zst

tar --sort=name --format=gnu --owner=0 --group=0 --numeric-owner \
    --mtime="@$EPOCH" -cf - src \
  | xz -9 -T0 -c > rh-lean-src-<short-sha>.tar.xz
```

**两个压缩器的取舍**：

| | zstd -19 | xz -9 |
|---|---|---|
| 产物大小 | 128,500,935 B | 120,232,252 B（小 6.4%） |
| 解压速度 | 快（zstd 的解码器比 LZMA 快一个数量级） | 慢 |
| 压缩耗时（本机 16 核） | ~1.5 min | ~9 min |
| 生态可用性 | zstd 1.4+ / `tar --zstd` / Python `zstandard` | `xz` 几乎处处都有 |

**结论：日常用 zstd，归档用 xz。** 本仓库的 Release 两个都给了。

## 4. 供应链校验链：三层

「压缩包发出去」这件事的质量，取决于**验证链有几层、每层各自能证明什么**。本仓库设计了三层 + 一个锚点。

```
  ┌─ 第 4 层：回到上游提交 ──────────────────────────────┐
  │  git checkout <sha> → 逐文件比对 → 完全一致          │
  │  证明：这些字节就是上游某个 commit 的字节             │
  └───────────────────────────────────────────────────────┘
  ┌─ 第 3 层：payload 哈希 ──────────────────────────────┐
  │  对「按路径排序的逐文件 sha256 清单」再取一次 sha256  │
  │  证明：整份源码可以用一个值指代，便于跨版本比对        │
  └───────────────────────────────────────────────────────┘
  ┌─ 第 2 层：逐文件 sha256 ─────────────────────────────┐
  │  60,493 条，gzip 后 3.1 MiB                          │
  │  证明：每一个模块单独可验，可定位到「哪几个文件变了」  │
  └───────────────────────────────────────────────────────┘
  ┌─ 第 1 层：资产 sha256 ───────────────────────────────┐
  │  SHA256SUMS，4 条                                    │
  │  证明：下载没损坏、下载的是我发布的那个文件            │
  └───────────────────────────────────────────────────────┘
```

### 4.1 第 1 层：资产级

```bash
sha256sum -c SHA256SUMS
```

只能证明「下载完整且是发布的那份」。**不能证明内容对**。

### 4.2 第 2 层：逐文件级

```bash
zcat files-sha256sums.txt.gz > files-sha256sums.txt
sha256sum -c files-sha256sums.txt     # 60,493 行
```

这一层的价值在**定位能力**：当上游 `main` 变了，你想知道「哪些证明内容变了」，对比两个版本的 `files-sha256sums.txt` 就行，而不用解包两个 128 MB 的包。

清单本身也有设计：路径是相对仓库根的 `src/...`，所以它能直接在上游 clone 里用 `sha256sum -c` 验。

### 4.3 第 3 层：payload 哈希（把 1 GB 压成一个值）

```bash
find src -name '*.lean' -type f -print0 | sort -z | xargs -0 sha256sum | sha256sum
```

它是对**逐文件 sha256 清单本身**再取一次 sha256，所以：

- 它不依赖 tar 格式、不依赖压缩算法——**换任何压缩方式，指针都一样**；
- 它是**一个 64 字符的值**，可以直接写进 issue、commit message、论文脚注。

⚠️ **但它是顺序敏感的，而且顺序写在清单里。** 正确的两个复算命令：

```bash
# 从源码树现算（清单按路径排序）
find src -name '*.lean' -type f -print0 | sort -z | xargs -0 sha256sum | sha256sum

# 从本仓库发布的清单复算（清单本身就是这个顺序，不要再排序）
zcat files-sha256sums.txt.gz | sha256sum
```

**本仓库这一版就是在这里翻过一次车。** 复算时顺手写成了 `zcat files-sha256sums.txt.gz | sort | sha256sum`——按**整行**排序也就是按**哈希**排序，得到 `167d6e3e8ddca19b0a72eff5b4019fab0b6cf810aaeae28c5330144f1d7fcbc7`，和发布的 `67bc88d6…` 对不上。两个值都是 64 位十六进制、看起来完全合法，**唯一能区分它们的是「清单的排序键是什么」这条约定**。

> **这是「顺序敏感的哈希」最典型的翻车方式**：
> **一个哈希值本身不携带「它是怎么算出来的」的语义。** 当你的算法里有一步「排序」时，
> **排序键（按路径 vs 按哈希）、排序实现（`sort` vs `sort -z`）、区域设置（`LC_ALL`）**
> 都不在哈希值里，但全都影响结果。
>
> **凡是「先排序再哈希」的校验值，都必须把排序键写进规范里，并且提供一条「从已发布数据复算」的命令。**
> 否则下一个人一定会重排一次。

本仓库的两个锚点值：

| 提交 | payload sha256 |
|---|---|
| `26c37b40…`（当前 main） | `67bc88d6529acb7133cb239e9394604befe6d20e0974bc03894d1407e64f917e` |
| `40e56bab…`（原版提交） | `b59c8a0bad6b814c87b8e44682664313514b1c1cfb619b3191a3aedde0d6179a` |

> **`sort -z` 的必要性**：文件名里有大量非 ASCII 字符时，LC_ALL 不同会导致 `sort` 的排序不同 → payload 哈希不同。要跨机器复现，必须固定 `LC_ALL=C`。这是一个非常容易踩、且踩了之后极难定位的坑。

### 4.4 第 4 层：回到上游

```bash
git clone --filter=blob:none https://github.com/leanprover-community/riemann-hypothesis
git checkout 26c37b400bc9cfd43c81d798aa5e798af5c55b94
sha256sum -c files-sha256sums.txt
```

**这一层是整套链条的终点**：证明「我手里的字节 = 上游某个 commit 的字节」。

注意 `--filter=blob:none`：**按需拉取 blob**，不要把 953 MiB 的历史全拉下来。

## 5. 为什么没有下载官方归档重新统计

诚实交代一个**没做的事**。

原计划是下载 `alpo.ge/lean.tar.gz.part01..14`、拼接、验证 sha256 `9631b4f0…`、然后做原样对比。**这一步在本机被安全策略拦下了**（下载并执行外部构建产物的行为），所以没有做。

**替代方案（在 `40e56bab` 上做）**：官方归档就是上游仓库的**第一个提交**（上游 README 与 `verification/NOTES.md` 都这么写，且 CI 里有一个 `mirror` job 每次重新下载官方归档、和 `40e56bab` 逐字节比对）。所以我改用 GitHub 的 codeload 拉了 `40e56bab` 的树，**独立统计出 175,187 个 `.lean`、1,030,531,854 字节**——和上游 NOTES.md 记录的数字**完全一致**。

所以：

| 数据 | 我的来源 | 可信度 |
|---|---|---|
| 原版文件数 / 字节数 | 从 `40e56bab` 独立统计 | **已与上游记录交叉验证一致** |
| 原版压缩后大小 | 我用 gzip -9 / zstd -19 / xz -9 实测 | 实测 |
| 官方归档大小 239,275,554 B | 上游 `verification/NOTES.md` 转述 | 转述（未实测） |
| 官方归档 sha256 | 上游转述，另见 Riemann@home 的 README 与 CONTRACT | 转述（未实测） |

**唯一没有实测的是官方归档文件本身。** 而它与我的 gzip -9 结果差 1.46%，这个差距本身也在支持「我的复现是准的」。

## 6. 许可证：分发一份无许可证的证明

这一节是本章的**必读项**，因为它决定了你能不能合法地做上面所有事。

上游 README 的原文：

> The submission belongs to its author and was published without a license.

**即：这份提交没有许可证，著作权属于原作者 Alpöge。** 社区镜像它、出 CI、出缓存，出于「让它能被检验」，但这不是一次授权。

由此推出三条实操约束：

**① 你可以分发，但不能声称授权。**
本仓库做的事是：**机械压缩后原样再分发一份本来就公开的内容**。压缩不改变任何字节语义（可由逐文件 sha256 证明），所以这属于「原样转发已公开内容」，而不是「再创作」或「授权分发」。

**② 你的许可证声明不能覆盖它。**
本仓库的 README 与 LICENSE 里写得很明确：

> The MIT license of this repository covers only the repository's own text, not the Lean sources in the Release assets.

**如果你在同一个仓库里既有 MIT 的文字，又有别人的无许可证源码，就必须把两者切开声明**，否则就是在替别人授权。

**③ 商业用途另说。**
「无许可证」在多数法域里意味着「保留所有权利」。学术复现、验证、评论是安全区；**把它编进产品、做成数据集、对外提供 API 则是另一回事**，需要找原作者谈授权。

> **给「分发别人的大型源码包」这条线的通用建议**：
> **（a）钉死提交；（b）逐字节可验；（c）把上游的授权状态原样抄进你的 README，不要替作者做任何澄清；（d）把自己的许可证限定在自己的文字上；（e）提供上游链接和 sha256，让人能自己核对。**
> 本章的仓库就是照这五条做的。

## 7. 为什么上游自己不发 release

合理的猜测是**上游不想背这个分发责任**：

| 理由 | 说明 |
|---|---|
| 授权状态未定 | 「published without a license」——社区镜像一份来检验是一回事，**主动提供打包下载是另一回事**。发 release 等于在提供分发服务。 |
| 体积与带宽 | 128 MB × N 次下载，GitHub 的 Release 流量是社区成本。 |
| 内容会动 | `main` 一天几十个 PR，任何「当前版本」的包第二天就过时。 |
| 已有替代品 | `git clone` + `lake exe cache get` 已经覆盖了「拿到代码」和「拿到能编译的东西」两个需求。 |

**这也说明为什么社区把力气花在缓存上而不是打包上**——缓存解决的是「能不能编译」，打包解决的是「能不能读」，后者用 git 就够了。

## 8. 踩坑清单

| # | 坑 | 后果 | 对策 |
|---|---|---|---|
| 1 | `sort` 受 `LC_ALL` 影响 | payload 哈希在别的机器上对不上，且极难定位 | 固定 `LC_ALL=C`；用 `sort -z` 处理非 ASCII 文件名 |
| 2 | `tar` 不加 `--sort=name` | 同样的输入产出不同的字节，「可复现」名存实亡 | 固定参数集，见 §3 |
| 3 | `gzip` 不加 `-n` | gzip 头里写了文件名和时间戳，输出不可复现 | 用 `gzip -n` |
| 4 | `tar --mtime` 用了当前时间 | 同上 | 用上游提交的 committer 时间 |
| 5 | 直接 `zstd -d` 后忘了 `tar -xf` | 得到一堆二进制碎片 | zstd 只是外壳，里面还是 tar |
| 6 | 用 `git archive` 而不是 `tar` | `git archive` 会用 `.gitattributes` 的 `export-ignore` 规则，可能悄悄丢文件 | 上游的 `.gitattributes` 里是 `* -text`（只禁换行转换，不排除文件），但仍要核对文件数是否 = 60,493 |
| 7 | 以为 `sha256sum -c` 能验证「内容对」 | 它只验证「和你手上那份清单一致」 | 必须同时验证清单本身来自可信来源（§4.4） |
| 8 | 在 Windows 上用 `git clone` 后直接 diff | `core.autocrlf` 会把 LF 转成 CRLF，diff 全是噪音 | `git config core.autocrlf false` + `.gitattributes` 写 `* -text`（和上游一致） |
| 9 | 直接把 1 GB 塞进 LLM 上下文 | 上下文和费用都会爆 | 用第 2 层的逐文件清单做**索引**，按需取单个文件；用第 3 层的 payload 哈希做**版本指针** |
| 10 | 复算 payload 哈希时把清单**又排了一次** | 得到一个看起来合法但不一样的值（本次实测踩到：`167d6e3e…` vs `67bc88d6…`） | 清单按**路径**排序，发布出去就带着这个顺序；复算时**不要再排**，并把排序键写进规范 |
